## 요약

- **무엇을 알아내려는가.** 여러 사용자가 MemMachine을 동시에 쓸 때 PostgreSQL(이하 PG)과 Qdrant가 어느 부하에서, 어떤 원인으로 병목이 되는지 알아낸다. 원인은 SSD 블록 I/O 수준까지 설명한다.
- **어떻게 알아낼 것인가.** 두 단계로 측정한다. 1단계에서는 실제 MemMachine 서버에 부하를 걸어 DB가 병목이 되는 시점을 찾는다. 2단계에서는 서버 없이 MemMachine과 같은 DB 호출을 보내는 에뮬레이터로 측정한다. DB가 아닌 구간은 1단계에서 잰 시간으로 채우고, DB 응답 시간은 실제로 잰다.
- **지금 어디까지 왔는가.** 방향을 정하는 질의응답은 끝났고 결정 11개가 확정됐다(6.1절). 설계 1절(전체 구조, 4장)을 제시했고 승인을 기다리고 있다. 구현과 커밋은 하지 않았다.
- **무엇을 정해야 하는가.** 설계 1절 승인, 데이터셋 제안 승인, 설계 문서 위치, 커밋 여부의 네 가지다(6.2절).

## 1. 배경: MemMachine이 DB에 시키는 일

### 1.1 저장 구조

MemMachine은 LLM 에이전트에 장기 기억을 제공하는 계층이다. 대화 메시지는 PG에 저장하고, 검색에 쓰는 임베딩 벡터는 Qdrant에 저장한다. 임베딩은 텍스트의 의미를 실수 벡터로 나타낸 것이다.

- 메시지 한 건은 PG에 **에피소드** 한 행으로 저장된다.
- 에피소드는 검색 단위인 **세그먼트**로 나뉜다. 세그먼트마다 임베딩할 텍스트(**파생 텍스트**)를 만들고, 그 벡터 하나가 Qdrant의 **포인트** 하나가 된다. 기본 설정에서는 메시지 하나가 포인트 하나다.
- 기억은 **세션** 단위로 나뉜다. Qdrant에서는 벡터 차원과 스키마 설정이 같은 세션들이 컬렉션 하나를 함께 쓴다. 세션은 포인트에 붙는 메타데이터(**payload**)의 파티션 키로 구분한다.
- 서버는 **워커** 프로세스 여러 개로 돈다. 워커마다 이벤트 루프, PG 커넥션 풀, Qdrant 클라이언트, **인스턴스 캐시**를 따로 가진다. 인스턴스 캐시는 세션별 기억 처리 객체를 보관한다.

### 1.2 사용자 한 턴 [확정]

사용자가 에이전트와 한 번 주고받는 과정을 **턴**이라고 부른다. 부하는 이 턴을 반복하는 형태로 만든다.

| 순서 | 동작 | DB 호출 |
|---|---|---|
| 1 | **검색(search)**: 질문과 관련된 기억을 찾는다. | 있음 |
| 2 | **LLM 응답 생성**: 찾은 기억과 질문을 LLM에 넣어 응답을 받는다. | 없음 |
| 3 | **추가(add)**: 질문과 응답을 기억으로 저장한다. | 있음 |
| 4 | **think time**: 사용자가 다음 질문을 보내기 전까지 쉰다. | 없음 |

### 1.3 요청 하나가 만드는 DB 호출

근거는 요청별 DB 연산 명세(`research/db_op_spec_acb4f9a.md`, 이하 "명세")다. 명세는 `acb4f9a` 코드를 따라가며 요청 하나가 DB에 보내는 호출을 순서대로 적은 문서다.

아래는 기본 설정(`top_k`=10, `expand_context`=0)에서 캐시 적중일 때의 흐름이다. PG 호출은 **왕복(RTT)** 수로 센다. `BEGIN`, SQL 문장 하나, `COMMIT`이나 `ROLLBACK`이 각각 왕복 1회다.

```
추가(add) 요청
  PG      에피소드 행 저장: BEGIN, INSERT, COMMIT                      왕복 3
  외부    임베딩 계산
  PG      세그먼트 저장: BEGIN, 파티션 행 조회(FOR SHARE),
          세그먼트 행 일괄 INSERT, 연결 행 일괄 INSERT, COMMIT          왕복 5
  Qdrant  포인트 N개 쓰기 (wait=true)                                  HTTP 1

검색(search) 요청
  외부    질의 임베딩 계산
  Qdrant  벡터 검색, 최대 40개 (top_k의 4배)                            HTTP 1
  PG      파생 텍스트 ID로 세그먼트 ID 조회                             왕복 3
  PG      세그먼트 내용 조회                                            왕복 3
  PG      원래 에피소드 조회                                            왕복 3
```

DB 호출 사이에는 세그먼트 분할, 포인트 생성, 점수 정렬 같은 서버 내부 연산이 끼어 있다. N은 추가 요청 하나에 담긴 메시지 수다.

| 경우 | PG 왕복 | Qdrant HTTP |
|---|---|---|
| 추가, 캐시 적중 | 8 | 1 |
| 검색, 캐시 적중 | 9 | 1 |
| 검색, 주변 문맥 확장(`expand_context` > 0) | 11–12 | 1 |
| 캐시 미스, 이미 있는 세션 | +6 | +1 |
| 캐시 미스, 처음 쓰는 세션 | +14 | +17+U |

- "+"는 캐시 적중 때의 값에 더해지는 양이다.
- 처음 쓰는 세션에서는 Qdrant **payload 인덱스** 11+U개를 `wait=true`로 다시 만든다. payload 인덱스는 payload 필드로 거르는 검색을 빠르게 하는 인덱스다. U는 사용자가 추가로 정의한 payload 필드 수이고 기본값은 0이다.
- 단계별 상세는 부록 A에 있다.

### 1.4 사용자가 늘면 DB 호출이 늘어나는 경로

- 워커의 인스턴스 캐시 용량은 100이다. 워커에 도달하는 활성 세션이 100을 넘으면 가장 오래 쓰지 않은 인스턴스부터 캐시에서 내보낸다. 사용 중인 인스턴스는 내보내지 않으므로 엄격한 상한은 아니다.
- 세션 접근이 고르게 무작위라면, 요청 하나가 캐시 미스가 될 확률은 1 − 100/N_w다. N_w는 워커에 도달하는 활성 세션 수다.
- 세션 수가 100보다 훨씬 많으면 거의 모든 요청이 캐시 미스 비용(PG 왕복 +6, Qdrant +1)을 더 낸다.
- 처음 쓰는 세션은 한 번에 PG 왕복 +14, Qdrant +17+U의 비용을 낸다.

## 2. 접근 방법: 두 단계로 측정한다 [확정]

이 구조는 검토자가 제안했다.

```
1단계  E2E 측정
       턴 부하 ──REST──▶ MemMachine 서버 ──▶ PG, Qdrant
       얻는 것: DB가 병목이 되는 시점, 구간별 처리 시간 분포, 실제 DB 호출 기록
          │
          │  구간별 처리 시간으로 모델 지연을 정한다
          ▼
2단계  에뮬레이터 측정
       에뮬레이터 ────────────────────────▶ PG, Qdrant
       MemMachine과 같은 DB 호출을 보낸다
       DB가 아닌 구간은 모델 지연으로 채운다
       DB 응답 시간은 실제로 잰다
```

- **1단계(E2E)**: 실제 MemMachine REST 서버에 턴 부하를 건다. 목적은 세 가지다. DB가 병목이 되는 시점을 찾고, 그 시점의 요청 처리 시간을 구간별로 모으고, 실제 DB 호출을 기록(캡처)한다.
- **2단계(에뮬레이터)**: 서버 없이 MemMachine과 같은 DB 호출을 PG와 Qdrant에 직접 보낸다. 임베딩, LLM, 서버 내부 연산처럼 DB가 아닌 구간은 실행하지 않는다. 대신 1단계에서 보정한 시간, 즉 **모델 지연**을 넣는다. 분석은 실제로 잰 DB 응답 시간으로 한다.

### 2.1 모델 지연이 대신하는 시간

논의에서 든 대표 예는 다음 셋이다.

| 위치 | 대신하는 시간 |
|---|---|
| 추가 요청 | Qdrant에 보낼 포인트를 채우기까지의 준비 시간(세그먼트 분할, 임베딩 등) |
| 검색 요청 | Qdrant에 요청하기 전 단계의 시간(요청 파싱, 임베딩 등) |
| 턴 사이 | LLM 응답 시간 |

- 구간별 시간은 MemMachine이 내보내는 Prometheus 지표로 계산한다. 상위 구간의 시간에서 그 안에 포함된 하위 연산의 시간을 빼는 방식이다. 식은 부록 B에 있다.
- 저장소 코드 안에 섞여 지표로 분리할 수 없는 연산 시간은, 에뮬레이터가 같은 연산을 재생해 잰 시간으로 보정한다.
- 동시 부하에서 이벤트 루프 대기열까지 재현하려면, CPU 연산 구간은 sleep이 아니라 CPU를 실제로 점유하는 방식으로 넣어야 한다. 요청 처리 중에는 외부 임베딩 API 호출만 대기 시간으로 넣는다.

### 2.2 에뮬레이터 구현: 저장소 클래스 재사용(방식 A) [확정]

- 에뮬레이터는 `acb4f9a`의 에피소드 저장소, 세그먼트 저장소, Qdrant 컬렉션 클래스를 서버 없이 직접 만들어 연결한다.
- 명세 순서대로 DB에 접근하는 메서드만 부르고, 호출 사이에 모델 지연을 넣는다. 벡터는 데이터셋에서 가져온다. HTTP 처리, 임베딩 호출, LLM 호출은 뺀다.
- MemMachine 코드를 그대로 쓰므로 SQL 문장, prepared statement, 트랜잭션, 커넥션 풀, Qdrant 요청 형식이 저절로 같아진다.
- 이 방식으로 한계에 부딪히거나 가정을 바꾼 실험이 필요할 때만 **방식 C**로 넓힌다. 방식 C는 핵심 연산을 DB 클라이언트 라이브러리로 직접 다시 짜는 방식이다.
- 세 클래스를 서버 없이 조립할 수 있음을 2026-09-14에 코드에서 확인했다. 단, 커넥션 풀 크기와 Qdrant 클라이언트의 HTTP 설정은 서버와 똑같이 맞춰야 한다. 근거는 부록 D에 있다.

## 3. 실험 구성

### 3.1 부하 [확정]

- 가상 사용자는 1.2절의 턴을 반복한다. LLM 응답이나 임베딩처럼 DB가 아닌 시간은 계산해서 넣는다.
- 부하는 두 축으로 바꾼다. 사용자 규모는 10, 50, 100, 200, 500명의 다섯 단계다. 규모마다 동시성을 단계적으로 올리며 같은 측정을 반복한다(**동시성 스위프**).
- 사용자 규모마다 다음 순서로 진행한다.

```
사전 적재 ──▶ 스냅샷 저장 ──▶ 턴 시뮬레이션(동시성 스위프)
```

- **사전 적재**는 턴 시뮬레이션 전에 사용자별 기억을 대량으로 넣는 작업이다. **스냅샷**은 적재가 끝난 DB 상태를 저장해 둔 것이다.
- 사전 적재 자체도 대량 쓰기 부하로 보고 병목을 측정한다.

### 3.2 요청 생성과 검증 [확정]

- 요청은 데이터로 합성한다.
- 합성한 요청이 실제와 같은지는 1단계에서 캡처한 DB 호출과 비교해 검증한다. 캡처는 PG 로그와 Qdrant 앞단의 HTTP 프록시로 하며, MemMachine 코드는 바꾸지 않는다.
- 충실도는 **부하 충실도**만 본다. 에뮬레이터가 DB에 주는 부하가 실제와 같은지만 확인한다. 검색 결과가 의미상 맞는지(시맨틱 recall)는 측정하지 않는다.

### 3.3 데이터

**요구 사항 [확정]**

- 공개된 사전 임베딩 벡터 데이터셋을 써서 임베딩 계산 단계를 건너뛴다.
- 서로 다른 벡터 차원 2개 이상을 비교하는 측정을 최소 한 번 한다.

**데이터셋 제안 [제안]**

| 역할 | 데이터셋 | 벡터 수 | 차원 | 라이선스 |
|---|---|---|---|---|
| 주 데이터 | Zenodo 17101276 (Pes2o 논문 전체 임베딩) | 8,293,485 | 2560 | CC-BY-4.0 |
| 대조군 | MS MARCO v2.1 Cohere `embed-english-v3`, 샤드 00–01 | 3,750,897 | 1024 | 임베딩은 Apache 2.0 |
| 1,000만 개 초과 확장 | Pes2o-VE | 88,453,763 | 2560 | ODC-BY 1.0 |

- **차원 비교 방법.** 주 데이터의 벡터는 Qwen3-Embedding-4B로 만들었다. 이 모델은 MRL을 지원한다(32–2560차원). MRL로 학습한 벡터는 앞부분만 잘라 길이를 다시 1로 맞추면(재정규화) 낮은 차원 벡터로 쓸 수 있다. 그래서 한 파일에서 2560, 1536, 1024, 768차원을 만들 수 있고, 데이터 분포는 그대로 둔 채 차원만 바꿀 수 있다.
- **텍스트.** 데이터셋에 텍스트가 없으므로 LongMemEval의 길이 분포에 맞춰 합성한다. 부하 충실도만 보므로 텍스트의 의미는 필요 없다.
- **사용자 할당.** 벡터를 사용자에게 나누는 방식(무작위, 군집)은 파라미터로 둔다.
- **조사 결과와의 관계.** 데이터셋 조사 문서(`research/vector_dataset_survey_2026-09-14.md`, 후보 33개)의 1순위는 다른 조합이었다. Snowflake arctic-embed-m-v1.5(768/256차원)와 Cohere msmarco-v2.1(텍스트 포함, 1024차원)이다. 이 순위는 텍스트 포함과 채팅 도메인을 포함한 6개 요건으로 매겼다. 이후 부하 충실도만 보기로 정하면서 텍스트와 도메인 요건이 필요 없어졌다. 그래서 한 파일에서 여러 차원을 얻을 수 있는 Zenodo Pes2o를 주 데이터로 다시 제안했다. 조사 문서는 Pes2o-VE를 원래 용도에는 권장하지 않았다.
- **[미확인]** Pes2o-VE의 파일 구성, 텍스트 포함 여부, 부분 다운로드 가능 여부는 확인하지 않았다.
- 파일 크기, 질의 세트 같은 상세는 부록 C에 있다.

### 3.4 장비와 측정 수단

**장비 [확정]**: PG 호스트, Qdrant 호스트, 부하 발생 호스트의 3대로 나눈다.

**측정 수단** (조사한 근거 자료이며, 설계 결정은 아니다)

- **Qdrant**
  - `/metrics?per_collection=true`는 REST와 gRPC 요청의 응답 수, 실패 수, 지연 히스토그램을 준다. 컬렉션 정보 조회, 컬렉션 목록 조회, 스냅샷 요청은 여기에 잡히지 않는다.
  - `GET /collections/{c}/optimizations?with=queued,completed,idle_segments`는 최적화 작업 상태를 준다. Qdrant v1.17이 이 API를 제공하는지는 **[미확인]**이다.
- **PG 16**
  - `pg_stat_io`는 I/O 통계 뷰다. `track_io_timing` 설정이 필요하다.
  - `pg_stat_statements`는 SQL 문장별 실행 통계이며 I/O 시간도 포함한다.
  - `pg_stat_activity`로 대기 이벤트 유형을 본다. 유형은 Activity, BufferPin, Client, Extension, IO, IPC, Lock, LWLock, Timeout이다.
- **호스트**: `iostat`, `biolatency`, `nvme smart-log`, cgroup `io.stat`으로 블록 장치와 SSD 수준을 본다.

**현재 MemMachine 지표의 한계**

- 저장소 연산 시간(트래커)에 커넥션 풀 대기와 이벤트 루프 지연이 섞여 있다.
- Summary 지표는 평균만 구할 수 있다.
- 히스토그램 버킷의 최소 단위가 5ms다.
- 현재 값을 나타내는 Gauge 지표가 없다.

### 3.5 산출물 [확정]

1. 포화 곡선과 병목 귀속 리포트. 포화 곡선은 부하를 늘릴 때 처리량과 지연이 어떻게 변하는지 보여 준다. 병목 귀속은 병목의 원인을 어느 계층에 돌릴지 판정하는 일이다.
2. SSD 블록 I/O 특성화
3. 에뮬레이터 충실도 검증 리포트
4. 재현 가능한 하네스 패키지. 하네스는 데이터 준비부터 분석까지 실험을 다시 돌릴 수 있게 묶은 도구 모음이다.

## 5. 위험과 확인할 항목

### 5.1 코드에서 확인한 위험 (명세 §6)

1. **처음 쓰는 세션의 동시 생성 경합.** 세션 행을 넣는 INSERT에 `ON CONFLICT`가 없다. 여러 워커가 같은 세션을 동시에 처음 쓰면 PG에서 `IntegrityError`로 요청이 실패한다. Qdrant 쪽에서도 컬렉션 등록을 다시 확인하는 단계에서 MemMachine이 `VectorStoreCollectionAlreadyExistsError`를 내며 실패한다. Qdrant가 돌려주는 409 응답 자체는 무시된다.
2. **인스턴스 캐시 초과.** 워커당 활성 세션이 100보다 훨씬 많으면 거의 모든 요청이 캐시 미스 비용을 더 낸다(1.4절).
3. **Qdrant 호출 타임아웃.** Qdrant 클라이언트가 쓰는 HTTP 라이브러리(httpx)의 기본 타임아웃이 5초다.
4. **PG 커넥션 풀.** 풀은 기본 5개이고 부족하면 10개까지 더 연다(overflow). overflow 커넥션은 반납할 때 닫힌다. 그래서 다시 연결할 때마다 드라이버가 `episode_type` enum 타입 정보를 다시 조회한다.
5. **SQL 재분석(Parse).** `IN (...)` 목록 길이가 다르면 SQL 텍스트가 달라진다. Parse는 커넥션과 서로 다른 SQL 텍스트의 조합마다 한 번 일어난다. 커넥션마다 100개까지 보관하고, 넘으면 오래된 것을 버린 뒤 나중에 다시 Parse한다.
6. **Qdrant 연결 재사용.** Qdrant 주소가 localhost이면 keep-alive를 쓰지 않는다. 다른 호스트이면 keep-alive 연결 20개, 전체 연결 100개로 제한한다. 따라서 Qdrant를 별도 호스트에 두면 연결 동작이 같은 호스트일 때와 달라진다.

### 5.2 1단계에서 확인할 항목 [미확인]

1. **payload 인덱스 중복 생성.** 이미 있는 payload 인덱스를 다시 만들 때 Qdrant가 어떻게 응답하는지 확인한다. 오류라면 두 번째 신규 세션 생성이 실패하고, 성공이라면 서버 작업량이 달라진다.
2. **`/optimizations` API.** Qdrant v1.17이 이 API를 제공하는지 확인한다.
3. **"Memory is closed" 오류.** 추가 요청은 인스턴스 참조를 놓은 뒤 인코딩을 한다. 워커당 활성 세션이 100을 넘으면 그 사이에 인스턴스가 캐시에서 내보내져 닫힐 수 있다. 그러면 에피소드 행만 남는다. 가능성은 있지만 재현하지 않았다.
4. **동시 생성 경합 재현.** 여러 워커가 같은 세션을 처음 쓸 때 `IntegrityError`가 실제로 나는지 확인한다.
5. **타임아웃 동작.** httpx 5초 타임아웃에 걸렸을 때 어떻게 동작하는지 확인한다.
6. **임베딩 응답 형식.** openai SDK는 `encoding_format`을 지정하지 않으면 base64로 요청한다. 이 동작을 로컬 openai 2.21.0에서만 확인했다. `speedkick`이 고정한 openai 2.54.0에서도 같은지 확인한다.

## 부록 B. 모델 지연 산출식 (명세 §5)

**기호**

- `r(X) = sum(rate(X_sum[w]))`: 지표 X의 누적 시간 증가율
- `c(X) = sum(rate(X_count[w]))`: 지표 X의 호출 횟수 증가율
- `w`: `rate`를 계산하는 시간 창

**일반 형태**: 구간 하나의 평균 시간 = `(r(상위 구간) − Σ r(하위 연산)) / c(상위 구간)`

**예: A7(포인트 생성) 시간**

```
A7 = [ r(phase vector_store) − r(vector_store_qdrant_latency_seconds{operation="upsert"}) ] / c(phase vector_store)
```

`phase vector_store`는 `event_memory_encode_events_phase_seconds{phase="vector_store"}`를 줄여 쓴 것이다.

**보정 (T_emu)**

저장소 연산 시간(트래커) 안에 섞인 내부 연산은 지표로 분리할 수 없다. 에뮬레이터가 같은 DB에서 같은 형태의 연산을 재생해 잰 시간 `T_emu`를 트래커 평균에서 빼서 추정한다. 이 보정은 동시성이 낮고 한 경로만 도는 부하에서 해야 한다(명세 §6-10).

| 경로 | T_emu로 보정하는 내부 연산 |

## 부록 D. 코드 근거 (2026-09-14 확인)

경로는 `acb4f9a`의 `packages/server/src/memmachine_server/` 기준이다.

**에뮬레이터 조립 순서** (`episodic_memory/long_term_memory/service_locator.py::_event_params`)

1. `vector_store.open_collection(name=partition_key)`를 호출한다.
2. 컬렉션이 없으면 `create_collection(EventMemory.expected_vector_store_collection_schema())`로 만든 뒤 다시 연다.
3. `segment_store.open_or_create_partition(partition_key)`를 호출한다.
4. `episode_storage`와 함께 `EventBackendParams`를 만든다.

**생성자**

- `SqlAlchemyEpisodeStore(engine, metrics_factory=None)`
- `SQLAlchemySegmentStore(SQLAlchemySegmentStoreParams(engine, metrics_factory, purge_max_segments, purge_max_partitions, …))`
- `QdrantVectorStore(QdrantVectorStoreParams(client: AsyncQdrantClient, is_distributed, registry_replication_factor, metrics_factory))`

**모의 임베더가 맞춰야 할 것** (`common/embedder/openai_embedder.py:238-255`)

- 호출 형태는 `embeddings.create(input=chunk_cluster, model=…, dimensions=…)`다. `dimensions`는 `_use_dimensions_parameter`가 참일 때만 보낸다.
- 400 응답 메시지에 "dimension"이 있으면 `dimensions` 없이 다시 보내고, 그 뒤로는 보내지 않는다.
- `encoding_format`을 지정하지 않으므로 SDK 기본값 base64(float32 little-endian)로 요청한다. 모의 임베더는 base64와 float 형식을 모두 지원해야 한다.
- 임베더로 가는 텍스트 형식은 `[timestamp] producer: "<json.dumps(text, ensure_ascii=False)>"`다(`episodic_memory/event_memory/deriver/text_deriver.py::_format_for_embedding`). 벡터 ID는 JSON 이스케이프를 거쳐도 그대로 남는 ASCII 토큰으로 심는다. 예: `vid_000012345`

**첫 판에서 고친 사실** (명세와 조사 문서 원문으로 확인)

1. 캐시 용량 초과 시 요청마다 더 드는 비용을 "신규 세션 미스 비용"이라고 적었다. 명세상으로는 **이미 있는 세션의 미스 비용**(PG 왕복 +6, Qdrant +1)이다.
2. 동시 생성 경합에서 "Qdrant가 AlreadyExists로 실패"한다고 적었다. 실제로는 Qdrant의 409 응답은 무시되고, **MemMachine이 `VectorStoreCollectionAlreadyExistsError`를 낸다**.
3. A8 payload를 "시스템 키 11개 + `sys-partition_key`"라고 적었다. 명세의 키 목록을 세면 **`sys-partition_key`를 포함해 11개**다.
4. 데이터셋 제안이 조사 문서의 1순위와 다른 이유를 적지 않았다. 3.3절 "조사 결과와의 관계"에 추가했다.
