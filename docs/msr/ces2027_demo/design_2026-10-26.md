# CES 2027 MemMachine 비교 데모 설계

- 작성일: 2026-10-26
- 브랜치: `msr_ces2027_demo` (`upstream/speedkick` `8d7b832a`에서 분기)
- 상태: 확정(2026-10-26 사용자 승인). 7장의 확인 항목은 구현 단계에서 닫고, 9장의 미결 사항은 구현을 막지 않으므로 정해지는 대로 반영한다.

## 1. 요약

CES 2027 부스에서 Open WebUI의 모델 비교 화면으로 같은 질문에 대한 두 답을 나란히 보여 준다. 왼쪽은 MemMachine에서 과거 대화를 검색해 그 기억을 먼저 목록으로 보여 주고 답하며, 오른쪽은 같은 LLM이 기억 없이 답한다. 관객은 왼쪽 목록에 뜬 과거 발화와 사이드바의 과거 채팅을 맞춰 보면서 기억이 답을 어떻게 바꾸는지 확인한다.

Open WebUI는 v0.12.4 공식 Docker 이미지를 그대로 쓰고 소스를 고치지 않는다. MemMachine 검색과 LLM 호출은 Open WebUI의 Pipe 함수 하나가 맡고, 나머지는 환경 변수와 관리 API로 설정한다. MemMachine도 서버 코드를 고치지 않고 기존 v2 REST API만 쓴다.

부스에는 서버 네 대를 둔다. LLM용 vLLM(H100), 임베더용 vLLM(H100), MemMachine과 Open WebUI를 함께 올린 앱 서버, Qdrant와 PostgreSQL을 올린 DB 서버다. 시연 화면 장비까지 다섯 대를 스위치 하나로 묶은 내부망만 쓰고 인터넷에는 연결하지 않는다. 한국에서 세팅과 리허설을 마친 뒤 전원을 끄고 옮겨서, 미국에서는 배선과 전원만 복구하면 동작하도록 설계한다. 이전 절차의 세부는 별도 문서로 다룬다.

개발은 이 Mac(16GB)에서 한다. H100이 없으므로 LLM과 임베더는 임의 값을 내는 가벼운 mock으로 대체하고, 코드 검토와 기본 동작 확인까지만 Mac에서 한다. 실제 GPU와 서버에서의 동작 확인은 브랜치를 `origin`에 push한 뒤 회사에서 당겨 받아 실제 vLLM으로 올려서 한다. 그래서 스택을 올리는 데 필요한 파일은 모두 브랜치에 두고, 장소마다 다른 값은 설정 파일로만 바꾼다(4.3절).

## 2. 시연 흐름과 성공 기준

시연은 다음 순서로 진행한다.

1. 시연 전에 적재 도구가 대본의 과거 세션들을 Open WebUI와 MemMachine에 넣는다. 사이드바에는 대본의 날짜와 제목이 붙은 채팅이 보이고, 열면 대본의 질문과 답이 그대로 있다. 각 턴은 같은 시각의 에피소드로 MemMachine에 저장된다(5.4절).
2. 스태프가 새 채팅을 열면 왼쪽 "MemMachine + 모델" 과 오른쪽 "모델" 두 개가 기본으로 선택되어 있다.
3. 스태프가 대본에 있는 영어 질문을 입력한다. 질문은 여러 과거 세션의 사실을 합쳐야 답할 수 있는 종류다.
4. 왼쪽 카드에는 검색된 기억 5개가 날짜와 세션 제목이 붙은 목록으로 먼저 뜨고, 그 아래에 기억을 근거로 한 답이 스트리밍된다.
5. 오른쪽 카드에는 같은 LLM이 질문만 보고 쓴 일반론 답이 스트리밍된다.
6. 관객이 원하면 사이드바의 과거 채팅을 열어 왼쪽 목록의 발화가 실제로 그 대화에 있었음을 보여 준다.

시연 중에는 Pipe가 MemMachine에 아무것도 저장하지 않는다. 같은 질문을 몇 번 하든 같은 기억이 검색된다. Pipe의 녹음 Valve(부록 D)가 꺼져 있는지 검사 스크립트가 확인한다.

성공 기준은 다음과 같다.

| 기준 | 확인 방법 |
|---|---|
| 대본 질문마다 미리 지정한 기대 기억이 모두 top-5 안에 든다 | 검사 스크립트가 질문을 돌려 자동 확인한다 |
| 오른쪽 답에는 과거 세션의 고유 정보가 나오지 않는다 | 리허설에서 눈으로 확인한다 |
| 두 답이 모두 수 초 안에 뜨기 시작한다 | 리허설에서 시간을 잰다. LLM 서버 성능에 따라 목표치를 정한다 |
| 인터넷 없이 전원만 켜서 동작한다 | 출국 전에 인터넷 선을 뽑고 리허설한다 |
| Open WebUI와 MemMachine 소스를 고치지 않는다 | 브랜치의 변경 파일 목록으로 확인한다 |

## 4. 전체 구성

### 4.1 부스 장비와 네트워크

```
                      +-----------------+
                      |  시연 화면 장비   |  브라우저로 http://app:3000 접속
                      +--------+--------+
                               |
   +---------+   +---------+   |   +------------------+   +-----------------+
   | llm     |   | embed   |   |   | app              |   | db              |
   | vLLM    |   | vLLM    |   |   | MemMachine :8080 |   | PostgreSQL :5432|
   | H100    |   | H100    |   |   | Open WebUI :3000 |   | Qdrant :6333    |
   | :8000   |   | :8001   |   |   |                  |   |                 |
   +----+----+   +----+----+   |   +--------+---------+   +--------+--------+
        |             |        |            |                      |
   =====+=============+========+============+======================+=====  스위치
```

서버마다 고정 IP를 주고, 모든 설정은 IP 대신 호스트 이름(`llm`, `embed`, `app`, `db`)을 쓴다. 컨테이너 안에서는 compose의 `extra_hosts`가 이 이름을 `deploy/.env`에 적은 IP로 풀고, 스크립트를 돌리는 장비와 시연 화면 장비에는 같은 대응을 `/etc/hosts`에 넣는다. IP 대역은 사무실 망과 겹치지 않는 사설 대역에서 고른다(예: `10.77.0.0/24`). 대역은 9장의 미결 사항이다.

LLM 서버와 임베더 서버의 포트는 8000과 8001로 다르게 둔다. 회사 검증 때 H100 두 장이 한 서버에 있어 두 vLLM을 같은 호스트에 올리더라도 compose 파일을 고치지 않게 하기 위해서다.

### 4.2 요청 흐름

질문 하나가 처리되는 순서는 다음과 같다.

1. 브라우저가 Open WebUI에 질문을 보낸다. 모델 두 개가 선택되어 있으므로 Open WebUI는 두 모델을 동시에 호출한다.
2. 오른쪽 모델은 Open WebUI가 `llm:8000/v1/chat/completions`를 직접 호출한다. 기억은 들어가지 않는다.
3. 왼쪽 모델은 Pipe 함수다. Pipe는 마지막 사용자 메시지를 질의로 삼아 `app:8080/api/v2/memories/search`를 `top_k=5`로 호출한다.
4. MemMachine은 질의 하나를 `embed:8001/v1/embeddings`로 임베딩하고, Qdrant에서 이웃을 찾은 뒤 PostgreSQL에서 에피소드 본문을 읽어 돌려준다.
5. Pipe는 받은 에피소드 5개를 목록으로 먼저 출력하고 구분선을 긋는다.
6. Pipe는 기억을 넣은 시스템 프롬프트와 원래 대화를 `llm:8000/v1/chat/completions`에 스트리밍으로 보내고, 받은 토큰을 그대로 흘려보낸다.

양쪽은 같은 LLM, 같은 기본 시스템 프롬프트, 같은 질문을 받는다. 다른 것은 기억 블록의 유무뿐이다.

### 4.3 개발과 검증의 세 환경

코드는 세 곳을 거친다. 세 곳 모두 같은 compose 파일과 같은 설정 파일을 쓰고, 장소마다 다른 값은 `deploy/.env` 한 파일에만 둔다. Mac에서는 다른 서버의 IP 자리에 `host-gateway`를 적어 컨테이너가 Mac 자신에 공개된 포트로 가게 한다.

| 환경 | 역할 | LLM과 임베더 | 여기서 확인하는 것 |
|---|---|---|---|
| Mac | 개발, 코드 검토, 기본 동작 확인 | mock 하나가 둘을 대신한다 | 컨테이너가 뜨고, 비교 화면에 목록과 답이 나오고, 적재와 검사 스크립트가 돈다 |
| 회사 GPU 서버 | 실제 모델로 동작 확인 | vLLM(H100) | Pipe와 vLLM의 호환, 검색 품질과 응답 시간, 모델 전환, 오프라인 준비물 생성 |
| 부스 | 리허설과 시연 | vLLM(H100) | 전원만 켜서 동작, 인터넷 없이 동작 |

코드는 git으로만 옮긴다. Mac에서 커밋한 뒤 `origin`에 push하면 회사에서 pull해서 올린다. 회사에서 고친 것이 있으면 같은 브랜치에 커밋해 push하고, Mac에서 pull해 검토한다. 회사 검증 결과(검사 스크립트 출력, 화면 캡처, 걸린 시간)는 `docs/msr/ces2027_demo/` 아래에 날짜를 붙인 검증 문서로 커밋해서 Mac에서도 읽을 수 있게 한다.

이 흐름에서 지켜야 할 것은 다음과 같다.

- 스택을 올리는 데 필요한 파일은 모두 브랜치에 둔다. 시나리오, compose, MemMachine 설정, 스크립트, README가 해당한다. Mac에만 있는 파일에 기대지 않는다.
- 장소마다 다른 값(IP, 공개 포트, 시간대, 모델 이름과 가중치 경로, GPU 메모리 비율)은 `deploy/.env`에 두고, 예시 파일 `deploy/.env.example`만 커밋한다. 임베딩 차원은 `memmachine.yml`에 직접 적는다(5.1절). 실제 `.env`와 `/etc/hosts`는 각 서버에 남는다.
- README의 회사용 절차는 명령을 그대로 복사해 실행할 수 있게 쓴다. Mac에서 검증하지 못한 항목은 README의 확인 목록에 "회사에서 확인"으로 표시해 둔다.
- 비밀 값은 없다. vLLM과 MemMachine은 API 키를 쓰지 않으므로 `dummy`를 넣는다.

## 5. 구성 요소 설계

### 5.1 MemMachine 서버 설정

MemMachine은 event 백엔드의 에피소드 장기 기억만 쓴다. Neo4j가 필요한 declarative 백엔드와 LLM이 필요한 단기 기억, 의미 기억은 쓰지 않는다.

| 설정 | 값 | 비고 |
|---|---|---|
| `episodic_memory.long_term_memory.backend` | `event` | VectorStore와 SegmentStore 조합이다 |
| `vector_store` | Qdrant (`db:6333`) | 에피소드 벡터 |
| `segment_store` | PostgreSQL (`db:5432`) | 에피소드 본문과 세션 정보 |
| `embedder` | `openai` provider, `base_url: http://embed:8001/v1`, 모델과 차원은 임베딩 모델을 정한 뒤 기입 | vLLM이 OpenAI 호환 임베딩 API를 낸다 |
| `reranker` | 생략 | 임베딩 점수로 정렬한다 |
| `short_term_memory_enabled` | 기본값 `false` 유지 | 저장할 때 LLM을 부르지 않는다 (부록 A.4) |
| `semantic_memory.enabled` | 기본값 `false` 유지 | 의미 기억을 만들지 않는다 (부록 A.4) |
| `episode_store`, `session_manager` | PostgreSQL | 공식 샘플과 같다 |

설정 파일의 `$ENV` 치환은 `password`와 `api_key` 필드에서만 된다(부록 A.5). 그래서 호스트 이름과 포트는 파일에 그대로 적되, 모든 장소에서 같은 이름(`db`, `embed`)을 쓰므로 파일은 바뀌지 않는다. PostgreSQL 비밀번호만 `$POSTGRES_PASSWORD`로 compose에서 넘긴다. 임베딩 모델의 서빙 이름은 vLLM의 `--served-model-name embed`로 고정하므로, 장소에 따라 달라지는 값은 임베딩 차원 `dimensions` 하나뿐이다. 임베딩 모델을 정할 때 이 값을 한 번 손으로 고친다. 개발용 mock은 요청의 `dimensions`를 그대로 따르므로 따로 맞출 것이 없다.

에피소드는 메시지 하나가 한 건이다. 적재 도구가 저장할 때 필드는 다음과 같이 채운다. Pipe의 녹음 모드(부록 D)도 같은 필드를 쓴다.

| 필드 | 값 |
|---|---|
| `content` | 발화 원문 |
| `producer` | 사용자 발화는 `user`, 어시스턴트 발화는 `assistant` |
| `role` | `user` 또는 `assistant` |
| `timestamp` | 대본의 턴 시각(세션 날짜에 턴 순서대로 1분씩 더한 값). 녹음 모드에서는 저장하는 시각 |
| `metadata` | `session_id`: Open WebUI 채팅 ID. 적재할 때는 가져오기 응답이 돌려준 ID, 녹음 모드에서는 `__chat_id__` |

검색 응답에서 Pipe가 쓰는 필드는 `content`, `created_at`, `metadata.session_id`다. 세션 제목은 저장하지 않고 검색할 때 채팅 ID로 Open WebUI에서 찾는다(5.2절). `score`는 받지만 표시하지 않는다.

프로젝트는 따로 만들지 않는다. 첫 저장이 프로젝트를 만들고, 저장 전의 검색은 에피소드가 비어 있는 정상 응답을 돌려준다(부록 A.2). 프로젝트 삭제 API는 되돌릴 수 없는 소프트 삭제라 지운 이름을 다시 쓸 수 없고, 에피소드 삭제 API는 의미 기억이 꺼진 이 설정에서 실패한다(부록 A.17). 그래서 기억을 비우는 대신 적재할 때마다 새 프로젝트 ID를 만들어 쓰고, Pipe는 Valve `PROJECT_ID`의 프로젝트만 검색한다(5.4절). 지난 프로젝트는 DB에 남지만 작아서 문제가 되지 않는다.

Neo4j 없이 서버가 뜨는지는 구현 1단계의 드라이런에서 확인한다(7장).

### 5.2 Open WebUI Pipe 함수

파일 하나(`tools/ces2027_demo/pipe/memmachine_pipe.py`)로 만든다. Open WebUI 이미지에 들어 있는 `httpx`와, 채팅 제목을 읽기 위한 Open WebUI 자체 모듈(`open_webui.models.chats`)만 쓰고 추가 패키지는 넣지 않는다. 관리 API로 올리고 켠다.

Valve는 다음과 같다. 모두 관리자 화면의 함수 설정에서 바꿀 수 있다.

| Valve | 기본값 | 용도 |
|---|---|---|
| `MEMMACHINE_URL` | `http://memmachine:8080` | MemMachine 주소. 같은 compose 안이라 컨테이너 이름을 쓴다 |
| `LLM_BASE_URLS` | `http://llm:8000/v1` | vLLM 주소. 세미콜론으로 여러 개. 세팅 스크립트가 `.env`의 같은 값을 넣고, 오른쪽 모델용 `OPENAI_API_BASE_URLS`도 그 값을 쓴다 |
| `LLM_API_KEY` | `dummy` | vLLM이 키를 요구하지 않아도 헤더는 보낸다 |
| `TOP_K` | `5` | 검색 개수 |
| `PROJECT_ID` | `universal` | 검색하고 저장하는 MemMachine 프로젝트. 적재 도구가 적재할 때마다 새 ID를 써 넣는다 |
| `RECORD_MEMORY` | `false` | 켜면 각 턴의 사용자 발화와 답을 MemMachine에 저장한다(녹음 모드, 부록 D). 시연 중에는 끈다 |
| `SHOW_SESSION_INFO` | `true` | 목록 항목에 날짜와 세션 제목을 붙일지 |
| `MEMORY_PREVIEW_CHARS` | `80` | 목록에 보여 주는 기억 본문의 최대 글자 수. 단어 경계에서 자르고 "..."를 붙인다. 비교 화면에서 두 줄 정도다. 0이면 전문을 보여 준다. LLM에는 항상 전문이 간다 |
| `BASE_SYSTEM_PROMPT` | 짧은 어시스턴트 지시문 | 세팅 스크립트가 `.env`의 문장에 `DEMO_DATE`의 "Today is ..." 줄을 붙여 넣는다. 오른쪽 모델에도 같은 문장을 넣는다 |
| `REQUEST_TIMEOUT` | `60` | 초 |

`pipes()`는 `LLM_BASE_URLS`의 각 서버에서 `GET /v1/models`를 읽어 모델마다 항목 하나를 돌려준다. Open WebUI는 이를 `memmachine_pipe.<모델 ID>`라는 ID와 `MemMachine + <모델 ID>`라는 이름으로 등록한다(부록 A.6). 표시 이름은 세팅 스크립트가 만드는 모델 항목이 덮어쓴다. vLLM에 닿지 못하면 오류를 이름으로 가진 항목 하나를 돌려줘서 화면에서 바로 알 수 있게 한다.

`pipe()`는 다음 순서로 동작한다.

1. `__task__`가 있으면(제목 생성 같은 보조 작업) 검색을 건너뛰고 vLLM에 그대로 전달한다. 보조 작업은 설정에서 모두 끄지만, 혹시 호출돼도 기억 검색을 하지 않도록 이중으로 막는다.
2. 마지막 사용자 메시지를 질의로 삼는다. 상태 표시로 "Searching memories" 를 띄운다.
3. `POST /api/v2/memories/search`를 `{"project_id": PROJECT_ID, "query": ..., "top_k": TOP_K}`로 호출한다. `org_id`는 생략한다. 아직 저장한 것이 없으면 빈 목록이 온다.
4. 응답의 `content.episodic_memory.long_term_memory.episodes`를 순서대로 쓴다. 항목마다 `metadata.session_id`로 Open WebUI의 채팅 제목을 찾아 붙인다(같은 프로세스 안이라 `Chats.get_chat_by_id`를 직접 부른다). 못 찾으면 날짜만 붙인다. 상태 표시를 "Retrieved N memories"로 바꾼다.
5. 아래 형식의 목록(Open WebUI 내장 NOTE 알림 블록)과 구분선을 먼저 내보낸다.
6. 시스템 프롬프트를 `BASE_SYSTEM_PROMPT`와 기억 블록 순으로 만들고 원래 대화를 뒤에 붙여 vLLM에 스트리밍 요청을 보낸다. 받은 토큰을 그대로 내보낸다.
7. MemMachine 호출이 실패하면 "Memory search failed: ..." 한 줄을 내보내고 멈춘다. LLM 호출이 실패하면 "LLM call failed: ..."를 답 자리에 내보낸다. 조용히 기억 없이 답하거나 스트림이 끊기면 고장을 알아채지 못하므로 일부러 눈에 띄게 실패시킨다. LLM 서버에 접속하는 제한 시간은 5초로 짧게 둔다. Open WebUI가 모델 목록을 고칠 때마다 `pipes()`를 부르므로 서버가 꺼져 있을 때 화면이 오래 멈추지 않게 하기 위해서다.
8. `RECORD_MEMORY`가 켜져 있으면 답이 끝난 뒤 사용자 발화와 답을 `POST /api/v2/memories`로 저장한다(5.1절의 필드). 저장이 실패하면 "Memory write failed: ..." 한 줄을 답 뒤에 붙인다.

목록 출력 형식은 다음과 같다. 점수는 넣지 않는다.

```markdown
> [!NOTE]
> **Memories retrieved (5)**
>
> 1. **Nov 3, 2026** (Peanut allergy and meal prep)
>    "Mia was diagnosed with a peanut allergy last year, so we keep the house..."
> 2. **Nov 18, 2026** (Mia's birthday ideas)
>    "Mia turns 7 in January and she is obsessed with dinosaurs right now."
> ...

---
```

`> [!NOTE]`는 Open WebUI가 파란 세로 띠와 "NOTE" 제목으로 그리는 내장 알림 문법이다. 같은 문법에 TIP(초록), IMPORTANT(보라), WARNING(노랑), CAUTION(빨강)이 있고 제목 글자는 종류마다 고정이다. 메시지 안의 HTML 태그와 `style`은 Open WebUI가 글자 그대로 보여 주므로 글자 색을 직접 바꿀 수는 없고, 기억 목록을 색 있는 블록으로 감싸는 것이 Pipe와 설정만으로 할 수 있는 전부다(A.23). 기억 본문은 `MEMORY_PREVIEW_CHARS` 글자에서 단어 경계로 자르고 "..."를 붙여 비교 화면에서 두 줄 안에 들어가게 한다. 프롬프트에는 항상 전문이 들어간다.

`RECORD_MEMORY`가 꺼져 있으면 Pipe는 `POST /api/v2/memories`를 호출하지 않는다. 시연 중의 대화는 MemMachine에 남지 않는다. 검사 스크립트가 이 Valve가 꺼져 있는지 확인한다(5.5절).

### 5.3 Open WebUI 설정

환경 변수로 정하는 항목은 다음과 같다. 모두 v0.12.4 소스에서 확인한 이름이다(부록 A.7, A.12에서 A.16).

| 환경 변수 | 값 | 이유 |
|---|---|---|
| `ENABLE_OPENAI_API`, `OPENAI_API_BASE_URLS`, `OPENAI_API_KEYS` | `true`, `http://llm:8000/v1`, `dummy` | 오른쪽 모델이 vLLM에 직접 붙는다. 여러 vLLM 서버는 세미콜론으로 나열한다 |
| `ENABLE_OLLAMA_API` | `false` | Ollama를 찾지 않게 한다 |
| `ENABLE_MEMORIES`, `USER_PERMISSIONS_FEATURES_MEMORIES` | `false` | 내장 메모리 기능을 끈다. 시스템 프롬프트에 기억을 넣는 경로, 대화 뒤 기억을 자동으로 쓰는 백그라운드 검토, 기억 검색 도구가 모두 이 값으로 막힌다(부록 A.12) |
| `ENABLE_NOTES`, `USER_PERMISSIONS_FEATURES_NOTES` | `false` | 노트 기능을 끈다. 입력창의 "Attach Notes"와 노트 검색 도구가 사라진다(부록 A.14) |
| `ENABLE_FOLDERS` | `false` | 폴더(프로젝트)의 시스템 프롬프트와 파일이 그 안의 채팅에 상속되는 경로를 없앤다(부록 A.15) |
| `ENABLE_CALENDAR`, `ENABLE_AUTOMATIONS`, `ENABLE_CONTEXT_COMPACTION` | `false` | 시연에 없는 기능이다. 앞의 둘은 켜 두면 내장 도구 목록에 들어가고, 마지막은 긴 대화를 요약해 바꿔치기한다 |
| `DEFAULT_MODELS` | `memmachine_pipe.<모델>,<모델>` | 새 채팅을 열면 두 모델이 비교 모드로 선택된다. 쉼표로 나눈다 |
| `ENABLE_TITLE_GENERATION`, `ENABLE_FOLLOW_UP_GENERATION`, `ENABLE_TAGS_GENERATION`, `ENABLE_SEARCH_QUERY_GENERATION`, `ENABLE_RETRIEVAL_QUERY_GENERATION` | `false` | 보조 LLM 호출을 없앤다. 켜 두면 제목 생성이 Pipe로 들어와 기억 검색을 한 번 더 한다 |
| `ENABLE_WEB_SEARCH`, `ENABLE_CODE_INTERPRETER`, `ENABLE_CODE_EXECUTION`, `ENABLE_COMMUNITY_SHARING` | `false` | 시연에 없는 기능이고 외부 접근을 시도할 수 있다 |
| `OFFLINE_MODE` | `true` | Hugging Face 접근과 버전 확인을 끈다 |
| `BYPASS_EMBEDDING_AND_RETRIEVAL`, `RAG_EMBEDDING_ENGINE` | `true`, `openai` | 문서 검색용 로컬 임베딩 모델을 내려받거나 올리지 않게 한다 |
| `ENABLE_PERSISTENT_CONFIG` | `false` | 환경 변수가 항상 최종값이 되게 해서 compose 파일 하나로 재현한다. 관리자 화면에서 바꾼 일반 설정은 재시작하면 사라진다. Valve와 모델 표시 정보는 별도 테이블이라 유지된다 |
| `WEBUI_AUTH` | `true` (기본) | 첫 가입자가 관리자가 된다. 세팅 도구가 스태프 계정을 만든다 |
| `ENABLE_SIGNUP`, `USER_PERMISSIONS_CHAT_*` | `false` (두 모델 동시 선택과 임시 채팅만 `true`) | 부스 화면이 로그인하는 일반 계정에서 첨부, 마이크, 음성 통화, 컨트롤 패널, 개인 시스템 프롬프트, 공유, 내보내기, 메시지 수정과 삭제와 평가를 없앤다. 임시 채팅은 허용해 두고 세팅 도구가 계정 설정으로 기본값으로 만든다(아래 문단). Open WebUI는 관리자에게는 이 제한을 적용하지 않는다. 가입 링크도 막는다. 채팅 삭제와 가져오기 권한은 적재 도구가 쓰므로 기본값(허용)으로 둔다 |
| `DEFAULT_PROMPT_SUGGESTIONS` | `[]` | 새 채팅 화면의 기본 추천 프롬프트("Overcome procrastination" 등)를 없앤다. 스태프가 대본 질문을 입력한다 |

이름과 로고는 바꾸지 않는다. `WEBUI_NAME`을 바꾸면 뒤에 " (Open WebUI)"가 자동으로 붙고, 브랜딩 변경은 Open WebUI 라이선스 4조의 제약을 받는다.

환경 변수로 할 수 없는 일은 세팅 도구가 관리 API로 한다.

| 작업 | API |
|---|---|
| 스태프 계정 생성(첫 가입자가 관리자) | `POST /api/v1/auths/signup` |
| 부스 계정 생성(일반 사용자) | `POST /api/v1/auths/add` (`role=user`) |
| 두 모델 항목에 모든 계정의 읽기 권한 | `POST /api/v1/models/model/access/update` (`access_grants`에 `principal_type=user`, `principal_id=*`, `permission=read`). 권한이 없는 항목은 관리자에게만 보인다. 모델 갱신 API는 권한을 건드리지 않으므로 별도 호출이다 |
| Pipe 함수 등록과 활성화 | `POST /api/v1/functions/create`, `POST /api/v1/functions/id/{id}/toggle` |
| Valve 설정 | `POST /api/v1/functions/id/{id}/valves/update` |
| 모델 표시 이름, 아바타, 시스템 프롬프트, 내장 도구와 첨부 차단 | `POST /api/v1/models/create` (`name`, `meta.profile_image_url`은 PNG data URI, `params.system`, `meta.capabilities.builtin_tools=false`, `meta.capabilities.file_upload=false`). 아바타는 `assets/`의 SVG를 PNG로 렌더링한 것이다. Open WebUI가 SVG 아바타는 기본 로고로 대체한다(A.22) |
| 계정 설정(릴리스 노트 창 끄기, 개인 시스템 프롬프트 비우기, 새 채팅을 임시 채팅으로) | `GET`, `POST /api/v1/users/user/settings/update` (`ui.showChangelog=false`, `ui.system=""`, `ui.temporaryChatByDefault=true`) |
| 과거 채팅 가져오기(적재 도구) | `POST /api/v1/chats/import` (`chat`, `created_at`, `updated_at`). 로그인은 `POST /api/v1/auths/signin` |
| 채팅 전체 삭제(적재 도구가 실행할 때마다) | `DELETE /api/v1/chats/` |
| Valve 읽기(녹음 모드가 꺼졌는지 검사) | `GET /api/v1/functions/id/{id}/valves` |

오른쪽 모델에는 `params.system`으로 Pipe의 `BASE_SYSTEM_PROMPT`와 같은 문장을 넣는다. `DEMO_DATE`는 `.env`에 두고 세팅 스크립트가 "Today is ..." 줄을 붙여 두 곳에 같은 문장을 쓴다. 서버 시계와 무관하게 "this Saturday" 같은 표현을 고정하고, 두 쪽의 차이가 기억 블록뿐임을 보장하기 위해서다. 표시 이름은 왼쪽 "MemMachine + <모델>", 오른쪽 "<모델> (no memory)"로 둔다.

#### 과거 맥락을 끌어오는 다른 기능과 차단

사용자 요청으로 v0.12.4 소스에서 Memory 외에 과거 맥락을 모델에 넣을 수 있는 경로를 모두 찾았다. 오른쪽 모델이 이 중 하나라도 쓰면 "기억 없는 답"이 아니게 되므로 전부 막는다. 가장 큰 것은 내장 도구다. v0.12.4는 기본 설정에서 화면 요청마다 `search_chats`(사용자의 모든 과거 채팅 검색), `view_chat`(채팅 본문 읽기), 노트와 지식 베이스 검색, 현재 시각 같은 도구를 `tools` 배열로 모델에 함께 보낸다. 모델이 이 도구를 부르면 오른쪽도 과거 채팅을 읽게 되고, vLLM이 도구 호출을 켜지 않았으면 요청 자체가 실패할 수 있다.

| 경로 | 동작 | 차단 방법 | 근거 |
|---|---|---|---|
| 내장 도구 `search_chats`, `view_chat` | 모델이 과거 채팅을 검색하고 읽는다. 기본으로 켜져 있다 | 두 모델 항목에 `meta.capabilities.builtin_tools=false`를 넣어 내장 도구 전체를 끈다. 이 값이 거짓이면 내장 도구 목록을 만드는 함수가 불리지 않으므로 항목이 적용된 모델에는 이것으로 끝난다. 화면에 `ask_user` 같은 도구 블록이 보이면 항목이 없는 모델로 채팅한 것이다(세팅 도구 실행 전이거나, 항목이 없는 다른 모델을 고른 경우). 부스 계정에는 항목이 있는 두 모델만 보이므로 이 경우가 생기지 않는다 | A.13 |
| 내장 도구 노트, 지식 베이스, 현재 시각, 달력, 자동화, 스킬 | 같은 묶음이다. 현재 시각 도구는 `DEMO_DATE`와 어긋나는 날짜를 준다 | 위와 같다. 노트, 달력, 자동화는 환경 변수로도 끈다 | A.13 |
| Memory 시스템 컨텍스트와 백그라운드 검토 | 사용자 기억을 시스템 프롬프트에 넣고, 대화가 끝나면 기억을 자동으로 쓴다 | `ENABLE_MEMORIES=false` | A.12 |
| 입력창 첨부 메뉴의 "Attach Chats", "Attach Notes", 파일 | 과거 채팅, 노트, 파일 본문이 문맥으로 들어간다 | 두 모델 항목에 `meta.capabilities.file_upload=false`를 넣는다. 선택한 모델 중 하나라도 이 값이 거짓이면 관리자에게도 첨부 메뉴가 열리지 않는다. 노트는 `ENABLE_NOTES=false`로도 막는다 | A.14, A.16 |
| 사이드바의 채팅, 폴더, 노트를 입력창에 끌어다 놓기 | 같은 경로로 문맥에 들어간다 | 막는 설정이 없다. 폴더와 노트는 기능을 꺼서 없애고, 채팅은 스태프가 대본 질문만 입력하는 규칙으로 막는다 | A.16 |
| 폴더(프로젝트)의 시스템 프롬프트와 파일 | 폴더 안의 채팅이 폴더 설정을 상속한다 | `ENABLE_FOLDERS=false`. 새 채팅은 폴더 밖에서 연다 | A.15 |
| 모델 지식(`meta.knowledge`)과 `#` 지식 베이스 첨부 | 지식 베이스 문서가 문맥으로 들어간다 | 지식 베이스를 만들지 않고 모델 항목에 지식을 붙이지 않는다 | A.13 |
| 웹 검색, 문맥 압축 | 외부 내용이나 요약이 들어간다 | 기본값이 꺼짐이다. compose에 명시한다 | A.7 |
| 설정 화면의 사용자 시스템 프롬프트 | 모든 채팅에 들어간다 | 세팅 도구가 계정 설정의 `system`을 빈 값으로 쓴다. 같은 호출로 첫 로그인 때 뜨는 "What's New" 릴리스 노트 창도 끈다(`showChangelog`) | A.22 |

계정은 둘이다. 스크립트가 쓰는 관리자 계정(`ADMIN_*`)과 부스 화면이 로그인하는 일반 계정(`BOOTH_*`)이다. Open WebUI는 관리자에게 어떤 기능 제한도 적용하지 않으므로, 입력창과 보내기 단추만 남은 화면은 일반 계정에서만 만들 수 있다. 세팅 도구가 부스 계정을 만들고 두 모델 항목에 모든 계정의 읽기 권한을 준다. 적재 도구는 채팅을 부스 계정 소유로 넣고, 검사 도구는 부스 계정으로 두 모델이 보이는지 본다. 일반 계정도 사이드바의 채팅을 입력창에 끌어다 놓는 것은 막지 못하므로, 스태프가 대본 질문만 입력하는 규칙은 그대로다. 개발용 mock은 요청에 `tools`가 들어 있으면 로그에 경고를 남겨서, 내장 도구 차단이 됐는지 Mac에서 바로 확인한다. 회사 검증에서는 vLLM 요청 로그로 같은 것을 본다.

시연 중의 질문은 저장하지 않는다. 세팅 도구가 두 계정의 설정 `ui.temporaryChatByDefault`를 켜서 새 채팅이 항상 임시 채팅으로 열리게 하고, compose는 임시 채팅 권한(`USER_PERMISSIONS_CHAT_TEMPORARY`)을 허용으로 둔다. 임시 채팅은 사이드바에 들어가지 않으므로 관객이 바뀔 때 스태프는 New Chat만 누르면 되고 사이드바는 적재한 과거 채팅 그대로다. 화면 위에는 "Temporary Chat" 표시가 뜬다. 권한 `USER_PERMISSIONS_CHAT_TEMPORARY_ENFORCED`로 강제하는 방법은 쓰지 않는다. 강제하면 Open WebUI가 그 계정의 채팅 생성과 가져오기를 403으로 막아 적재 도구가 동작하지 않고, `ENABLE_PERSISTENT_CONFIG=false`에서는 실행 중에 풀 수도 없다(A.24).

### 5.4 과거 세션 만들기 (적재 도구)

과거 세션은 대본 파일에 적고 적재 도구(`scripts/load_scenario.py`) 하나가 Open WebUI와 MemMachine에 넣는다. 질문, 답, 시각이 모두 대본대로 들어가고, LLM 없이 몇 초면 끝난다. Open WebUI 소스는 고치지 않는다. 채팅 가져오기 API가 채팅의 `created_at`과 `updated_at`, 메시지마다의 `timestamp`를 그대로 저장하고, 화면은 메시지에 마우스를 올리면 그 시각을 "Nov 3, 7:12 PM" 꼴로 보여 주기 때문이다(부록 A.19). MemMachine 쪽도 메시지마다 `timestamp`를 받는다(부록 A.20).

세션마다 도구가 하는 일은 다음과 같다.

1. 대본의 턴을 Open WebUI의 `history.messages` 트리로 만든다. 메시지마다 `id`, `parentId`, `childrenIds`, `role`, `content`, `timestamp`를 채우고, 어시스턴트 메시지에는 왼쪽 모델 ID를 `model`로 넣어 이름과 아바타가 왼쪽 모델로 보이게 한다. 턴의 시각은 세션 날짜에 턴 순서대로 1분씩 더한 값이다.
2. `POST /api/v1/chats/import`로 넣는다. `created_at`은 세션 날짜, `updated_at`은 마지막 턴의 시각이다. 응답이 돌려주는 채팅 ID를 받는다.
3. 같은 턴을 `POST /api/v2/memories`로 보낸다. 턴마다 `timestamp`에 1의 시각을, `metadata.session_id`에 2의 채팅 ID를 넣는다(5.1절). 첫 호출이 프로젝트를 만든다(부록 A.17).

도구는 실행할 때마다 처음부터 다시 넣는다. 새 MemMachine 프로젝트 ID(`ces-<날짜와 시각>`)를 만들어 거기에 저장하고, Pipe의 Valve `PROJECT_ID`를 그 ID로 바꾸고, `DELETE /api/v1/chats/`로 계정의 채팅을 모두 지운 뒤 가져온다. 프로젝트를 지우거나 에피소드를 지우는 API는 쓰지 않는다(5.1절). 대본을 고치면 그냥 다시 실행한다. 도구는 `.env`의 스태프 계정으로 Open WebUI에 로그인하고, 왼쪽 모델 ID는 `.env`의 모델 이름으로 만든다. 요청 본문의 예는 부록 C에 있다.

세션 날짜는 시연 날짜에 맞춰 정한다. 사이드바 묶음("Previous 30 days" 등)이 브라우저의 현재 시각 기준이기 때문이다(부록 A.8). 시연이 2027년 1월 초이므로 세션을 2026년 11월과 12월에 두면 "Previous 30 days"와 그보다 앞선 달로 나뉘어 보인다. 발화 안의 시간 표현("last year" 등)도 이 날짜에 맞춘다. 시각은 시연 장비의 시간대를 붙여 적는다.

대본 파일(`scenario/script.sample.json`)은 세션과 검사용 질문을 담는다. 어시스턴트 답은 대본에 적는다. LLM으로 한 번 만들어 다듬어 넣어도 된다.

```json
{
  "sessions": [
    {
      "title": "Peanut allergy and meal prep",
      "date": "2026-11-03T19:12:00-08:00",
      "turns": [
        {"role": "user", "content": "Mia was diagnosed with a peanut allergy last year, so we keep the house peanut-free."},
        {"role": "assistant", "content": "Got it. I will keep every suggestion peanut-free. ..."}
      ]
    }
  ],
  "questions": [
    {
      "text": "Can you plan a menu for Mia's birthday party this Saturday?",
      "expected": ["peanut-free", "turns 7 in January"]
    }
  ]
}
```

`expected`는 그 질문의 top-k 본문 어딘가에 반드시 들어 있어야 하는 문구다. 검색 품질을 미리 확인하는 용도이므로 대본의 발화에서 한 구절을 적는다.

시연 중에 관객 앞에서 세션을 하나 더 만들고 바로 묻는 연출이 필요하면 Pipe의 녹음 모드를 쓴다(부록 D).

### 5.5 검사 스크립트

`demo_check.py`는 전원을 켠 뒤 명령 하나로 준비 상태를 확인한다.

1. 다섯 끝점의 상태를 본다. `llm:8000/v1/models`, `embed:8001/v1/models`(vLLM과 mock 모두 모델 목록을 돌려준다), `app:8080/api/v2/health`, `app:3000/health`, `db`의 PostgreSQL과 Qdrant 포트다.
2. vLLM의 모델 목록과 Open WebUI에 보이는 모델 목록이 맞는지 본다.
3. 대본의 질문마다 MemMachine 검색을 직접 호출해 `expected` 문구가 top-k 본문 안에 모두 있는지 확인한다.
4. Pipe의 Valve를 읽어 `RECORD_MEMORY`가 꺼져 있는지 확인한다.
5. 질문 하나를 Open WebUI의 채팅 완성 API로 Pipe 모델에 보내 답이 비어 있지 않은지 확인한다.
6. 결과를 표로 출력하고, 하나라도 실패하면 0이 아닌 종료 코드를 낸다.

### 5.6 개발용 mock

`mock_llm.py`는 FastAPI 앱 하나로 세 끝점을 낸다. 프로세스 하나에 메모리 100MB 안쪽이다.

| 끝점 | 동작 |
|---|---|
| `GET /v1/models` | 가짜 모델 ID 두 개를 돌려준다. 모델 전환을 시험하기 위해서다 |
| `POST /v1/chat/completions` | 스트리밍으로 짧은 답을 낸다. 시스템 프롬프트에 기억 블록이 있으면 "Using N memories: ..." 하고 첫 기억의 앞부분을 되풀이해서, 기억이 프롬프트에 들어갔는지 화면에서 바로 보이게 한다. 요청에 `tools`가 들어 있으면 로그에 경고를 남긴다(5.3절 보충) |
| `POST /v1/embeddings` | 단어를 해시해 고정 차원 벡터에 더하고 정규화한다. 같은 문장은 항상 같은 벡터가 되고, 단어가 겹치는 문장끼리 가까워진다. 의미 검색은 아니지만 개발 중의 top-k가 아주 엉뚱하지는 않다 |

같은 mock이 LLM과 임베더 역할을 모두 하며, 개발용 compose에서는 `llm`과 `embed`가 둘 다 이 프로세스를 가리킨다. 부스에서는 주소만 vLLM으로 바꾼다. 다른 브랜치의 `tools/mock_inference`는 실제 데이터셋 벡터를 내주는 부하 시험용이라 여기에는 쓰지 않는다.

개발용 프로필(`docker compose --profile local`)은 PostgreSQL, Qdrant, MemMachine(공개 이미지 `memmachine/memmachine:0.4.1-dev1`), Open WebUI, mock 다섯 개를 올린다. Mac에서 잰 메모리는 합쳐서 1.1GB 안팎이었다. 이 Mac에는 immich 등이 이미 돌고 있으므로 모든 컨테이너에 메모리 상한을 둔다. 목록의 날짜는 `.env`의 `TZ`(시연 장비의 시간대)로 표시해 사이드바의 채팅 시각과 맞춘다.

### 5.7 LLM 서버와 임베더 서버

두 서버 모두 vLLM 컨테이너를 쓴다. 모델 가중치는 로컬 디스크에 두고 `HF_HUB_OFFLINE=1`로 띄운다.

- LLM 서버: 채팅 모델 하나당 vLLM 프로세스 하나다. 모델을 두 개 이상 띄우려면 포트를 달리해 컨테이너를 추가하고 `gpu-memory-utilization`으로 H100 80GB를 나눈다. 8B급 두세 개는 함께 들어가지만 70B급(FP8)은 혼자서 대부분을 쓴다. 시연 도중의 모델 교체는 재시작이 필요하므로 하지 않고, 띄워 둔 모델 사이에서만 드롭다운으로 바꾼다.
- 임베더 서버: 임베딩 모델 하나를 `--runner pooling`으로 띄우고 서빙 이름은 `embed`로 고정한다(`memmachine.yml`이 이 이름을 가리킨다). 차원 수를 MemMachine 설정의 `dimensions`와 맞춘다. 임베더는 바꾸면 기억을 다시 넣어야 하므로 한 번 정하면 고정한다. MemMachine은 임베딩 요청에 `dimensions`를 붙이는데, 모델 설정에 Matryoshka 표시가 없으면 vLLM이 "does not support matryoshka representation, changing output dimensions ..."로 거절하고 MemMachine은 그 오류를 보고 `dimensions` 없이 다시 보낸다. 그 재시도의 결과는 모델 기본 길이라서 설정의 `dimensions`와 다르면 저장이 실패하므로, 회사 실행서 6.2절은 `dimensions`를 붙인 요청이 성공하는 것을 통과 조건으로 삼는다(부록 A.21).
- `--served-model-name`으로 모델 ID를 짧고 보기 좋은 이름으로 정한다. 이 이름이 화면의 모델 이름이 된다.

compose의 `llm`과 `embed` 프로필이 이 두 서버다. 같은 vLLM 이미지(`VLLM_IMAGE`, v0.26.0으로 고정)를 쓰고, 가중치 디렉터리를 `/model`로 읽기 전용 마운트하며 `HF_HUB_OFFLINE=1`로 띄운다. GPU 번호(`LLM_GPU`, `EMBED_GPU`), 메모리 비율, 최대 길이, 모델에 따라 필요한 추가 인자(`LLM_EXTRA_ARGS`, `EMBED_EXTRA_ARGS`)는 `.env`에 둔다. 회사 검증에서 H100 두 장이 한 서버에 있으면 두 프로필을 같은 호스트에서 올리고 GPU 번호만 다르게 준다. healthcheck의 `start_period`는 모델 적재 시간을 감안해 10분이다. Mac에서는 compose 문법만 검사했고 실제 기동은 회사 검증 항목이다.

모델 선택은 9장의 미결 사항이다. 선택과 무관하게 설정 파일의 값만 바뀐다.

### 6.2 compose 공통 규칙

- 모든 서비스는 `restart: unless-stopped`로 두어 부팅할 때 자동으로 뜬다. Docker 데몬도 부팅 시 시작되게 한다.
- 다른 서버의 서비스는 `depends_on`으로 기다릴 수 없다. MemMachine은 DB 서버가 늦게 켜지면 실패하고 재시작 정책으로 다시 뜬다. 재시작 간격이 길어지지 않는지 리허설에서 본다.
- compose 파일은 하나다. 서비스마다 `profiles`로 속한 서버(`db`, `app`, `llm`, `embed`)와 Mac(`local`)을 적어 같은 서비스 정의를 모든 장소에서 쓴다.
- 쉘이 없는 Qdrant 이미지를 빼고 모든 서비스에 healthcheck를 둔다. Qdrant는 검사 스크립트가 포트로 확인한다. 상태는 `docker compose ps`에서 본다.
- 데이터는 이름 있는 볼륨에 둔다. PostgreSQL, Qdrant, Open WebUI 데이터가 해당한다.
- 이미지 태그는 모두 고정한다. `latest`는 쓰지 않는다.
- 다른 서버의 이름(`db`, `llm`, `embed`)은 `extra_hosts`로 풀고 IP는 `.env`에서 받는다. Mac에서는 `host-gateway`를 적어 Mac에 공개된 포트로 간다.

### 6.3 오프라인 준비물

회사에서 실제 검증을 마친 뒤 회사 망에서 다음을 모두 내려받고 디스크에 둔다. Mac에는 모델 가중치를 두지 않는다.

- 컨테이너 이미지: Open WebUI v0.12.4, PostgreSQL(pgvector), Qdrant, vLLM, 공개 MemMachine 이미지 `memmachine/memmachine:0.4.1-dev1`. 데모는 배포된 서버를 쓰고 브랜치에는 데모 도구와 문서만 있다. 브랜치에서 빌드하지 않으므로 회사 망의 TLS 검사 때문에 빌드가 막히는 문제(GitHub 이슈 #45)도 피한다. 각 서버에서 `docker pull`한 뒤 `docker save`로 tar 파일도 남겨서, 이미지가 지워져도 복구할 수 있게 한다.
- 모델 가중치: 채팅 모델과 임베딩 모델. 두 서버의 로컬 디스크에 둔다.
- 브랜치 전체. 앱 서버에 clone해 둔다. 시나리오와 도구가 여기에 있다.
- 적재가 끝난 뒤의 DB 볼륨 백업(PostgreSQL, Qdrant, Open WebUI). 적재는 다시 할 수 있지만 볼륨을 되돌리는 쪽이 빠르다.

### 6.4 기동과 복구

전원을 켜면 모든 서버가 자동으로 컨테이너를 올린다. 스태프는 시연 화면 장비에서 `demo_check.py`를 실행해 전부 통과하는지 보고, 브라우저로 Open WebUI에 접속한다. 검사가 실패하면 표에 어느 서버의 무엇이 안 되는지 나온다.

### 6.5 이전 원칙

한국에서 세팅을 마친 뒤 전원과 배선을 모두 끊고 옮겨서, 미국에서 배선과 전원만 복구하면 동작해야 한다. 이 요구는 본 설계의 다음 원칙으로 반영했다.

1. 완전 오프라인 동작 (6.3절)
2. 고정 IP와 호스트 이름 (4.1절)
3. 전원만 켜면 자동 기동 (6.2절)
4. 디스크 볼륨과 백업으로 데이터 보존 (6.2절, 6.3절)
5. 명령 하나로 준비 상태 확인 (5.5절)

전원을 끄기 전의 정상 종료 절차, 미국에서의 배선과 점검 순서, 문제가 생겼을 때의 조치는 [이전 절차서](relocation_2026-10-27.md)에 있다. 처음 올리는 사람을 위한 단계별 명령은 [사용 가이드](guide_2026-10-27.md)에 있다.

### 6.6 리허설

출국 전에 사무실 망에서 분리한 상태로 전체를 한 번 끈 뒤 켜고, 검사 스크립트와 대본 전체를 돌려 본다. 이때 걸린 시간과 문제를 기록해 이전 절차서에 반영한다.

## 7. 위험과 확인할 사항

| 위험 | 영향 | 대응 | 확인 시점 |
|---|---|---|---|
| MemMachine이 Neo4j 설정 없이 뜨지 않을 수 있다 | event 백엔드만으로는 못 쓴다 | 설정 검증 코드를 보고, 필요하면 쓰지 않는 더미 항목을 둔다 | 구현 1단계 드라이런 |
| Open WebUI가 오프라인에서 문서 검색용 모델을 찾다 멈출 수 있다 | 기동 실패 | `OFFLINE_MODE`, `BYPASS_EMBEDDING_AND_RETRIEVAL`, `RAG_EMBEDDING_ENGINE=openai` 조합을 인터넷을 끊고 시험한다 | 구현 1단계 |
| 비교 화면에서 Pipe의 목록 마크다운이 의도대로 보이지 않을 수 있다 | 관객이 목록을 못 읽는다 | 실제 화면에서 형식을 조정한다. 시안(부록 B)은 소스를 읽고 그린 것이다 | 구현 1단계 |
| DB 서버보다 앱 서버가 먼저 켜지면 MemMachine이 실패한다 | 기동 지연 | 재시작 정책으로 복구되는지, 몇 분 안에 뜨는지 잰다 | 리허설 |
| vLLM 버전에 따라 임베딩 서빙 옵션 이름이 다르다 | 임베더 기동 실패 | v0.26.0 문서 기준으로 `--runner pooling`을 쓴다. 모델이 자동 변환되지 않으면 `EMBED_EXTRA_ARGS=--convert embed`를 준다 | 회사 검증 |
| 임베딩 모델 설정에 Matryoshka 표시가 없으면 vLLM이 `dimensions`가 붙은 요청을 거절한다 | 첫 저장 실패 | MemMachine의 재시도는 모델 기본 길이를 돌려주므로 설정값과 다르면 소용이 없다(부록 A.21). 회사 실행서 6.2절대로 `dimensions` 요청이 성공하는지 먼저 보고, 거절되면 `--hf-overrides '{"is_matryoshka": true}'`를 주거나 `dimensions`를 기본 길이로 맞춘다 | 회사 검증 |
| Open WebUI가 쓰는 `DEFAULT_MODELS`에 manifold 모델 ID가 그대로 먹히는지 | 새 채팅이 비교 모드로 열리지 않는다 | 소스상 쉼표로 나눠 선택한다(부록 A.7). 실제 화면에서 확인한다 | 구현 1단계 |
| Pipe 응답이 느리면 오른쪽 답이 먼저 끝나 대비가 약해진다 | 연출 저하 | 검색 시간은 보통 수백 ms다. 리허설에서 재고, 필요하면 오른쪽 모델에만 짧은 지연 Valve를 두는 것을 검토한다 | 리허설 |
| mock에서 통과한 것이 실제 vLLM에서 다르게 동작할 수 있다 | 회사에서야 발견된다 | Pipe는 OpenAI 호환 형식만 쓰고 mock도 같은 형식을 지킨다. 모델 목록의 이름, 스트리밍 조각 형식, 임베딩 차원은 회사 검증 목록에 넣는다 | 구현 3단계 회사 검증 |
| Open WebUI가 기본 설정에서 모델에 내장 도구(`search_chats` 등)를 붙여 보낸다 | 오른쪽이 과거 채팅을 읽거나, vLLM이 `tools`를 거부한다 | 두 모델 항목에서 `builtin_tools`를 끈다. mock 로그(1단계)와 vLLM 요청 로그(회사 검증)에서 `tools`가 없는지 본다 | 구현 1단계, 3단계 |
| 도구가 만든 채팅 JSON이 v0.12.4 화면에서 제대로 열리지 않을 수 있다 | 사이드바의 과거 채팅이 비어 보인다 | 화면에서 내보낸 채팅 JSON과 같은 구조로 만들고, 2단계에서 실제로 열어 질문, 답, 시각을 확인한다 | 구현 2단계 |
| 녹음 Valve를 끄지 않고 시연하면 질문과 답이 기억에 쌓인다 | 다음 질문의 목록이 달라진다 | 검사 스크립트가 Valve를 확인한다. 쌓였으면 `load_scenario.py`를 다시 실행해 새 프로젝트로 넣는다 | 리허설 |
| 라이선스 | 브랜딩 변경 금지 | 이름과 로고를 바꾸지 않는다 | 설계로 해결 |

## 8. 구현 계획

| 단계 | 산출물 | Mac에서 확인 | 회사에서 확인 |
|---|---|---|---|
| 1. 로컬 스택 | `docker-compose.yml`(local 프로필), `memmachine.yml`, `mock_llm.py`, Pipe 초안, `setup_openwebui.py` | 다섯 컨테이너가 뜨고, 비교 화면에 Pipe 모델과 mock 모델이 보이며, 질문 하나에 목록과 답이 나온다 | 없음 |
| 2. 적재와 검사 | `load_scenario.py`, `demo_check.py`, `script.sample.json`, Pipe 녹음 모드 | 예시 대본을 적재하고 검사 스크립트가 전부 통과한다. 사이드바에 대본의 날짜와 제목으로 채팅이 보이고, 열면 질문과 답과 시각이 대본대로 있으며 왼쪽 목록의 제목과 맞는다 | 없음 |
| 3. 부스 프로필 | vLLM 서비스(llm, embed 프로필), `.env.example`의 부스 값, `hosts.example`, README | compose 문법 검사. vLLM은 올릴 수 없다 | push 후 pull해서 실제 vLLM으로 올린다. Pipe와 vLLM 호환, 모델 전환, 응답 시간을 확인하고 검증 문서로 커밋한다 |
| 4. 대본과 모델 | 실제 대본 파일, 모델 선택, 아바타 | 형식 검사와 mock 적재 | 실제 임베더로 대본을 적재하고 검사 스크립트가 통과하는지 본다. 기대 기억이 top-5에 안 들면 대본을 고치고 다시 적재한다 |
| 5. 부스 준비와 이전 절차서 | 오프라인 준비물, 별도 문서 | 없음 | 인터넷을 끊고 리허설한다 |

각 단계는 끝날 때 커밋한다. push는 사용자가 지시할 때 한다. 1단계가 끝나면 실제 화면을 캡처해 시안과 비교한다. 3단계부터는 회사 검증이 끝나야 다음 단계로 간다.

## 9. 미결 사항

사용자 결정이 필요한 항목이다. 설계 진행을 막지는 않는다.

1. 시나리오 내용: 페르소나, 과거 세션의 수와 날짜, 세션마다의 질문과 답, 대본 질문. 질문마다 2개에서 3개 세션의 사실이 필요하다. (초안 완료: `scenario/script.json`, 세션 일곱 개와 질문 넷. 기대 문구는 회사에서 실제 임베더로 조정한다)
2. 채팅 모델: 종류와 개수. H100 메모리 분배가 여기에 달려 있다. 추천 기본값은 영어 지시 수행이 안정적이고 8B급이라 응답이 빠른 모델 하나(예: Qwen3-8B 또는 Llama-3.1-8B-Instruct)이며, 생각(reasoning)을 먼저 출력하는 모델은 카드가 한동안 비어 보이므로 끄거나 피한다.
3. 임베딩 모델과 차원 수. 추천 기본값은 `BAAI/bge-m3`(1024차원, vLLM pooling 지원)이며, 정하면 `memmachine.yml`의 `dimensions`를 그 값으로 한 번 고친다.
4. 내부망 IP 대역과 스위치 사양.
5. 시연 화면 장비의 종류와 브라우저. 화면 해상도에 따라 두 카드의 너비가 정해진다.
6. 모델 아바타 이미지. (완료: `assets/`의 PNG 둘. 다른 그림을 쓰려면 파일만 바꾼다)
7. 앱 서버와 DB 서버의 사양. GPU가 없어도 되지만 메모리와 디스크는 확인해야 한다.
8. 회사 검증 환경의 형태. H100 두 장이 한 서버에 있는지 서버 여러 대인지, 그리고 그 장비가 부스로 가는 장비와 같은지. 같다면 회사 세팅이 곧 부스 세팅이 되고, 다르다면 부스 장비에 한 번 더 올려야 한다.
9. 회사에서 올리는 사람. (완료: 사람과 Claude Code 모두를 위한 [사용 가이드](guide_2026-10-27.md)와, git clone부터 검증 결과 push까지 작은 모델의 Claude Code도 따라갈 수 있게 쓴 [회사 실행서](company_runbook_2026-10-27.md)를 썼다)

## 부록 D. 보조: Pipe 녹음 모드

적재 도구 대신 Open WebUI에서 직접 쓰면서 기억을 쌓는 방식이다. 시연 중에 관객 앞에서 세션을 하나 더 만든 뒤 바로 질문하는 연출에 쓴다. 날짜가 쓰는 시각으로 남고 답을 LLM이 쓰므로, 미리 만드는 과거 세션에는 쓰지 않는다.

Pipe의 `RECORD_MEMORY` Valve를 켜면 Pipe는 평소대로 검색하고 답한 뒤, 그 턴의 사용자 발화와 답을 MemMachine에 저장한다(5.2절 8번). 채팅은 Open WebUI가 평소처럼 저장하므로 사이드바에 남고, 채팅 ID `__chat_id__`가 에피소드의 `session_id`가 되어 적재한 세션과 같은 방식으로 제목이 붙는다.

절차는 다음과 같다.

1. 관리자 화면의 함수 설정에서 `RECORD_MEMORY`를 켠다.
2. 새 채팅을 열고 모델 선택에서 오른쪽 모델을 빼서 "MemMachine + 모델"만 남긴다. 둘 다 둔 채 쓰면 오른쪽 답도 채팅에 저장되어 과거 채팅에 답이 둘씩 보인다.
3. 사용자 발화를 입력하고 답을 기다린다.
4. 사이드바에서 채팅 이름을 바꾼다. 제목 생성을 꺼 두었으므로 처음에는 첫 발화가 제목이 된다(부록 A.18).
5. `RECORD_MEMORY`를 끈다. 끄지 않으면 이후의 질문들이 기억에 쌓인다(7장).

연출이 끝난 뒤 원래 상태로 돌리려면 `load_scenario.py`를 다시 실행해 새 프로젝트로 넣는다.
