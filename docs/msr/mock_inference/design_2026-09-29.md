# mock 임베더와 리랭커 서버 설계

작성일 2026-09-29(3판). 기준 코드는 `upstream/speedkick` HEAD `8d7b832`(2026-09-17)이며, 인용 `[C:파일:행]`은 이 트리(`~/Projects/MemMachine/mm_speedkick`)의 줄 번호다. 확인이 끝난 문장은 `[사실]`, 측정하지 않은 추정은 `[추론]`으로 표시한다.

이 문서는 **이것만 보고 도구를 끝까지 만들고, 데이터셋 없이 드라이런까지 마친 뒤, 사내 서버에서 한 단계씩 확인하며 배포할 수 있도록** 쓴다. 파일 형식, 요청과 응답의 바이트 단위 형식, 여러 프로세스가 벡터 번호를 나누는 규칙, 변환기의 병렬 구조, 합성 데이터 규격, 로컬 드라이런 절차, 사내 적용 절차, 합격 기준을 모두 적는다.

## 0. 요약

임베딩과 리랭킹을 **계산 없이 즉시 응답하는 mock 서버 하나**로 대체한다. 목적은 정확도가 아니라 부하 제거다. 이 서버가 병목이 되지 않아야 MemMachine과 DB의 한계가 드러난다.

- 임베딩은 `POST /v1/embeddings`(OpenAI 호환)로 받고, 입력 텍스트와 무관하게 **미리 변환해 둔 벡터 파일에서 순서대로** 꺼내 준다. 파일의 차원을 그대로 서빙하므로 laion(768차원)이든 msmarco(1536차원)이든 같은 서버다.
- 리랭킹은 `POST /v2/rerank`(Cohere 호환, vLLM과 같은 형식)로 받고, **받은 순서를 그대로 보존하는 점수**를 돌려준다.
- **목표는 10,000 RPS**다. Python 프로세스 하나로는 안 되므로(§10) worker 프로세스 여러 개가 **주소 하나, 포트 하나**를 같이 받는다. 클라이언트(MemMachine 인스턴스 여러 개)는 mock 하나만 설정하고, 내부 병렬은 mock이 알아서 한다. `--target-rps`를 주면 worker 수와 코어를 그에 맞게 잡는다.
- 여러 worker가 벡터를 **겹치지 않고 빠짐없이 순서대로** 주도록, 벡터 번호를 파일 잠금으로 구간 대여(lease)한다.
- parquet를 `.npy`로 바꾸는 변환기는 파일 단위로 **병렬**이며 디스크 쓰기 속도가 상한이다.
- **데이터셋 없이도 전부 돌려 볼 수 있다.** 합성 벡터 파일과 합성 parquet 생성기를 두어, 개발 머신(macOS)에서 서버, 변환기, SDK 왕복, 여러 worker의 순서 보장, MemMachine 리소스 매니저 결합까지 드라이런한다(§14). 실데이터 변환, 10,000 RPS 실측, MemMachine 실사용은 사내 서버에서 한 단계씩 확인한다(§15).
- MemMachine이 아닌 응용도 그대로 쓴다. OpenAI 임베딩 API를 쓰는 클라이언트와 Cohere, vLLM, Jina 형식의 rerank 클라이언트는 `base_url`만 바꾸면 된다.

## 1. 목적과 범위

보장하는 것은 다음이다.

1. 클라이언트가 실제 vLLM이나 OpenAI에 보내는 것과 같은 HTTP 요청을 받아 같은 형식으로 응답한다. 클라이언트의 SDK, 재시도, 차원 검증, 배치 분할이 그대로 돈다.
2. 벡터는 실제 데이터셋의 벡터라서 벡터 DB에 저장되는 벡터의 분포와 크기가 진짜와 같다.
3. 응답 시간이 밀리초 아래라서 클라이언트 쪽 한계가 먼저 드러난다.
4. 목표 RPS를 정하면 그 부하를 병목 없이 받는다.

보장하지 않는 것은 벡터와 점수의 의미다. 같은 텍스트를 두 번 보내면 다른 벡터가 온다(순차 모드). 같은 텍스트에 같은 벡터가 필요한 응용을 위해 해시 모드를 둔다(§8.3).

LLM(`/v1/chat/completions`)은 만들지 않는다. MemMachine의 이번 부하 경로(episodic add와 search)는 LLM을 부르지 않는다.

| 12 | 사내 적용 | 실데이터 변환, 처리량 실측, MemMachine 설정과 실사용, 배포는 사내 Linux 서버에서 §15의 순서대로 한 단계씩 확인한다. |

## 3. 용어

| 용어 | 뜻 |
|---|---|
| parquet 파일 | 데이터셋 배포본을 이루는 파일 하나. Zilliz는 laion 1억 행을 `train-00-of-100.parquet`부터 `train-99-of-100.parquet`까지 100개로 나누어 배포하며 파일마다 1,000,000행이다. msmarco는 `msmarco_passage_00-0.parquet` 같은 이름으로 277개다. 앞선 문서에서 이 파일 하나를 "shard"라고 불렀는데, **Qdrant의 shard와 아무 관계가 없는 단순한 파일 분할**이다. 이 문서는 "parquet 파일"이라고만 쓴다. |
| row group | parquet 파일 안의 읽기 단위. laion은 파일당 3개다. 변환기가 이 단위로 읽는다. |
| 행, 벡터 번호 | 변환된 `.npy`에서 벡터 하나의 위치. 0부터 N-1. parquet 파일을 이름순으로 이어 붙인 순서다. |
| worker | 요청을 처리하는 프로세스 하나. 포트를 공유하는 여러 worker가 한 서버를 이룬다. |
| lease | worker가 벡터 번호 구간 `[a, b)`를 자기 것으로 빌리는 것. 빌린 구간은 그 worker만 준다. |
| CHUNK | lease 한 번의 크기. 기본 20,000. |
| 합성 데이터 | 데이터셋 대신 쓰는, 시드로 재현되는 무작위 단위 벡터. `synth`가 `.npy`로, `synth-parquet`가 Zilliz와 같은 스키마의 parquet로 만든다(§7.5, 부록 C). |
| 드라이런 | 데이터셋과 MemMachine 실환경 없이 도구의 모든 기능을 끝까지 돌려 보는 것(§14). |

## 4. 클라이언트가 실제로 보내는 요청

mock이 맞춰야 할 것은 SDK가 실제로 보내고 실제로 검사하는 것뿐이다. MemMachine을 기준으로 확인했고, 다른 응용도 같은 SDK를 쓰면 같다.

### 4.1 임베딩

- MemMachine의 `OpenAIEmbedder`는 `openai.AsyncOpenAI`로 `embeddings.create(input=..., model=..., dimensions=...)`를 부른다. `[사실]` `[C:packages/server/src/memmachine_server/common/embedder/openai_embedder.py:237-247]`
- openai SDK는 `encoding_format`을 주지 않으면 **자동으로 `"base64"`를 붙여 보내고** 응답의 base64를 float32 배열로 복원한다. `[사실]` `[C:.venv/lib/python3.12/site-packages/openai/resources/embeddings.py:235-236]` 그래서 mock은 float32 바이트를 base64로 돌려주면 되고, 이것이 직렬화 비용도 가장 적다.
- 요청 하나에 입력 최대 2,048개, 총 75,000자를 넘기지 않도록 MemMachine이 먼저 나눈다. `[사실]` `[C:openai_embedder.py:72-75, 150-157]`
- 응답에서 읽는 것은 `data[i].embedding`과 `usage.prompt_tokens`, `usage.total_tokens`뿐이다. 첫 벡터 길이가 설정 `dimensions`와 다르면 `ExternalServiceAPIError`를 낸다. `[사실]` `[C:openai_embedder.py:306-323]`
- `dimensions` 파라미터가 400으로 거부되고 메시지에 `dimension`이 있으면 파라미터 없이 다시 부른다. `[사실]` `[C:openai_embedder.py:249-257]`
- 빈 문자열은 MemMachine이 `"."`로 바꿔 보낸다. `[사실]` `[C:openai_embedder.py:141]`
- 호출 수는 add 요청 한 번에 `ingest_embed` 한 번(에피소드 수만큼 입력), search 한 번에 `search_embed` 한 번(입력 1개)이다. `[사실]` `[C:packages/server/src/memmachine_server/episodic_memory/event_memory/event_memory.py:269, 406]`
- 임베더가 만들어질 때 `validate=True`면 `search_embed(["a"])`로 검증 호출을 한 번 한다. 로그는 `Validating embedder 'NAME' is working.`과 `Embedder 'NAME' is valid.`다. `[사실]` `[C:packages/server/src/memmachine_server/common/resource_manager/embedder_manager.py:136-143]` 이 호출이 벡터 하나를 소비한다.

### 4.2 리랭킹

- `provider: cohere`면 `cohere.AsyncClientV2(api_key=..., base_url=...)`가 만들어지고 `client.rerank(model=..., query=..., documents=candidates)`를 부른다. `[사실]` `[C:packages/server/src/memmachine_server/common/resource_manager/reranker_manager.py:169-189]` `[C:packages/server/src/memmachine_server/common/reranker/cohere_reranker.py:48-52]`
- cohere SDK는 `base_url`의 끝 슬래시를 떼고 `/v2/rerank`를 붙여 POST 한다. 본문은 `model`, `query`, `documents`이고 None인 필드(`top_n` 등)는 빠진다. `[사실]` `[C:.venv/lib/python3.12/site-packages/cohere/core/http_client.py:212]` `[C:.venv/lib/python3.12/site-packages/cohere/v2/raw_client.py:2591-2600]`
- 응답 파싱에 **필수인 것은 `results[].index`와 `results[].relevance_score`뿐**이다. `id`, `meta`, `document`는 선택이고 모르는 필드는 허용된다. `[사실]` `[C:.venv/lib/python3.12/site-packages/cohere/v2/types/v2rerank_response.py:8-11]` `[C:.venv/lib/python3.12/site-packages/cohere/types/rerank_response_results_item.py:7-14]`
- MemMachine은 `scores[result.index] = relevance_score`로 원래 자리에 되돌린다. `[사실]` `[C:cohere_reranker.py:61-66]` 후보가 없거나 전부 공백이면 mock을 부르지 않는다. `[사실]` `[C:cohere_reranker.py:40-45]`
- 리랭커가 만들어질 때 `rerank("a", ["a", "b"])`로 검증 호출을 한 번 한다. 로그는 `Validating reranker NAME is working.`과 `Reranker NAME is working.`이다. `[사실]` `[C:reranker_manager.py:100-107]`
- 점수는 후보를 내림차순 정렬하는 데만 쓰이고 코사인 점수와 섞이지 않는다. `[사실]` `[C:event_memory.py:470-499]` `score_threshold` 기본값은 None이다. `[사실]` `[C:packages/server/src/memmachine_server/episodic_memory/long_term_memory/long_term_memory.py:229-244]`
- 검색 한 번에 리랭커로 가는 후보는 최대 `limit × 4`개다. `[사실]` `[C:long_term_memory.py:107, 310-313]` limit=20이면 rerank 요청 하나에 문서 80개다.

### 4.3 vLLM이 서빙하는 형식

vLLM 공식 문서(2026-09-29 확인)는 rerank를 `/rerank`, `/v1/rerank`, `/v2/rerank`로 서빙하며 Cohere v1과 v2, Jina v1 호환이라고 밝힌다. 응답은 `id`, `model`, `usage.total_tokens`, `results[{index, document.text, relevance_score}]`이고 `top_n` 생략 시 문서 수와 같다. 임베딩은 `/v1/embeddings`에서 `encoding_format` `float`과 `base64`를 모두 받는다. `[사실]`

### 4.4 MemMachine 리소스 매니저는 DB 없이 만들 수 있다

`ResourceManagerImpl(conf)`의 생성자는 DatabaseManager, EmbedderManager, LanguageModelManager, RerankerManager를 만들 뿐 어느 DB에도 연결하지 않는다. `[사실]` `[C:packages/server/src/memmachine_server/common/resource_manager/resource_manager.py:99-121]` `get_embedder(name, validate=True)`와 `get_reranker(name, validate=True)`는 각각 mock에 검증 호출을 보낸다. 그래서 **PostgreSQL과 Qdrant 없이도 MemMachine의 실제 설정 파서와 매니저 코드로 mock을 검증할 수 있다**(§14 D7). 생성자가 DB 설정을 검증하는지는 K6에서 확인하고, 필요하면 최소한의 `databases` 절을 넣는다.

## 5. 구성

```
[클라이언트 호스트들]                          [mock 호스트]
  memmachine-server ×k ──HTTP──▶  :8000 (worker W개가 포트 공유)
  다른 응용            ──HTTP──▶     ├─ POST /v1/embeddings
                                     ├─ POST /v2/rerank  (/v1/rerank, /rerank)
                                     ├─ GET  /v1/models
                                     └─ GET  /health
                                          │ 벡터: np.load(mmap_mode="r") 슬라이스
                                          │ 번호: state.json + state.lock (lease)
                                     /data/vectors/laion_100m.npy      (307.2GB)
                                     /data/vectors/msmarco_138m.npy    (850.1GB)
```

코드는 `tools/mock_inference/`에 두고 패키지 이름은 `mock_inference`, 진입점은 `python -m mock_inference <subcommand>`다.

| 파일 | 역할 |

의존은 서버가 `numpy`, `uvicorn`, `uvloop`, `httptools`, `orjson`, `xxhash`, 변환기와 합성기가 `pyarrow`, 검사 스크립트가 `openai`, `cohere`, `httpx`다. 프레임워크 없이 ASGI 인터페이스를 직접 구현한다. 라우팅이 네 개뿐이라 프레임워크가 주는 것보다 프레임워크의 요청당 오버헤드가 더 크다.

## 6. 벡터 파일 형식

`.npy` 한 파일이다. numpy 표준 헤더에 shape `(N, dim)`과 dtype `<f4`(float32 리틀엔디언), C-order가 들어 있어 어떤 언어에서도 헤더를 읽고 `offset + row × dim × 4`로 행에 접근할 수 있다. 헤더는 보통 128바이트이고 `info`가 정확한 오프셋을 찍는다. 서버는 `np.load(path, mmap_mode="r")`로 열어 슬라이스만 한다.

| 데이터셋 | N | dim | 행 크기 | `.npy` 데이터부 | 원본 parquet |
|---|---|---|---|---|---|
| laion_large_100m | 100,000,000 | 768 | 3,072B | 307.2GB (286.1GiB) | 100개, 212.3GB |
| msmarco_v2_138M | 138,364,198 | 1536 | 6,144B | 850.1GB (791.7GiB) | 277개, 851.2GB |
| 합성(드라이런 기본) | 200,000 | 768 | 3,072B | 614.4MB | 없음 |

msmarco의 행 수와 파일 수, 크기는 앞선 문서에서 확인한 값이다. `[사실]` `[C:docs/msr/qdrant_bottleneck/dataset_download_2026-09-21.md:358, 740]` laion의 스키마는 `id: int64`, `emb: large_list<float>`다. `[사실]` `[C:dataset_download_2026-09-21.md:95]` msmarco의 열 이름은 확인하지 않았으므로 변환기가 **벡터 열을 자동으로 찾는다**(§7.2). 합성 데이터는 laion과 같은 스키마로 만든다.

디스크는 변환 중 parquet와 `.npy`가 같이 있어야 한다. laion은 520GB, msmarco는 1.71TB가 비어 있어야 한다. 부족하면 `--rows`로 앞부분만 변환한다.

`python -m mock_inference info FILE.npy`는 헤더를 읽어 N, dim, dtype, 데이터 오프셋, 파일 크기, 기대 크기(`offset + N × dim × 4`)와의 일치 여부를 찍는다.

## 7. 변환기

### 7.1 요구

- parquet 파일 여러 개를 `.npy` 하나로 잇는다. 순서는 파일 이름순, 파일 안은 원래 순서다.
- 파일 단위로 병렬이다. 상한은 디스크 쓰기 속도다.
- 중단 후 재실행하면 끝난 파일은 건너뛴다.
- 끝나면 표본을 대조해 스스로 검증한다.

### 7.2 절차

**1단계, 계획.** 글롭에 맞는 파일을 이름순으로 나열하고 파일마다 `pyarrow.parquet.ParquetFile(f).metadata.num_rows`를 읽는다(메타데이터만 읽으므로 파일당 수 밀리초다). 첫 파일의 스키마에서 **타입이 `list<float>`, `large_list<float>`, `fixed_size_list<float>`(float32 또는 float64) 중 하나인 첫 열**을 벡터 열로 잡는다. `--vector-column`을 주면 그 열을 쓴다. 첫 row group의 첫 행으로 dim을 정한다. 파일별 시작 행 번호(누적 합)를 계산한다. `--rows R`이 있으면 누적 합이 R을 넘는 지점에서 계획을 자른다. 결과를 `<out>.plan.json`에 쓴다. 이미 있는 `<out>.plan.json`이 새 계획과 다르면(파일, 행 수, 열이 바뀜) 쓰지 않고 `<out>`, `<out>.done`, `<out>.plan.json`을 지우고 다시 시작하라는 메시지와 함께 끝낸다. 재개는 파일 이름만 보고 건너뛰므로, 시작 행이 달라진 계획을 이어 쓰면 잘못된 행이 남기 때문이다.

```json
{"dim": 768, "rows": 100000000, "vector_column": "emb", "source_dtype": "float32",
 "files": [{"path": ".../train-00-of-100.parquet", "rows": 1000000, "offset": 0}, ...]}
```

**2단계, 할당.** `np.lib.format.open_memmap(out, mode="w+", dtype="<f4", shape=(rows, dim))`로 파일을 만든다. ext4, xfs, APFS에서 sparse 파일이라 즉시 끝난다. 파일이 이미 있으면(재실행) 모양이 계획과 같을 때만 그대로 쓰고, 다르면 `<out>`과 `<out>.done`을 지우고 다시 시작하라는 메시지와 함께 끝낸다. 있는 파일을 덮어쓰면 건너뛴 파일의 행이 0이 되어 재개가 깨지기 때문이다.

**3단계, 병렬 채우기.** `multiprocessing.Pool(jobs)`에 파일 하나를 작업 하나로 넘긴다. `jobs` 기본값은 코어 수다. 작업은 다음을 한다.

1. `<out>.done/<파일이름>.ok`가 있으면 즉시 반환한다(재개).
2. `np.load(out, mmap_mode="r+")`로 연다.
3. `ParquetFile(path).iter_batches(batch_size=65536, columns=[vector_column])`로 읽는다. 배치마다 `pyarrow.compute.list_flatten(column).to_numpy()`로 평탄화하고 `.astype("<f4", copy=False).reshape(-1, dim)`으로 만든 뒤 memmap의 `[offset + 지금까지 쓴 행 수 : ...]`에 대입한다. 배치의 리스트 길이가 dim과 다른 행이 하나라도 있으면(`list_value_length`로 확인) 실패로 끝낸다.
4. 파일을 다 쓰면 `memmap.flush()` 후 `.ok`를 만든다.

파일마다 행 범위가 겹치지 않으므로 여러 프로세스가 같은 memmap에 동시에 써도 안전하다. 잠금은 없다.

**4단계, 검증.** 전체 계획에서 행 100개를 무작위로 뽑아 parquet에서 다시 읽고 `.npy`의 해당 행과 바이트 단위로 비교한다. L2 노름의 최소, 최대, 평균을 찍는다(laion은 1.0 근처여야 한다. `[사실]` `[C:dataset_download_2026-09-21.md:97]`). 하나라도 다르면 종료 코드 1이다. `--verify-only`를 주면 `<out>.plan.json`을 읽어 이 단계만 다시 한다.

### 7.3 성능

작업 하나는 parquet 복호(CPU)와 memmap 쓰기(디스크)다. `list_flatten`은 float 리스트에서 사실상 복사 한 번이라 코어당 `[추론]` 300MB/s 이상 나오고, 코어 10개면 디스크 쓰기가 먼저 막힌다. NVMe 1.5GB/s 기준 laion 307GB는 `[추론]` 4분에서 10분, msmarco 850GB는 10분에서 30분이다. 실측은 사내 C3에서 남긴다.

작업 하나는 65,536행짜리 배치 하나를 한 번에 메모리에 올리므로, 768차원 float32 소스 기준 작업당 약 1.2GB가 필요하다(측정치; 1536차원이거나 소스가 float64면 두 배 안팎으로 커진다). `--jobs`를 코어 수 그대로 주면 코어당 여유 RAM이 이보다 적을 때 스왑되거나 OOM이 날 수 있으므로, 코어당 여유 RAM을 먼저 확인하고 모자라면 `--jobs`를 줄인다. 디스크 쓰기가 이미 상한이라 12 정도로 줄여도 속도는 거의 그대로다.

쓰기는 페이지 캐시를 거치므로 변환 중 호스트 메모리가 캐시로 가득 찬다. 부하 시험과 같은 호스트에서 변환하지 않는다.

### 7.4 명령

```bash
python -m mock_inference convert \
  --parquet-glob "/data/laion_large_100m/train-*-of-100.parquet" \
  --out /data/vectors/laion_100m.npy --jobs 10

python -m mock_inference convert \
  --parquet-glob "/data/msmarco_v2_138M_parquet/msmarco_passage_*.parquet" \
  --out /data/vectors/msmarco_138m.npy --jobs 10
# 앞 1,000만 행만: --rows 10000000
# 열 이름을 지정: --vector-column emb
# 이미 만든 .npy의 표본만 다시 검사(계획을 다시 세우지 않음): --verify-only (--parquet-glob 없이 실행 가능)
```

### 7.5 합성 데이터 생성기

데이터셋 없이 변환기와 서버를 끝까지 돌리기 위한 것이다. 규격은 부록 C에 있고 요점은 **같은 `--seed`, 같은 `--dim`이면 행 i의 벡터가 항상 같다**는 것이다. 그래서 `synth`로 만든 `.npy`와 `synth-parquet`로 만든 parquet를 `convert`한 `.npy`는 **바이트 단위로 같아야 하며**, 이것이 변환기 드라이런의 합격 기준이다(§14 D5).

```bash
# 합성 .npy: 200,000행 768차원
python -m mock_inference synth --rows 200000 --dim 768 --seed 42 --out /tmp/mockinf/synth_768_200k.npy

# 합성 parquet: 파일 3개, 파일당 10,000행, row group 4,000행, laion 과 같은 스키마
python -m mock_inference synth-parquet --files 3 --rows-per-file 10000 --dim 768 --seed 42 \
    --row-group-size 4000 --schema-variant largelist32 --out-dir /tmp/mockinf/pq
# 파일 이름은 synth-00-of-03.parquet 형식. id 열은 전역 행 번호.
# --schema-variant: largelist32(기본, laion 과 같음) | list32 | largelist64
```

`--schema-variant`는 변환기의 열 자동 인식과 dtype 변환을 시험하기 위한 것이다. msmarco의 실제 스키마를 모르므로 세 가지를 모두 통과시켜 둔다.

## 8. 서빙 순서

### 8.1 상태

`.npy`와 같은 디렉터리(또는 `--state-dir`)에 두 파일이 있다. 실제 이름은 `.npy` 이름을 앞에 붙인 `<이름>.state.lock`, `<이름>.state.json`이다(예: `laion_100m.state.json`). 한 디렉터리에 벡터 파일이 여럿 있어도 상태가 섞이지 않는다. 이 문서에서는 줄여서 `state.lock`, `state.json`이라고 부른다.

- `state.lock`: 빈 파일. `fcntl.flock(LOCK_EX)`의 대상.
- `state.json`: `{"next": 1234567, "wraps": 0, "start": 0, "end": 100000000}`. 임시 파일에 쓰고 `rename`으로 바꾼다. 없으면 서버가 시작할 때 `next = start`로 만든다.

### 8.2 순차 모드(기본)와 lease

worker는 자기 구간 `[cur, lim)`을 갖는다. 요청에 n개가 필요하면 다음을 한다.

```
def take(n):
    parts = []
    while n > 0:
        if cur == lim:
            cur, lim = lease()
        k = min(n, lim - cur)
        parts.append(vecs[cur:cur + k])
        cur += k; n -= k
    return concatenate(parts)         # (n, dim) float32

def lease():
    with flock(state.lock):
        st = read(state.json)
        a = st.next
        b = min(a + CHUNK, st.end)
        if b == st.end:
            st.next = st.start; st.wraps += 1
        else:
            st.next = b
        write(state.json)
    return a, b
```

성질은 다음과 같다.

- worker 안에서는 잠금이 없다. worker는 단일 스레드 이벤트 루프이므로 `take`는 원자적이다.
- worker 사이 잠금은 CHUNK(20,000)마다 한 번이다. 10,000 RPS에 worker 10개여도 초당 잠금 1회 미만이다.
- 전체 소비 구간은 앞에서부터 채워지며, 어느 순간에도 빌렸지만 아직 안 준 벡터는 최대 `W × CHUNK`개다.
- 서버를 다시 띄우면 `state.json`의 `next`부터 이어간다. 죽기 전에 빌려 두고 못 준 구간(최대 `W × CHUNK`)은 건너뛰며, **이미 준 벡터를 다시 주는 일은 없다.** 처음부터 다시 하려면 서버를 멈추고 `python -m mock_inference reset`을 실행한다. `serve`는 더 이상 `--reset`을 받지 않고, 포트가 이미 다른 프로세스에 물려 있으면 그대로 시작을 거부하므로(§17), 떠 있는 서버를 향해 실수로 실행해도 상태부터 망가지는 일은 없다.
- `state.json`의 `start`, `end`가 서버의 `--range`와 다르면 시작을 거부한다(메시지에 두 구간과 `reset` 사용법을 안내한다). 다른 구간의 상태를 말없이 이어 쓰지 않기 위해서다. 이 확인은 `serve`의 부모 프로세스가 worker를 띄우기 전에 한다. worker 안에서만 실패하면 uvicorn이 죽은 worker를 계속 다시 띄워, 포트는 잡힌 채 응답이 없는 상태가 되기 때문이다.
- `end`에 닿으면 `start`로 돌아가고 `wraps`가 1 오른다. `/health`에 보인다.
- 요청이 구간 경계에 걸치면 `take`가 두 번 이상 lease 한다. 요청당 입력은 최대 2,048개이므로, `--chunk`가 2,048 이상이면 최대 두 번이다(그보다 작은 `--chunk`에서는 걸치는 lease 횟수가 늘어난다).
- 서버를 처음 띄운 직후 `next`는 `start`다. 첫 요청(또는 MemMachine의 검증 호출)이 오면 첫 lease로 `next`가 `start + CHUNK`가 된다. 드라이런에서 `/health`를 읽을 때 이 점을 감안한다.

### 8.3 해시 모드

`--mode hash`면 번호를 `start + (xxh64(text) mod (end - start))`로 정한다. 같은 텍스트는 항상 같은 벡터다. 상태 파일을 쓰지 않는다. 페이지 접근이 무작위가 되므로 NVMe에서만 쓴다. 10,000 RPS면 초당 4KB 무작위 읽기 1만 회이고 NVMe 한도에 한참 못 미친다.

### 8.4 여러 호스트

호스트를 둘 이상 두려면 각 호스트에 `--range START:END`로 구간을 나눈다. `state.json`은 호스트마다 따로다. 클라이언트마다 다른 mock을 가리키거나 L4 로드밸런서 뒤에 둔다.

### 8.5 차원

서버 차원은 파일에서 나오고 `/health`에 보인다. 요청 `dimensions`가 이와 다르면 400이다. 클라이언트 설정의 차원은 파일과 같아야 하고, 벡터 DB 컬렉션도 이 차원으로 새로 만들어야 한다.

## 9. 엔드포인트

모든 응답은 `Content-Type: application/json`이고 orjson으로 만든다. 인증 헤더는 읽지 않는다. 요청 본문이 JSON이 아니면 400이다.

### 9.1 `POST /v1/embeddings`

읽는 필드는 `input`, `model`, `dimensions`, `encoding_format`이다.

| `input` | 벡터 수 |
|---|---|
| 문자열 | 1 |
| 문자열 리스트 | 리스트 길이 |
| 정수 리스트(토큰 id 하나의 열) | 1 |
| 정수 리스트의 리스트 | 바깥 리스트 길이 |
| 빈 리스트, 그 외 타입 | 400 |

`dimensions`가 있고 파일 차원과 다르면 400이며 메시지는 `"dimensions X not supported; this mock serves Y-dim vectors"`다. MemMachine은 이때 파라미터 없이 다시 부르고 파일 차원 벡터를 받은 뒤 자기 설정과 달라 **크게 실패한다**(§4.1). 설정 오류를 숨기지 않기 위해 mock이 차원을 맞춰 주지 않는다.

`encoding_format`이 없거나 `"base64"`면 `embedding`은 float32 리틀엔디언 바이트를 base64로 인코딩한 문자열이고, `"float"`면 실수 리스트다. 그 외 값은 400.

```json
{
  "id": "embd-<hex 16자리>",
  "object": "list",
  "model": "<요청의 model 그대로, 없으면 \"mock-embed\">",
  "data": [{"object": "embedding", "index": 0, "embedding": "<base64>"}],
  "usage": {"prompt_tokens": <문자열이면 총 문자수÷4, 토큰이면 토큰 수>, "total_tokens": <같은 값>}
}
```

오류 본문은 openai SDK가 `BadRequestError`로 올리도록 OpenAI 형식이다.

```json
{"error": {"message": "...", "type": "invalid_request_error", "param": null, "code": null}}
```

### 9.2 `POST /v2/rerank` (별칭 `/v1/rerank`, `/rerank`)

읽는 필드는 `documents`(길이 n), `top_n`, `return_documents`, `model`이다. `query`와 문서 내용은 점수에 쓰지 않는다.

i번째 문서의 `relevance_score`는 `1 - i / n`이고 `results`는 내림차순(곧 입력 순서)이다. `top_n`이 있으면 앞에서 그만큼만 남긴다. `documents`가 비어 있으면 `results`도 비어 있다. `documents`의 원소가 문자열이 아니고 `{"text": "..."}` 객체면(Cohere v2, Jina 형식) 그대로 받아들인다. `return_documents`가 true면 `document: {"text": <원문>}`을 넣고, 아니면 넣지 않는다.

순서 보존을 택한 근거는 §4.2다. MemMachine이 넘기는 후보는 벡터 검색의 코사인 순서이므로, 순서 보존은 "리랭커가 없을 때"와 같은 결과를 HTTP 왕복만 더한 채 낸다.

```json
{
  "id": "rerank-<hex 16자리>",
  "model": "<요청의 model 그대로, 없으면 \"mock-rerank\">",
  "usage": {"total_tokens": <query와 documents 총 문자수÷4>},
  "results": [{"index": 0, "relevance_score": 1.0}, {"index": 1, "relevance_score": 0.5}]
}
```

오류 본문은 `{"message": "..."}`다.

### 9.3 `GET /v1/models`

OpenAI 클라이언트 중 시작 시 모델 목록을 확인하는 것이 있어 둔다.

```json
{"object": "list", "data": [{"id": "mock-embed", "object": "model", "owned_by": "mock"},
                            {"id": "mock-rerank", "object": "model", "owned_by": "mock"}]}
```

### 9.4 `GET /health`

`state.json`을 읽어 돌려준다(잠금 없이 읽고, rename 덕에 항상 온전한 파일이다).

```json
{"status": "ok", "dim": 768, "total": 100000000, "mode": "sequential",
 "range": [0, 100000000], "next": 1234567, "wraps": 0, "workers": 10, "chunk": 20000,
```

## 10. 동시성과 코어 할당

### 10.1 프로세스 하나로는 안 되는 이유

Python은 GIL 때문에 프로세스 하나가 코어 하나를 넘지 못한다. 임베딩 요청(입력 1개) 하나는 HTTP 파싱, JSON 파싱, 3KB 슬라이스와 base64, 직렬화, 응답 쓰기를 합쳐 `[추론]` 300에서 500µs이므로 프로세스 하나는 `[추론]` 2,000에서 3,000 RPS다. rerank(문서 80개, 문서당 1KB, 본문 약 100KB)는 JSON 파싱이 지배해 `[추론]` 700에서 1,000 RPS다. 목표 10,000 RPS에 프로세스 하나는 부족하다.

### 10.2 worker 모델

uvicorn의 `workers=W`로 프로세스 W개를 띄운다. 부모가 소켓을 만들어 자식에 물려주므로 **포트 하나**를 W개가 같이 받고 커널이 연결을 나눈다. 클라이언트는 mock 주소 하나만 안다. MemMachine 인스턴스 k개가 동시에 쏘아도 연결이 W개 worker에 흩어진다.

각 worker는 `uvloop` 이벤트 루프와 `httptools` 파서를 쓴다. 설정은 uvicorn이 앱을 import 문자열로 다시 불러오므로 **환경 변수**(`MOCKINF_VECTORS`, `MOCKINF_MODE`, `MOCKINF_RANGE`, `MOCKINF_CHUNK`, `MOCKINF_STATE_DIR`, `MOCKINF_WORKERS`, `MOCKINF_AFFINITY`)로 넘긴다. `serve.py`가 인수를 환경 변수로 옮긴 뒤 `uvicorn.run("mock_inference.app:app", workers=W, loop="uvloop", http="httptools", lifespan="off", access_log=False, backlog=4096, timeout_keep_alive=75)`를 부른다(앱이 HTTP만 다루므로 lifespan은 끈다). uvicorn은 worker를 spawn 방식으로 만들므로 macOS와 Linux에서 같은 방식이 통한다.

### 10.3 목표 RPS에서 worker 수와 코어

`--target-rps R`과 `--rps-per-worker r`(기본 1,000, 보수적)에서 `W = ceil(R / r)`이다. 필요한 코어는 `W + 2`다. 2개는 커널의 네트워크 처리와 그 밖의 프로세스 몫이다.

| `--target-rps` | W | 권장 코어 |
|---|---|---|
| 1,000 | 1 | 3 |
| 5,000 | 5 | 7 |
| 10,000 | 10 | 12 |
| 20,000 | 20 | 22 |

`--workers W`를 직접 주면 그 값을 쓴다. `--cores 0-11` 같은 목록을 주면 `serve.py`가 uvicorn을 부르기 전에 `os.sched_setaffinity(0, cores)`를 호출하고, 자식 worker가 이를 물려받는다. 코어 수가 `W + 2`보다 적으면 경고를 찍고 계속한다. **macOS에는 `sched_setaffinity`가 없으므로**(`[사실]` 개발 머신에서 `hasattr(os, "sched_setaffinity")`가 False) `--cores`는 경고만 찍고 무시하며 `/health`의 `affinity`가 `null`이 된다. 코어 고정은 사내 Linux에서만 확인할 수 있다(§16).

코어를 고정하는 이유는 같은 호스트의 다른 프로세스와 섞이지 않게 하고, 나중에 mock 자체의 CPU 사용량을 코어 단위로 읽기 위해서다.

`r`의 기본값 1,000은 §10.1 추정의 하한이다. 호스트에서 한 번 재면 정확해진다. `--workers 1`로 띄우고 §13의 검증 2 명령을 돌려 나온 RPS의 80%를 `--rps-per-worker`로 준다.

### 10.4 호스트 설정

- `ulimit -n 65536` 이상. worker마다 연결 수천 개를 받을 수 있어야 한다. macOS 기본값은 256이라 드라이런에서도 올려야 한다.
- Linux: `sysctl net.core.somaxconn=4096`. `backlog=4096`이 실제로 먹게 한다.
- 클라이언트 쪽 연결 수는 openai와 cohere 클라이언트 모두 keep-alive를 쓰므로 MemMachine worker당 수십 개다.

### 10.5 요청당 메모리

임베딩 응답은 벡터당 base64 4KB(768차원)이며 입력 2,048개면 8MB다. rerank 요청은 문서 80개에 100에서 300KB다. worker당 동시 요청 1,000개여도 수백 MB다. mmap한 벡터 페이지는 파일 캐시이지만, 상주하는 동안에는 worker RSS(Linux `RssFile`, macOS/top의 RES)에 그대로 잡힌다. 순차 모드에서는 그 worker가 소비한 행 수 × 행 크기만큼 RSS가 오르며, 이론상 파일 크기까지 갈 수 있다(laion 307GB 파일이면 worker당 RSS가 수십 GB로 보일 수 있다). 커널이 압력을 받으면 회수할 수 있는 페이지 캐시이므로 그 자체로는 누수가 아니며, 누수 여부는 익명 메모리인 `RssAnon`으로 본다. 다만 회수 가능한 페이지도 OOM 점수 계산(`get_mm_rss`)에는 포함되므로, worker RSS가 커졌다고 해서 OOM 대상에서 완전히 자유로운 것은 아니다.

## 11. MemMachine 설정

임베더는 `provider: openai` 그대로 두고 주소와 차원만 바꾼다. 리랭커는 `provider: cohere`로 바꾼다. `cohere_key`는 필수 필드라 있어야 하지만 값은 아무 문자열이어도 된다. `[사실]` `[C:packages/server/src/memmachine_server/common/configuration/reranker_conf.py:57-71]` `[C:packages/server/src/memmachine_server/common/configuration/embedder_conf.py:59-90]`

```yaml
resources:
  embedders:
    mock_embedder:
      provider: openai
      config:
        model: "mock-embed"
        api_key: "mock"
        base_url: "http://MOCK_HOST:8000/v1"   # openai 쪽은 /v1 까지
        dimensions: 768                        # .npy 차원과 같아야 한다. msmarco 면 1536
  rerankers:
    mock_reranker:
      provider: cohere
      config:
        cohere_key: "mock"
        model: "mock-rerank"
        base_url: "http://MOCK_HOST:8000"      # cohere 쪽은 호스트까지만. SDK가 /v2/rerank 를 붙인다

episodic_memory:
  long_term_memory:
    embedder: mock_embedder
    reranker: mock_reranker
retrieval_agent:
  reranker: mock_reranker
semantic_memory:
  embedding_model: mock_embedder
```

`base_url`의 `/v1` 유무가 두 프로바이더에서 다른 것이 가장 흔한 실수다. openai SDK는 `base_url + /embeddings`, cohere SDK는 `base_url + /v2/rerank`를 부른다. MemMachine 인스턴스 여러 개가 모두 같은 `MOCK_HOST:8000`을 가리키면 된다.

`checks/mm_mock_config.yml`은 위 절에 `MOCK_HOST`를 `127.0.0.1`로 둔 드라이런용 설정이다. MemMachine의 설정 파서가 없으면 거부하는 절(`logging.path`, 빈 `session_manager`와 `episode_store`, `semantic_memory.config_database`)이 더 들어 있지만 DB는 열지 않는다. `databases` 절은 필요 없다. 사내에서는 이 파일을 복사해 호스트와 차원만 바꾼다.

## 12. 다른 응용에서 쓰기

OpenAI 임베딩 API를 쓰는 어떤 클라이언트든 `base_url`을 `http://MOCK_HOST:8000/v1`로 바꾸면 된다. rerank는 Cohere v2 SDK(`base_url="http://MOCK_HOST:8000"`), vLLM용 클라이언트(`/v1/rerank` 또는 `/v2/rerank`), Jina 형식(`/v1/rerank`, `return_documents`) 모두 받는다.

```python
from openai import OpenAI
c = OpenAI(base_url="http://MOCK_HOST:8000/v1", api_key="mock")
v = c.embeddings.create(input=["a", "b"], model="mock-embed").data   # 2개, 768차원

import cohere
r = cohere.ClientV2(api_key="mock", base_url="http://MOCK_HOST:8000")
r.rerank(model="mock-rerank", query="q", documents=["a", "b", "c"]).results
```

같은 텍스트에 같은 벡터가 필요한 응용(캐시 검증, 중복 제거 시험)은 `--mode hash`로 띄운다. 여러 응용이 mock 하나를 같이 쓰면 순차 모드에서는 하나의 스트림을 나눠 쓴다.

검증 2는 두 단계로 나눠서 잰다. `oha`는 `-q`가 없으면 닫힌 루프로 동작해 클라이언트가 512개 연결을 쉬지 않고 채우므로, 이때의 지연은 대기 시간(대략 동시 연결 수 / RPS)이지 20ms 기준과 비교할 값이 아니다. 그래서 처리량(포화) 측정과 목표 RPS 확인을 분리한다.

처리량(포화) 측정 — 제한 없이 최대로 밀어 Requests/sec만 본다:

```bash
oha -z 60s -c 512 --no-tui -m POST -H 'content-type: application/json' \
    -d '{"input":["hello"],"model":"m"}' http://MOCK_HOST:8000/v1/embeddings
oha -z 60s -c 512 --no-tui -m POST -H 'content-type: application/json' \
    -D checks/rerank80.json http://MOCK_HOST:8000/v2/rerank
```

목표 RPS 확인 — `-q 10000`으로 초당 요청 수를 10,000으로 고정하고 `--latency-correction`으로 대기 시간을 보정해 실제 지연을 잰다:

```bash
oha -z 60s -c 512 -q 10000 --latency-correction --no-tui -m POST -H 'content-type: application/json' \
    -d '{"input":["hello"],"model":"m"}' http://MOCK_HOST:8000/v1/embeddings
oha -z 60s -c 512 -q 10000 --latency-correction --no-tui -m POST -H 'content-type: application/json' \
    -D checks/rerank80.json http://MOCK_HOST:8000/v2/rerank
```

결과는 `docs/msr/mock_inference/verification_<날짜>.md`에 환경(호스트, 코어, worker 수), 두 단계의 RPS, p50, p99, 오류 수를 표로 남긴다. 로컬 드라이런의 숫자는 하드웨어가 달라 참고값일 뿐이며 표에 "로컬"이라고 적는다.

## 17. 옵션과 문제 해결

| 옵션 | 기본값 | 뜻 |
|---|---|---|
| `--vectors PATH` | 필수 | `.npy` |
| `--target-rps R` | 없음 | worker 수를 `ceil(R / rps-per-worker)`로. 1 이상이어야 한다 |
| `--rps-per-worker r` | 1000 | worker 하나의 처리량 가정 |
| `--workers W` | `--target-rps`에서 계산, 둘 다 없으면 1 | worker 수를 직접 지정 |
| `--cores LIST` | 고정 안 함 | `0-11` 또는 `0,2,4`. macOS에서는 무시 |
| `--mode sequential\|hash` | sequential | §8.2, §8.3 |
| `--chunk N` | 20000 | lease 크기. 1 이상이어야 한다(0 이하면 시작 때 바로 `error: --chunk must be >= 1`로 거부한다) |
| `--range START:END` | 파일 전체 | 이 호스트가 맡을 구간 |
| `--state-dir DIR` | `.npy`와 같은 디렉터리 | `state.json`, `state.lock` |
| `--reset` | 끔 | 상태를 START부터 다시 시작한다(순차 모드만; 해시 모드에는 상태 파일이 없다) |
| `--host`, `--port` | 0.0.0.0, 8000 | |

떠 있는 서버를 향해 실수로 `serve`를 또 실행해도 상태가 망가지지 않는다: `serve`는 시작 전에 포트를 먼저 확인해 이미 다른 프로세스에 물려 있으면 그대로 거부하고 종료한다(`error: port already in use: ...`, exit 2). 서버를 띄우지 않고 상태만 처음으로 되돌리려면 `python -m mock_inference reset --vectors PATH [--state-dir DIR] [--range START:END]`를 쓴다(순차 모드만 해당). `convert --verify-only`도 마찬가지로 계획을 다시 세우지 않고 이미 만든 `.npy`의 표본만 다시 검사하므로 `--parquet-glob` 없이 실행할 수 있다.

| 증상 | 원인 | 조치 |
|---|---|---|
| MemMachine 로그 `Received embedding dimensionality 768 does not match expected dimensionality ...` | 설정 `dimensions`가 파일과 다름 | `/health`의 `dim`에 맞추고 Qdrant 컬렉션을 지운 뒤 재시작 |
| 리랭커 검증에서 404 | cohere `base_url`에 `/v1`을 붙임 | 호스트까지만 적는다 |
| 임베더에서 404 | openai `base_url`에 `/v1`을 빠뜨림 | `/v1`까지 적는다 |
| `/health`의 `wraps`가 1 이상 | 벡터를 다 씀 | 의도가 아니면 시험 규모를 다시 본다 |
| 목표 RPS에서 p99가 튐 | worker 부족 또는 코어 경합 | `--workers`를 올리거나 `--cores`로 다른 프로세스와 분리. 그래도 안 되면 클라이언트 호스트가 병목인지 `oha`를 다른 호스트에서 다시 |

## 19. 가정과 한계, 나중에 더할 것

- 부하 경로가 episodic add/search뿐이라는 것은 인터뷰 답변에 따른 가정이다. semantic memory나 retrieval_agent가 켜져 있으면 LLM 호출이 먼저 막힌다. 시험 설정에서 두 기능이 꺼져 있는지 시작 전에 확인한다.
- 순차 모드에서는 같은 텍스트를 두 번 넣으면 다른 벡터다. MemMachine에 임베딩 캐시가 없어 동작에는 문제가 없지만, "같은 내용이 가까이 검색된다"는 가정으로 결과를 해석하면 안 된다.
- 검색 질의 벡터는 아직 저장되지 않은 다음 행이다. 검색은 항상 "저장된 것 중 가장 가까운 남"을 찾는다. HNSW 탐색 비용을 실제와 크게 다르게 만들지는 않는다고 본다. `[추론]`
- mock은 벡터를 내주기만 한다. 몇 개가 실제로 소비되는지는 부하 시험이 add를 몇 건 치느냐가 정한다. add 건수는 부하 시험 계획의 항목이다.
- 프로세스당 처리량과 변환 시간은 추정이며 C3, C4에서 실측으로 바꾼다.
- 합성 벡터는 무작위 단위 벡터라 실데이터와 분포가 다르다. 드라이런은 기능과 형식만 증명하며, 검색 동작의 부하 특성은 사내 실데이터에서만 본다.

## 부록 C. 합성 데이터 규격

`synth`와 `synth-parquet`가 같은 규격을 쓰므로 둘의 결과가 바이트 단위로 같다.

- 생성기는 `numpy.random.default_rng(seed)`다. 행을 65,536개씩 블록으로 만든다. 블록 b는 `rng_b = default_rng([seed, b])`로 독립된 생성기를 쓰고 `rng_b.standard_normal((65536, dim), dtype=np.float32)`를 만든 뒤 행마다 L2 노름으로 나눈다(float32 연산). 그래서 행 i의 벡터는 `seed`, `dim`, `i`에만 의존하고 전체 행 수와 무관하다. 어떤 행 수로 만들든 앞부분이 같다.
- `synth --rows R --dim D --seed S --out X.npy`는 행 0부터 R-1을 `.npy`에 쓴다.
- `synth-parquet --files F --rows-per-file P --dim D --seed S --row-group-size G --schema-variant V --out-dir DIR`는 파일 f(0부터)에 행 `f × P`부터 `(f+1) × P - 1`을 쓴다. 파일 이름은 `synth-{f:02d}-of-{F:02d}.parquet`이고 열은 `id: int64`(전역 행 번호)와 `emb`다. `emb`의 타입은 V가 `largelist32`면 `large_list<float32>`, `list32`면 `list<float32>`, `largelist64`면 `large_list<float64>`(float32 값을 그대로 올림)다. row group은 G행마다 끊는다.
- 따라서 `convert`가 `synth-parquet`의 결과를 변환하면 `synth --rows F×P`와 같은 파일이 나와야 한다(`largelist64`는 float32로 되돌리면 정확히 같다).
- 드라이런 기본값은 `--seed 42`, `--dim 768`이다. 1536차원도 같은 규격이며 `--dim 1536`으로 만든다.
