# mock 임베더와 리랭커 서버 사용 가이드

작성일 2026-09-29. 이 문서는 **처음 보는 사람이 명령을 하나씩 복사해 붙여 넣으며 끝까지 갈 수 있도록** 쓴 것이다. 왜 만드는지와 설계 근거는 `design_2026-09-29.md`에, 이 문서의 각 단계가 실제로 통과한 기록은 `verification_2026-09-29.md`에 있다. 이 문서만으로 부족한 곳이 있으면 그 둘을 연다.

각 단계는 같은 형식이다. **왜** 한 문장, **명령** 복사해 붙여 넣기, **나와야 하는 것**, **다르면** 어떻게 할지. 앞 단계가 통과하기 전에 다음 단계로 가지 않는다.

## 0. 이 도구가 하는 일 (3분)

MemMachine은 문장을 저장할 때 **임베더**에게 벡터를 받아 Qdrant에 넣고, 검색할 때 **리랭커**에게 후보의 점수를 받아 순서를 정한다. 둘 다 GPU 모델이라 느리고, 부하 시험을 하면 이 둘이 먼저 한계에 닿아 MemMachine과 DB의 한계를 볼 수 없다.

이 도구는 그 둘을 흉내 내는 HTTP 서버다. 임베더 흉내는 문장을 보지 않고 **미리 준비한 벡터 파일에서 다음 벡터를 하나 꺼내 준다.** 리랭커 흉내는 문서를 보지 않고 **받은 순서 그대로 점수를 매겨 돌려준다.** 계산이 없으니 응답이 1밀리초 아래이고, MemMachine 쪽은 설정에서 주소 두 줄만 바꾸면 된다.

용어 다섯 개만 알면 된다.

| 용어 | 뜻 |
|---|---|
| `.npy` 파일 | 벡터를 한 줄에 하나씩 차례로 담은 파일. 서버가 여기서 벡터를 꺼낸다. 데이터셋(parquet)을 한 번 변환해서 만든다. |
| 행(row) | `.npy` 안의 벡터 하나. 0번부터 센다. |
| worker | 요청을 처리하는 프로세스. 여러 개가 같은 포트를 나눠 받는다. |
| `next` | 다음에 줄 행 번호. 서버가 `<파일이름>.state.json`에 적어 두어 재시작해도 이어진다. |
| lease | worker가 행을 20,000개씩 미리 자기 몫으로 빌리는 것. 그래서 요청 하나만 보내도 `next`가 20,000 단위로 뛴다. 정상이다. |

서버가 받는 요청은 넷이다.

| 요청 | 누가 부르나 | 하는 일 |
|---|---|---|
| `POST /v1/embeddings` | MemMachine 임베더(OpenAI 형식) | 입력 개수만큼 다음 벡터를 준다 |
| `POST /v2/rerank` (`/v1/rerank`, `/rerank`도 같음) | MemMachine 리랭커(Cohere/vLLM 형식) | 문서 순서를 지키는 점수를 준다 |
| `GET /health` | 사람, 모니터링 | 차원, 전체 행 수, `next`, worker 수 |
| `GET /v1/models` | 일부 클라이언트 | 모델 이름 두 개 |

## 1. 준비 (10분)

### 1.1 코드 받기

**왜**: 도구는 MemMachine 저장소의 `tools/mock_inference/`에 있다.

```bash
git clone -b msr_qdrant_speedkick <MemMachine 저장소 주소> ~/mm
cd ~/mm
ls tools/mock_inference
```

**나와야 하는 것**: `README.md  checks  deploy  mock_inference  pyproject.toml  tests`

**다르면**: 브랜치 이름을 확인한다. 이미 받아 둔 저장소가 있으면 `git checkout msr_qdrant_speedkick && git pull`.

### 1.2 Python 환경 만들기

**왜**: 도구는 Python 3.12 이상과 몇 개의 패키지가 필요하다. 시스템 Python을 더럽히지 않도록 전용 venv를 만든다.

```bash
python3 --version                      # 3.12 이상이어야 한다
python3 -m venv ~/mock_venv
. ~/mock_venv/bin/activate
pip install -e "tools/mock_inference[checks]"
python -m mock_inference --help
```

**나와야 하는 것**: 마지막 명령에 `{serve,convert,info,synth,synth-parquet}` 다섯 개가 보인다.

**다르면**: `python3 --version`이 3.11 이하면 3.12를 설치한다(`uv python install 3.12` 또는 배포판 패키지). `pip install` 오류는 대부분 네트워크나 프록시다.

이 문서의 이후 모든 명령은 **venv를 활성화한 상태**(`. ~/mock_venv/bin/activate`), **저장소 루트**(`cd ~/mm`), **파일 한도를 올린 상태**(`ulimit -n 65536`, 바로 아래 §1.3)에서 실행한다. 새 터미널을 열 때마다 다음 세 줄을 먼저 친다.

```bash
. ~/mock_venv/bin/activate && cd ~/mm && ulimit -n 65536
```

### 1.3 파일 한도 올리기

**왜**: 서버가 연결을 수천 개 받는다. 기본 한도(macOS 256, Linux 1024)로는 부하를 받을 때 연결이 끊긴다.

```bash
ulimit -n 65536
ulimit -n
```

**나와야 하는 것**: `65536`

**다르면**: 이 설정은 터미널마다 다시 해야 한다. 서버를 띄우는 터미널에서 했는지 확인한다. Linux에서 오류가 나면 `/etc/security/limits.conf`에 한도를 올려 두고 다시 로그인한다.

### 1.4 부하 도구 설치 (처리량을 잴 때만)

brew install oha          # macOS

## 2. 데이터 없이 한 바퀴 돌려 보기 (20분)

실제 데이터셋은 수백 GB라 받는 데 오래 걸린다. 도구에는 **가짜 벡터를 만드는 명령**이 있어서, 그것으로 서버부터 검사까지 전부 돌려 볼 수 있다. 처음 쓰는 사람은 반드시 여기부터 한다. 사내 서버에서도 실데이터를 만지기 전에 이 절을 한 번 돌린다.

작업 폴더를 하나 만든다.

```bash
mkdir -p /tmp/mockinf
```

### 2.1 가짜 벡터 파일 만들기

**왜**: 768차원 벡터 20만 개짜리 `.npy`를 만든다. 실제 laion 데이터셋과 같은 차원이다.

```bash
python -m mock_inference synth --rows 200000 --dim 768 --seed 42 --out /tmp/mockinf/synth_768_200k.npy
python -m mock_inference info /tmp/mockinf/synth_768_200k.npy
```

**나와야 하는 것**:

```
wrote /tmp/mockinf/synth_768_200k.npy: 200000 rows x 768 dims
rows:        200000
dim:         768
dtype:       <f4
data offset: 128
data bytes:  614400000
file size:   614400128  (matches)
```

**다르면**: `(MISMATCH ...)`가 나오면 디스크가 꽉 찼거나 쓰다 끊긴 것이다. 파일을 지우고 다시 만든다.

### 2.2 서버 띄우기

**왜**: 방금 만든 파일로 서버를 띄운다. worker 2개, 8000번 포트.

터미널 A(서버용):

```bash
. ~/mock_venv/bin/activate && cd ~/mm && ulimit -n 65536
python -m mock_inference serve --vectors /tmp/mockinf/synth_768_200k.npy --workers 2 --port 8000 --reset
```

**나와야 하는 것**:

```
INFO:     serving /tmp/mockinf/synth_768_200k.npy: 200000 rows x 768 dims, range 0:200000, mode sequential, workers 2, affinity None
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)
INFO:     Started parent process [...]
```

그 뒤 `Started server process` 두 줄이 나오면 준비된 것이다. 이 터미널은 그대로 둔다. 서버를 끄려면 여기서 Ctrl-C.

**다르면**: `Address already in use`면 누가 8000번을 쓰고 있다. `--port 8001`로 바꾸고 아래 명령의 포트도 같이 바꾼다. 이 경우 §2.7에서 쓸 `checks/mm_mock_config.yml`도 복사해서 두 `base_url`의 `:8000`을 같은 포트로 바꿔 두고, 그 복사본을 `--config`에 준다 — 원본 그대로 쓰면 `Connection error` / `InvalidEmbedderError`로 실패한다(§2.7 다르면, §7 참고). `covers rows ... start with --reset`이 나오면 이전에 다른 구간으로 띄웠던 상태 파일이 남은 것이다. 위 명령처럼 `--reset`을 붙인다.

### 2.3 눈으로 확인하기

터미널 B(명령용). 아래 다섯 개를 하나씩 친다.

**health**

```bash
curl -s localhost:8000/health
```

나와야 하는 것: `{"status":"ok","dim":768,"total":200000,"mode":"sequential","range":[0,200000],"next":0,"wraps":0,"workers":2,"chunk":20000,"platform":"...","affinity":null}`

**임베딩(사람이 읽을 수 있는 실수 형식)**

```bash
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' \
  -d '{"input": ["hello"], "model": "x", "encoding_format": "float"}' | head -c 200
```

나와야 하는 것: `{"id":"embd-...","object":"list","model":"x","data":[{"object":"embedding","index":0,"embedding":[0.0050893863663077354,-0.05983969196677208,...` 실수가 768개 이어진다.

**임베딩(기본 형식)**

```bash
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' \
  -d '{"input": ["hello"], "model": "x"}' | head -c 200
```

나와야 하는 것: `"embedding":"AAAA..."` 처럼 base64 문자열이 온다. MemMachine의 SDK가 기본으로 이 형식을 요청하므로 서버도 이것이 기본이다. 사람이 읽을 수 없는 것이 정상이다.

**rerank**

```bash
curl -s localhost:8000/v2/rerank -H 'content-type: application/json' \
  -d '{"model": "x", "query": "q", "documents": ["a", "b", "c"]}'
```

나와야 하는 것: `{"id":"rerank-...","model":"x","usage":{"total_tokens":1},"results":[{"index":0,"relevance_score":1.0},{"index":1,"relevance_score":0.6666666666666667},{"index":2,"relevance_score":0.33333333333333337}]}` 점수가 입력 순서대로 내려간다.

**일부러 틀린 차원**

```bash
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' \
  -d '{"input": ["hello"], "model": "x", "dimensions": 1536}'
```

나와야 하는 것: `{"error":{"message":"dimensions 1536 not supported; this mock serves 768-dim vectors",...}}` 이것은 **일부러 실패하는 것**이다. MemMachine 설정의 차원이 파일과 다르면 이렇게 크게 실패해서 설정 오류를 바로 알 수 있게 되어 있다.

**다시 health**

```bash
curl -s localhost:8000/health
```

나와야 하는 것: `"next":20000` 또는 `"next":40000`. 요청 몇 번에 2만이 뛰는 이유는 §0의 lease다. worker 하나가 빌렸으면 20000, 둘 다 빌렸으면 40000이다.

**다르면**: `curl: (7) Failed to connect`면 서버가 안 떠 있다. 터미널 A를 본다. JSON이 아니라 HTML이나 빈 응답이면 포트를 잘못 쳤다.

### 2.4 검사 스크립트 1: SDK 왕복

**왜**: curl은 형식만 본다. 이 스크립트는 MemMachine이 실제로 쓰는 것과 같은 openai, cohere SDK로 서버를 부르고, **받은 벡터가 파일의 어떤 행과 바이트 단위로 같은지** 확인한다.

```bash
python tools/mock_inference/checks/sdk_roundtrip.py --base http://127.0.0.1:8000 --vectors /tmp/mockinf/synth_768_200k.npy
```

**나와야 하는 것**: 검사 항목이 한 줄씩 `ok ...`로 찍히고 마지막 줄이 `PASS sdk_roundtrip`.

**다르면**: 첫 `FAIL` 줄을 읽는다. 대개 `--base`의 포트가 틀렸거나 `--vectors`가 서버가 띄운 파일과 다른 것이다.

### 2.5 검사 스크립트 2: worker 여러 개가 같은 벡터를 두 번 주지 않는지

**왜**: 실제 부하에서는 worker 여러 개가 동시에 요청을 받는다. 이 스크립트는 클라이언트 64개로 10만 개 벡터를 받아 **같은 행이 두 번 나오지 않는지**, 그리고 **서버를 껐다 켜도 이어지는지** 본다. 이 검사는 행이 넉넉해야 하므로 100만 행 파일을 새로 만든다.

터미널 A에서 Ctrl-C로 서버를 끈다. 터미널 B에서:

```bash
python -m mock_inference synth --rows 1000000 --dim 768 --seed 42 --out /tmp/mockinf/synth_768_1m.npy
```

터미널 A에서 worker 8개로 다시 띄운다:

```bash
python -m mock_inference serve --vectors /tmp/mockinf/synth_768_1m.npy --workers 8 --port 8000 --reset
```

터미널 B에서 첫 실행:

```bash
python tools/mock_inference/checks/stream_check.py --base http://127.0.0.1:8000 --vectors /tmp/mockinf/synth_768_1m.npy \
  --clients 64 --total 100000 --out /tmp/mockinf/run1.json
```

**나와야 하는 것**: `ok   no row served twice: 0 duplicates`, `ok   missing rows <= workers x chunk: ... <= 160000`, 마지막 줄 `PASS stream_check`.

이제 **재시작 검사**. 터미널 A에서 Ctrl-C로 서버를 끄고, **`--reset` 없이** 같은 명령으로 다시 띄운다:

```bash
python -m mock_inference serve --vectors /tmp/mockinf/synth_768_1m.npy --workers 8 --port 8000
```

터미널 B에서 두 번째 실행:

```bash
python tools/mock_inference/checks/stream_check.py --base http://127.0.0.1:8000 --vectors /tmp/mockinf/synth_768_1m.npy \
  --clients 64 --total 100000 --out /tmp/mockinf/run2.json --after /tmp/mockinf/run1.json
```

**나와야 하는 것**: 마지막 줄 `PASS stream_check (restart)`. 두 번째 실행의 모든 행 번호가 첫 실행의 최대값보다 크다는 뜻이다. 즉 껐다 켜도 이미 준 벡터를 다시 주지 않는다.

**다르면**: `duplicates`가 0이 아니면 스트림이 한 바퀴 돈 것이다(`wraps`가 1 이상) — 파일을 더 크게 만들거나 `--total`을 줄인다. 재시작 검사가 `FAIL restart: all rows beyond previous run: 0 > <N>`으로 실패하면 재시작할 때 `--reset`을 붙인 것이다 — 빼고 다시 띄운다. `missing rows <= workers x chunk`가 실패하면(표시되는 workers/chunk는 stream_check의 옵션이 아니라 `/health`에서 읽은 값이다) 이 검사가 도는 동안 다른 터미널에서 같은 mock에 curl/oha 등으로 따로 요청을 보내고 있지 않은지 본다.

### 2.6 변환기 검사: parquet에서 .npy로

**왜**: 실데이터는 parquet 파일 여러 개로 배포된다. 변환기가 그것을 `.npy` 하나로 잇는다. 가짜 parquet를 만들어 변환하고, 같은 시드로 직접 만든 `.npy`와 **바이트 단위로 같은지** 본다. 같으면 변환기가 정확한 것이다.

```bash
python -m mock_inference synth-parquet --files 3 --rows-per-file 10000 --dim 768 --seed 42 \
  --row-group-size 4000 --schema-variant largelist32 --out-dir /tmp/mockinf/pq
python -m mock_inference convert --parquet-glob "/tmp/mockinf/pq/*.parquet" --out /tmp/mockinf/conv_768.npy --jobs 3
python -m mock_inference synth --rows 30000 --dim 768 --seed 42 --out /tmp/mockinf/ref_768_30k.npy
cmp /tmp/mockinf/conv_768.npy /tmp/mockinf/ref_768_30k.npy && echo SAME
```

**나와야 하는 것**: 변환 로그에 `plan: 3 files, 30000 rows x 768 dims, column 'emb' (float32)`, `write synth-0N-of-03.parquet rows=10000` 세 줄, `verify PASS 100/100 rows (seed 12345), norm min 1.000000 max 1.000000 mean 1.000000`. 마지막에 `SAME`.

**이어서 하기 검사**: 변환은 중간에 끊겨도 같은 명령을 다시 치면 끝난 파일은 건너뛴다. 확인해 본다.

```bash
rm /tmp/mockinf/conv_768.npy.done/synth-01-of-03.parquet.ok
python -m mock_inference convert --parquet-glob "/tmp/mockinf/pq/*.parquet" --out /tmp/mockinf/conv_768.npy --jobs 3
```

**나와야 하는 것**: `skip synth-00-of-03.parquet`, `skip synth-02-of-03.parquet`, `write synth-01-of-03.parquet rows=10000`, verify PASS.

**다르면**: `cmp`가 `differ`를 찍으면 변환기 문제이니 진행을 멈추고 알린다. `... differs from the new plan ... delete ... to start over`가 나오면 이전 변환의 계획이 남은 것이다. 메시지에 적힌 세 가지(`.npy`, `.done/`, `.plan.json`)를 지우고 다시 한다.

### 2.7 MemMachine 설정 파서로 확인 (DB 없이)

**왜**: MemMachine이 실제로 mock을 임베더와 리랭커로 받아들이는지, **DB를 띄우지 않고** MemMachine의 설정 파서와 리소스 매니저만으로 확인한다. MemMachine이 설치된 Python(`memmachine_server`를 import 할 수 있는 venv)이 필요하다.

터미널 A에서 서버를 worker 1개로 다시 띄운다(2.5에서 행을 많이 써서 새로 시작한다):

```bash
python -m mock_inference serve --vectors /tmp/mockinf/synth_768_200k.npy --workers 1 --port 8000 --reset
```

터미널 B에서, **MemMachine venv의 python**으로:

```bash
<MemMachine 설치 경로>/.venv/bin/python tools/mock_inference/checks/mm_resource_check.py \
  --config tools/mock_inference/checks/mm_mock_config.yml --health http://127.0.0.1:8000/health
```

**나와야 하는 것**: 로그에 다음 네 줄이 있고 마지막 줄이 `PASS mm_resource_check`.

```
Validating embedder 'mock_embedder' is working.
Embedder 'mock_embedder' is valid.
Validating reranker mock_reranker is working.
Reranker mock_reranker is working.
```

맨 앞에 `Decomposer import FAILED ... No module named 'spacy'` 같은 traceback이 찍힐 수 있다. MemMachine을 import 하면 항상 나오는 것이라 무시한다. 실행 폴더에 `mm_resource_check.log`가 생기는데 지워도 된다.

**다르면**: `No module named 'memmachine_server'`면 MemMachine venv가 아닌 python으로 실행한 것이다. `404`가 나오면 `mm_mock_config.yml`의 `base_url`을 본다. 임베더는 `/v1`까지, 리랭커는 호스트까지만이다(§4.1). `Connection error` / `InvalidEmbedderError`가 나오면 `base_url`의 포트가 서버 포트와 다른 것이다(§2.2 다르면, §7).

### 2.8 hash 모드와 --range 확인

**왜**: §4.3과 §8이 코어가 모자라면 `--range`로 mock 호스트를 나누라고 하고, `--mode hash`는 같은 문장에 항상 같은 벡터를 주고 싶을 때 쓴다. 여기서 미리 확인해 둔다.

터미널 A에서 hash 모드로 띄운다:

```bash
python -m mock_inference serve --vectors /tmp/mockinf/synth_768_200k.npy --workers 1 --port 8000 --mode hash
```

터미널 B에서 같은 문장을 두 번, 다른 문장을 한 번 보낸다:

```bash
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' -d '{"input": ["hello world"], "model": "x"}'
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' -d '{"input": ["hello world"], "model": "x"}'
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' -d '{"input": ["different text"], "model": "x"}'
```

**나와야 하는 것**: 첫 두 응답의 `embedding` 값(base64)이 완전히 같고, 세 번째는 다르다. `id` 필드는 매번 무작위라 비교 대상이 아니다. `curl -s localhost:8000/health`에는 `next`, `wraps`가 없다 — hash 모드는 상태 파일을 쓰지 않는다.

터미널 A에서 Ctrl-C로 끈다.

이어서 `--range`(mock 호스트 여러 대에 행 구간을 나눠 줄 때 쓴다, §8):

```bash
python -m mock_inference serve --vectors /tmp/mockinf/synth_768_200k.npy --workers 1 --port 8000 --range 100000:200000 --reset
curl -s localhost:8000/health
```

**나와야 하는 것**: `"range":[100000,200000]`, `"next":100000` — 0이 아니라 구간의 시작부터다. 임베딩 요청을 하나 보내면:

```bash
curl -s localhost:8000/v1/embeddings -H 'content-type: application/json' -d '{"input": ["hello"], "model": "x"}' > /dev/null
curl -s localhost:8000/health
```

`"next":120000`으로 뛴다.

**다르면**: `next`가 0에서 시작하면 `--range`를 안 붙이고 띄운 것이다.

터미널 A에서 Ctrl-C로 끈다.

여기까지 전부 통과했으면 도구가 정상이고, 사용법도 익힌 것이다.

## 3. 사내 서버에서 실데이터 준비 (변환 1시간 안팎)

이 절부터는 **별도의 mock 호스트**(MemMachine이나 DB와 다른 서버)에서 한다. mock의 CPU와 디스크 읽기가 측정 대상에 섞이지 않게 하기 위해서다.

이 문서에서 `MOCK_HOST`는 이 mock 호스트의 IP 또는 호스트 이름이다(예: `10.0.0.5`, 스킴이나 포트 없이). 이후 모든 절에서 그대로 쓴다.

### 3.1 사전 점검

**왜**: 변환은 디스크를 많이 쓰고, 서버는 코어를 많이 쓴다. 모자라면 중간에 멈춘다.

```bash
nproc
lscpu -e=CPU,CORE,SOCKET,NODE
df -h /data
python3 --version
ulimit -n
sysctl net.core.somaxconn
```

**나와야 하는 것**: 코어 12개 이상. `lscpu -e`의 `CORE`(물리 코어 번호)가 하나의 `NODE`(NUMA 노드) 안에서 서로 다른 것을 12개 이상 찾을 수 있어야 한다 — SMT/하이퍼스레딩이 켜져 있으면 같은 `CORE`를 공유하는 논리 CPU 두 개는 물리 코어 하나를 나눠 쓸 뿐이라 `--cores`에는 서로 다른 `CORE`만 고른다(§4.2). `/data`(데이터셋과 `.npy`를 둘 곳)에 필요한 여유 공간은 원본 parquet가 이미 그 호스트에 있다는 전제로 **`.npy` 크기만큼**이다: laion이면 **307GB 이상**, msmarco면 **850GB 이상**. `df -h`는 TB가 아니라 TiB 단위다(1TiB ≈ 1.1TB). Python 3.12 이상. `ulimit -n` 65536. `somaxconn` 4096.

**다르면**: 디스크가 모자라면 §3.3의 `--rows`로 앞부분만 변환한다. `somaxconn`은 `sudo sysctl -w net.core.somaxconn=4096`.

그리고 §1과 §2.1–§2.6, §2.8을 이 호스트에서 한 번 더 한다(§2.7은 MemMachine이 설치된 python이 있어야 하므로 여기서는 건너뛰고, MemMachine 호스트에서 §5.2로 대신한다). Linux라서 §2.2의 `affinity`가 `null`이 아니라 코어 목록으로 나올 수 있다는 것만 다르다.

### 3.2 데이터셋 위치 확인

**왜**: 변환기는 파일 이름 패턴(글롭)으로 parquet를 찾는다. 이름을 정확히 알아야 한다.

```bash
ls /data/laion_large_100m/ | head -3
ls /data/laion_large_100m/train-*-of-100.parquet | wc -l
ls /data/msmarco_v2_138M_parquet/ | head -3
ls /data/msmarco_v2_138M_parquet/msmarco_passage_*.parquet | wc -l
```

**나와야 하는 것**: laion은 `train-00-of-100.parquet`부터 100개, msmarco는 `msmarco_passage_00-0.parquet` 같은 이름으로 277개. 경로는 실제 받아 둔 위치로 바꾼다.

참고로 laion은 파일 하나에 1,000,000행이 들어 있고 100개가 1억 행을 이룬다. 파일이 여러 개인 것은 배포 편의상 나눈 것일 뿐이며, Qdrant의 shard와는 아무 관계가 없다.

### 3.3 변환 실행

**왜**: parquet 100개를 `.npy` 하나(307GB)로 만든다. 코어 수만큼 병렬로 돌고, 디스크 쓰기 속도가 상한이다. `--jobs`는 기본으로 `nproc`이지만, 작업 하나가 65,536행 배치를 메모리에 올려 768차원 기준 약 1.2GB의 RAM을 쓴다(1536차원이거나 소스가 float64면 2.5GB 근처까지 오른다). 디스크 쓰기가 병목이라 코어가 아주 많은 호스트에서도 8-12개면 충분하다 — RAM이 `--jobs × 1.2GB`보다 적으면 그만큼 `--jobs`를 줄인다.

```bash
mkdir -p /data/vectors
python -m mock_inference convert \
  --parquet-glob "/data/laion_large_100m/train-*-of-100.parquet" \
  --out /data/vectors/laion_100m.npy --jobs $(nproc)
```

**나와야 하는 것**: 첫 줄 `plan: 100 files, 100000000 rows x 768 dims, column 'emb' (float32)`. 이어서 `write train-NN-of-100.parquet rows=1000000`이 100줄(순서는 뒤섞여도 된다). 마지막에 `done: 100000000 rows x 768 dims, wrote 100000000 rows in NNNs (NNN MB/s)`와 `verify PASS 100/100 rows (seed 12345), norm min ... mean ...`(laion은 1.0 근처).

**걸리는 시간**: 디스크에 달렸다. NVMe면 10분에서 30분. 다른 터미널에서 `iostat -xm 5`를 띄워 두면 쓰기 MB/s가 보인다. 소요 시간과 MB/s를 `verification_<날짜>.md`에 적어 둔다.

**중간에 끊기면**: 같은 명령을 다시 친다. 끝난 파일은 `skip`, 안 끝난 것만 `write`한다.

**다르면**: `no list<float> column`이 나오면 벡터 열을 자동으로 못 찾은 것이다. 그 parquet 파일 하나의 스키마를 직접 본다.

```bash
python -c "import pyarrow.parquet as pq; print(pq.ParquetFile('<파일 하나>').schema_arrow)"
```

`list<float>`나 `fixed_size_list<float>` 열이 보이면(둘 다 받아들인다) 그 이름으로 `--vector-column <이름>`을 준다. 벡터로 보이는 열이 없으면 진행을 멈추고 알린다. `list length != dim`이 나오면 먼저 `plan:` 줄에 찍힌 자동 감지 column 이름이 실제 임베딩 열이 맞는지 본다 — 아니면 `--vector-column`으로 바로잡는다. 열이 맞는데도 나면 그제서야 그 파일이 깨진 것이니 다시 받는다. `verify FAIL`이면 진행을 멈추고 알린다.

msmarco는 파일 이름과 출력 이름만 다르다.

```bash
python -m mock_inference convert \
  --parquet-glob "/data/msmarco_v2_138M_parquet/msmarco_passage_*.parquet" \
  --out /data/vectors/msmarco_138m.npy --jobs $(nproc)
```

`plan:` 줄에 `138364198 rows x 1536 dims`가 나와야 한다. 디스크가 모자라면 `--rows 10000000`(앞 1,000만 행만)을 붙인다.

### 3.4 변환 결과 확인

```bash
python -m mock_inference info /data/vectors/laion_100m.npy
```

**나와야 하는 것**: `rows: 100000000`, `dim: 768`, `dtype: <f4`, `file size: ... (matches)`.

## 4. 서버 띄우고 처리량 재기 (30분)

### 4.1 worker 하나로 처리량 재기

**왜**: worker 수를 정하려면 이 호스트에서 worker 하나가 몇 RPS를 내는지 알아야 한다. 재는 것은 다른 호스트(클라이언트 호스트)에서 `oha`로 한다. 같은 호스트에서 재면 클라이언트가 CPU를 나눠 써서 낮게 나온다.

mock 호스트, 터미널 A:

```bash
. ~/mock_venv/bin/activate && cd ~/mm && ulimit -n 65536
python -m mock_inference serve --vectors /data/vectors/laion_100m.npy --workers 1 --reset
```

클라이언트 호스트(이 호스트에는 mock의 체크아웃이 없다 — rerank 부하에 쓸 파일만 가져온다):

```bash
ulimit -n 65536
scp MOCK_HOST:~/mm/tools/mock_inference/checks/rerank80.json .
oha -z 60s -c 512 --no-tui -m POST -H 'content-type: application/json' \
    -d '{"input":["hello"],"model":"m"}' http://MOCK_HOST:8000/v1/embeddings
oha -z 60s -c 512 --no-tui -m POST -H 'content-type: application/json' \
    -D ./rerank80.json http://MOCK_HOST:8000/v2/rerank
```

**나와야 하는 것**: `oha` 요약에서 `Requests/sec`, `Status code distribution`(전부 200), `Error distribution`(없음). 두 번의 `Requests/sec` 중 **작은 값**을 적어 둔다. 이것이 worker 하나의 처리량이다. 참고로 개발 머신(M4)에서는 임베딩 약 42,000, rerank 약 17,000이 나왔다. `-c 512`로 한도까지 밀어붙인 것이라 여기 찍히는 `99.00% in`(p99)은 서버가 포화 상태에서 쌓인 대기 시간일 뿐이다 — §4.3의 20ms 기준과는 비교하지 않는다. 지금은 `Requests/sec`만 적어 둔다.

**다르면**: `Error distribution`에 `connection refused`나 `too many open files`가 있으면 클라이언트 호스트의 `ulimit -n`을 올린다. `oha`가 `Error: No such file or directory`로 바로 끝나면(요청이 하나도 나가지 않은 것이다) `-D` 경로가 틀린 것이다 — 위 `scp`로 `rerank80.json`을 받았는지 본다.

### 4.2 목표 처리량으로 띄우기

**왜**: 목표 10,000 RPS를 위해 worker 몇 개가 필요한지 도구가 계산하게 한다. `--rps-per-worker`에는 §4.1에서 적어 둔 값의 **80%**를 준다(여유). `--cores`는 worker 수 + 2개를 준다(2개는 커널 네트워크 몫).

예를 들어 §4.1에서 작은 값이 15,000이었다면 `--rps-per-worker 12000`이고, worker는 `ceil(10000 / 12000) = 1`개다. 그래도 최소 2개는 두는 것이 안전하므로 이 경우 `--workers 2 --cores 0-3`으로 직접 준다. 값이 1,000 근처라면 worker 10개, `--cores 0-11`이다.

mock 호스트, 터미널 A. SSH가 끊겨도 서버가 죽지 않도록 tmux 안에서 띄운다(§6에서 systemd로 옮기기 전까지).

```bash
tmux new -s mock
. ~/mock_venv/bin/activate && cd ~/mm && ulimit -n 65536
python -m mock_inference serve --vectors /data/vectors/laion_100m.npy \
  --target-rps 10000 --rps-per-worker <값> --cores 0-<worker수+1> --reset
```

`Ctrl-b d`로 tmux에서 빠져나와도 서버는 계속 돈다(`tmux attach -t mock`으로 다시 들어간다).

터미널 B:

```bash
curl -s localhost:8000/health
```

**나와야 하는 것**: 터미널 A 시작 로그에 `workers N, affinity [0, 1, ...]`. 터미널 B `/health`의 `workers`가 N이고 `affinity`가 코어 목록이다.

**다르면**: `affinity null`에 경고가 찍히면 Linux가 아니다. `pinned to N cores for M workers; use at least workers + 2`가 뜨면 `--cores`를 더 준다.

### 4.3 목표 처리량 확인

§4.1과 달리 여기서는 `oha`에 `-q`로 초당 요청 수를 10,000으로 고정한다 — §4.1처럼 closed-loop로 한도까지 밀면 p99가 `c/RPS`로 커져서 20ms 기준을 항상 넘기게 된다. 클라이언트 호스트에서:

```bash
oha -z 60s -c 512 -q 10000 --latency-correction --no-tui -m POST -H 'content-type: application/json' \
    -d '{"input":["hello"],"model":"m"}' http://MOCK_HOST:8000/v1/embeddings
oha -z 60s -c 512 -q 10000 --latency-correction --no-tui -m POST -H 'content-type: application/json' \
    -D ./rerank80.json http://MOCK_HOST:8000/v2/rerank
```

**합격**: 두 경로 모두 실제로 낸 `Requests/sec`가 10,000 근처(`-q`로 요청한 값에 가깝게 나왔는지)이고 p99가 20ms 이하이며 오류 0. 결과를 `docs/msr/mock_inference/verification_<날짜>.md`에 표로 남긴다(호스트, 코어, worker 수, RPS, p50, p99, 오류 수).

**다르면**: worker를 늘려 다시 띄운다. 코어를 다 써도 모자라면 호스트를 하나 더 두고 `--range 0:50000000`과 `--range 50000000:100000000`으로 구간을 나눈다(설계 §8.4, §2.8에서 --range를 확인했다).

## 5. MemMachine 연결 (30분)

### 5.1 설정 바꾸기

**왜**: MemMachine은 코드 수정 없이 설정만으로 임베더와 리랭커의 주소를 바꿀 수 있다. 원본 설정은 남겨 두고 복사본을 고친다.

```bash
cp <MemMachine 설정>.yml <MemMachine 설정>.mock.yml
```

복사본에서 `resources:` 아래 `embedders:`와 `rerankers:`를 다음으로 바꾸거나 추가한다. `MOCK_HOST`는 mock 호스트 주소다.

```yaml
resources:
  embedders:
    mock_embedder:
      provider: openai
      config:
        model: "mock-embed"
        api_key: "mock"
        base_url: "http://MOCK_HOST:8000/v1"   # 임베더는 /v1 까지 적는다
        dimensions: 768                        # laion 768, msmarco 1536. /health 의 dim 과 같아야 한다
  rerankers:
    mock_reranker:
      provider: cohere
      config:
        cohere_key: "mock"
        model: "mock-rerank"
        base_url: "http://MOCK_HOST:8000"      # 리랭커는 호스트까지만 적는다
```

그리고 이 둘을 가리키는 곳을 바꾼다.

```yaml
episodic_memory:
  long_term_memory:
    embedder: mock_embedder
    reranker: mock_reranker
```

이 시험은 에피소드 add/search만 잰다. `retrieval_agent`와 `semantic_memory`는 **끈 채로 둔다**. 아래 두 줄은 그 둘을 일부러 같이 켜서 시험하고 싶을 때만 추가한다 — 둘 다 켜면 요청마다 실제 LLM 호출이 섞여 mock만으로 부하를 재는 의미가 없어진다.

```yaml
# retrieval_agent와 semantic_memory를 일부러 같이 켜 둔 경우만 추가한다
retrieval_agent:
  reranker: mock_reranker
semantic_memory:
  embedding_model: mock_embedder
```

**MemMachine이 이 파일을 읽게 하기**: MemMachine은 `MEMORY_CONFIG` 환경변수가 가리키는 파일을 읽는다.

```bash
MEMORY_CONFIG=<복사본>.mock.yml memmachine-server
```

docker-compose로 띄운다면 복사본을 컨테이너에 마운트하고 `MEMORY_CONFIG`를 그 경로로 설정한다.

**확인**:

```bash
diff <원본>.yml <복사본>.mock.yml
```

바뀐 곳이 위 항목뿐이어야 한다. `retrieval_agent.llm_model`이 비어 있고 `semantic_memory.enabled`가 `true`가 아닌지도 본다 — 둘 다 그렇다면 자동으로 꺼진 채 시작하고, MemMachine 시작 로그에 `Semantic memory is disabled; skipping semantic service startup.`가 찍힌다.

**가장 흔한 실수**: 임베더 `base_url`에 `/v1`을 빠뜨리거나, 리랭커 `base_url`에 `/v1`을 붙이는 것. 임베더 SDK는 주소 뒤에 `/embeddings`를, 리랭커 SDK는 주소 뒤에 `/v2/rerank`를 스스로 붙인다.

### 5.2 DB 없이 먼저 확인

**왜**: §2.7과 같은 검사를 사내 설정으로 한다(§2.7은 mock 호스트가 아니라 지금 이 MemMachine 호스트에서, mock 호스트를 가리키는 §5.1 복사본으로 하는 것뿐이다). MemMachine을 띄우기 전에 설정 오류를 잡는다. `--health`를 주면 이 검사 전후로 mock의 `next`가 1~worker 수 만큼의 lease로만 늘었는지도 본다 — 델타 기반이라 이미 부하를 받은 mock이어도 새로 띄우거나 리셋할 필요가 없다.

```bash
<MemMachine 설치 경로>/.venv/bin/python tools/mock_inference/checks/mm_resource_check.py \
  --config <복사본>.mock.yml --health http://MOCK_HOST:8000/health
```

**나와야 하는 것**: §2.7과 같은 네 줄과 `PASS mm_resource_check`.

**다르면**: `does not match expected dimensionality`면 `dimensions`가 파일과 다르다. `404`면 `base_url`의 `/v1`을 본다. `Connection refused`면 mock 호스트 방화벽에서 8000번 포트를 연다. `FAIL health: next advanced by ... leases`면 검사 도중 다른 트래픽이 같은 mock을 함께 쓴 것이다 — mock을 잠깐 이 검사 전용으로 두고 다시 돌린다.

### 5.3 MemMachine 하나 띄워서 단건 확인

**왜**: 실제로 add 한 건이 Qdrant에 들어가고, 그 벡터가 `.npy`의 행과 같은지 본다. 이것이 되면 연결이 끝난 것이다.

이 브랜치의 MemMachine은 시작할 때 임베더/리랭커를 **검증 없이** 데워 둔다. semantic memory를 켜지 않았다면(§5.1) `Validating embedder ...` 줄은 아예 안 나온다 — 대신 로그에서 `Starting server with N worker(s)`를 찾는다. 검증 호출이 없으므로 **첫 add는 0번 행**이다(예전 문서의 "0번은 검증이 먼저 쓴다"는 이 브랜치에는 맞지 않는다). worker가 여러 개면 새 연결이 어느 worker로 갈지 알 수 없어 행 번호를 예측할 수 없으므로, 이 단건 확인만은 mock을 `--workers 1`로 잠깐 다시 띄운다.

1. Qdrant 컬렉션을 비운다(아래 5번 참고). 차원이 다른 컬렉션이 남아 있으면 MemMachine이 저장에 실패한다.
2. mock을 worker 1개, `--reset`으로 다시 띄운다(확인이 끝나면 §4.2 명령으로 되돌린다).

```bash
python -m mock_inference serve --vectors /data/vectors/laion_100m.npy --workers 1 --reset
```

3. MemMachine 인스턴스 하나를 복사본 설정으로 시작한다. 시작 로그에 `Starting server with 1 worker`가 있어야 하고, semantic memory를 껐다면 `Semantic memory is disabled; skipping semantic service startup.`도 있어야 한다.
4. MemMachine API로 메모리 하나를 add 하고, 검색을 한 번 한다. `AddMemoriesSpec`/`SearchMemoriesSpec`(`packages/server/src/memmachine_server/server/api_v2/router.py`의 `/memories`, `/memories/search`)은 `org_id`/`project_id`가 `"universal"`로 기본값을 가지므로 아래가 최소 body다.

```bash
curl -s -X POST http://<MemMachine 주소>/api/v2/memories \
  -H 'content-type: application/json' \
  -d '{"messages": [{"content": "hello mock"}]}'
curl -s -X POST http://<MemMachine 주소>/api/v2/memories/search \
  -H 'content-type: application/json' \
  -d '{"query": "hello"}'
```

5. Qdrant에 들어간 벡터를 `.npy` 행으로 되돌려 본다. 먼저 데이터 컬렉션 이름을 찾는다 — MemMachine이 만드는 이름은 `<namespace>__<64자리 hex>`다(`__registry`로 끝나는 것은 컬렉션 이름→설정 등록부이니 건너뛴다).

```bash
curl -s http://<Qdrant 주소>:6333/collections
python tools/mock_inference/checks/qdrant_row_check.py --qdrant http://<Qdrant 주소>:6333 \
  --collection <위에서 찾은 이름> --vectors /data/vectors/laion_100m.npy --rows 0:100000
```

**나와야 하는 것**: `<point id> -> row 0` 처럼 행 번호가 찍히고, 마지막 줄에 코사인 유사도 기준 `PASS`/`FAIL`이 찍힌다(Qdrant는 Cosine 컬렉션에 넣을 때 벡터를 정규화하므로 바이트 비교가 아니라 코사인으로 맞춘다). worker 1개, `--reset` 직후라면 add는 0번, search는 1번 행을 썼다. worker가 여러 개면 요청이 어느 worker로 갔는지에 따라 0, 20000, 40000 ... 중 하나다(`--reset` 직후 각 worker의 lease 시작 행). `curl -s http://MOCK_HOST:8000/health`의 `next`는 그 worker 수만큼의 20000 단위다.

확인이 끝나면 mock을 §4.2에서 정한 worker 수로 다시 띄운다.

**다르면**: `not in window`면 `--rows`를 넓힌다(`0:1000000`). 컬렉션이 비어 있으면 MemMachine 로그에서 임베더 오류를 찾는다. 데이터 컬렉션만 지우고 다시 시험했는데 이전 벡터가 남아 있는 것처럼 보이면, `__registry` 컬렉션에 그 컬렉션 이름의 등록 정보가 남아 MemMachine이 존재하지 않는 컬렉션의 핸들을 그대로 돌려준 것이다(`qdrant_vector_store.py`의 `open_or_create_collection`, 750번째 줄 근처). 완전히 새로 시작하려면 데이터 컬렉션과 `__registry` 컬렉션을 함께 지우거나, 확실하지 않으면 Qdrant를 새 볼륨으로 띄운다.

### 5.4 여러 인스턴스 연결과 짧은 부하

**왜**: 모든 MemMachine 인스턴스가 mock 하나를 가리켜도 되는지, 그리고 부하 중 mock이 여유가 있는지 본다.

1. 모든 MemMachine 인스턴스를 복사본 설정으로 바꾼다. 주소는 전부 같은 `MOCK_HOST:8000`이다.
2. 부하 시험을 5분만 돌린다.
3. mock 호스트에서 관찰한다:

```bash
mpstat -P ALL 5                       # worker 코어 사용률
watch -n 10 'curl -s localhost:8000/health'   # next 가 얼마나 빨리 느는지
```

**나와야 하는 것**: MemMachine 로그에 임베더와 리랭커 오류 0. `next`는 요청마다 오르는 게 아니라 worker가 20,000개 단위 lease를 새로 받을 때만 뛴다 — 관찰 구간이 짧으면 계단식으로 보인다. 몇 분간 누적한 증가량은 그동안의 add 에피소드 수와 search 수를 더한 것과 비슷해야 한다. worker 코어 사용률이 80% 미만. worker의 RSS(`ps`, `top`)는 서비스한 행 수만큼 계속 오른다 — mmap한 파일 페이지가 파일 캐시로 상주하기 때문이며 누수가 아니다(Linux는 `RssFile`). 진짜 누수인지는 `RssAnon`(`/proc/<pid>/status`)이 같이 오르는지로 본다.

**다르면**: 코어 사용률이 80%를 넘으면 `--target-rps`를 올려(worker를 늘려) 다시 띄운다. mock이 멈췄는데(응답이 하나도 안 오는데) MemMachine 쪽에서 오류 없이 지연만 계속 늘어난다면 주의한다 — 임베딩은 최대 30분(openai SDK가 600초씩 3번 재시도), rerank는 최대 5분까지 오류 없이 걸려 있을 수 있다. `curl -s localhost:8000/health`로 mock이 실제로 응답하는지 먼저 확인한다.

## 6. 서비스로 등록하기 (15분)

**왜**: 터미널을 닫아도, 재부팅해도 mock이 살아 있게 systemd에 등록한다.

지금까지 손으로 띄운 서버(§4.2 터미널 A, tmux 안)를 먼저 끈다. 켜 둔 채로 systemd를 올리면 systemd 쪽은 포트 충돌로 계속 재시작에 실패하는데 `curl`은 손으로 띄운 쪽이 계속 응답해서, 서비스가 정상인 것처럼 잘못 보인다.

```bash
tmux attach -t mock    # §4.2에서 그 이름으로 띄웠다면
# Ctrl-C로 서버를 끄고 tmux 세션도 종료한다
ss -ltnp | grep :8000   # 아무 줄도 없어야 한다
```

```bash
sudo cp tools/mock_inference/deploy/mock-inference.service /etc/systemd/system/
sudo vi /etc/systemd/system/mock-inference.service
```

고칠 곳은 다섯이다.

- `User=`: venv, `~/mm` 체크아웃(에디터블 설치라 소스도 여기서 읽는다), `--vectors`가 가리키는 디렉터리(상태 파일을 그 옆에 쓴다)를 모두 읽고 쓸 수 있는 계정이어야 한다. 가장 간단한 선택은 **§3–§5를 진행한 계정 그대로 쓰는 것**이다. 별도 서비스 계정(예: `mock`)을 쓰려면 `sudo chown -R <그 계정> /data/vectors`를 먼저 하고, venv와 `~/mm`도 그 계정이 읽을 수 있게 한다.
- `ExecStart=`의 python 경로(`~/mock_venv/bin/python`의 절대 경로).
- `--vectors` 경로.
- `--target-rps`와 `--rps-per-worker`와 `--cores`(§4.2에서 정한 값). 유닛에 이미 `--rps-per-worker` 줄이 있으니 값만 채운다.

**`--reset`은 절대 넣지 않는다.** 넣으면 재시작할 때마다 처음 행부터 다시 주어 Qdrant에 같은 벡터가 쌓인다.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now mock-inference
systemctl status mock-inference
curl -s localhost:8000/health
journalctl -u mock-inference -n 20
```

**나와야 하는 것**: `active (running)`, `/health` 정상, 로그에 `serving ...` 줄. `curl`이 실제로 이 서비스에서 응답하는지는 `systemctl show -p MainPID mock-inference`의 PID가 `ss -ltnp | grep :8000`이 보여주는 PID와 같은지로 확인한다.

**status가 `activating (auto-restart)`에서 안 넘어가면** 설정 오류다(포트 충돌, 잘못된 경로, 권한 문제 등). `Restart=always`가 계속 재시도하므로 `enable --now`는 성공을 반환해도 서비스는 뜬 적이 없다. `journalctl -u mock-inference -n 50`으로 실제 오류를 읽는다.

**새 시험을 시작할 때**(Qdrant를 비우고 처음부터 넣을 때):

```bash
sudo systemctl stop mock-inference
sudo -u <User=에 적은 계정> <venv 절대경로>/bin/python -m mock_inference reset --vectors /data/vectors/laion_100m.npy
sudo systemctl start mock-inference
curl -s localhost:8000/health        # next 가 0
```

`.state.lock`은 절대 지우지 않는다 — worker들이 그 파일로 서로 잠그고 있어서, 지운 순간 두 worker가 동시에 상태를 고쳐 쓸 수 있다.

## 7. 문제가 생겼을 때

| 증상 | 원인 | 조치 |
|---|---|---|
| MemMachine 로그 `Received embedding dimensionality 768 does not match expected dimensionality 1536` | 설정 `dimensions`가 파일 차원과 다름 | `/health`의 `dim`에 맞추고 Qdrant 컬렉션을 지운 뒤 다시 |
| MemMachine 시작 시 리랭커 검증에서 404 | 리랭커 `base_url`에 `/v1`을 붙임 | 호스트까지만 적는다 |
| MemMachine 시작 시 임베더에서 404 | 임베더 `base_url`에 `/v1`을 빠뜨림 | `/v1`까지 적는다 |
| MemMachine 로그 `Connection error` / `InvalidEmbedderError` | `mm_mock_config.yml`(또는 §5.1 복사본)의 `base_url` 포트가 실제 서버 포트와 다름 | 포트를 바꿨으면 그 설정 파일의 포트도 같이 바꾼다(§2.2 다르면) |
| `serve`가 `covers rows ... start with --reset`으로 안 뜸 | 다른 `--range`로 띄웠던 상태 파일이 남음 | 이어서 쓸 게 아니면 `--reset` |
| `serve`가 `PermissionError`로 죽음(특히 `.state.lock`) | 상태 파일을 쓸 디렉터리에 쓰기 권한이 없음 | 디렉터리 권한을 고치거나 `--state-dir`로 쓸 수 있는 곳을 준다 |
| `/health`나 임베딩 요청이 전부 `503` | 서비스가 도는 중에 `.state.json`이 지워지거나 깨짐 | `systemctl stop` → `reset`(§6) → `systemctl start`로 되살린다. `.state.lock`은 지우지 않는다 |
| `systemctl status`가 `activating (auto-restart)`에서 안 넘어감 | 설정 오류(포트 충돌, 잘못된 경로/권한 등)로 매번 재시작만 함 | `journalctl -u mock-inference`로 실제 오류를 읽는다 |
| `/health`의 `wraps`가 1 이상 | 벡터를 다 써서 처음으로 돌아감 | 시험 규모를 다시 본다. 같은 벡터가 다시 들어가고 있다는 뜻 |
| `oha`에 `too many open files` | 클라이언트 쪽 `ulimit -n` | 65536으로 올린다 |
| 목표 RPS에서 p99가 튐 | worker 부족 또는 다른 프로세스와 코어 경합 | worker를 늘리거나 `--cores`로 분리. 클라이언트 호스트가 병목일 수도 있으니 다른 호스트에서 다시 잰다 |
| 변환이 `list length != dim` | 자동 감지된 열이 임베딩 열이 아니거나(먼저 의심), 그 다음이 파일 손상 | `plan:` 줄의 column 이름을 본다 → 아니면 `--vector-column`. 열이 맞는데도 나면 그 파일만 다시 받는다 |
| 변환이 `differs from the new plan` | 글롭이나 `--rows`가 지난번과 다름 | 메시지의 세 파일을 지우고 처음부터, 또는 지난번과 같은 인수로 |
| `mm_resource_check`가 `No module named 'memmachine_server'` | 일반 python으로 실행 | MemMachine venv의 python으로 |
| `mm_resource_check`가 `FAIL health: next advanced by ... leases` | 검사 도중 다른 트래픽이 같은 mock을 함께 씀 | mock을 잠깐 이 검사 전용으로 두고 다시 돌린다 |
| `next`가 요청 하나에 20,000씩 뜀 | lease 단위 | 정상 |

## 8. 자주 하는 질문

**같은 문장을 두 번 넣으면 같은 벡터가 나오나?** 아니다. 기본(순차) 모드는 문장을 보지 않고 다음 행을 준다. 같은 벡터가 필요하면 `--mode hash`로 띄운다. 이때는 상태 파일도 쓰지 않는다.

**검색 결과가 이상한데?** 정상이다. 벡터가 문장과 무관하므로 검색 품질은 의미가 없다. 이 도구는 부하를 재는 것이지 정확도를 재는 것이 아니다.

**벡터를 다 쓰면?** 처음으로 돌아가고 `/health`의 `wraps`가 오른다. laion은 1억 개라 add 100 RPS에 에피소드 10개씩이면 28시간 걸린다.

**mock 호스트를 두 개 두려면?** 각 호스트에 `--range`로 구간을 나눠 준다. 예: A는 `--range 0:50000000`, B는 `--range 50000000:100000000`. MemMachine 인스턴스마다 다른 주소를 가리키게 한다.

**다른 데이터셋을 쓰려면?** parquet에 `list<float>` 열이 있으면 §3.3의 변환 명령 그대로다. 차원이 다르면 MemMachine `dimensions`와 Qdrant 컬렉션도 그 차원으로 바꾼다.

**MemMachine 말고 다른 프로그램에서도 쓸 수 있나?** OpenAI 임베딩 API를 쓰는 프로그램은 `base_url`을 `http://MOCK_HOST:8000/v1`로, Cohere나 vLLM rerank를 쓰는 프로그램은 `http://MOCK_HOST:8000`으로 바꾸면 된다.
