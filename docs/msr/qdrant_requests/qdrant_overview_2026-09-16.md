# 다중 사용자를 어떻게 나눌 것인가 — 저장소 부하로 본 두 가지 선택

- 작성일: 2026-09-16
- 대상 독자: 코드를 직접 보지 않는 분
- 기준 코드: upstream `speedkick` 최신 커밋 `a8322a7`
- 근거: 실제 서버를 띄워 저장소로 나간 요청을 전수 기록한 결과와 코드 정밀 검토
- 기술 세부가 필요하면 같은 폴더의 `qdrant_report_2026-09-16.md`

---

# 요약

1. 사용자를 나누는 방법은 두 가지다. **사용자마다 별도의 방을 주는 방식(세션 분리)**과 **한 방을 같이 쓰되 이름표로 구분하는 방식(이름표 분리)**이다.
2. 두 방식은 저장소를 부르는 횟수와 위험 지점이 완전히 다르다. 세션 분리는 **사용자 수에 비례하는 고정비**가 들고, 이름표 분리는 **모든 검색에 이름표 조건을 빠뜨리면 안 되는 부담**이 생긴다.
3. **현재 평가 코드는 둘 중 어느 쪽도 아니다.** 한 방을 같이 쓰면서 이름표 조건을 걸지 않는다. 그래서 사용자를 늘려도 두 방식의 차이가 측정되지 않는다.
4. 평소 요청 1건은 저장소 질의 1회다. 이 숫자를 키우는 것은 검색 옵션이 아니라 **준비 상태**다.
5. 의심했던 서버 내부 잠금은 병목이 아니었다. 실측 결과 저장소 왕복보다 세 자릿수 작다.

# 1부. 용어 세 개

은행 창구에 비유한다.

| 용어 | 비유 | 실제 의미 |
|---|---|---|
| **세션** | 고객의 **계좌** | 기억을 담는 칸. 고객사와 프로젝트 조합으로 하나씩 만들어진다 |
| **인스턴스** | 창구 직원의 **업무 세팅** | 그 계좌를 다루려고 서버가 메모리에 올려둔 준비물 |
| **캐시** | 책상 위 **세팅 100칸** | 자주 쓰는 준비물만 올려둔다 |

계좌는 영구히 남지만 업무 세팅은 수시로 치워진다.

## 인스턴스 안에는 무엇이 있나

가장 오해가 많은 부분이다. 인스턴스는 **기억을 담는 상자가 아니라 기억을 꺼내러 갈 때 쓰는 도구 세트**다.

| 들어 있는 것 (도구) | 없는 것 (항상 저장소에서 가져옴) |
|---|---|
| 이 세션이 저장소의 어느 칸인지 가리키는 주소 | 기억 본문 |
| 데이터베이스 연결 통로 | 기억을 숫자로 바꾼 값 |
| 쪼개고 변환하는 방식 설정 | 검색 결과 |

업무 세팅에 있는 것은 **금고 몇 번 칸인지 적은 메모와 열쇠**다. 돈은 언제나 금고 안에 있다. 그래서 한 세션에 기억이 수백만 건 쌓여도 인스턴스 크기는 거의 변하지 않는다.

**인스턴스가 있어도 검색은 반드시 저장소에 한 번 간다.** 인스턴스가 아껴 주는 것은 검색이 아니라 검색 앞의 준비 동작이다.

# 2부. 사용자를 나누는 두 가지 방법

## 2.1 방식 A — 세션 분리 (사용자마다 방 하나)

사용자 한 명에게 계좌 하나를 준다. 저장소 안에서 물리적으로 칸이 나뉜다.

**장점**
- 검색할 때 **자기 방만 보는 것이 기본 동작**이다. 개발자가 조건을 빠뜨려도 남의 기억이 나오지 않는다
- 사용자 한 명을 지우려면 그 방을 통째로 지우면 된다

**비용**
- 사용자를 처음 받을 때마다 **방을 만드는 등록 절차 17회**가 든다. 500명이면 8,500회
- 서버 책상이 100칸뿐이라 **동시에 활동하는 사용자가 100명을 넘으면** 세팅을 치웠다 다시 차리는 일이 반복된다
- 데이터베이스 쪽에도 사용자 수만큼 칸이 생긴다

## 2.2 방식 B — 이름표 분리 (한 방을 같이 쓰기)

모든 사용자가 한 계좌를 쓰고, 기억마다 누구 것인지 이름표를 붙인다. 검색할 때 이름표 조건을 걸어 걸러낸다.

**장점**
- 방을 만드는 등록 절차가 **전체를 통틀어 한 번**이다
- 서버 책상도 한 칸만 쓴다. **100칸 한도 문제가 아예 생기지 않는다**

**비용과 위험**
- **검색할 때마다 이름표 조건을 반드시 붙여야 한다.** 빠뜨리면 남의 기억이 그대로 나온다. 서버가 강제하지 않으므로 앞단에서 반드시 붙여야 한다
- 이름표를 "말한 사람"으로만 걸면 **상대방(AI)의 답변이 빠진다.** "내가 말한 것 또는 나에게 한 말" 두 조건을 함께 걸어야 대화가 온전해진다
- 사용자 한 명만 지우려면 그 사람의 기억을 하나씩 찾아 지워야 한다

## 2.3 한눈에 비교

| | A. 세션 분리 | B. 이름표 분리 |
|---|---|---|
| 저장소 안의 칸 | 사용자마다 1개 | 전체 1개 |
| 신규 등록 비용 | 사용자 수 × 17회 | 전체 1회 |
| 서버 책상 100칸 | **100명 넘으면 문제** | 문제 없음 |
| 격리 방식 | **구조적** (기본 동작) | **정책적** (조건을 붙여야) |
| 조건을 빠뜨리면 | 아무 일 없음 | **남의 기억 노출** |
| 사용자 1명 삭제 | 방 하나 삭제 | 기억을 하나씩 삭제 |
| AI 답변까지 찾기 | 자동으로 포함 | 조건을 두 개 걸어야 포함 |

**둘 중 하나가 정답인 것은 아니다.** 사용자 수가 적고 격리가 중요하면 A, 사용자 수가 많고 운영 비용이 중요하면 B가 맞는다. 다만 **어느 쪽을 쓸지 먼저 정해야 부하 시험 설계가 나온다.** 두 방식은 서로 다른 병목을 드러내기 때문이다.

- A를 고르면 **칸이 늘어날 때 저장소가 어떻게 되는가**를 본다
- B를 고르면 **한 칸이 커질 때 이름표 검색이 어떻게 되는가**를 본다

# 3부. 현재 평가 코드는 어느 쪽인가

**둘 다 아니다.** 정확히는 B의 형태인데 B의 핵심인 이름표 조건이 빠져 있다.

| 항목 | 현재 상태 |
|---|---|
| 방 나누기 | 하지 않는다. 모든 사용자가 기본 방 하나를 쓴다 |
| 이름표 붙이기 | **한다.** 대화의 화자 이름이 그대로 이름표가 된다 |
| 검색할 때 이름표 조건 | **걸지 않는다** |
| 상대방 표시 | 붙이지 않는다 (코드에 주석 처리되어 있다) |

그 결과 두 가지가 동시에 일어난다.

1. **검색하면 다른 사용자의 기억까지 후보에 들어간다.** 대화별로 정확도를 보는 평가라면 결과에 영향을 줄 수 있다
2. **사용자를 1명에서 500명까지 늘려도 서버 입장에서는 방이 계속 하나다.** 방식 A의 비용도, 방식 B의 필터 비용도 드러나지 않는다

**계획된 다중 사용자 실험을 하려면 평가 도구를 먼저 고쳐야 한다.** 어느 방식을 시험할지 정하고, A면 사용자마다 다른 방을 쓰도록, B면 검색에 이름표 조건을 붙이도록 바꿔야 한다.

# 4부. 요청 1건이 저장소를 몇 번 부르나

방식과 무관하게 공통으로 적용되는 부분이다.

## 4.1 세 가지 상황

| 상황 | 무슨 뜻인가 | 준비 질의 | 본래 일 | 합계 |
|---|---|---|---|---|
| **바로 처리** | 업무 세팅이 책상에 있다 | 0 | 1 | **1회** |
| **재준비** | 계좌는 있는데 세팅만 치워졌다 | 1 | 1 | **2회** |
| **신규 등록** | 계좌 자체가 없다 | 17 | 1 | **18회** |

**재준비**가 되는 경우는 셋이다. 서버를 재시작했을 때, 그 세션을 10분 넘게 안 썼을 때, 한 서버가 맡은 세션이 100개를 넘었을 때다. 같은 사용자라도 반복해서 겪는다.

**신규 등록**은 그 방을 생애 처음 쓸 때 한 번이다. 등록 17회 중 11회는 검색용 색인을 붙이는 작업이다.

## 4.2 검색 옵션은 횟수를 바꾸지 않는다

찾을 개수, 조건, 앞뒤 문맥, 점수 기준을 어떻게 바꿔도 저장소 질의는 1회다. 앞뒤 문맥은 다른 데이터베이스에서 가져오고, 점수 기준은 결과를 받은 뒤 걸러낸다.

## 4.3 기억을 저장할 때 갈라지는 것은 다른 쪽이다

저장 요청에 메시지를 많이 담으면 저장소 질의는 계속 1회지만, **기억을 숫자로 바꾸는 외부 호출이 여러 번으로 갈라진다.** 한 번에 보낼 수 있는 양에 상한이 있기 때문이다. 게다가 이 호출은 실패해도 재시도하지 않는다.

저장이 느려졌을 때 원인이 저장소가 아니라 이쪽일 수 있다는 뜻이다.

# 5부. 서버(worker)를 늘리면

MemMachine 서버 한 대는 내부적으로 **worker라는 작업 프로세스 여러 개**로 돌릴 수 있고, 앞의 로드밸런서가 요청을 나눠 준다.

**캐시가 worker마다 따로 있다.** 서로의 캐시를 모른다. 그래서 같은 사용자의 세션이 여러 worker에 중복으로 올라가고, 그 사용자를 처음 받는 worker마다 재준비가 한 번씩 발생한다. 특정 사용자를 늘 같은 worker로 보내는 설정은 없다.

신규 등록 17회는 늘지 않는다. 저장소에 실제로 방을 만드는 작업이라 어느 worker든 한 번 만들면 끝이다.

**기본값은 worker 1개**이므로 이 문제는 2개 이상으로 올렸을 때만 생긴다.

# 6부. 다중 사용자 평가에서 예상되는 문제

각 주장을 반대로 반박해 보는 검증까지 거친 결과다.

| 조건 | 결과 | 어느 방식에서 |
|---|---|---|
| 평가 도구가 방을 나누지 않음 | **실험 자체가 성립하지 않는다** | 공통 |
| 검색에 이름표 조건이 없음 | 다른 사용자 기억이 결과에 섞인다 | B |
| 동시에 처리 중인 방이 100개 초과 | 책상이 100칸을 넘겨 커진다. 무한히 커지지는 않는다 | A |
| 활성 사용자 100명 초과, 일부는 쉬는 중 | 쉬는 세션이 밀려나 재준비가 반복된다. **응답 시간이 흔들린다** | A |
| 10분 이상 쉬었다 재요청 | 세션당 재준비 1회 | A |
| worker를 2개 이상으로 | 캐시가 나뉘어 적중률이 떨어진다 | A |
| 요청 진행 중에 그 프로젝트를 삭제 | 진행 중 작업이 실패하거나, 삭제 실패 후에도 계속 동작하는 불일치가 생긴다 | 공통 |

## 병목이 아닌 것

서버 내부의 캐시 잠금이 전체를 줄 세우는 병목일 것이라는 의심이 있었으나 **실측 결과 병목이 아니었다.** 요청당 수 마이크로초로, 저장소 왕복(밀리초)보다 세 자릿수 작다. 부하 시험에서 느려진다면 재준비 반복, 데이터베이스 연결 수, 저장소 자체를 먼저 봐야 한다.

## 측정 수단이 없다

캐시가 몇 번 적중했고 몇 번 밀려났는지 볼 수 있는 지표가 없다. 부하 시험 전에 추가하는 것을 권한다.

# 7부. speedkick에 관련 수정이 있었나

**없다.** 캐시 파일 변경은 타입 표기 정리 4줄뿐이고 동작은 그대로다. 용량 100과 유휴 10분을 바꾸거나 설정으로 뺀 변경도, 한계를 설명하는 주석도 없다.

관련 작업이 아예 없었던 것은 아니다. **9개월 전(2026년 1월)** 잠금 구조를 개선한 작업이 있었고 그 뒤로는 손대지 않았다. speedkick의 최근 작업은 모두 저장소 계층에 집중돼 있다.

# 8부. 권고

우선순위 순이다.

1. **A와 B 중 어느 방식을 시험할지 먼저 정한다.** 이것이 정해져야 나머지가 따라온다
2. **평가 도구를 그 방식에 맞게 고친다.** A면 사용자마다 다른 방을, B면 검색에 이름표 조건을 붙인다
3. **B를 고른다면 조건을 서버 앞단에서 강제한다.** 개발자가 빠뜨릴 수 있는 구조로 두지 않는다
4. **캐시 적중과 축출 지표를 추가한다**
5. **책상 100칸과 10분을 설정으로 조정할 수 있게 한다.** A 방식의 경계를 옮겨가며 측정하려면 필요하다
6. **요청 진행 중 삭제가 겹치는 문제를 고친다.** 사용자에게 실패로 보이는 유일한 항목이다
