# MemMachine과 Qdrant — 요청 동작과 다중 사용자 분리 방식

- 작성일: 2026-09-16
- 기준 코드: upstream `speedkick` `a8322a7` (2026-09-14). 캐시 관련 파일은 작업 브랜치 `msr_multiuser`와 동일하다
- 검증: Qdrant 1.17.0과 PostgreSQL 16 컨테이너에 실제 요청을 흘려 HTTP 계층에서 전수 기록. 코드 리뷰는 각 주장을 반박하는 검증 단계를 거쳤다

# 0부. 이 문서의 범위

**이 문서가 세는 것은 Qdrant 요청뿐이다.** PostgreSQL 호출은 이 문서의 모든 숫자에서 제외했다.

MemMachine은 요청 하나를 처리하면서 Qdrant와 PostgreSQL을 함께 쓴다. 예를 들어 검색 한 건은 Qdrant에 1회, PostgreSQL에 여러 번 간다. 두 저장소를 한 표에 섞으면 어느 쪽이 병목인지 알 수 없으므로, 이 문서는 Qdrant만 집계하고 PostgreSQL이 관여하는 지점은 "이 집계 밖"이라고 표시한다. PostgreSQL 호출까지 세려면 별도 측정이 필요하다.

임베딩 API 호출은 저장소가 아니지만 같은 요청 경로에서 직렬로 일어나므로 9부에서 따로 다룬다.

---

# 1부. 결론

1. **평상시 요청 1건은 Qdrant 질의 1회다.** 이 수를 키우는 것은 검색 옵션이 아니라 준비 상태다. 바로 처리 1회, 재준비 2회, 신규 등록 18회다.
2. **사용자 분리 방식은 두 가지이고 비용 구조가 다르다.** 세션 분리(A)는 사용자 수에 비례하는 고정비를 내고 구조적 격리를 얻는다. `producer_id` 분리(B)는 고정비가 없는 대신 모든 검색에 필터를 붙여야 하고 격리가 정책에 의존한다.
3. **현재 평가 코드는 A도 B도 아니다.** org/project를 보내지 않아 세션이 `universal/universal` 하나로 수렴하고, 검색에 필터를 넘기지 않는다.
4. **인스턴스 캐시의 잠금은 병목이 아니다.** 요청당 마이크로초 단위다. 다만 용량 100과 유휴 600초는 조정 수단이 없다.
5. **speedkick에 캐시 관련 수정이나 설명은 없다.**

# 2부. 이 문서에서 쓰는 말

앞선 판에서 설명 없이 쓴 용어를 여기 모았다.

## 2.1 세션과 세션 키

**세션**은 기억을 담는 칸이다. 세션 키는 `org_id/project_id` 형태의 문자열이고, 서버가 요청의 두 값을 이어 붙여 만든다(`server/api_v2/service.py:44-45`).

클라이언트가 두 값을 보내지 않아도 세션 키는 만들어진다. API 스펙에 기본값 `"universal"`이 박혀 있어서 서버가 그 값을 채운다(`packages/common/.../api/spec.py:29, 167`). 즉 **전달하지 않으면 세션 키를 못 만드는 것이 아니라, 모두가 같은 기본 세션 키를 쓰게 된다.**

세션 키는 다시 **파티션 키**로 바뀐다. 규칙(소문자·숫자·밑줄, 32바이트 이하)에 맞으면 그대로 쓰고, 아니면 `sha256[:32]`로 줄인다(`episodic_memory/long_term_memory/service_locator.py:158-182`). `/`가 들어가므로 실제로는 항상 해시가 된다. 이 값이 Qdrant payload의 `sys-partition_key`에 저장된다.

## 2.2 인스턴스와 그 안의 네 가지

**인스턴스**는 한 세션을 다루기 위해 서버 메모리에 올려둔 객체다. 기억은 들어 있지 않고 도구만 들어 있다. "인스턴스 확보"는 이 도구 묶음을 손에 넣는 동작이다.

| 도구 | 실제로 무엇인가 | 왜 필요한가 |
|---|---|---|
| **컬렉션 핸들** | Qdrant 클라이언트 참조, 대상 컬렉션 이름, 이 세션의 파티션 키, 컬렉션 설정을 담은 객체 (`QdrantVectorStoreCollection`) | 요청을 보낼 주소와 이 세션을 가리키는 값이 여기 있다. 없으면 registry를 조회해 컬렉션 이름과 설정을 다시 알아내야 한다 |
| **파티션 핸들** | PostgreSQL 세그먼트 저장소에서 이 세션 몫을 가리키는 객체. 핵심은 `incarnation` UUID다 (3.2 참조) | 원문 조각과 앞뒤 문맥을 읽고 쓸 때 이 값으로 자기 행만 고른다 |
| **임베더** | 임베딩 모델 이름, 차원 수, API 클라이언트를 가진 객체 | 저장할 때와 검색할 때 텍스트를 벡터로 바꾼다. 이름별로 프로세스에서 공유된다 |
| **분할기와 파생기** | 긴 글을 어떻게 자를지(분할기), 자른 조각에서 임베딩할 텍스트를 어떻게 만들지(파생기) 정하는 설정 객체 | 기본값은 자르지 않는 passthrough와 조각 전체를 그대로 쓰는 whole_text다 |

네 가지 모두 **설정과 연결 정보**이고 기억 데이터가 아니다. 그래서 한 세션에 기억이 아무리 쌓여도 인스턴스 크기는 거의 변하지 않는다.

## 2.3 캐시와 세 가지 상태

인스턴스는 **캐시**에 보관된다. 프로세스(uvicorn worker)당 하나이고 100칸이다.

| 상태 | 정확한 뜻 | Qdrant 질의 |
|---|---|---|
| **바로 처리** | 인스턴스가 캐시에 있다 (캐시 적중) | 본래 일 1회 |
| **재준비** | **캐시에 없다(캐시 미스).** 다만 세션은 Qdrant registry에 등록돼 있다 | 확인 1회 + 본래 일 1회 = 2회 |
| **신규 등록** | 캐시에도 없고 Qdrant registry에도 없다 | 생성 17회 + 본래 일 1회 = 18회 |

**재준비는 캐시 미스를 가리키는 말이 맞다.** 캐시 미스가 나면 registry를 조회해 컬렉션 설정을 다시 읽고 인스턴스를 새로 만든다. 이때 추가되는 Qdrant 질의가 registry 조회 1회다.

캐시 미스가 나는 경우는 셋이다. worker를 재시작했을 때, 그 세션을 600초 넘게 쓰지 않았을 때, 100칸이 찬 상태에서 유휴 인스턴스로 밀려났을 때다. 세 번째에는 조건이 붙는다. 100칸이 전부 사용 중이면 밀어낼 대상이 없어 미스가 나지 않고 캐시가 그대로 넘친다.

## 2.4 축출 규칙

**축출**은 캐시에서 인스턴스를 빼내는 것이다. 규칙은 두 가지뿐이고, 공통 전제가 하나 있다.

- **전제: 지금 사용 중인 인스턴스는 절대 빼지 않는다.** 각 인스턴스에는 "지금 몇 개의 요청이 쓰고 있는지" 세는 숫자가 붙어 있고, 이 숫자가 0인 것만 축출 대상이다.
- **규칙 1 (자리 부족).** 새 인스턴스를 넣어야 하는데 100칸이 찼으면, 가장 오래 안 쓴 것부터 순서대로 빼서 자리를 만든다.
- **규칙 2 (오래 방치).** 2초마다 도는 청소 작업이 마지막 사용 후 600초를 넘긴 것을 뺀다.

여기서 나오는 성질 하나. **100칸이 전부 사용 중이면 아무것도 빼지 못한 채 새 인스턴스를 그냥 넣는다.** 그래서 캐시가 일시적으로 100칸을 넘을 수 있다. 무한히 늘지는 않고, 상한은 "그 순간 동시에 사용 중인 서로 다른 세션 수"다. 요청이 끝나면 다음 삽입 때 100으로 돌아온다.

축출된 인스턴스는 곧바로 닫히지 않고 정리 대기열에 들어가며, 별도 작업이 나중에 닫는다.

## 2.5 그 밖의 용어

| 용어 | 뜻 |
|---|---|
| **카디널리티** | 어떤 필터 조건에 맞는 포인트가 **몇 개나 되는지**를 뜻한다. Qdrant는 검색 전에 이 수를 추정해 탐색 방법을 고른다. 조건에 맞는 것이 적으면(낮은 카디널리티) 그것만 하나씩 비교하는 편이 빠르고, 많으면 그래프를 타는 편이 빠르다 |
| **헬퍼** | 평가 코드에 있는 REST 클라이언트 래퍼 파일을 가리킨다(`evaluation/utils/memmachine_helper_restapiv2.py`). 평가 스크립트가 직접 HTTP를 만들지 않고 이 파일의 함수를 부른다. MemMachine 서버 코드가 아니라 평가 쪽 코드다 |
| **incarnation** | PostgreSQL 세그먼트 저장소에서 파티션 하나를 가리키는 UUID다 (3.2 참조) |
| **파생(derivative)** | 세그먼트에서 실제로 임베딩할 텍스트를 만든 단위. Qdrant 포인트 1개가 파생 1개에 대응한다 |

# 3부. 저장소 구조

## 3.1 Qdrant

컬렉션은 두 개뿐이고, 세션이 늘어도 컬렉션은 늘지 않는다.

| 컬렉션 | 이름 | 역할 |
|---|---|---|
| registry | `long_term_memory__registry` | 세션 하나당 포인트 1개. 벡터는 1차원 더미이고 payload에 이름·차원 수·인덱스 스키마가 들어간다. 포인트 id가 파티션 키의 uuid5라서 이름만 알면 id를 계산해 바로 조회한다 |
| native | `long_term_memory__<sha256(설정)>` | 실제 벡터. 이름이 설정 해시라서 같은 설정을 쓰는 **모든 세션이 이 하나를 공유한다** |

세션이 늘 때 실제로 늘어나는 것은 registry 포인트 1개와 native 컬렉션 안의 `sys-partition_key` 값 하나다. 이 필드에는 `is_tenant=true` keyword 인덱스가 걸린다(`common/vector_store/qdrant_vector_store.py:649-704`).

포인트 하나에는 벡터와 payload만 들어가고 본문 텍스트는 저장하지 않는다. payload 키는 `sys-partition_key`, `_timestamp`, `_episode_uid`, `_session_key`, `_producer_id`, `_producer_role`, `_produced_for_id`, `_sequence_num`, `_episode_type`, `_content_type`, `_created_at`, 그리고 사용자 metadata다.

## 3.2 PostgreSQL 세그먼트 저장소 — "파티션"이 무엇인가

이 문서의 요청 집계에는 들어가지 않지만, 두 방식을 비교하려면 구조를 알아야 한다.

**테이블이 파티션마다 생기는 것이 아니다.** 테이블은 넷뿐이고 모든 세션이 공유한다(`episodic_memory/event_memory/segment_store/sqlalchemy_segment_store.py:143-236`).

| 테이블 | 역할 |
|---|---|
| `segment_store_pt` | 파티션 등록부. `partition_key` → `incarnation`(UUID) 매핑을 가진다 |
| `segment_store_sg` | 세그먼트 본문. 기본키 앞자리가 `incarnation`이다 |
| `segment_store_dv_ln` | 세그먼트와 파생의 연결 |
| `segment_store_gc` | 삭제 대기 목록 |

즉 **"PostgreSQL 세그먼트 파티션"은 별도 테이블이 아니라 공유 테이블 안의 논리 구획**이다. 파티션 키 하나에 `incarnation` UUID가 하나 발급되고, 그 세션의 모든 행이 이 값으로 묶인다. 세션을 삭제하면 incarnation을 폐기하고 `segment_store_gc`에 넣어 나중에 실제 행을 회수한다. 그래서 방식 A에서 사용자가 늘어도 테이블 수는 그대로이고, 늘어나는 것은 등록부 행 하나와 그 세션의 데이터 행이다.

# 4부. Qdrant 요청 여섯 가지 — 각각 무엇을 하는가

실제로 나가는 REST 요청은 여섯 종류뿐이다.

## 4.1 `GET /collections` — 연결 확인

프로세스가 시작할 때 Qdrant에 닿는지 확인한다. 컬렉션 목록을 받지만 내용은 쓰지 않는다. 프로세스당 1회다(`common/resource_manager/database_manager.py:647`).

이와 별개로, 클라이언트 라이브러리가 생성될 때 별도 스레드가 `GET /`로 서버 버전을 읽어 호환성을 확인한다. qdrant-client 1.19.0은 서버 1.17.0에 대해 경고를 낸다.

## 4.2 `POST /collections/long_term_memory__registry/points` — 세션이 있는지 확인

**언제**: 인스턴스를 새로 만들 때(캐시 미스), 세션을 만들 때, 세션을 지울 때.

**무엇을 보내나**: 조회할 포인트 id 하나. id는 파티션 키로 계산한 uuid5이므로 검색이 아니라 직접 지정이다.

```
POST /collections/long_term_memory__registry/points
  {"ids": ["<uuid5(네임스페이스, 파티션 키)>"], "with_payload": true}
```

**무엇이 돌아오나**: 있으면 payload(컬렉션 이름 계산에 쓰는 차원 수와 인덱스 스키마), 없으면 빈 결과. 컬렉션 자체가 없으면 404다.

**왜 필요한가**: 이 세션이 어느 native 컬렉션에 속하는지, 그 컬렉션이 어떤 설정으로 만들어졌는지 알아야 컬렉션 핸들을 만들 수 있다. **재준비에서 추가되는 1회가 바로 이 요청이다.**

## 4.3 `PUT /collections/{이름}` — 컬렉션 생성

**언제**: 신규 등록 때만. registry 컬렉션과 native 컬렉션 각 1회씩, 합쳐 2회.

**무엇을 보내나**: 벡터 차원 수와 거리 방식, HNSW 설정.

```
PUT /collections/long_term_memory__<hash>
  {"vectors": {"size": 1536, "distance": "Cosine"},
   "hnsw_config": {"m": 0, "payload_m": 16}}
```

**무엇이 돌아오나**: 성공이면 200, 이미 있으면 409. 코드는 409를 "이미 있음"으로 처리하고 넘어간다.

`m: 0`은 전역 그래프를 만들지 말라는 뜻이고, `payload_m: 16`은 payload 값별 하위 그래프를 만들라는 뜻이다. 7.3에서 다시 설명한다.

## 4.4 `PUT /collections/{이름}/index?wait=true` — payload 인덱스 생성

**언제**: 신규 등록 때 11회. 인덱스가 이미 있어도 매번 나간다.

**무엇을 보내나**: 필드 이름과 인덱스 종류.

```
PUT /collections/long_term_memory__<hash>/index?wait=true
  {"field_name": "sys-partition_key",
   "field_schema": {"type": "keyword", "is_tenant": true}}
```

11개는 `sys-partition_key`, `_timestamp`, 그리고 시스템 필드 9개다.

**왜 11회나 매번 보내나**: 낭비가 아니라 결함 수정이다. 예전에는 컬렉션 생성과 인덱스 생성을 한 덩어리로 묶어 처리했는데, 컬렉션이 이미 있으면 첫 호출에서 예외가 나면서 **인덱스가 하나도 만들어지지 않았다.** 이를 고치면서 둘을 분리하고 인덱스를 개별로 보내도록 바꿨다(커밋 `a2a1754`).

## 4.5 `PUT /collections/{이름}/points?wait=true` — 저장

**언제**: 저장 요청 1건당 1회. 요청에 메시지가 몇 개든 1회다.

**무엇을 보내나**: 포인트 목록. 각 포인트는 id(파생 uuid), 벡터, payload다.

```
PUT /collections/long_term_memory__<hash>/points?wait=true
  {"points": [{"id": "...", "vector": [0.01, ...],
               "payload": {"sys-partition_key": "bd36…", "_producer_id": "userA", ...}}, ...]}
```

**`wait=true`의 뜻**: Qdrant가 포인트를 세그먼트에 반영할 때까지 응답을 미룬다. 다만 HNSW 그래프 구축까지 기다리는 것은 아니다. 그래프는 나중에 최적화 작업이 만든다.

**실패하면**: 포인트 목록을 반으로 나눠 다시 보낸다. 1개까지 줄여도 실패하면 예외를 올린다.

## 4.6 `POST /collections/{이름}/points/query/batch` — 검색

**언제**: 검색 요청 1건당 1회.

**무엇을 보내나**: 검색 벡터 1개, 가져올 개수, 필터.

```
POST /collections/long_term_memory__<hash>/points/query/batch
  {"searches": [{"query": [0.02, ...], "limit": 80,
                 "with_payload": false, "with_vector": false,
                 "filter": {"must": [{"key": "sys-partition_key",
                                      "match": {"value": "bd36…"}}]}}]}
```

- `limit`은 요청한 개수(top_k)의 4배다. 한 에피소드가 여러 조각으로 나뉘었을 때 중복을 제거하고도 개수를 채우기 위한 여유분이다. 기본 구성에서는 에피소드 1개가 포인트 1개라 이 여유분이 쓰이지 않는다
- `with_payload: false`, `with_vector: false`이므로 **돌아오는 것은 포인트 id와 점수뿐이다.** 본문은 Qdrant에 없으므로 이후 다른 저장소에서 가져온다
- 필터는 항상 파티션 조건을 포함한다. 사용자 필터가 있으면 AND로 묶인다

## 4.7 `POST /collections/{이름}/points/delete?wait=true` — 삭제

**언제**: 에피소드 삭제 1건당 1회, 세션 삭제 때 파티션 전체에 1회.

**무엇을 보내나**: 지울 대상을 가리키는 필터.

```
에피소드 삭제: {"filter": {"must": [{파티션 조건}, {"has_id": ["<파생 uuid>", ...]}]}}
세션 삭제:     {"filter": {"must": [{파티션 조건}]}}
```

# 5부. 요청 1건이 흐르는 경로

## 5.1 저장

1. 서버가 메시지를 받아 에피소드로 만들고 PostgreSQL에 저장해 uid를 받는다
2. **인스턴스 확보** — 캐시에서 꺼내거나 새로 만든다. 여기서 Qdrant 질의가 0회, 1회, 17회로 갈린다
3. **에피소드를 이벤트로 변환** (5.3)
4. 분할기가 이벤트를 세그먼트로 나눈다 (기본은 나누지 않음)
5. 파생기가 세그먼트에서 임베딩할 텍스트를 만든다
6. 임베더가 그 텍스트를 벡터로 바꾼다
7. PostgreSQL 세그먼트 저장소에 세그먼트를 쓴다
8. **Qdrant upsert 1회** (4.5)

## 5.2 검색

1. **인스턴스 확보** — 저장과 같은 함수를 쓴다
2. **필터 조립** (5.4)
3. 임베더가 질의문을 벡터로 바꾼다
4. **Qdrant 검색 1회** (4.6). 포인트 id와 점수만 돌아온다
5. 그 id로 PostgreSQL에서 세그먼트를 찾고, 필요하면 앞뒤 문맥을 더 읽는다 *(이 문서의 Qdrant 집계 밖)*
6. 점수 기준으로 거르고 본문을 채워 응답을 만든다

## 5.3 "에피소드를 이벤트로 변환"이 하는 일

에피소드는 API가 받은 메시지 한 건이고, 이벤트는 장기 기억 내부가 쓰는 형식이다. 변환은 세 가지를 한다(`episodic_memory/long_term_memory/long_term_memory.py:735-794`).

1. **식별자를 정한다.** 에피소드 uid로부터 이벤트 uuid를 계산한다(uuid5). 같은 에피소드는 항상 같은 이벤트 uuid가 되므로 되돌릴 수 있다
2. **payload를 만든다.** 시스템 필드에는 밑줄을 붙이고(`producer_id` → `_producer_id`), 사용자 metadata는 그대로 둔다. 이 payload가 그대로 Qdrant 포인트에 실린다
3. **밑줄로 시작하는 사용자 키를 거부한다.** 그렇지 않으면 클라이언트가 `_producer_id`를 직접 넣어 다른 사용자인 척할 수 있다

즉 이 단계는 **Qdrant에 저장될 payload를 확정하는 단계**다.

## 5.4 "필터 조립"이 하는 일

검색 필터는 **클라이언트가 보낸다.** `filter` 필드에 문자열로 넣으면 된다. 조립은 그 문자열을 Qdrant가 이해하는 형식으로 바꾸고 파티션 조건과 합치는 과정이다.

1. **파싱** — `"producer_id = 'userA'"` 같은 문자열을 조건 트리로 바꾼다
2. **검증** — 시스템 필드 이름이 맞는지 확인한다. 오타면 여기서 오류가 난다. `m.<키>`는 사용자 metadata로 취급해 통과시킨다
3. **이름 변환** — `producer_id` → `_producer_id`, `m.user_id` → `user_id`로 바꾼다. 저장할 때의 규칙과 같다
4. **Qdrant 형식으로 변환** — AND는 `must`, OR은 `should`, NOT은 `must_not`이 된다
5. **파티션 조건과 AND로 결합**

**실제 필터링은 Qdrant가 한다.** 조립은 조건을 만들어 넘기는 단계이고, 걸러진 결과가 돌아온다는 이해가 맞다. 다만 한 가지 주의점이 있다. **필터를 안 보내면 파티션 조건만 남으므로 그 세션의 모든 사용자 기억이 후보가 된다.** 서버는 사용자 조건을 강제하지 않는다.

# 7부. 사용자를 나누는 두 방식

## 7.1 요약 비교

| 항목 | A. 세션 = 사용자 | B. `producer_id` = 사용자 |
|---|---|---|
| 파티션 키 | 사용자마다 다른 값 | 프로젝트 1개 값 |
| 신규 등록 비용 | 사용자당 17회 | 전체 1회 |
| 캐시 점유 | 사용자당 1칸 (한도 100) | 1칸 |
| 캐시 미스(재준비) | 사용자별로 발생 | 사실상 없음 |
| 검색 필터 | 파티션 조건만으로 격리 완성 | 사용자 조건을 반드시 추가 |
| 필터 누락 시 | 영향 없음 | **타 사용자 기억 노출** |
| 사용자 단위 삭제 | 세션 삭제 한 번 | 7.2 참조 |
| HNSW 하위 그래프 기준 | 사용자별 건수 | 프로젝트 전체 건수 |

## 7.2 사용자 한 명만 지우기

**못 지우는 것이 아니다. 한 번에 묶어주는 경로가 없을 뿐이다.**

삭제 API는 셋뿐이다.

| 경로 | 무엇을 지우나 |
|---|---|
| `POST /projects/delete` | 세션 전체. 에피소드 저장소, Qdrant 파티션, PostgreSQL 세그먼트 파티션, 시맨틱 세트, 세션 레코드가 **모두 연결되어** 지워진다 |
| `POST /memories/episodic/delete` | 에피소드 uid **목록** |
| `POST /memories/semantic/delete` | 시맨틱 특징 id **목록** |

**필터로 지우는 API는 없다.** 요청 본문이 uid 목록만 받는다(`api/spec.py:581-593`).

- **방식 A**는 사용자 하나가 세션 하나이므로 `POST /projects/delete` 한 번으로 끝난다
- **방식 B**는 그 사용자의 에피소드 uid를 먼저 모아야 한다. 검색이나 목록 조회로 uid를 수집한 뒤 `/memories/episodic/delete`에 넘기고, 시맨틱 특징도 따로 지워야 한다. 건수가 많으면 여러 번 나눠 보내야 한다

참고로 서버 내부에는 이미 같은 패턴이 있다. 세션 삭제가 `session_key` 조건으로 에피소드 id를 페이지 단위로 조회해 지운다(`main/memmachine.py:370-385`). 즉 **사용자 단위 삭제를 만들려면 이 패턴을 `producer_id` 조건으로 노출하면 되고, 지금은 그 API가 없다.**

## 7.3 HNSW 하위 그래프 — 임계값은 어느 단위인가

`m=0`이라 전역 그래프는 없고, `payload_m=16` 때문에 **payload 값마다 별도의 하위 그래프**가 만들어진다. 여기서 payload 값은 `sys-partition_key` 값, 즉 세션이다.

하위 그래프는 그 값에 속한 포인트가 임계값을 넘어야 만들어진다. 임계값은 10000KB를 포인트 수로 환산한 값으로 1536차원이면 약 1,667개, 1024차원이면 2,500개다.

**질문하신 이해가 맞다.**

| | 임계값을 재는 단위 | 결과 |
|---|---|---|
| **A. 세션 = 사용자** | 사용자 한 명의 기억 건수 | 한 명이 약 1,667건을 넘겨야 그 사용자의 그래프가 생긴다. 대부분의 사용자는 못 넘기므로 **평생 필터 후 순차 비교로 검색된다** |
| **B. producer_id = 사용자** | 프로젝트 전체 기억 건수 | 모든 사용자의 합이 약 1,667건을 넘으면 그래프가 생긴다. **훨씬 일찍 만들어진다** |

다만 B에서 그래프가 생겼다고 항상 그래프를 타는 것은 아니다. 검색할 때 Qdrant가 (파티션 조건 AND 사용자 조건)의 **카디널리티**를 추정해서, 조건에 맞는 것이 적으면 그것만 순차 비교하고 많으면 그래프를 탄다. 사용자 한 명의 데이터가 전체의 일부라면 순차 비교로 가는 경우가 많다.

소규모에서는 순차 비교가 오히려 빠르므로 A의 "그래프가 안 생긴다"는 점 자체가 단점은 아니다.

## 7.4 방식 B의 필터 정확도

런타임 검증 결과다 (사용자 3명, 12건 적재).

| 필터 | 사용자 발화 | assistant 응답 | 타 사용자 유입 |
|---|---|---|---|
| `producer_id = 'user_a'` | 2/2 | **0/2** | 0 |
| `producer_id = 'user_a' OR produced_for_id = 'user_a'` | 2/2 | **2/2** | 0 |
| `m.user_id = 'user_a'` | 2/2 | 2/2 | 0 |
| OR 필터, `produced_for`를 비운 경우 | 2/2 | **0/2** | 0 |

`_producer_id`와 `_produced_for_id`는 Qdrant 인덱스가 있다. `m.<키>`는 인덱스가 없으므로 규모가 커지면 비용이 든다.

## 7.5 `producer_id`에 왜 `assistant`가 들어가나

**클라이언트가 보내는 값이다.** 서버가 붙이지 않는다.

- API 필드는 `producer`, `produced_for`, `role` 세 개이고 기본값은 각각 `"user"`, `""`, `""`다(`api/spec.py:416-429`)
- 서버는 이를 `producer_id`, `produced_for_id`, `producer_role`로 옮겨 담을 뿐이다(`server/api_v2/service.py:59-70`)
- 채팅 구현체가 관례적으로 사용자 메시지에 `producer="사용자"`, AI 응답에 `producer="assistant"`를 넣기 때문에 그렇게 보이는 것이다

**"그냥 user_id를 넣으면 되지 않나"** — 넣을 수 있다. 다만 두 가지를 고려해야 한다.

1. **누가 말했는지 구분이 사라진다.** 사용자 메시지와 AI 응답 모두 `producer=user_id`로 넣으면 발화자 정보가 없어진다. 역할 구분은 `producer_role`에 맡겨야 한다
2. **시맨틱 메모리가 이 값을 사용자 식별자로 쓴다.** 적재할 때 `producer_id`를 메타데이터에 넣고(`semantic_session_manager.py:123`), 그 값이 있으면 사용자 프로필 세트 유형을 만들며(`:337-338`), 기본 세트를 `producer_id` 기준으로 생성한다(`:396`). 지금처럼 AI 응답에 `assistant`가 들어가면 **`assistant`라는 이름의 사용자 프로필이 생긴다**

정리하면 선택지는 셋이다.

| 방법 | 검색 필터 | 비고 |
|---|---|---|
| 관례대로 두고 `produced_for`를 채운다 | `producer_id = X OR produced_for_id = X` | 두 필드 모두 인덱스가 있다. 발화자 정보가 남는다 |
| 양쪽 메시지에 `producer = user_id` | `producer_id = X` | 단순하지만 발화자 구분이 사라지고 시맨틱 프로필이 섞인다 |
| metadata에 `user_id`를 넣는다 | `m.user_id = X` | 가장 명시적이지만 인덱스가 없다 |

# 8부. 현재 평가 코드의 상태

| 항목 | 상태 | 코드 |

그 결과 방식 A의 고정비도, 방식 B의 필터 비용도 측정되지 않는다. 사용자 수를 늘려도 캐시는 계속 1칸만 쓴다.

부수 결함으로 `memmachine_helper_restapiv2.py:257`에 `if page_num: lm_payload["org_id"] = page_num`이 있다. 목록 조회에서 페이지 번호를 org_id에 덮어쓴다.

# 9부. 임베딩 호출 (저장소는 아니지만 같은 경로)

저장과 검색 모두 논리 호출은 1회다. 다만 한 요청에 입력 2,048개 또는 총 75,000자를 넘으면 HTTP 요청이 나뉘어 동시에 나간다.

| 구간 | 입력 | 논리 호출 | HTTP 요청 |
|---|---|---|---|
| 저장, 에피소드 4건 | 4개 336자 | 1 | 1 |
| 검색 1건 | 1개 16자 | 1 | 1 |
| 저장, 16만 자 1건 | 1개 160,039자 | 1 | 3 |
| 저장, 에피소드 2,100건 | 2,100개 186,780자 | 1 | 3 |

**재시도가 없다.** 모든 호출부가 `max_attempts` 기본값 1을 쓴다(`common/embedder/embedder.py:15-57`). 429나 5xx를 받으면 저장 또는 검색이 그대로 실패한다.

검색에서 임베딩과 Qdrant 질의는 직렬이므로 병목 측정 시 둘을 분리해야 한다.

# 10부. 인스턴스 캐시 리뷰

## 10.1 구조

캐시는 프로세스당 하나이고 100칸을 모든 세션이 공유한다. worker를 늘리면 worker마다 별도 캐시가 생기고 세션 어피니티는 없다. `MEMMACHINE_WORKERS` 기본값은 1이다(`docker-compose.yml:87`).

용량 100과 유휴 600초는 `EpisodicMemoryManagerParams`의 기본값이고(`episodic_memory_manager.py:43-52`), 이를 주입하는 곳이 없다. 즉 **코드 고정 리터럴이 아니라 주입 가능하지만 아무도 주입하지 않는 기본값**이며, 결과적으로 조정 수단이 없다.

## 10.2 잠금

캐시 적중은 전역 배타 잠금을 2회, 미스는 4회 잡는다. 임계구역 안에 대기 지점이 없어 경합이 구조적으로 생기지 않는다. 검증에서 동시성 1/10/100/500 모두 40만 회 획득에 0.54초, 실제 경합 0회였다. **병목이 아니다.**

## 10.3 확인된 결함

| 심각도 | 내용 |
|---|---|
| 높음 | 저장과 삭제 호출부가 인스턴스 사용 구간을 벗어난 뒤 실제 작업을 시작한다(`main/memmachine.py:775`와 788, `1214`와 1219). 진행 중 저장과 세션 삭제가 겹칠 수 있다 |
| 중간 | 삭제가 "사용 중" 오류로 실패할 때 사용 횟수가 1 남는다(`episodic_memory_manager.py:304-307`). 더 큰 문제는 캐시 적중 경로가 세션 상태 검사를 건너뛰어, 삭제 실패한 프로젝트가 재시작 전까지 계속 동작하는 점이다 |
| 낮음 | 세션별 잠금 딕셔너리가 제거 경로 없이 증가한다. 500 사용자 규모에서는 1MB 미만이라 무해하다 |
