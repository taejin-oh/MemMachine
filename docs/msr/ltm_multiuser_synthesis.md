# 요약 (이 장만 보셔도 됩니다)

## 한 줄

> **MemMachine을 채택한 것만으로는 차별화가 생기지 않는다는 사실을 확인했습니다.
> 차별화는 "사용자마다 검색 공간을 분리하되 그 비용을 감당 가능하게 만드는 것" —
> 현재 어떤 오픈소스도 풀지 못한 이 문제를 우리가 푸는 데서 나옵니다.**

## 확인한 것 4가지

| | 내용 |
|---|---|
| **1** | **업계 공통 구조**: Mem0·Zep·Letta 등 주요 오픈소스 메모리 솔루션 전부가 "하나의 저장소에 여러 사용자를 섞어 넣고, 검색 후 사용자 딱지로 걸러내는" 방식입니다. 사용자별로 검색 공간을 나누는 곳은 없습니다. |
| **2** | **MemMachine도 기본 설정에서는 동일**합니다. 조직/프로젝트 하나에 여러 사용자를 넣으면 Mem0와 실질적으로 같습니다. |
| **3** | **다만 MemMachine은 경계를 우리가 정할 수 있습니다.** 프로젝트 단위를 사용자 단위로 내리면 사용자별 검색 공간 분리가 실제로 가능합니다. Mem0 오픈소스로는 불가능합니다. |
| **4** | **그런데 그 대가가 큽니다.** 사용자마다 데이터베이스에 실제 저장 구획이 하나씩 생기는 구조라, 사용자가 늘면 여기서 먼저 한계가 옵니다. **아무도 이 방식을 쓰지 않는 이유입니다.** |

## 그래서 할 일

**"사용자별 검색 공간 분리를 실용적인 비용으로 가능하게 만든다."**
이것이 본 과제의 기술 목표이며, 성공하면 Mem0·Zep·Letta 어느 것도 하지 못하는 지점이 됩니다.

1단계(개인 사용자·정확도)에서 문제를 찾아 해결하고 특허로 이어간 것과 **같은 패턴**을,
2단계(다중 사용자·성능)에서 반복합니다. 이번에는 측정을 시작하기도 전에
구조적 문제를 먼저 찾아냈습니다.

# 1. 배경 — 이 조사가 왜 필요했나

## 우리 로드맵에서의 위치

```
올해 목표: 우리 솔루션에 최적화된 차별화 LTM(장기 기억) 시스템 확보
           기반 기술로 오픈소스 MemMachine 채택

 1단계 (완료) — 개인 사용자 관점: "정확도"
    · 평가 체계 구축 → 문제 발견 → adaptive-k 기법 개발
    · 결과: 정확도 유지하면서 비용(토큰) 약 10% 절감
    · 직무발명 제안서 작성 완료

 2단계 (본 과제) — 다중 사용자 관점: "성능"      ◀ 지금 여기
    · 사용자가 늘어날 때 시스템에 걸리는 부하를 확인하고
    · 문제를 찾아 해결해서 차별화 포인트로 만든다
```

## 이번 조사의 출발 질문

평가 환경을 만들기 전에, **"우리가 바람직하다고 보는 구조가 무엇이고,
기존 솔루션들은 그렇게 되어 있는가"** 를 먼저 확인했습니다.

우리가 바람직하다고 본 구조:

```
   사용자 A                     사용자 B
   ┌──────────────┐            ┌──────────────┐
   │ A의 기억 저장소 │            │ B의 기억 저장소 │
   │  ├ 대화1      │            │  ├ 대화1      │
   │  └ 대화2      │            │  └ 대화2      │
   └──────────────┘            └──────────────┘
          ▲                            ▲
     A가 검색하면                  B가 검색하면
     A의 저장소만 본다              B의 저장소만 본다
```

# 2. 배경 지식 — 왜 이게 어려운 문제인가

*(익숙하신 분은 건너뛰셔도 됩니다)*

## AI의 기억 검색은 "비슷한 것 찾기"입니다

AI 메모리는 "지금 질문과 **의미가 비슷한** 과거 대화"를 찾습니다.
모든 문장을 숫자 목록으로 바꿔 놓고 가까운 것을 찾는 방식입니다.

문제는 **기억이 수백만 개면 전부 비교할 수 없다**는 점입니다.
그래서 미리 **"비슷한 것끼리 이어놓은 지도"** 를 만들어 둡니다.
이 지도를 **인덱스**라고 합니다.

## 여기서 다중 사용자 문제가 생깁니다

지도를 하나만 만들어 모든 사용자의 기억을 넣으면,
A가 검색할 때 그 지도를 따라가다 **B·C·D의 기억을 계속 지나가게** 됩니다.

```
   지도가 하나뿐일 때 A가 검색하면
   ┌──────────────────────────────────┐
   │  A─B─C─A─D─B─A─C─D─A             │  ← 길을 따라가는데
   │  ↑     ↑       ↑                 │     남의 것을 계속 밟음
   │  내것   남의것   내것              │
   └──────────────────────────────────┘
        나중에 "A 것만" 골라냄
```

**결과적으로 세 가지가 나빠집니다.**

| | 문제 |
|---|---|
| **비용** | 남의 기억을 밟는 만큼 헛일을 합니다 |
| **품질** | 길을 따라가다 보면 내 기억이 충분히 안 나올 수 있습니다 (사용자가 많을수록 심함) |
| **안전** | 걸러내는 조건을 빠뜨리면 **남의 기억이 그대로 나옵니다** |

# 3. 핵심 발견 ① — 업계 전부가 같은 방식을 씁니다

## 조사 결과

| 솔루션 | 사용자를 어떻게 구분하나 | 검색할 때 남의 것을 밟나 |
|---|---|---|
| **Mem0** (오픈소스) | 기억에 사용자 딱지를 붙이고 검색 후 걸러냄 | **밟음** |
| **Zep / Graphiti** | 그래프 요소에 그룹 딱지를 붙이고 걸러냄 | **밟음** |
| **Letta** | 에이전트 단위로 묶고 걸러냄 | **밟음** |
| **Memobase** | 데이터를 사용자 순으로 정렬해 그 구간만 봄 | 안 밟음 |
| **MemMachine** | 조직/프로젝트 단위로 검색 공간이 나뉨 | 프로젝트 밖은 안 밟음 |

## 왜 다들 이렇게 하는가 — 이유가 있습니다

"사용자마다 저장소를 따로 만들면 되지 않나?" 라는 생각이 자연스럽지만,
**벡터 데이터베이스 공급사들이 명시적으로 금지하는 방식**입니다.

> Qdrant 공식 문서: *"테넌트(사용자)마다 저장소를 만들지 마세요.
> 수백 개를 넘기면 확장이 안 되고 자원을 낭비합니다."*
> (클라우드 서비스는 저장소 1,000개 상한)

> Milvus 공식 문서: 확장성 순위에서 이 방식을 하위로 분류

저장소를 하나 만들 때마다 메모리·파일·관리 비용이 고정으로 붙기 때문입니다.
**즉 업계가 게을러서가 아니라, 쉬운 해법이 실제로는 막혀 있기 때문입니다.**

## 결론

**"사용자별로 검색 공간을 분리한다"는 요구를 실용적인 비용으로 만족하는
오픈소스 솔루션은 현재 없습니다.** 유일하게 근접한 Memobase는
원본 대화를 저장하지 않고 요약본만 다루는 방식으로 우회합니다.

# 4. 핵심 발견 ② — MemMachine의 실제 위치

## 4.1 잘 되어 있는 부분

MemMachine은 벡터 데이터베이스(Qdrant) 설정에서 **전체를 잇는 지도를 아예 만들지 않고,
구획별로 별도의 지도를 만들도록** 되어 있습니다.

```python
# 설정 요지
m = 0            # 전체를 잇는 지도를 만들지 않음
payload_m = 16   # 대신 구획(프로젝트)별 지도를 만듦
```

Qdrant 공식 문서 확인: *"m을 0으로 설정하면 컬렉션의 전역 인덱스를 비활성화한다.
단일 지도를 유지하는 대신 **구획 값별로 별도의 지도를 만든다.**"*

```
  ┌─ 프로젝트 A ─┐  ┌─ 프로젝트 B ─┐  ┌─ 프로젝트 C ─┐
  │   ●─●─●     │  │   ●─●        │  │   ●─●─●     │
  └─────────────┘  └──────────────┘  └─────────────┘
      ↑ 이 셋을 잇는 길이 하나도 없음
        → 검색이 다른 프로젝트로 넘어갈 경로 자체가 없음
```

Mem0 오픈소스는 이런 설정을 하지 않습니다(전체 지도 하나를 그대로 사용).

## 4.2 ⚠ 그러나 — 기본 사용법에서는 Mem0와 동일합니다

**여기가 이번 조사에서 가장 중요한 정정 사항입니다.**

위 구획은 **"조직/프로젝트" 단위**입니다. **사용자 단위가 아닙니다.**
따라서 하나의 프로젝트 안에 여러 사용자를 넣으면:

```
  ┌──── 프로젝트 1개 ────┐
  │  A─B─C─A─D─B─A─C    │  ← 사용자 A,B,C,D가 한 지도에 섞임
  └─────────────────────┘
     검색: 이 안을 걸어다니며 남의 것을 밟고
           사용자 딱지로 걸러냄  ← Mem0와 완전히 동일
```

**즉 "MemMachine이라서 더 낫다"는 성립하지 않습니다.**
같은 설정에서는 비용도, 품질 저하도, 유출 위험도 Mem0와 같습니다.

## 4.3 진짜 차이는 "경계를 우리가 정할 수 있다"는 점뿐입니다

| | 검색 공간을 나눌 수 있는 최소 단위 | 사용자별 분리 |
|---|---|---|
| Mem0 오픈소스 | **없음** (배포당 저장소 하나) | ❌ 불가능 |
| Mem0 유료 서비스 | 조직/프로젝트 (공개 문서 기준) | 문서에 없음 · **확인 불가** |
| **MemMachine** | **우리가 정하는 값** | ✅ 프로젝트를 사용자 단위로 두면 가능 |

MemMachine의 이점은 **설계가 우월해서가 아니라 우리가 직접 운영하기 때문에
경계를 자유롭게 정할 수 있다**는 데서 옵니다. 이 점을 정확히 인식해야
과제의 목표를 잘못 잡지 않습니다.

> **참고**: Mem0 유료 서비스에도 조직/프로젝트 개념이 있습니다.
> 다만 공개 문서는 이를 **접근 권한·멤버 관리·API 키 범위** 관점으로 설명하며,
> 내부 저장 구조는 비공개입니다. 따라서 "저장소가 나뉘는지"는 확인할 수 없습니다.
> 어느 쪽이든 **우리가 통제할 수 없는 영역**이라는 점은 동일합니다.

# 5. 핵심 발견 ③ — 사용자 단위로 내리면 비용이 발생합니다

프로젝트를 사용자 단위로 내리면 검색 공간은 분리되지만, 공짜가 아닙니다.

| 구성 요소 | 사용자를 늘릴 때 생기는 비용 | 심각도 |
|---|---|---|
| **관계형 데이터베이스** | **사용자마다 실제 저장 구획(파티션)이 하나씩 생성됨** | ⚠ **가장 큼** |
| 애플리케이션 | 사용자마다 작업 공간을 차지 (기본 100개 한도, 초과 시 반복 생성·삭제) | 중간 |
| 벡터 데이터베이스 | 구획별 지도 (공급사 권장 방식이라 부담 낮음) | 낮음 |

## 관계형 데이터베이스 문제가 핵심입니다

MemMachine은 검색 공간이 하나 생길 때마다 데이터베이스에 **실제 저장 구획을
만듭니다.** 이것이 3장에서 말한 "공급사가 금지하는 방식"에 해당하며,
**조사한 어떤 솔루션도 이렇게 하지 않습니다.**

### 근거 ① — 사용자 1명당 테이블 2개가 실제로 생성됩니다

MemMachine 코드가 실행하는 명령문 (파일: `sqlalchemy_segment_store.py`,
함수: `_create_pg_child_tables()`):

```sql
CREATE TABLE "segment_store_sg_p_<사용자키>"     PARTITION OF segment_store_sg     ...
CREATE TABLE "segment_store_dv_ln_p_<사용자키>"  PARTITION OF segment_store_dv_ln  ...
```

**사용자 1명 = 테이블 2개.** 사용자 500명이면 테이블 1,000개가 생성됩니다.

### 근거 ② — PostgreSQL 공식 문서가 명시한 한계

PostgreSQL 공식 문서 "선언적 파티셔닝 모범 사례" 원문:

> *"쿼리 플래너는 일반적으로 **수천 개까지의** 파티션 계층을 꽤 잘 처리합니다 —
> 단, 일반적인 쿼리가 플래너로 하여금 소수를 제외한 전부를 잘라낼 수 있게 해준다는
> 전제 하에서입니다."*

> *"파티션 정리(pruning) 후에도 **남는 파티션이 많을수록 계획 수립 시간이 길어지고
> 메모리 소비가 커집니다.**"*

여기에 더해, 우리 사용 형태에 직접 해당하는 항목이 있습니다:

> *"파티션이 많을 때 우려되는 또 다른 이유는 **서버의 메모리 소비가 시간이 지나며
> 크게 증가할 수 있다는 점입니다. 특히 많은 세션이 다수의 파티션을 건드릴 때
> 그렇습니다.** 각 파티션은 그것을 건드리는 **모든 세션의 로컬 메모리에 메타데이터가
> 적재되어야 하기 때문입니다.**"*

→ 다중 사용자 서비스는 데이터베이스 연결을 공유해서 쓰므로 **하나의 연결이 여러
사용자의 파티션을 차례로 건드리게 됩니다.** 공식 문서가 경고하는 바로 그 상황입니다.
계획 수립 시간 외에 **메모리 증가**라는 두 번째 비용이 따로 발생합니다.

### 근거 ③ — 파티션 생성은 구조적으로 한 번에 하나씩만 됩니다

MemMachine 코드가 파티션 생성 전에 거는 잠금:

```sql
LOCK TABLE segment_store_pt IN SHARE ROW EXCLUSIVE MODE
```

PostgreSQL 공식 문서: *"이 모드는 SHARE 모드보다 제한적인데, **한 번에 오직 하나의
트랜잭션만 이 잠금을 보유할 수 있기 때문입니다.**"* (자기 자신과 충돌하는 잠금 모드)

→ **추정이 아니라 코드와 명세로 확정된 사실입니다.** 사용자 N명이 동시에 처음
저장을 시작하면 파티션 생성이 **완전히 직렬화**되어 줄을 섭니다.

## 애플리케이션 작업 공간도 사용자마다 차지합니다

MemMachine 서버는 검색 공간(=사용자)마다 작업 공간 객체를 만들어 캐시에 보관합니다.

- 기본 한도: **100개** (`instance_cache_size`, 기본값 100)
- 유휴 정리: **600초** (10분간 미사용 시 제거)

동작을 코드로 확인한 결과, 상황에 따라 **두 가지 다른 방식으로 나빠집니다.**

| 상황 | 동작 | 결과 |
|---|---|---|
| 사용자들이 번갈아 사용 (사용 후 반납) | 한도 초과 시 오래된 것부터 제거 | **만들었다 지웠다 반복** → 재생성 비용 |
| **사용자들이 동시에 사용 중** | 사용 중인 항목은 제거하지 못하고 건너뜀. 제거할 것이 없으면 **한도를 넘겨서 그냥 추가** | **한도가 지켜지지 않고 메모리가 계속 증가** |

즉 100이라는 숫자는 **동시 사용 상황에서는 상한으로 동작하지 않습니다.**
이 역시 측정으로 확인할 항목입니다.

## 종합

**→ 사용자 확장의 한계가 벡터 데이터베이스가 아니라 관계형 데이터베이스와
애플리케이션 계층에서 먼저 올 것으로 봅니다.**
이것이 본 과제에서 숫자로 확인할 1순위 항목입니다.

# 6. 그래서 우리 차별화는 무엇인가

## 아무도 풀지 않은 자리가 보입니다

```
   사용자 아래 대화 단위 구분 ↑
                            │
              Mem0  ●       │       ◎  ← 우리가 목표하는 자리
                            │          (현재 비어 있음)
   ─────────────────────────┼──────────────────→ 사용자별 검색 공간 분리
                Zep  ●      │   ● Memobase (요약본만 다뤄서 우회)
              Letta  ●      │   ● MemMachine (프로젝트 단위까지만)
```

**두 가지를 동시에 만족하는 솔루션이 하나도 없습니다.**
- 검색 공간을 나누는 쪽(Memobase, MemMachine)은 **사용자 아래 대화 단위 구분이 없고**
- 대화 단위를 구분하는 쪽(Mem0)은 **검색 공간을 안 나눕니다**

## 본 과제의 기술 목표

> **사용자별 검색 공간 분리를, 사용자가 늘어도 감당 가능한 비용으로 실현한다.**

구체적으로 두 가지를 해결합니다.

| # | 과제 | 현 상태 |
|---|---|---|
| **1** | 사용자 계층 도입 (사용자 아래 대화 단위 구분) | 현재 개념 자체가 없음 |
| **2** | 관계형 데이터베이스의 사용자당 비용 제거 | 현재 사용자마다 저장 구획 생성 |

**벡터 데이터베이스 쪽은 손댈 필요가 없습니다** — 이미 공급사 권장 방식입니다.

## 기대 효과

- **기술**: 오픈소스가 못 하는 구조 확보 → 우리 LTM 솔루션의 차별화 근거
- **지식재산**: 개선 방식에서 신규 발명 발굴 (1단계 adaptive-k 특허의 후속)
- **사업**: 사용자 증가 시 비용·품질 예측 가능 → 서비스 적용 판단 근거
- **연계**: 다중 사용자 워크로드가 저장장치에 주는 부하 데이터 → 스토리지 신규 과제 입력

# 7. 추진 계획

## 인원과 역할 (2인)

| | 담당 |
|---|---|
| **오태진** | 목표·구조 설계, 평가 시나리오 정의, 결과 해석 |
| **박준혁 TL** | 구조 실측 검증 → 평가 환경 구축 → 측정 (주 절반 이상 투입) |

## 일정 (1개월 목표)

| 주차 | 박준혁 TL | 오태진 |
|---|---|---|
| 1주 | **실측 검증** — 아래 3가지가 실제로 그런지 확인 | 계획 확정, 평가 시나리오 작성 |
| 2주 | 평가 환경 구축 착수 (적재 부분) | 측정 항목 확정 |
| 3주 | 동시 검색 + 측정 기록 | 측정 매트릭스 확정 |
| 4주 | **최소 동작 환경 완성** + 1차 결과 공유 | 결과 검토 → 개선 설계 착수 |

## 1주차 실측 검증 항목 (가장 먼저 확인할 3가지)

| # | 확인할 것 | 왜 |
|---|---|---|
| 1 | 사용자마다 데이터베이스 저장 구획이 실제로 생기는가, **몇 명에서 느려지는가** | 5장 문제의 정량화 — 개선 대상 확정 |
| 2 | 벡터 데이터베이스의 구획별 지도가 **실제로 방어해 주는가** | 확인되면 "벡터 쪽은 그대로 두고 관계형만 고친다"가 수치로 뒷받침됨 |
| 3 | 여러 사용자가 동시에 처음 저장할 때 줄서기가 발생하는가 | 초기 적재 성능 문제 확인 |

## 평가 데이터

**LongMemEval-M** 사용. 질문 500개 각각에 그 사람의 긴 대화 기록이 붙어 있어,
**질문 1개 = 사용자 1명**으로 매핑하면 복제 없이 실사용 데이터로 **최대 500명**을
구성할 수 있습니다.

| 항목 | 실측값 |
|---|---|
| 사용자 1명당 대화 세션 | 약 482개 |
| 사용자 1명당 대화 turn | 약 5,057개 |
| 사용자 1명당 텍스트 양 | 약 5MB |
| 100명 기준 총량 | 에피소드 약 50만 건 |
| 500명 기준 총량 | 에피소드 약 250만 건 (벡터 데이터 약 15GB) |

**정답 위치가 데이터에 표시되어 있어** 검색 품질 채점과
"남의 기억이 섞였는지" 검증을 자동으로 할 수 있습니다.

## 8.4 이전 문서와 달라진 점

이번 종합 과정에서 **초기 판단 두 가지를 정정**했습니다.

| 초기 판단 | 정정 |
|---|---|
| "MemMachine이 구조적으로 앞서 있다" | **Mem0 오픈소스와의 비교에 한정.** 같은 설정(프로젝트 하나에 여러 사용자)에서는 동일함 |
| "MemMachine은 사용자 필터가 안 된다"는 취지의 외부 서술 | **필터는 지원됨** (최신 코드 재확인). 다만 선택 사항이고 서버가 강제하지 않음 |

이 정정으로 과제의 목표가 **"MemMachine이 낫다는 것을 증명"이 아니라
"아무도 못 푼 문제를 우리가 푼다"** 로 더 명확해졌습니다.
