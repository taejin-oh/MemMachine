## 0. 이 문서의 위치

**목적**: 다중 사용자 환경의 LTM 구조를 정의하고, MemMachine으로 구성했을 때
실제로 어떤 구조가 되는지를 확정한다. 그 이해 위에서 평가 환경을 설계하고,
현재 지원 DB들이 다중 사용자 환경에 적합한지 예측한 뒤 구축·검증한다.

**연구 흐름 4단계** — 이 문서는 ①②를 종합하고 ③의 설계 근거를 제시한다.

```
① 상위 구조 조사 (완료)   업계는 다중 사용자를 어떻게 다루는가
                          → 프로젝트 단위 격리 + 사용자 단위 필터링이 공통 형태
② 실물 구조 확인 (완료)   MemMachine이 실제로 어떻게 저장·검색하는가
                          → 사용자 → MemMachine → DB 전 경로를 코드로 확정
③ 평가 환경 설계 (진행)   ②의 이해로 무엇을 어떻게 측정할지 정의
④ 구축·검증 (예정)        예측한 적합성 판단을 실측으로 확인
```

## 1. 출발점 — 상위 구조 조사 결과 (①)

### 1.1 업계 공통 형태

주요 오픈소스 LTM을 조사한 결과, 다중 사용자를 다루는 방식이 사실상 하나로 수렴한다.

| 솔루션 | 상위 격리 | 사용자 구분 | 검색 시 사용자 격리 |
|---|---|---|---|
| **MemMachine** | `org_id/project_id` | `producer_id` / metadata | 필터 (선택) |
| **Mem0 OSS** | 없음 (배포당 컬렉션 1개) | `user_id`/`agent_id`/`run_id` | 필터 (**필수**) |
| **Mem0 Platform** | org/project | `user_id` 등 | 비공개 |
| **Supermemory** | containerTag | 태그 문자열에 인코딩 | 태그 (필수) + API 키 권한 |
| **Zep/Graphiti** | `group_id` | 없음 (앱 책임) | 속성 필터 |
| **Memobase** | project | **user (1급 엔티티)** | 키 선행 인덱스 |

→ **"상위 단위로 격리하고, 그 아래는 필터로 구분한다"** 가 공통 골격.
Memobase만 사용자를 1급으로 두지만, 원문 대신 프로필·요약만 다루는 우회로 성립.

### 1.2 그래서 시작 구조를 이렇게 잡았다

MemMachine의 방식이 업계 표준과 다르지 않으므로, **프로젝트 단위 격리 +
사용자 단위 필터링**을 기본 구성으로 두고 출발한다.
(이후 §4에서 이 선택의 대안과 비용을 다룬다)

## 2. 실물 구조 확인 결과 (②)

### 2.1 사용자 → MemMachine → DB 전 경로

```
[사용자·프로젝트]   org_id + project_id
        │           (사용자 u1·u2는 이 계층에 없음 — payload 속성으로만 존재)
        ▼
[MemMachine]        session_key = "org_id/project_id"    ← 유일한 상위 식별자
        │           partition_key = sha256(session_key)[:32]  ("/" 포함이라 항상 해시)
        │
        ├──▶ [관계형DB] episode_store  : 대화 원문 + uid 발급 ← 진실의 원천
        │              (파티션 없는 전역 공유 테이블 · uid = 자동증가 정수 PK
        │               격리는 session_key 평문 컬럼)
        │              segment_store   : 파생(문맥 확장용) — _sg·_dv_ln만 LIST 파티션
        │                                 → 파티션당 자식 테이블 2개
        │
        └──▶ [벡터DB]  파생만 저장 (임베딩 + 속성 + uid 참조)
                       Qdrant : 컬렉션 1개, 파티션은 payload 값
                       Milvus : 컬렉션 1개, 파티션 키 → hash%64 물리 버킷
```

**핵심 4가지** (상세: `memmachine_vectordb_full_guide.md`)

1. **격리는 데이터 구조가 아니라 질의 규율이다.** 저장 시점에는 `sys-partition_key`도
   `user_id`도 payload의 동등한 항목이다. 파티션이 경계처럼 보이는 것은 검색 시
   MemMachine 코드가 조건을 **무조건 AND로 결합**하기 때문이다 (`:352` 하드코딩).
2. **벡터DB에 원문이 없다.** 원본 참조는 payload의 `_episode_uid`이고, 복원은
   관계형DB에서 `WHERE id IN (…)` PK 조회로 한다. uid는 관계형DB가 `INSERT …
   RETURNING`으로 **그 순간 발급하는 자동증가 정수 PK**여서, 원문을 쓰기 전에는
   존재하지 않는다. 그래서 "원문 선저장 → uid → 인덱싱" 순서는 관례가 아니라
   **구조적 강제**다.
3. **프로젝트 증가 시 구조 변경(DDL)이 발생하는 곳은 Postgres뿐이다.**
   벡터DB는 payload 값 추가 또는 해시 배정으로 끝난다.
   단 같은 Postgres 안에서도 둘이 다르다 — `segment_store`만 파티션 테이블을
   만들고, `episode_store`는 전역 테이블 1개에 행만 쌓인다.
4. **사용자 조건이 가속되지 않는 구간이 하나 있다 — 문맥 확장.**
   `expand_context > 0`이면 `segment_store_sg`를 시간순으로 걸으며 사용자
   조건을 **행마다 JSON으로 평가**한다(그 컬럼에 인덱스가 없다). 의미는
   정확하지만 비용이 **대상 사용자의 발화 밀도**에 반비례한다. 벡터 검색은
   payload 인덱스로 방어되는 반면 여기는 방어 수단이 없어, 멀티유저에서
   가장 먼저 무너질 후보다. (기본값 `expand_context=0`에서는 미발생)

### 2.2 상위 조사와 달랐던 점

①에서는 "프로젝트 격리 + 사용자 필터"로 동일해 보였으나, 실물을 보니
**같은 개념이 백엔드별로 전혀 다른 물리 구조**가 된다.

| | Qdrant | Milvus |
|---|---|---|
| 사용자 조건 가속 | **값-기반 엣지**(payload-value subgraph)가 필드마다 생성 | 없음 — 비트셋(사후 걸러내기) |
| 범위 좁히기 축 | 색인한 필드 수만큼 | **파티션 키 1개뿐**(컬렉션당 제한) |
| 사용자 metadata 색인 | payload 인덱스 생성 | **생성 안 함** (동적 필드, 무인덱스) |

→ 이것이 §3 평가 설계와 §4 적합성 예측의 출발점이다.

## 3. 평가 환경 설계 근거 (③)

### 3.1 무엇을 측정해야 하는가 — ②에서 도출

②의 구조 이해가 곧 측정 항목의 근거가 된다.

| 구조적 사실 (②) | → 측정해야 할 것 |
|---|---|
| 프로젝트마다 Postgres 테이블 2개 + 생성 DDL 직렬화 | 프로젝트 수 스윕에서 계획 시간·메모리·DDL 대기 |
| 세션 작업공간 LRU 100 (초과 시 재생성 반복) | 동시 활성 프로젝트 수에 따른 지연 변화 |
| Qdrant만 값-기반 엣지 보유 | 사용자 수 증가 시 조건 검색 방어 효과 (백엔드 대조) |
| Milvus는 `_p_*` 무인덱스 → 전 행 평가 | 같은 조건에서 Qdrant 대비 비용 격차 |
| `properties_schema` 등록 여부로 경로가 갈림 | 등록/미등록 성능 차 (등가성 검증의 전제) |
| 벡터 인덱스는 임계값 넘어야 생성 | `indexed_vectors_count` 확인 없이는 비교 무의미 |

### 3.2 평가 환경 구성 요건

| 요건 | 근거 |
|---|---|
| **워크로드가 프로젝트·사용자 2축으로 스윕 가능** | 격리 단위(프로젝트)와 필터 단위(사용자)가 분리돼 있으므로 |
| **동일 `properties_schema` 고정** | 스키마가 다르면 컬렉션이 갈라져 비교 불가 (해시 기반 명명) |
| **`user_id` 등록 필수** | 미등록 시 파티션 전수 평가로 떨어져 다른 것을 측정하게 됨 |
| **인덱싱 상태 사전 확인** | 임계값 미달이면 인덱스 효과 자체가 관측 불가 |
| **관계형DB 계측 포함** | 병목 후보 1순위가 벡터DB가 아니라 Postgres |
| **서버 모드 병행** | LRU·세션 락은 REST 경로에서만 관측됨 |

### 3.3 평가 설계에 남은 결정

| # | 결정할 것 | 선택지 |
|---|---|---|
| 1 | 사용자를 프로젝트에 담을 것인가, 프로젝트로 나눌 것인가 | §4.3 참조 |
| 2 | 사용자 구분을 `producer_id`로 할 것인가 `m.user_id`로 할 것인가 | 전자는 등록 불필요하나 어시스턴트 응답 누락 |
| 3 | 등가성 확보 방식 | 필터 없는 조건 비교 / 필터 있는 조건도 병행 |

## 4. DB 적합성 예측 (④의 가설)

### 4.1 예측 — 구조에서 따라 나오는 것

| 항목 | Qdrant | Milvus | 근거 |
|---|---|---|---|
| 프로젝트 수 증가 | 영향 미미 | 영향 미미 | 양쪽 다 컬렉션 불변 |
| **사용자 수 증가(한 프로젝트 내)** | **방어 가능** | **선형 악화 예상** | 값-기반 엣지 유무 |
| 사용자 조건 검색 비용 | 색인+엣지로 가속 | 전 행 평가 | `_p_*` 무인덱스 |
| 다축 스코프(사용자+세션) | 가능 | **1축만** | 파티션 키 제한 |
| 전체 확장 한계 | **Postgres에서 먼저** | **Postgres에서 먼저** | DDL은 백엔드 무관 |

**요약 가설**: **다중 사용자 환경에서 MemMachine과 합이 맞는 것은 Qdrant다.**
Milvus는 동작하지만 사용자 축 가속이 구조적으로 없다.
단 **어느 백엔드든 확장 한계는 Postgres가 먼저 만든다.**

### 4.2 검증 방법 (④)

| # | 가설 | 검증 |
|---|---|---|
| 1 | Postgres가 1순위 병목 | 프로젝트 100/500/1000 스윕 |
| 2 | Qdrant 값-기반 엣지가 사용자 수 증가를 방어 | 사용자 수 스윕 × 백엔드 대조 |
| 3 | Milvus는 사용자 조건에서 선형 악화 | 동일 조건 비교 |
| 4 | LRU 100 초과 시 지연 급증 | 동시 활성 수 스윕 (서버 모드) |
| 5 | 등록/미등록 성능 차가 유의미 | 동일 워크로드 대조 |

### 4.3 구조 선택지 — 평가 결과에 따라 갈림

| 구성 | 사용자 격리 | 사용자당 고정비 | 사용자 전체 검색 |
|---|---|---|---|
| **A. 프로젝트 공용** (현재 기본) | 필터 의존 | 0 | 프로젝트 안에서만 |
| **B. `project = user`** | 구조가 보장 | Postgres 테이블 2개 | 자동 |
| **C. 파티션 바인딩 해제** | 필터 의존 | 0 | 전 프로젝트 횡단 |

A는 업계 표준과 동일(§1). B는 격리를 얻는 대신 §4.1의 확장 한계를 앞당긴다.
C는 코드 3지점 수정으로 성립하며 Qdrant 전제다.
→ **어느 쪽이 우리 요구에 맞는지가 평가의 최종 산출물이 되어야 한다.**
