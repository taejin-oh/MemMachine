# 과제 계획서 초안 — 멀티유저 AI 에이전트 메모리 평가

*작성 2026-08-11 · 초안 v1 (이번 주 확정 목표)*

---

## 1. 과제 개요

| | |
|---|---|
| 과제명(안) | 「멀티유저 환경 LTM 시스템의 부하 분석 및 개선」 (짧게: MemMachine 멀티유저 평가·개선) |
| 성격 | **연간 LTM 솔루션 확보 로드맵의 2단계** (스토리지 워크로드 신규과제와는 독립, 결과로만 연결) |
| 기간 | 계획서 확정 이번 주 → **MVP 1개월** → 이후 모니터링 환경 확장 |
| 인원 | 2인 — 오태진(구조·목표·관리) / 박준혁 TL(실측·구현, 주 절반 이상 투입) |

### 왜 하나 — 로드맵에서의 위치

**올해 목표: 우리 솔루션에 최적화된 차별화 LTM(장기 기억) 시스템 확보.**
그 기반으로 MemMachine을 선정했고, 두 단계로 진행한다.

```
1단계 (완료) — 개인 사용자 관점: "정확도"
  · LongMemEval 기반 정확도 평가 체계 구축
  · adaptive-k + bias 검색 기법 개발
    → 정확도 유지·향상 + 토큰 약 10% 절감 (실측)
    → 직무발명 제안서 작성 (특허 진행 중)

2단계 (본 과제) — 멀티 사용자 관점: "성능"        ◀ 지금 여기
  · 사용자가 늘어날 때 MemMachine과 backend(벡터DB·Postgres)에
    걸리는 부하를 실측
  · 문제점을 찾아서 → 해결한다 → 그 해결이 차별화 포인트가 된다
```

### 한 줄 목표

> 유저 수를 늘려가며 **어디가 언제 무너지는지**(앱 / DB / SSD) 숫자로
> 확인하고, **찾은 문제를 해결해 차별화된 LTM 시스템으로 만든다.**

측정은 수단이고, 목적은 **문제 발견 → 해결**이다. 1단계에서
"정확도 문제 발견 → adaptive-k로 해결 → 특허"로 이어진 것과 같은 패턴을
성능 축에서 반복하는 것.

### 유리한 조건 2가지

1. MemMachine은 저장 백엔드를 갈아끼울 수 있어(Qdrant/Milvus/SQLite-vec/
   Postgres) **같은 조건 비교 실험대**로 쓸 수 있다 — 문제의 원인 분리에 유리.
2. 사전 코드 분석에서 이미 유력한 병목 후보를 찾아 놨다 —
   **벡터DB가 아니라 Postgres가 먼저 무너질 가능성** (아래 §3).
   실측으로 확인만 하면 바로 개선 대상이 된다.

## 2. 산출물과 성공 기준

**핵심 성공 기준 (과제의 존재 이유)**:
> 사용자 증가에 따른 부하 특성을 규명하고,
> **발견한 문제점 최소 1건을 해결·개선하여 효과를 수치로 입증**한다.
> (1단계의 "정확도 문제 → adaptive-k → 특허" 패턴의 성능판)

| 산출물 | 성공 기준 | 시점 |
|---|---|---|
| ① 병목 진단 + 개선 | 문제점 목록(수치 근거 포함) + 개선 1건 이상 적용·입증 | MVP 후 순차 |
| ② 특허 발굴 | 개선 아이디어에서 신규 발명 1건 이상 (adaptive-k 특허 후속) | 수시 |
| ③ 학회 논문 | 시스템/스토리지 학회 투고 | 2027 상반기 |
| ④ 디바이스 요구사항 리포트 | 멀티유저 메모리 워크로드의 SSD 요구사항 정리 → 스토리지 신규과제로 연결 | 본측정 후 |
| ⑤ 재현 가능한 평가 하네스 | clone→setup→run 이 다른 서버에서 그대로 됨 (upstream 기여 후보) | MVP+1개월 |

**MVP(1개월)의 정의**: 유저 N명(최소 100)이 longmemeval_m 데이터로
동시 적재 + 동시 검색이 돌고, 유저별·단계별 시간이 기록되는 환경.
모니터링(리소스·SSD 계측)은 MVP **다음** 단계.

## 3. 우리가 이미 아는 것 (사전 분석 요약 — 준혁 TL 공유용)

> 상세: `docs/msr/multiuser_eval_plan_longmemeval.md` (쉬운 판),
> `multiuser_eval_design.md` (근거 코드 위치 포함)

**구조**: MemMachine에서 유저 1명 = `session_key` 1개. 저장은
벡터DB(임베딩) + Postgres(대화 원문·메타) 이중 구조.

**핵심 발견 — 코드에서 확인했고 실물 검증이 필요한 것들**:

| # | 발견 | 예상 문제 |
|---|---|---|
| F1 | Postgres에 **유저마다 진짜 테이블 파티션**이 생김 (`LIST (partition_key)`) | 유저 수백~수천에서 파티션 수 폭발 → **1순위 벽 후보** |
| F2 | 파티션 만들기(DDL)는 한 번에 하나씩 | N명 동시 첫 적재 때 줄서기 스파이크 |
| F3 | Postgres 연결 풀 기본 **15개** | 동시 100명이면 DB가 아니라 통로에서 병목 → 측정 전 튜닝 필수 |
| F4 | Qdrant/Milvus는 유저별 통을 안 만들고 **한 통 + 유저 딱지** (벤더 권장 방식) | 유저 수 자체로는 안 터질 것 — F1과 대비되는 그림 |
| F5 | 서버 모드에만 유저 작업공간 캐시 **100개 제한** | 동시 활성 100 초과 시 thrash — 서버 모드로만 관측 가능 |
| F6 | SQLite-vec은 동시 쓰기 불가 | 적재 직렬화 (예상된 결과, I/O 관측은 제일 깨끗) |

**데이터셋 확정**: longmemeval_m — 질문 500개, **질문 1개 = 유저 1명** 매핑.
유저당 대화 세션 ~482개 / turn ~5,057개 / 텍스트 ~5MB. 최대 500유저 실데이터.
질문마다 정답 세션 번호가 있어 검색 품질 채점 + 격리(남의 기억 섞임) 검증 자동화 가능.

**평가 환경 현황: 준비된 것은 없다 — 우리가 만들어야 한다.**

- MemMachine 공식 평가 도구는 전부 **단일 사용자·정확도** 벤치마크
  (locomo / longmemeval / BEAM 등). 유저 수를 늘리며 부하를 재는
  멀티유저 **성능** 평가 환경은 없다.
- 외부에도 멀티유저 에이전트 메모리 벤치마크는 공개된 것이 없다
  → 우리가 만드는 것 자체가 과제의 차별성이자 산출물(§2-⑤).
- 따라서 T1(실측 조사)으로 구조를 확인한 뒤, **T2에서 평가 환경을
  직접 설계·구축**한다 (MVP).

재사용할 수 있는 **재료** (환경이 아니라 부품):

| 재료 | 쓸 곳 |
|---|---|
| longmemeval_m 데이터셋 | "질문 1개 = 유저 1명" 매핑으로 유저 500명분 데이터 |
| 단일 유저 평가 스크립트들 | 적재·검색 코드 부품 (동시성·시간기록은 새로 만들어야) |
| docker compose (Postgres/Neo4j) | DB 기동 골격 (Qdrant/Milvus는 추가 필요) |
| 하네스 소규모 수리본 (오태진 fork) | 라이브러리 모드 정밀 비교용 — upstream PR 예정, T1·T2(서버 모드)와는 무관 |

## 4. 추진 체계 — 2인 역할

```
오태진 (관리·구조)                박준혁 TL (실측·구현)
─────────────────                ─────────────────────
과제 계획서·목표 수치 확정   ──→  [T1] 멀티유저 구조 실측 조사 (1주)
평가 시나리오 정의 (W 튜플)  ──→  [T2] MVP 멀티유저 환경 구축 (2~4주)
결과 해석·논문 스토리        ←──  실측 리포트·측정 데이터
다음 단계(모니터링 환경) 정의 ──→  [T3] 모니터링 가능 환경 (MVP 이후)
```

**코드 기준선**: 준혁 TL은 **MemMachine 메인라인(upstream/main)** 기준으로
진행 (특정 커밋 고정 권장, 현재 `a681abf`). T1·T2는 서버 모드(REST)라
메인라인 그대로 가능. 오태진 측 하네스 수리본은 upstream PR로 제출해
메인라인에 합류시키는 흐름 (머지 전까지 준혁 TL 작업에 영향 없음).

# 부록 A. 박준혁 TL — 첫 태스크 지시서 (T1, 1주)

## T1. MemMachine 멀티유저 구조 실측 조사

**목적**: 코드 분석으로 찾은 병목 후보(위 F1~F4)가 **실물에서 진짜 그런지** 확인.
이 결과가 MVP 설계의 근거이자 **개선 대상 후보 목록**이 됨 — 이 과제의
최종 목표는 측정이 아니라 찾은 문제를 고쳐 차별화 포인트로 만드는 것.

**환경**: 본인 리눅스 서버 + docker (Postgres, Qdrant) +
**MemMachine 메인라인** (upstream/main, 커밋 `a681abf` 고정 권장).

**실행 방식**: 서버 모드 —
```
1. configuration.yml에서 event 백엔드 활성화
   (sample_configs/episodic_memory_config.cpu.sample 의
    "Alternative backend: event" 주석 블록 참고:
    backend: event / vector_store: event_vector_store(qdrant) /
    segment_store: profile_storage(postgres))
2. memmachine-server 기동
3. v2 REST API로 유저 생성·적재·검색
   (유저 1명 = 프로젝트 1개: POST /projects → POST /memories →
    POST /memories/search — docs/openapi.json 참조)
```
적재 스크립트는 curl 반복이든 간단한 python이든 무방. 유저 = `user_000` 형식 권장.

### 확인 항목 (체크리스트)

**A. Postgres — 유저당 파티션이 진짜 생기나 (F1)**
```
1. event 백엔드 설정으로 유저(프로젝트) 10개 적재
2. psql에서 확인:
   \d+ segment_store_sg          -- LIST 파티션 테이블인지
   SELECT count(*) FROM pg_class WHERE relispartition;  -- 유저 수만큼 늘었는지
3. 유저 100 / 500 / 1000개로 늘리며:
   - 새 유저 첫 적재 시간 (파티션 생성 포함) 변화
   - 기존 유저 검색 시간 변화
   - pg_catalog 크기 변화
→ 산출: "파티션 수 vs 성능" 표. 한계가 보이면 그 숫자.
```

**B. 동시 적재 때 파티션 생성이 줄 서나 (F2)**
```
유저 20개를 "동시에" 첫 적재 시작 → 앞 유저 대비 뒷 유저의
첫 적재 지연이 커지는지. (DDL 락 대기 관찰: pg_locks)
```

**C. 연결 풀 15개 제한 (F3)**
```
기본 설정(pool_size 5 + max_overflow 10)에서 동시 요청 50개
→ 풀 대기/타임아웃 발생 확인 → pool_size 50으로 올려 재확인
→ 산출: "측정 전 필수 튜닝값" 권고
```

**D. Qdrant — 정말 한 통인가 (F4)**
```
유저 100개 적재 후:
curl localhost:6333/collections        -- 컬렉션 수가 1개(+registry)인지
컬렉션 상세에서 payload 인덱스(partition_key, is_tenant) 확인
→ 유저 수를 늘려도 컬렉션이 안 늘어나는지 확인
```

**E. 서버 사양 보고** (계획서 반영용)
```
CPU / RAM / SSD 모델·용량·인터페이스 / OS / docker 버전
```

### 산출물

- 실측 리포트 1건 (표 + 로그/스크린샷): F1~F4 각각 "가설대로였다 / 달랐다(어떻게)"
- 한계 숫자: "유저 몇에서 무엇이 몇 배 느려졌다"
- MVP 설계에 반영할 권고 3줄 이내

### 보너스 (여유 있으면)

**F5 미리보기**: 서버 모드에서 유저 150개를 번갈아 검색하면 세션 캐시
(기본 100개)를 넘겨 인스턴스 재생성이 반복되는지 — 로그·지연으로 관찰 가능.

# 부록 B. 오태진 — 첫 태스크 (이번 주)

## T0. 평가 시나리오 1페이지 확정

준혁 TL의 MVP가 "무엇을 만들면 합격인지"를 정의하는 문서. 항목:

1. **워크로드 수치 확정** — 유저 수 스윕 (안: 1/10/50/100/200/500),
   유저당 데이터 (안: m 기본 + s 병행), 동시 활성 비율 (안: 100%/50%/10%)
2. **측정 항목 확정** — 유저별 적재 시간 / 검색 p50·p95·p99 /
   recall / 격리 위반 0건
3. **MVP 합격 기준** — "유저 100, m 데이터, 동시 적재+검색이 돌고
   위 항목이 기록으로 남는다"
4. **하네스 수리본 upstream PR 제출** (Claude 대행 가능) — 머지되면
   메인라인만으로 라이브러리 모드 비교 측정까지 가능해짐.
   머지 전까지 준혁 TL은 서버 모드라 영향 없음
5. **임베딩 키 방침** — 사내 프록시 가능 여부 확인, 불가 시 로컬 임베더 결정

→ 이 문서가 W2부터 준혁 TL의 요구사항 명세가 됨.
