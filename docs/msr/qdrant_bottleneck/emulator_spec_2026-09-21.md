## 1. 요약

이 문서는 Qdrant에 직접 요청을 보내는 부하 도구를 어떻게 만들지 정한다. 도구는 세 프로그램으로 나뉜다. 적재기 `loader` 가 데이터 파일을 읽어 컬렉션을 만들고 세션 키를 붙여 포인트를 넣은 뒤 적재 완료를 판정하고 마스터 사본을 뜨며, 부하기 `driver` 가 부하 구간 동안 검색과 저장과 삭제만 보내고, 제어기 `runner` 가 조건 전환 스크립트 호출과 적재기와 부하기 호출과 구간 경계 스냅샷을 맡는다. 세 프로그램 모두 이 문서의 산출물이다. 조건을 세우는 일 자체는 환경 문서 5.3절의 `run_condition.sh` 가 "조건이 섰다"까지 책임지고, 제어기는 그 뒤를 잇는다(4.7절).

**이 문서는 설계서 4.6절 작업 단계 3(Qdrant 부하 도구 제작) 전체에 해당한다.** 3.1 부하 평가 변수 정리는 3장, 3.2 적재기는 4.2절과 4.5절, 3.3 부하기는 5장과 6장, 3.4 제어기는 4.7절, 3.5 충실도 검증은 7장이다.

**MemMachine 서버를 거치지 않는 이유는 측정 대상이 Qdrant 내부이기 때문이다.** MemMachine을 거치면 임베딩 생성과 세션 관리와 중복 제거가 응답 시간에 함께 섞여 들어오고, 그 비용은 조건마다 달라지므로 메모리 한도를 바꿨을 때 달라진 것이 Qdrant인지 그 앞단인지 가를 수 없게 된다. 또 설계서 4.4절이 요구하는 파라미터 중 필터 통과 비율과 저장 배치 크기와 `wait` 는 MemMachine을 통해서는 임의로 바꿀 수 없다. 대신 MemMachine을 우회한 대가로 요청의 모양이 실제와 달라질 위험이 생기므로, 7장의 충실도 검증이 그 대가를 갚는다.

**설계의 핵심 판단은 셋이다.** 첫째, 적재기와 부하기와 제어기를 별도 프로그램과 별도 컨테이너로 나누고 부하기 컨테이너에 데이터 볼륨을 아예 마운트하지 않는다. 이렇게 하면 함정 대책 3번이 사람의 규율이 아니라 구조로 보장되고 `docker inspect` 한 줄로 확인된다. 둘째, 설계서 4.4절의 파라미터를 데이터 형상과 부하 형상으로 갈라 설정 파일을 둘로 나눈다. 데이터 형상을 바꾸면 적재를 다시 해야 하고 부하 형상은 그렇지 않으므로, 파일 위치가 그 질문에 답하게 만든다. 셋째, 필터 통과 비율 1%에서 99%까지를 이미 색인되는 `_producer_id` 필드에 세션과 독립인 값을 실어 만든다. 새 필드를 만들지 않으므로 payload 인덱스 개수가 11개로 유지되어 MemMachine 구성과 어긋나지 않는다.

**제작 순서에서 가장 먼저 쓸모가 생기는 지점은 M2인 검색 전용 최소 부하기다.** 그것만 나와도 `instrumented_build_2026-09-21.md` 7장의 왜곡 검증이 열리고, 작업 단계 4.5 왜곡 검증이 닫힌다. 다만 그 앞에 M0 바닥 측정을 두어 구현 언어를 실측으로 확정한다.

## 2. 요구사항

### 2.1 반드시 만족해야 할 것

| # | 요구사항 | 어디서 왔나 | 어떻게 확인하나 |
|---|---|---|---|
| R1 | 부하 도구가 데이터 파일을 직접 만지지 않는다 | 설계서 4.3절 대책 3번 | `docker inspect` 의 마운트 목록에 결과 디렉터리 한 줄만 나온다(4.3절) |
| R2 | 도구 자체가 병목이 되지 않는다 | 설계서 1.1절의 포화 판정이 p99 지연을 쓴다 | M0 바닥 측정(8장)과 `driver_peak_cpu_pct`(6장) |
| R3 | 요청의 모양이 MemMachine과 같다 | 설계서 4.4절 충실도 검증 | `driver trace` 와 대조 스크립트(7장) |
| R4 | 동시 요청 수가 입력 변수다 | 설계서 1.1절이 동시 요청 수를 한 칸씩 올린다 | 5.1절의 폐루프 모델 |
| R5 | 한 실행의 조건을 결과만 보고 재구성할 수 있다 | 조건마다 컨테이너를 새로 만들어 실행 횟수가 많다 | `load_config.json` 을 그대로 다시 넣어 재현한다(6장) |
| R6 | 부하기가 계측 창구와 cgroup 계수기를 읽지 않는다 | 설계서 3.3절, 수집 문서 10장 3번 | 허용 API 목록 밖 경로의 요청 수가 0이다(4.4절) |
| R7 | 결과가 `$RAW` 에 떨어지고 `$BENCH` 에 쓰지 않는다 | 수집 문서 9.1절 | `findmnt` 로 두 경로가 다른 장치임을 확인한다 |

### 2.2 R2를 풀어 적는다

**도구의 자체 지연은 측정값에 그대로 섞인다.** 설계서 1.1절의 포화 판정이 p99 지연의 1.5배 상승을 쓰는데, 가비지 수집 정지나 GIL 경합처럼 주기적으로 발생하는 멈춤은 정확히 그 꼬리에 나타난다. 도구가 꼬리를 만들면 포화 판정 자체가 무효가 된다.

합격 기준은 두 가지다. 바닥 지연의 p99가 본 측정 대상 검색의 p50보다 충분히 작아야 하고, 도구가 낼 수 있는 최대 QPS가 본 측정에서 필요한 QPS보다 넉넉히 커야 한다. **"충분히"의 구체값은 지금 정하지 않는다.** 본 측정 대상의 p50을 아직 모르기 때문이며, 여기서 배수를 적으면 지어낸 값이 된다. 첫 스모크 측정 뒤에 정해 설계서 4.4절에 적는다.

**적재기와 제어기는 R2의 적용을 받지 않는다.** 둘 다 부하 구간 밖에서 도는 프로그램이다.

### 2.3 요구사항이 아닌 것

아래는 요구하지 않는다. 지금 만들면 쓰이지 않는 코드가 된다.

- 분산 실행. 부하기는 한 호스트에서 돈다. 설계서 4.1절이 단일 서버 구성을 확정했다.
- 검색과 저장을 별도 워커 풀로 나누는 모드. 5.3절에서 이유를 적는다.
- 결과 시각화. 시계열과 히스토그램 덤프를 남기면 분석은 사후에 한다.
- 조건 전환 자동화. 작업 단계 1.5의 조건 전환 스크립트 `run_condition.sh` 의 몫이며, 제어기는 그 스크립트를 호출만 한다(4.7절).

| `wait` 설정 | 코드가 `wait` 를 넘기지 않으며 qdrant-client 1.19.0 기본값이 `True` 다. 요청마다 WAL 확정을 기다린다 | `qdrant_vector_store.py:316-319, 397-409, 671-675`, qdrant-client `async_qdrant_client.py:836, 1095, 1959`, 트레이스의 쿼리스트링 |
| 저장 배치 크기 | 어댑터에 상한이 없고 한 add 호출의 에피소드 수가 곧 포인트 수(기본 설정에서 에피소드당 1개). 트레이스 관측값은 4건과 2건 | `qdrant_vector_store.py:299-310`, `event_memory.py:280-290`, 트레이스 S4, S5, 부록 4.3절 |
| 저장 실패 처리 | 실패하면 배치를 절반으로 쪼개 대기 없이 재시도한다 | `qdrant_vector_store.py:312-325`, 부록 4.4절 |
| 삭제 | `POST /collections/<coll>/points/delete?wait=true`, 파티션 필터 AND `has_id` | `qdrant_vector_store.py:397-409`, 트레이스 S12, S13 |

**부하 도구의 기본값은 이 표를 그대로 따른다.** 특히 `over_fetch=4` 와 `wait=true` 와 `with_payload=false` 는 사용자가 명시적으로 바꾸지 않는 한 이 값이어야 한다. 셋 다 코드나 트레이스를 읽기 전에는 알 수 없는 값이고, 셋 다 측정 결과를 크게 바꾼다. 셋 모두 부록 8장이 파일과 줄 번호로 확정했다.

### 3.2 파라미터를 두 묶음으로 나눈다

설계서 4.4절이 제어 파라미터 열두 개를 요구한다. 이를 전부 명령행 인자로 받으면 한 줄이 수백 자가 되고, 더 나쁘게는 결과 파일만 보고 그 실행의 조건을 되짚을 수 없게 된다. 또 4.4절 파라미터는 성격이 둘로 갈리는데 섞어 두면 "이 값을 바꾸면 적재를 다시 해야 하는가"를 매번 사람이 판단해야 한다.

| 묶음 | 설계서 4.4절 파라미터 | 누가 쓰는가 | 바꾸면 |
|---|---|---|---|
| 데이터 형상 | 포인트 수, 벡터 차원, 세션 수, 세션당 포인트 수 분포, payload 인덱스 개수 | 적재기 | **적재를 다시 해야 한다** |
| 부하 형상 | 동시 요청 수, 검색 대 저장 비율, `top_k`, 필터 통과 비율, 필터 조합, 저장 배치 크기, `wait` | 부하기 | 적재 없이 바꿀 수 있다 |

이 분할이 곧 적재 경로와 부하 경로의 분리이기도 하다. 설정 파일이 둘로 나뉘므로 위 질문이 파일 위치로 답해진다.

### 3.3 데이터 형상 파라미터

| 파라미터 | 기본값 | 허용 범위 | 비고 |
|---|---|---|---|
| `points` | 없음. 반드시 지정 | 1만부터 1억까지 | 설계서 4.4절 |
| `dim` | 768 | 768, 1024, 1536, 2560 | 설계서 4.5.5절이 2560차원 1억 개는 RAM 1TB에 들어가지 않는다고 적었다 |
| `sessions` | 없음. 반드시 지정 | 1부터 10만까지 | 파티션 키 값의 개수다 |
| `session_size_dist` | `{dist: zipf, s: 1.0}` | `uniform`, `zipf`, `lognormal` | 세션 하나에 포인트를 몇 개 넣는가. 설계서 5.4절이 실제 분포를 미정으로 두었다 |
| `payload_index_count` | 11 | 0부터 11까지 | 3.1절에서 확인한 11개 목록의 앞에서부터 자른다. `sys-partition_key` 는 0일 때도 남긴다 |
| `producer_dial_values` | 100 | 1부터 1000까지 | 3.5절의 선택도 다이얼 |
| `distance` | `Cosine` | `Cosine` | 3.1절에서 확인한 값. 바꿀 이유가 없다 |
| `hnsw.m` | 0 | 고정 | 3.1절에서 확인한 값 |
| `hnsw.payload_m` | 16 | 고정 | 같음 |

`payload_index_count` 를 0으로 주어도 `sys-partition_key` 를 남기는 이유는 그것이 파티션 키라 없으면 필터 자체가 성립하지 않기 때문이다. 설계서 5.3.4절이 payload 인덱스를 빼면 안 된다고 적은 대상도 이 필드다.

**세션 배정은 적재기가 한다.** 적재기가 포인트를 넣으면서 `sys-partition_key` 에 세션 키를 붙이고, 세션 수와 세션당 포인트 수 분포는 위 표의 `sessions` 와 `session_size_dist` 가 정한다. 기본 분포는 위 표대로 zipf에 `s=1.0` 이다. 데이터 문서(`dataset_download_2026-09-21.md`) 3.8절의 세션 라벨 parquet 사전 생성 방식은 폐기되었으며, 라벨 파일을 따로 만들거나 읽지 않는다.

### 3.4 부하 형상 파라미터와 설정 파일

부하 설정 파일의 모양은 아래와 같다. MemMachine 기본값을 따르는 항목과 도구가 정한 항목을 표에서 구분한다.

```yaml
# cond.yaml
condition_tag: mem256_c64          # 결과 디렉터리 이름과 태그에 그대로 쓴다
target:
  url: http://127.0.0.1:6333       # REST. MemMachine 기본값이 prefer_grpc=false 다
  protocol: rest                   # rest 또는 grpc. 기본은 rest
  collection: laion100m
  timeout_ms: 5000                 # MemMachine 실효값(httpx 기본 5초, 3.1절 전송 방식 행, 부록 2.2절). 포화 시 타임아웃도 MemMachine 이 겪는 현상이다
workload:
  mode: closed                     # closed 또는 open. 기본은 closed
  concurrency: 64                  # 4.4 동시 요청 수. 1부터 1000까지
  think_time_ms: 0                 # 폐루프의 생각 시간. 기본 0
  search_write_ratio: [9, 1]       # 4.4 검색 대 저장 비율
  session_skew: {dist: zipf, s: 1.0}
  search:
    top_k: 20                      # 4.4 top_k. 도구가 정한 값. 파이썬 직접 호출 기본값이자 트레이스 관측값. REST 기본은 10. 아래 설명
    over_fetch: 4                  # 확인한 값. limit 은 top_k 의 4배가 된다
    with_payload: false            # 확정값. 어댑터가 리터럴로 고정한다. 부록 5.4절
    with_vector: false             # 확정값. 같은 곳
    filter: partition_only         # partition_only 또는 partition_and_property
    selectivity_pct: 1             # 4.4 필터 통과 비율. 1부터 99까지
  write:
    batch_size: 4                  # 4.4 저장 배치 크기. 1부터 256까지
    wait: true                     # 확인한 값. MemMachine 은 wait=true 다
  delete:
    enabled: false                 # 삭제는 기본으로 섞지 않는다
duration:
  warmup_sec: 60
  measure_sec: 300
```

항목별 출처는 아래와 같다. "MemMachine 기본값" 은 speedkick 소스나 그 클라이언트 기본값에서 나온 값이고, "도구가 정한 값" 은 MemMachine 에 대응하는 고정값이 없어 이 문서가 고른 값이다.

| 항목 | 출처 | 근거 |
|---|---|---|
| `target.protocol: rest`, `target.url` 의 REST 주소 | MemMachine 기본값(`prefer_grpc=False`) | 3.1절 전송 방식 행 |
| `target.timeout_ms: 5000` | MemMachine 실효값(httpx 기본 5초) | 3.1절 전송 방식 행, 부록 2.2절과 8장 |
| `search.over_fetch: 4` | MemMachine 상수 `_EVENT_BACKEND_DEDUP_OVERFETCH` | 3.1절 검색 over-fetch 행 |
| `search.with_payload: false`, `search.with_vector: false` | MemMachine 리터럴 | 3.1절 검색 반환 옵션 행, 부록 5.4절 |
| `search.filter` 의 두 모양 | MemMachine 필터 조립 규칙 | 3.1절 필터 방식 A와 B, 3.5절, 부록 5.3절 |
| `write.wait: true` | qdrant-client 기본값을 MemMachine 이 그대로 씀 | 3.1절 `wait` 설정 행 |
| `search.top_k: 20` | 도구가 정한 값. 이유는 바로 아래 | 부록 5.2절 |
| `write.batch_size: 4` | 도구가 정한 값. 트레이스 S4 관측값이며 MemMachine 에는 상한이 없다 | 3.1절 저장 배치 크기 행, 부록 4.3절 |
| `target.collection`, `workload` 의 나머지 항목, `delete.enabled`, `duration` | 도구가 정한 값. 설계서 4.4절의 스윕 축과 이 문서 5장이 정한다 | 3.2절, 5장 |

**`top_k` 가 20 인 이유.** 파이썬 직접 호출 경로의 기본값이 20 이고 기존 트레이스의 관측값(`limit=80`)도 그 값이기 때문이다(부록 5.2절). REST 경로의 기본 `top_k` 는 10 이므로 REST 기본 검색을 재현할 때는 10 으로 바꾼다.

**명령행으로 덮어쓸 수 있는 것은 스윕 축뿐이다.** `--concurrency`, `--selectivity-pct`, `--out`, `--condition-tag` 넷으로 제한하며, 그 밖의 값을 명령행에서 바꾸려 하면 도구가 이유를 적고 거부한다. 이렇게 해야 사다리 스윕을 한 줄로 돌리면서도 나머지 조건이 고정되어 있음이 보장된다.

**`over_fetch` 를 파라미터로 노출하되 기본값에서 벗어나면 결과에 표시한다.** 설계서 4.4절 목록에는 없는 값이지만 3.1절에서 확인한 대로 실제 `limit` 을 정하는 값이라, 노출하지 않으면 충실도를 조용히 깨뜨릴 수 있다.

### 3.5 필터 통과 비율 1%에서 99%까지를 만드는 방법

설계서 4.4절은 필터 통과 비율을 1%에서 99%까지 요구하는데 **파티션 키 필터만으로는 이 범위를 만들 수 없다.** 세션이 10만 개면 세션 하나가 전체의 0.001%이고, 이는 설계서 5.1절이 직접 지적한 문제다. 세션 수를 줄여 통과 비율을 올리면 세션 수라는 다른 축이 함께 움직여 버려서 "통과 비율만 바꿨을 때 무엇이 달라지는가"를 물을 수 없게 된다.

**세션과 독립인 축이 하나 더 필요하다.** 그런데 그 축을 위해 새 payload 필드를 만들어 색인하면 payload 인덱스가 12개가 되어 3.1절에서 확인한 11개와 달라진다. 설계서 0.3절이 지적한 대로 색인 개수는 저장 비용에 직접 들어가므로 이 차이를 만들면 안 된다.

**그래서 이미 색인되는 필드에 다이얼을 싣는다.** `_producer_id` 는 keyword로 색인되며 트레이스 S7에서 실제로 필터 조건으로 쓰인다. 적재기가 이 필드에 세션과 독립인 값을 넣는다.

```
적재기: 포인트마다 _producer_id 를 "p00" 부터 "p99" 까지 100개 값 중 하나로
        균등하게, 세션과 독립적으로 배정한다

부하기: 통과 비율 k% 를 원하면 그 100개 중 k 개를 골라 필터에 넣는다.
        모양은 부록 5.3절의 조립 규칙(=, OR, AND)을 그대로 따른다
        k=1  이면  {"must":[{"key":"_producer_id","match":{"value":"p00"}}]}
        k=2  이면  {"should":[{"must":[{"key":"_producer_id","match":{"value":"p00"}}]},
                            {"must":[{"key":"_producer_id","match":{"value":"p01"}}]}]}
        k=3  이면  {"should":[{"should":[{"must":[{"key":"_producer_id","match":{"value":"p00"}}]},
                                        {"must":[{"key":"_producer_id","match":{"value":"p01"}}]}]},
                            {"must":[{"key":"_producer_id","match":{"value":"p02"}}]}]}
        k 가 하나 늘 때마다 왼쪽 가지가 한 단계 더 깊어진다
```

**평평한 `should` 배열 하나가 아니다.** MemMachine 의 파서는 `OR` 을 이항 트리로 만들고 어댑터는 하위 Filter 를 평탄화하지 않으므로, 잎마다 `must` 로 감싸이고 k 가 3 이상이면 `should` 안에 `should` 가 다시 중첩된다(부록 5.3절, `qdrant_vector_store.py:103-106`). k=2 의 모양이 트레이스 S7 과 같다. 부하기는 이 중첩 모양을 그대로 만들며, Qdrant 가 평평한 배열과 이 모양을 같은 비용으로 처리하는지는 확인하지 않았다(부록 11장).

**필터 조합 두 가지가 여기서 자연스럽게 나온다.**

| 조합 | 필터 모양 | 통과 비율의 의미 |
|---|---|---|
| `partition_only` (방식 A) | `must:[파티션]` | 세션 크기를 전체로 나눈 값. 세션 수와 세션 크기가 정한다 |
| `partition_and_property` (방식 B) | `must:[{must:[파티션]},<다이얼 Filter>]`. 다이얼 Filter 는 k=1 이면 `{must:[match]}`, k 가 2 이상이면 위의 이항 중첩 `should` | 세션 안에서 k%. 절대 건수는 세션 크기에 k/100 을 곱한 값 |

**비율과 절대 건수를 모두 기록한다.** 설계서 0.2절이 말하는 갈림길, 곧 전수 비교인가 그래프 탐색인가는 카디널리티 추정값이 `full_scan_threshold` 를 넘느냐로 갈리므로 비율만이 아니라 절대 건수가 판정에 필요하다. `run.json` 에 `selectivity_pct` 와 `expected_matching_points` 를 함께 적는다.

**실제로 어느 경로를 탔는지는 사후에 확인한다.** 설계서 4.5.2절이 적은 대로 `/telemetry` 9칸 중 어디에 시간이 쌓였는지를 보면 되고, 계측 빌드에서는 S1부터 S6이 0인지 아닌지로도 갈린다(`instrumented_build_2026-09-21.md` 11장).

**검증 기준.** `selectivity_pct` 를 1, 10, 50, 99로 바꿔 돌렸을 때 `/telemetry` 의 경로별 호출 수가 전수 비교에서 그래프 탐색으로 옮겨 가는 지점이 보이고, payload 인덱스 개수는 네 조건 모두 11개로 같다.

## 4. 구조

### 4.1 세 프로그램으로 나눈다

**함정 대책 3번을 규율이 아니라 구조로 보장하기 위해서다.** 한 프로그램이 적재와 부하를 모두 하면 "이번 실행에서는 파일을 안 읽었다"를 사람이 확인해야 하고, 그 확인은 언젠가 빠진다. 프로그램을 나누고 컨테이너 마운트 목록을 다르게 주면 부하기는 파일을 읽고 싶어도 읽을 수 없다.

| 프로그램 | 데이터 파일 접근 | Qdrant 저장소 접근 | Qdrant API | 언제 도는가 |
|---|---|---|---|---|
| 적재기 `loader` | 읽기 가능 | 마스터 사본 생성만(적재 완료 뒤, 부하 구간 밖) | 컬렉션 생성, 색인 생성, 대량 upsert, 적재 완료 판정 조회 | 부하 구간 이전에만 |
| 부하기 `driver` | **접근 없음** | **접근 없음** | 검색, 저장, 삭제만 | 부하 구간에만 |
| 제어기 `runner` | 읽기 가능(질의 파일) | 직접 접근 없음. 복원은 `run_condition.sh` 호출로 한다 | 관리 창구 조회(스냅샷), `run_condition.sh` 와 적재기와 부하기 호출 | 부하 구간 밖에서 |

**적재기는 부하기가 아니다.** 적재기는 처리량이 측정 대상이 아니므로 파이썬으로 충분하고, 오히려 parquet과 big-ann `.bin` 같은 파일 형식 처리가 쉬운 쪽이 낫다. 적재기가 하는 일은 `instrumented_build_2026-09-21.md` 6.3절이 curl로 수동으로 하던 것을 자동화한 것이다. 포인트를 넣으면서 세션 키를 붙이는 세션 배정(3.3절)과 적재 완료 판정(`loader verify`)과 적재 직후의 마스터 사본 생성(`loader master`)까지가 적재기 몫이다. 데이터 문서 3.8절의 세션 라벨 파일 방식은 폐기되었다.

**제어기도 이 문서의 산출물이다.** 작업 단계 3.4에 해당한다. 조건을 세우는 일은 `environment_setup_2026-09-21.md` 5.3절의 `run_condition.sh` 가 앞 조건 폐기와 작업본 복원과 캐시 비우기와 컨테이너 재생성과 게이트 통과까지를 한 묶음으로 수행해 "조건이 섰다"를 출력하는 자리까지 책임지고, 제어기는 그 스크립트를 호출한 뒤 적재기 호출과 완료 대기, 마스터 사본 생성, 구간 경계 스냅샷, 부하기 호출, 저장 부하 뒤 마스터 복원을 맡는다. 환경 문서 5.4절이 제어기 몫으로 받아 적은 의무 네 가지는 4.7절이 받는다. 수집기를 띄우고 스냅샷을 찍는 순서는 수집 문서 11.2절에 있고 제어기는 그 순서를 그대로 따른다.

### 4.2 명령행 계약

```
loader load    --config load.yaml
loader verify  --config load.yaml
loader master  --config load.yaml
driver floor   --concurrency N --duration S --out DIR
driver run     --config cond.yaml [--concurrency N] [--selectivity-pct P] [--condition-tag T] --out DIR
driver ladder  --config cond.yaml --rungs 1,2,4,8,16 --out DIR
driver trace   --config cond.yaml --n 100 --out DIR
driver recall  --config cond.yaml --queries 200 --out DIR
```

`--out` 은 파일이 아니라 디렉터리다. 수집 문서 9.1절이 조건 하나를 디렉터리 하나로 두었으므로 부하 도구의 산출물은 그 아래 `load/` 에 들어간다. 6장에서 그 안의 파일을 정한다.

**적재기 세 명령의 몫.** `loader load` 는 컬렉션과 색인을 만들고 세션 키와 `_producer_id` 를 붙여 포인트를 넣는다. `loader verify` 는 수집 문서 6.2절의 적재 완료 판정 네 조건이 연속 60초 유지되는지 관리 창구로 확인하고, 포인트 수와 세션 수와 payload 인덱스 개수가 `load.yaml` 과 같은지를 보고한다. 이 판정을 적재기가 하는 이유는 "요청을 다 보냈다"와 "적재가 끝났다"가 다르기 때문이며, 그 차이는 수집 문서 6.2절에 있다. `loader master` 는 `verify` 통과 뒤에만 돌며, `preparation_2026-09-21.md` 5.7절 블록의 앞 절반, 곧 작업본을 마스터로 복사하고 `du -sb` 로 두 크기가 같은지 확인하는 일을 한다. 마스터가 이미 있으면 덮어쓰지 않고 이유를 적고 멈춘다. 세 명령 모두 부하 구간 밖에서만 돈다.

**부하기는 파일 경로를 받는 인자를 설정 파일과 출력 디렉터리 말고는 갖지 않는다.** 질의 벡터도 경로가 아니라 표준 입력으로 받는다. 5.4절에 이유가 있다.

### 4.3 대책 3번의 구조적 보장

**부하기 컨테이너에는 `$RAW` 도 `$BENCH` 도 마운트하지 않는다.** 결과를 쓸 출력 디렉터리 하나만 붙인다. 경로 변수는 `preparation_2026-09-21.md` 1.3절의 것을 그대로 쓴다.

아래는 부하기 컨테이너를 띄우는 블록이다. `$RUNDIR` 이 수집 문서 9.1절에서 만든 조건 디렉터리이고, `$LOADGEN_CPUS` 가 `environment_setup_2026-09-21.md` 6.3절이 산출하는 부하 생성기 몫의 코어 범위다. 그 절이 Qdrant 코어의 SMT 형제를 모두 뺀 뒤 앞에서부터 32개를 고르는 규칙과 그 산출 블록을 이미 갖고 있으므로, 이 문서는 범위를 따로 정하지 않고 그 값을 받아 쓴다. 정상이면 컨테이너 ID 한 줄이 나온다.

```bash
if [ -z "${RUNDIR:-}" ] || [ -z "${LOADGEN_CPUS:-}" ]; then
  echo "RUNDIR 또는 LOADGEN_CPUS 가 비어 있다. 수집 문서 9.1절과 환경 문서 6.3절을 먼저 마친 뒤 이 블록을 다시 실행한다."
else
  mkdir -p "$RUNDIR/load"
  docker run -d --name qdrant-driver \
    --network host \
    --cpuset-cpus "$LOADGEN_CPUS" \
    --memory 4g --memory-swap 4g \
    --mount type=bind,source="$RUNDIR/load",target=/out \
    qdrant-driver:1 run --config /out/cond.yaml --out /out
  echo "컨테이너를 띄웠다. 다음 블록으로 마운트 목록을 확인한다."
fi
```

**바인드 마운트를 `-v` 가 아니라 `--mount type=bind` 로 붙인다.** 환경 문서 4.1절이 세운 규칙이며, `-v` 는 원본 경로가 없으면 디렉터리를 조용히 만들어 버리고 `--mount` 는 실행 자체를 실패시킨다. 여기 붙는 것은 저장소가 아니라 결과 디렉터리라 함정과는 무관하지만, 두 문서가 같은 표기를 쓰는 편이 다음 사람이 규칙을 예외로 오해할 여지를 없앤다.

**부하기 컨테이너에도 메모리 한도를 건다.** 환경 문서 6.3절이 측정 창을 열기 전에 실행 중인 컨테이너를 모두 훑어 한도 없는 것이 하나도 없어야 한다고 요구하므로, 한도를 빠뜨리면 부하기 자신이 그 검사에 걸려 측정에 들어가지 못한다. 같은 절의 셋째 항목도 부하 생성기와 수집기가 자신의 메모리 한도를 따로 걸 것을 요구한다. `--memory-swap` 을 `--memory` 와 같은 값으로 주어 스왑 경로를 막는 방법은 환경 문서 3.4절이 Qdrant 컨테이너에 쓴 것과 같다.

**4GiB라는 값은 부하기가 실제로 쓰는 메모리에서 나왔다.** 가장 큰 항목이 5.4절의 질의 집합이며, 최대 차원인 2560에서 10만 개를 올리면 `100000 × 2560 × 4` 로 1,024,000,000바이트, 곧 0.95GiB다. 다음이 동시 요청 1000개분의 요청과 응답 버퍼인데, 2560차원 float32를 JSON 텍스트로 적으면 요청 본문이 30KB 남짓이고 `with_payload=false` 인 응답은 그보다 훨씬 작으므로 1000개를 모두 더해도 0.1GiB 안팎이다. 나머지는 `requests.tsv` 쓰기 버퍼와 HDR 히스토그램이며 둘 다 고정 크기라 수십 MiB에 그친다. 합이 1.1GiB 남짓이므로 세 배가 넘는 여유를 두어 4GiB로 잡는다. 한도에 닿으면 부하기가 OOM으로 죽어 그 실행을 통째로 잃으므로 여유를 크게 두었고, M0 바닥 측정에서 실제 상주 메모리를 재어 이 값을 조정한다. 실제 상주량은 6.2절의 `query_set_rss_bytes` 로 남는다.

확인은 아래 한 블록으로 한다. 출력에 결과 디렉터리 한 줄만 나와야 한다.

```bash
if docker inspect qdrant-driver >/dev/null 2>&1; then
  docker inspect qdrant-driver --format '{{range .Mounts}}{{.Source}} => {{.Destination}}{{"\n"}}{{end}}'
else
  echo "qdrant-driver 컨테이너가 없다. 앞 블록으로 컨테이너를 띄운 뒤 이 블록을 다시 실행한다."
fi
```

`$BENCH` 나 원본 데이터 경로가 보이면 대책 3번 위반이므로 **그 실행의 측정값을 버린다.**

**대책 3번의 범위를 정확히 해 둔다.** 함정은 컨테이너가 서비스하는 파일을 호스트나 다른 cgroup이 먼저 읽는 것이다. 따라서 금지의 핵심은 Qdrant 저장소 디렉터리인 `$BENCH` 이며, 그 디렉터리에 부하기가 닿지 않으면 대책은 충족된다. 다만 판정을 단순하게 유지하기 위해 원본 데이터 디렉터리도 함께 막는다. 예외를 하나 두면 다음번에 예외가 둘이 된다.

**결과 디렉터리를 `$RUNDIR/load` 로 두는 것은 대책 3번과 충돌하지 않는다.** 수집 문서 9.1절이 결과를 `$RAW` 에 쓰기로 했고 준비 문서 5.3절이 `$RAW` 와 `$BENCH` 를 서로 다른 블록 장치에 두었으므로, 부하기가 쓰는 페이지는 Qdrant가 읽는 장치의 통계에 섞이지 않는다.

### 4.4 호출해도 되는 API를 목록으로 제한한다

부하기는 아래 셋만 호출한다.

```
POST /collections/<coll>/points/query/batch
PUT  /collections/<coll>/points?wait=<bool>
POST /collections/<coll>/points/delete?wait=<bool>
```

컬렉션 생성과 색인 생성과 스냅샷은 적재기 몫이고, `/telemetry` 와 `/metrics` 와 `/stage_timings` 와 `/collections/<coll>` 계열 조회는 전부 제어기 몫이다. 설계서 3.3절과 수집 문서 8.1절이 적은 대로 `/metrics` 읽기가 모든 세그먼트에 읽기 잠금을 걸어 그 자체가 부하이므로, 부하기가 이를 건드리면 측정 대상을 오염시킨다.

**부하기는 자기가 보낸 경로별 요청 수를 세어 `run.json` 의 `endpoint_counts` 에 남긴다.** 목록 밖 경로가 0이 아니면 그 실행을 무효로 본다.

### 4.5 부하 구간에 적재기가 살아 있으면 안 된다

제어기가 부하 시작 직전에 확인한다. 적재기가 아직 돌고 있으면 그 프로세스가 데이터 파일을 읽어 페이지 캐시를 자기 앞으로 과금하므로 함정이 그대로 재발한다.

```bash
if pgrep -f 'loader load' > /dev/null 2>&1; then
  echo "적재기가 아직 돌고 있다. 끝날 때까지 기다린 뒤 부하를 건다."
else
  echo "적재기 없음. 부하를 걸어도 된다."
fi
```

### 4.6 구현 언어

**부하기는 Rust를 권고하고, 적재기와 제어기는 파이썬으로 한다.** 다만 이 권고는 M0 바닥 측정(8장)으로 확정하며, 그 전에는 확정으로 쓰지 않는다.

부하기를 Rust로 권고하는 근거는 넷이다. 첫째, 목표 동시 요청 수가 1000이다(설계서 4.4절). 파이썬 단일 프로세스는 GIL 때문에 요청 직렬화와 응답 처리를 한 코어에서 하며, 768차원 float32 질의 벡터 하나를 JSON으로 적는 작업이 요청마다 반복된다. 프로세스를 여러 개로 나누면 처리량은 늘지만 프로세스마다 다른 시점에 가비지 수집이 일어나 꼬리가 오히려 지저분해진다. 둘째, Rust 도구사슬이 이미 필요하다. 계측 빌드가 v1.19.1 소스를 빌드하므로(`instrumented_build_2026-09-21.md` 5장) 같은 빌드 이미지를 재사용할 수 있고 새 도구사슬을 서버에 추가할 필요가 없다. 셋째, 필요한 것이 전부 있다. 비동기 실행기는 `tokio`, HTTP 클라이언트는 `reqwest`, 지연 분포는 `hdrhistogram` 이다. 넷째, 가비지 수집이 없으므로 꼬리 지연에 도구가 기여하는 성분이 구조적으로 작다.

**차선은 Go다.** 가비지 수집 정지가 밀리초 아래라 검색 지연 규모에서 허용 가능하고 팀이 읽기 쉽다. 다만 `preparation_2026-09-21.md` 4장의 설치 목록에 Go 도구사슬이 없어 추가 설치가 필요하다.

**전송은 REST로 고정한다.** 3.1절에서 확인한 대로 MemMachine의 `prefer_grpc` 기본값이 `False` 이므로 실제 운영은 REST다. gRPC로 바꾸면 Qdrant의 16코어 안에서 일어나는 JSON 파싱 비용이 사라져 측정 대상이 달라진다. `protocol` 파라미터로 노출하되 기본값은 REST이며, gRPC와의 차이는 한 번만 재서 기록한다.

**Qdrant 공식 클라이언트를 쓰지 않는다.** 요청 본문을 직접 조립해야 7장의 대조가 가능하고, 클라이언트 라이브러리가 넣는 기본값이 충실도를 조용히 깨뜨리는 일을 막을 수 있다.

### 4.7 제어기

**제어기 `runner` 는 이 문서의 산출물이며 작업 단계 3.4에 해당한다.** 환경 문서 5.3절의 `run_condition.sh` 가 "조건이 섰다"를 출력한 자리부터 그 조건의 결과 디렉터리를 봉인할 때까지가 제어기의 범위다. 조건을 세우는 아홉 단계는 그 스크립트가 하고 제어기는 호출만 한다. 4.6절대로 파이썬으로 만든다.

조건 하나에 대해 제어기가 하는 일은 아래 순서다. 각 항목이 무엇을 하는지는 이미 다른 절이 정했으므로 여기서는 순서와 호출만 고정한다. 순서 번호는 (1)부터 (7)까지로 부르며 작업 단계 번호나 제작 순서 M0부터 M6까지와는 다른 것이다.

```
(1) run_condition.sh 호출        환경 문서 5.3절. RELOAD 기본값은 copy 이고 마스터가 없으면 ingest 로 부른다.
                                 "조건이 섰다" 를 확인한 뒤 수집 문서 11.1절대로 CG, IODEV, DISKDEV 를 잡고,
                                 수집 문서 9.1절의 결과 디렉터리를 만들고 수집기를 띄운다 (수집 문서 11.2절).
                                 snap 00_start
(2) 적재기 호출과 완료 대기       RELOAD=ingest 이면 loader load 뒤 loader verify.
                                 RELOAD=copy  이면 loader verify 만. 복원된 작업본이 수집 문서 6.2절의 네 조건을
                                 만족하는지를 관리 창구로 확인한다.
                                 끝나면 4.5절대로 적재기 프로세스가 남아 있지 않은지 확인한다.
(3) 마스터 사본 생성              마스터가 없을 때 한 번만 loader master 를 부른다 (준비 문서 5.7절).
                                 마스터를 뜬 뒤에는 run_condition.sh 를 RELOAD=copy 로 다시 불러 (1)부터 다시 시작한다.
(4) snap 10_ingest_end           SNAP_RESET=1 (수집 문서 6.3절)
(5) 부하기 호출(사다리)           질의 파일을 읽어 부하기의 표준 입력으로 흘려 넣고 driver run 을 부른다 (5.4절).
                                 단마다 driver run 을 한 번씩 부르고, 호출 사이에 부하가 멈춘 상태에서
                                 snap 2N_step_<n> 을 SNAP_RESET=1 로 찍는다. 올림 사다리 뒤에 내림 사다리 (6.4절).
                                 스냅샷마다 6.5절의 묶음 파일을 곁들인다.
(6) 꼬리 구간과 봉인              정리 작업 소진 대기, snap 90_tail_end 를 SNAP_RESET=0 으로, 수집기 정지, 봉인
                                 (수집 문서 11.2절과 11.3절).
(7) 저장 부하 뒤 마스터 복원      저장 부하가 섞인 실행이었으면 다음 조건을 세우기 전에 run_condition.sh 를
                                 RELOAD=copy 로 다시 부른다. 호스트가 마스터 사본을 작업본으로 복사한 뒤 시스템
                                 캐시를 비우고, 컨테이너를 새로 띄워 처음 읽게 하며, 게이트 A (캐시 잔류 없음) 와
                                 게이트 C (컨테이너 앞으로 디스크 읽기 과금) 를 다시 통과하는 것이 그 안에 들어 있다
                                 (환경 문서 5.4절과 5.5절).
```

**(3)에서 마스터를 뜬 뒤 조건을 다시 세우는 이유.** `run_condition.sh` 의 8단계 게이트 C 판정은 `RELOAD=copy` 경로에서만 실행되고 `ingest` 경로는 그 판정을 건너뛴다(환경 문서 5.3절). 또 마스터 생성은 호스트가 작업본 전체를 읽고 한 벌을 더 쓰는 일이라 그 직후의 호스트 캐시 상태가 다른 조건과 다르다. 그래서 측정은 게이트를 통과한 `copy` 조건에서만 한다. 마스터 생성은 부하 구간 밖에서만 하며, 부하 구간 뒤에 뜨면 저장 부하가 넣은 포인트가 마스터에 섞인다.

**부하기 컨테이너는 4.3절의 블록과 같은 마운트와 한도로 띄운다.** 다만 (5)에서 표준 입력을 흘려 넣어야 하므로 제어기는 `-d` 가 아니라 `-i` 로 앞에서 돌리고 단이 끝나면 컨테이너를 지운다. 4.3절의 블록은 마운트 목록을 확인하는 용도이며 마운트와 한도의 값은 두 곳이 같아야 한다.

**환경 문서 5.4절의 의무 네 가지를 여기서 받는다.** 그 표의 근거는 모두 이 문서에 있으며, 위 순서에서의 자리는 아래와 같다.

| 환경 문서 5.4절의 의무 | 위 순서에서의 자리 | 근거 |
|---|---|---|
| 1. 부하를 걸기 직전에 적재기가 끝났는지 확인한다 | (2)의 끝 | 4.5절 |
| 2. 질의 파일을 읽어 부하기의 표준 입력으로 흘려 넣는다 | (5) | 5.4절 |
| 3. 사다리를 제어기가 돌고 단 사이에 경계 스냅샷을 찍는다 | (5) | 6.4절, 수집 문서 6.4절 |
| 4. 저장 부하가 섞인 실행이 끝나면 마스터에서 복원한다 | (7) | 5.3절, 준비 문서 5.7절 |

**제어기는 부하 구간에 아무것도 하지 않는다.** 부하기가 도는 동안 제어기는 `driver run` 의 종료만 기다린다. 스냅샷과 창구 조회는 전부 부하가 멈춘 사이에 하며, 그 이유는 수집 문서 6.1절에 있다. 제어기가 `manifest.json` 을 만들 때 `run.json` 에서 가져다 쓰는 항목은 6.2절에 있다.

**검증 기준.** 조건 하나를 제어기로 돌린 뒤 `$RUNDIR` 아래에 수집 문서 9.1절의 디렉터리 구조와 6.1절의 `load/` 산출물과 `snap/` 의 경계 스냅샷이 모두 남고, 스냅샷 이름의 순서가 위 (4)부터 (6)까지와 같으며, 저장 부하가 섞인 실행 뒤에 다음 조건의 `condition.log` 에 `RELOAD=copy` 복원과 게이트 A 와 게이트 C 통과가 찍혀 있다.

## 5. 워크로드 모델

### 5.1 도착 모델은 폐루프가 기본이다

설계서 1.1절의 포화 판정이 동시 요청 수를 한 칸씩 올리는 것이므로 **동시 요청 수가 제어 변수여야 한다.** 개루프, 곧 고정 도착률에서는 동시 요청 수가 결과이지 입력이 아니어서 그 판정 규칙을 적용할 수 없다.

기본은 폐루프다. 워커 N개가 각자 요청을 보내고 응답을 기다린 뒤 다음 요청을 보낸다. N이 곧 설계서 4.4절의 동시 요청 수다. 선택적으로 지수분포 생각 시간 `think_time_ms` 를 넣어 도착을 포아송에 가깝게 만들 수 있게 하되 기본값은 0이다.

개루프 모드 `mode: open` 은 보조로 둔다. 포화 이후에 대기열이 어떻게 자라는지를 보려면 필요하다.

**조정된 누락을 드러내는 방법은 이미 정해져 있다.** 수집 문서 9.3절이 `requests.tsv` 에 `t_plan` 과 `t_send` 를 따로 남기고 포화 판정을 `t_recv - t_plan` 으로 하라고 적었다. 부하기는 폐루프에서도 `t_plan` 을 기록한다. 폐루프에서 `t_plan` 은 직전 요청의 응답을 받은 시각에 생각 시간을 더한 값이며, 생각 시간이 0이면 `t_send` 와 거의 같아진다. 이 경우 두 값이 같다는 사실 자체가 기록되어야 나중에 해석할 수 있다.

### 5.2 세션 접근 치우침

**치우침이 페이지 캐시의 작업 집합 크기를 정하고, 그 작업 집합이 곧 메모리 축 실험이 보려는 대상이다.** 치우침을 주지 않으면 적재한 전체가 작업 집합이 되어 어느 메모리 한도에서도 똑같이 무너진다.

Zipf를 기본으로 하고 지수 `s` 를 파라미터로 노출한다. `s=0` 이면 균등이고 `s` 가 커질수록 소수 세션에 몰린다.

**세션당 포인트 수 분포는 이것과 다른 축이며 적재기 몫이다. 둘을 섞지 않는다.**

| 파라미터 | 소속 | 무엇을 정하는가 |
|---|---|---|
| `session_skew.s` | 부하기 | 어느 세션을 얼마나 자주 **검색하는가** |
| `session_size_dist` | 적재기 | 세션 하나에 포인트를 몇 개 **넣는가** |

**검증 기준.** `session_skew.s` 를 0과 1.0으로 바꿔 돌리면 같은 메모리 한도에서 `memory.stat` 의 `workingset_refault_file` 이 뚜렷이 달라진다.

### 5.3 검색과 저장의 혼합

**워커 풀 하나를 두고 요청마다 가중 추첨한다.** 설계서 5.1절 (가)에서 동료에게 받기로 한 값이 "검색 9 저장 1" 형태의 비율이므로 그 값을 그대로 넣을 수 있는 모양이어야 한다. 풀을 검색용과 저장용으로 나누면 "동시 요청 수 64"가 무엇을 뜻하는지 애매해진다.

**달성된 비율을 결과에 기록한다.** 저장이 샤드당 워커 하나로 직렬화되므로(설계서 0.3절) 부하가 높아지면 의도한 비율과 달성 비율이 벌어지는데, 그 벌어짐 자체가 저장 쪽 포화의 신호다.

분리 풀 모드는 나중에 필요해지면 추가한다. 지금 만들지 않는다.

**저장 부하가 쓰는 벡터.** 부하기는 파일을 읽지 못하므로 시작 시 받아 둔 질의 집합의 벡터를 재사용하고 작은 난수 섭동을 더해 완전한 중복을 피한다. 합성 난수 벡터를 쓰지 않는 이유는 설계서 4.5.1절이 설명한 대로 군집 구조가 없으면 옵티마이저가 만드는 그래프가 실제와 달라지기 때문이다.

**저장 부하는 데이터를 오염시킨다.** 넣는 포인트는 별도 id 대역과 payload 표식을 갖게 하고, 저장 부하가 섞인 실행 뒤에는 제어기가 `preparation_2026-09-21.md` 5.7절의 마스터 복원을 반드시 수행한다. 실제 복원은 `run_condition.sh` 를 `RELOAD=copy` 로 다시 부르는 것으로 하며 4.7절 순서 (7)에 있다. 그 스크립트 안에서 호스트가 마스터 사본을 작업본으로 복사한 뒤 시스템 캐시를 비우고, 컨테이너를 새로 띄워 데이터 페이지를 처음 읽게 하며, 게이트 A(캐시 잔류 없음)와 게이트 C(컨테이너 앞으로 디스크 읽기 과금)로 그 사실을 증명한다.

### 5.4 질의 벡터 공급 경로

질의 벡터는 어딘가에서 와야 하는데, 부하기가 파일을 읽으면 대책 3번을 깨고 난수로 만들면 설계서 4.5.1절이 경고한 대로 고차원에서 거리가 모두 같아져 그래프 경로의 지연과 리콜이 실제를 예측하지 못한다. **그래서 파일을 읽지 않으면서 실제 임베딩을 쓰는 경로가 필요하다.**

```
제어기: 질의 파일(데이터셋에 딸린 질의 집합)을 읽는다
        그 내용을 부하기 컨테이너의 표준 입력으로 흘려 넣는다
부하기: 표준 입력에서 질의 벡터 M개를 읽어 메모리에 올린다
        부하 구간 동안 그 배열에서 골라 쓴다
```

표준 입력을 쓰면 부하기 컨테이너에 마운트를 하나도 추가하지 않아도 되고, 4.3절의 `docker inspect` 확인이 계속 유효하다.

**M을 작게 유지한다.** 질의 집합이 크면 부하기 프로세스가 호스트 메모리를 많이 쓰고, 그만큼 호스트 여유가 줄어 Qdrant 컨테이너 바깥의 조건이 조건마다 달라질 수 있다. 768차원 float32 기준 10만 개는 `100000 × 768 × 4` 로 계산하면 307,200,000바이트이며, 1TB 호스트에서는 무시할 수 있는 크기다. M과 실제 상주 메모리를 `run.json` 에 적는다.

**질의 집합은 적재한 포인트와 겹치지 않아야 한다.** 적재한 벡터를 그대로 질의로 쓰면 가장 가까운 이웃이 자기 자신이라 탐색이 즉시 끝나고 실제 경로와 달라진다. 데이터셋에 딸린 질의 파일을 쓰고, 없으면 적재에서 제외한 홀드아웃 구간을 쓴다.

**이 경로가 함정에 걸리지 않는 이유를 명시해 둔다.** 질의 파일은 Qdrant 저장소인 `$BENCH` 에 들어가지 않으므로 호스트가 이를 읽어 페이지 캐시에 올려도 Qdrant 컨테이너의 cgroup 과금과 무관하다. 함정은 컨테이너가 서비스하는 파일을 다른 cgroup이 먼저 읽을 때 생긴다.

## 6. 출력과 부하 상승 방식

### 6.1 어디에 무엇을 남기나

**출력 위치와 요청 로그의 스키마는 수집 문서 9.1절과 9.3절이 이미 정했다. 이 문서는 거기에 더할 세 가지를 정한다.** 부하 도구의 산출물은 전부 `$RUNDIR/load/` 아래에 들어간다.

```
$RAW/results/<RUN_ID>/load/
├── requests.tsv         요청 한 건이 한 줄. 스키마는 수집 문서 9.3절
├── load_config.json     유효 설정 전문. 수집 문서 9.1절이 요구한 파일
├── run.json             환경 지문과 총계. 이 문서가 정한다
├── series.csv           1초 간격 시계열. 이 문서가 정한다
└── hist/
    ├── search.hgrm      HDR 히스토그램 덤프. 이 문서가 정한다
    └── write.hgrm
```

**세 갈래로 남기는 이유가 있다.** 설계서 2.1절이 평균을 쓰지 않고 p50과 p95와 p99를 쓰겠다고 못 박았고 1.1절의 포화 판정이 p99를 직접 쓴다. 그런데 높은 QPS에서 모든 표본을 배열에 담으면 메모리가 폭증하고 워커별로 나눠 담으면 합칠 수 없다. 또 한 실행에서 값 하나만 남기면 옵티마이저가 도는 구간과 안 도는 구간이 뭉개져 나중에 잘라낼 수 없다.

| 파일 | 왜 필요한가 |
|---|---|
| `run.json` | 조건을 나중에 되짚을 수 있다 |
| `series.csv` | 구간을 사후에 잘라낼 수 있다 |
| `hist/*.hgrm` | 임의 분위수를 다시 뽑을 수 있고 워커별 히스토그램을 합칠 수 있다 |

HDR 히스토그램을 쓰는 이유가 셋이다. 고정 메모리로 동작해 동시성 1000에서도 커지지 않는다. 워커가 여럿이어도 합칠 수 있어 다중 프로세스 구현으로 바뀌어도 집계 코드가 그대로다. 사후에 p99.9가 필요해져도 다시 돌리지 않는다.

**`series.csv` 와 `hist/` 는 `requests.tsv` 와 겹치지만 중복이 아니다.** `requests.tsv` 는 요청 한 건이 한 줄이라 높은 QPS에서 파일이 매우 커진다. 그 비용이 측정을 방해하는 것으로 드러나면 표본을 솎아야 하는데, 그때도 `series.csv` 와 `hist/` 는 모든 요청을 세어 만든 값이라 정확도를 잃지 않는다. 솎을지 여부와 그 비율은 첫 스모크 측정에서 정하고 `run.json` 에 적는다. 9장에 위험으로 옮겨 적었다.

`series.csv` 의 열은 아래와 같다.

```
t_sec,op,sent,ok,err,timeout,inflight,p50_us,p95_us,p99_us,max_us
```

### 6.2 `run.json` 에 반드시 들어가야 하는 것

수집 문서 9.2절의 `manifest.json` 은 조건 전체의 메타이고 제어기가 쓴다. `run.json` 은 부하기가 자기 실행에 대해 아는 것만 적는다. 둘이 겹치는 항목은 부하 형상 파라미터이며, 제어기가 `manifest.json` 을 만들 때 `run.json` 에서 가져다 쓴다.

```
condition_tag
effective_config_file      # "load_config.json"
effective_config_sha256    # 설정 파일이 뒤에 바뀌어도 이 실행의 조건이 남는다
driver_version, driver_commit, driver_cpuset, driver_peak_cpu_pct
started_at_utc, warmup_sec, measure_window_sec
achieved_search_write_ratio, total_requests, endpoint_counts
error_counts_by_class      # 연결 거절, 응답 타임아웃, 4xx, 5xx 를 나눠 센다
selectivity_pct, expected_matching_points
query_set_size, query_set_rss_bytes
requests_tsv_sampling      # 전수면 1, 솎았으면 그 비율
```

**설정 전문을 `run.json` 에 복사하지 않고 `load_config.json` 을 가리키는 이유가 있다.** 같은 내용을 두 곳에 두면 둘이 어긋날 수 있고, 수집 문서 9.1절이 이미 `load_config.json` 을 요구했다. 해시를 함께 적으면 그 파일이 이 실행의 것인지 확인할 수 있다.

**`driver_peak_cpu_pct` 가 중요하다.** 부하기에 준 코어가 포화하면 그 실행의 지연은 서버가 아니라 도구를 재고 있는 것이다. 이 값이 임계를 넘은 실행은 무효로 표시한다. 임계의 구체값은 M0 바닥 측정 뒤에 정한다.

**에러를 분류해 센다.** 설계서 2.4절이 실패와 타임아웃 건수를 포화 판정의 보조 근거로 쓰기로 했다. 연결 거절과 응답 타임아웃은 원인이 다르므로 합쳐 세면 안 된다. **이 값은 `requests.tsv` 를 솎더라도 전수로 센 값이어야 한다.**

**검증 기준.** `load_config.json` 을 그대로 새 설정 파일로 써서 다시 돌리면 같은 조건이 재현된다. 명령행으로 `--top-k` 같은 비스윕 파라미터를 주면 도구가 이유를 적고 거부한다.

### 6.3 계측 창구 값은 제어기가 붙인다

부하기는 `/stage_timings` 와 `/telemetry` 와 cgroup 계수기를 읽지 않는다. 제어기가 부하 전후로 읽어 같은 조건 디렉터리의 `snap/` 아래에 떨어뜨리며, 그 절차와 파일 이름은 수집 문서 6.3절과 11.2절에 있다. 설계서 3.3절이 요구한 대로 모든 누적값은 두 번 찍어 빼서 쓴다. 계측 지점 18개소의 값을 보고할 때 여덟 묶음으로 묶어 읽는 방식과 제어기가 그 묶음 파일을 곁들이는 규칙은 6.5절에 있다.

### 6.4 포화점 탐색 방식

설계서 1.1절이 동시 요청 수를 1, 2, 4, 8, 16으로 올리며 포화점을 찾으라고 한다. 그런데 함정 대책 1번과 2번은 조건을 바꿀 때마다 컨테이너를 새로 만들고 캐시를 비우라고 한다. 사다리의 각 단을 별도 조건으로 보면 단 하나마다 컨테이너 재생성과 저장소 복원과 재검증이 붙어 사다리 한 벌에 몇 시간이 든다. 반대로 한 컨테이너 안에서 연속으로 올리면 앞 단이 캐시를 데워 뒤 단이 유리해진다.

**한 Qdrant 컨테이너 안에서 연속으로 올린다.** 근거는 셋이다. 첫째, 메모리 한도가 주 변수이고 동시 요청 수는 그 축 위에서 포화점을 찾는 보조 축이다. 함정 대책이 겨냥하는 것은 메모리 한도를 바꿀 때이지 동시성을 바꿀 때가 아니다. 둘째, 단마다 재생성하면 `preparation_2026-09-21.md` 5.7절의 마스터 복원이 단마다 붙는다. 셋째, 각 단의 캐시 상태는 계수기로 기록할 수 있으므로 비교 가능성을 잃지 않는다.

**단 하나가 곧 수집 문서 6.4절의 구간 하나다.** 수집 문서는 계단마다 부하를 멈춘 뒤 경계 스냅샷을 찍고 `stage_timings` 를 초기화하라고 적었다. 부하기가 스스로 창구를 읽지 않으므로(4.4절) 스냅샷을 찍는 주체는 제어기이며, 제어기가 찍을 시간을 확보해야 한다.

**그래서 사다리를 도는 주체는 제어기다.** 제어기가 단마다 `driver run` 을 한 번씩 호출하고 호출 사이에 스냅샷을 찍는다(4.7절 순서 (5)). Qdrant 컨테이너는 그동안 그대로 살아 있으므로 캐시가 유지되고, 부하기 프로세스만 단마다 새로 뜬다. 이 방식이 고정된 간격을 두고 부하기와 제어기가 박자를 맞추는 방식보다 안전하다. 수집 문서 8.2절이 무거운 창구의 읽기 비용을 아직 재지 못했다고 적었으므로 간격을 미리 정할 근거가 없기 때문이다.

**`driver ladder` 는 스냅샷이 필요 없는 자리에만 쓴다.** M0 바닥 측정과 스모크가 그런 자리다. 단마다 스냅샷이 필요한 본 측정에서는 제어기가 `driver run` 을 반복 호출한다.

**세 가지 안전장치를 둔다.**

첫째, 사다리 앞에 고정 길이 워밍업 구간을 둔다. 모든 단이 같은 정상 캐시 상태에서 출발하게 한다.

둘째, **올림 사다리와 내림 사다리를 한 벌씩 돌린다.** 같은 동시성 단의 지연 분포가 두 방향에서 같으면 캐시 이력 의존이 없다고 본다. 벌어지면 캐시 상태가 지배하는 것이므로 단마다 컨테이너를 새로 만드는 쪽으로 바꾼다. 일치 판정의 구체 기준은 첫 측정에서 관측한 반복 간 산포를 보고 정한다.

셋째, 각 단의 시작과 끝에 계수기를 찍는다. 찍을 대상과 절차는 수집 문서 6.3절에 있다.

**옵티마이저가 도는 단은 비교 대상이 아니다.** 어떤 단에서 `queued_segments` 가 0에서 벗어났다면 그 단은 병목이 아니라 정리 작업을 재고 있는 것일 수 있다. 결과에 표시해 두고 분석에서 따로 다룬다.

**각 단의 길이는 최소 지속 시간과 최소 표본 수를 모두 만족해야 끝난다.** 동시성 1에서는 표본이 모이는 데 시간이 걸리고 동시성 1000에서는 금세 모이므로 한쪽 조건만으로는 단마다 신뢰도가 달라진다.

**판정은 도구가 계산해 참고로 남기고 사람이 확정한다.** 설계서 1.1절의 초안 규칙인 동시성 2배에 처리량 10% 미만 증가와 p99 1.5배 이상 상승을 도구가 적용해 `saturation_rung` 으로 적되, 설계서가 그 숫자를 첫 측정 후 조정한다고 못 박았으므로 자동 판정을 최종 답으로 쓰지 않는다.

**검증 기준.** 올림 사다리와 내림 사다리의 같은 단에서 p50과 p99가 반복 간 산포 안에서 일치한다. 일치하지 않으면 그 사실을 기록하고 단마다 컨테이너를 새로 만드는 절차로 전환한다.

### 6.5 계측 값을 읽는 묶음

`snap/<이름>/stage_timings.json` 에는 계측 지점 18개소의 값이 코드에 있는 그대로 남는다. 보고와 1차 분석에서는 이를 아래 여덟 묶음으로 묶어 읽고, 18개 상세는 묶음에서 이상이 보일 때 파고드는 용도로 둔다. 묶음은 읽는 방식이지 코드를 바꾸는 것이 아니며, 계측 지점의 수와 이름은 `stage_isolation_2026-09-18.md` 8장 그대로다.

| 경로 | 묶음 | 포함하는 지점 | 남기는 값 |
|---|---|---|---|
| 검색 | 잠금 대기 | S0 `s0_segment_read_lock` | 시간 합 |
| 검색 | 후보 고르기 | S1 `s1_cardinality_estimate`, S2 `s2_filter_eval` | 시간 합 |
| 검색 | 거리 계산 | S3 `s3_scorer_setup`, S4 `s4_distance_calc`, S5 `s5_result_collect`, S6 `s6_post_process` | 시간 합 |
| 검색 | 결과 합치기 | S7 `s7_segment_merge`. S8 `s8_rerun` 은 시간이 아니라 횟수를 곁들인다 | 시간 합, S8 횟수 |
| 저장 | 대기열 | W0 `w0_queue_reserve` | 시간 합 |
| 저장 | WAL 기록과 확정 | W1 `w1_wal_write`, W2 `w2_wal_flush` | 시간 합 |
| 저장 | 락 대기 | W3 `w3_global_write_lock`, W4 `w4_segment_holder_lock` | 시간 합 |
| 저장 | 세그먼트 쓰기 | W5 `w5_segment_select`, W6 `w6_vector_write`, W7 `w7_payload_write`, W8 `w8_index_update`. W8 은 따로도 남긴다 | 시간 합, W8 별도 |

**제어기가 스냅샷마다 묶음 파일을 곁들인다.** 부하기는 4.4절대로 `/stage_timings` 를 읽지 않으므로 이 일은 제어기 몫이다(4.7절 순서 (5)). 제어기는 `snapshot.sh` 가 남긴 `stage_timings.json` 을 손대지 않고, 같은 디렉터리에 위 여덟 묶음의 `total_nanos` 합과 S8 횟수와 W8 값을 담은 `stage_groups.json` 을 만든다. **18개와 8묶음이 둘 다 남아야 한다.** 묶음만 남기고 상세를 버리면 이상이 보였을 때 파고들 곳이 없고, 상세만 남기면 조건 셋을 나란히 놓고 읽는 표가 열여덟 줄이 되어 어디가 달라졌는지가 한눈에 들어오지 않는다.

**묶음 안에서 지점의 `count` 는 서로 다를 수 있다.** S0 는 세그먼트마다 한 번이고 S4 와 S5 는 청크마다 누적된다(`stage_isolation_2026-09-18.md` 3.1절). 그래서 묶음의 시간은 `total_nanos` 를 더해 만들고 횟수는 더하지 않으며, 횟수가 필요하면 `stage_timings.json` 의 지점별 값을 본다. 마스터 복원 방식의 검색 전용 조건에서 저장 네 묶음이 전부 0인 것은 수집 문서 6.6절대로 정상이다.

**검증 기준.** 스냅샷 디렉터리마다 `stage_timings.json` 과 `stage_groups.json` 이 함께 있고, 각 묶음의 시간 합이 그 묶음에 속한 지점의 `total_nanos` 를 더한 값과 같으며, 검색 네 묶음의 합이 S0부터 S7까지의 합과 같고 저장 네 묶음의 합이 W0부터 W8까지의 합과 같다.

## 7. 충실도 검증

### 7.1 값이 아니라 요청의 모양을 대조한다

설계서 4.4절이 `qdrant_request_trace.json` 과의 대조를 요구한다. 그런데 트레이스의 값은 그 실행의 값일 뿐이고 에뮬레이터는 다른 값으로 돌아야 한다. 트레이스는 64차원에 배치 크기 4이고 본 측정은 768차원부터 2560차원까지다. **값을 비교하면 항상 불일치가 나고 그러면 검증이 형식만 남는다. 비교해야 하는 것은 요청의 구조다.**

**부하기에 `trace` 모드를 둔다.** 실제로 전송한 요청을 기존 트레이스와 같은 스키마로 소량 덤프한다. 로그를 따로 짜지 않고 전송 직전의 본문을 그대로 쓴다.

```bash
if [ -z "${RUNDIR:-}" ]; then
  echo "RUNDIR 이 비어 있다. 수집 문서 9.1절로 돌아간 뒤 이 블록을 다시 실행한다."
else
  driver trace --config "$RUNDIR/load/cond.yaml" --n 100 --out "$RUNDIR/load"
  echo "$RUNDIR/load/driver_trace.json 이 생겼는지 확인한다."
fi
```

### 7.2 대조 기준은 원문 트레이스다

**대조의 기준은 부록 9장의 절차로 speedkick `8d7b832` 에서 새로 뜨는 원문 트레이스 `qdrant_request_trace_raw.json` 이다.** 기존 `qdrant_request_trace.json` 은 검색과 저장의 `body` 를 요약 문자열로만 남겨(검색은 `"searches=1; limit=80 with_payload=False with_vector=False filter={...}"`, 저장은 `"points=4 dim=64 payload_keys=['_content_type', ...]"`) 바이트 단위 대조가 불가능했고, 요약에 적히지 않은 필드(질의 벡터, `score_threshold` 유무, 포인트별 payload 값, 실제 컬렉션 이름)는 달라도 잡히지 않았다. `docs/msr/qdrant_requests/reproduce/trace_qdrant_requests_raw.py` 는 같은 훅과 같은 시나리오로 요청마다 `request_body` 와 `response_body` 원문과 헤더와 바이트 수와 실제 경로를 남기며, 기존 요약 문자열 `body` 도 글자 하나 바꾸지 않고 유지해 옛 트레이스와 diff 할 수 있다(부록 9.1절).

| 요청 | 원문 트레이스의 대조 방법 |
|---|---|
| 검색 | `request_body` 를 부록 5.1절의 본문과 키 집합, 값, 필터 구조까지 직접 비교한다. 질의 벡터 값만 정규화한다 |
| 저장 upsert | `request_body` 의 `points[*].payload` 키 집합을 부록 4.2절과 비교하고 벡터와 uuid 값은 정규화한다 |
| 삭제 | 원본 JSON 구조를 직접 비교한다(부록 6장) |
| 컬렉션 생성과 색인 생성 | 원본 JSON 을 바이트 단위로 비교한다(부록 3.2절부터 3.4절) |

**원문 트레이스가 아직 없을 때의 임시 기준.** 부록 9장의 실행이 끝나기 전에는 부록의 JSON 본문 자체가 기준이다. 부록의 본문은 speedkick venv 에서 qdrant-client 1.19.0 으로 실제 직렬화한 것이라 요약 문자열보다 정확하다. **부하기의 `trace` 모드는 요약본과 원본 본문을 둘 다 남긴다.** 원본은 원문 트레이스와 대조하고, 요약본은 옛 트레이스와의 연속성 확인에 쓴다.

### 7.3 대조 스크립트가 보는 것

| 비교 항목 | 정규화 방법 |
|---|---|
| 메서드와 경로 | 컬렉션 이름을 `<coll>` 로 치환한다 |
| 쿼리스트링 | 키와 값을 그대로 본다. `wait=true` 가 붙는지가 핵심이다 |
| 본문의 최상위 키 집합 | 키 이름만 본다 |
| 필터 트리의 구조 | `must` 와 `should` 와 `must_not` 의 중첩 모양과 각 잎의 키 이름을 본다. 값은 보지 않는다 |
| 옵션 값 | `with_payload`, `with_vector`, 그리고 `limit` 과 `top_k` 의 비율은 값까지 본다 |

**합격 기준은 3.1절 표의 모든 행이며 그 값은 부록 8장이 확정한다.** 특히 아래 다섯은 틀리기 쉽고 틀리면 측정이 달라진다.

1. 검색 `limit` 이 `top_k` 의 4배여야 한다. 3배로 보내면 S5 결과 수집과 S7 세그먼트 병합의 비용이 달라진다.
2. 저장에 `wait=true` 가 붙어야 한다. 빠뜨리면 설계서 0.3절 ④의 WAL 확정과 W2와 W3이 응답 경로에서 빠져 저장 지연이 통째로 달라진다.
3. 검색이 `points/query/batch` 여야 하고 `searches=1` 이어야 한다. 단건 `points/query` 로 보내면 경로가 다르다.
4. 파티션 키 필터가 `must` 의 첫 항목으로 들어가고 사용자 조건은 별도 `must` 항목으로 중첩되어야 한다. 한 `must` 배열에 평평하게 펼치면 카디널리티 추정이 달라질 수 있다. 이 모양은 코드에서도 확인했다. `common/vector_store/qdrant_vector_store.py:342-353` 이 필터가 있을 때 `must=[partition_key_filter, property_qdrant_filter]` 로 감싸고 없을 때는 파티션 필터만 그대로 쓴다(부록 5.3절).
5. 검색의 `with_payload` 와 `with_vector` 가 모두 `false` 여야 한다. 부록 5.4절이 두 검색 경로 모두에서 확정한 값이며(`qdrant_vector_store.py:361-362`), `true` 로 보내면 payload 저장소 읽기가 응답 경로에 들어와 메모리 축 실험의 방향이 달라진다.

**차원 차이는 예외로 명시한다.** 트레이스는 64차원으로 기록되었고 본 측정은 768부터 2560까지다. 이는 값의 차이이므로 불일치로 보지 않되, 요청 본문 크기가 차원에 비례해 커진다는 점은 기록한다.

**방식 B의 필터 필드가 트레이스와 다르다는 점도 예외로 명시한다.** 트레이스 S8은 `user_id` 로 거르는데 3.1절에서 확인한 대로 그 필드는 색인 11개에 들어 있지 않다. 부하기는 색인된 `_producer_id` 로 거르므로 필터 트리의 구조는 같지만 잎의 키 이름이 다르다. 이 차이가 측정에 미치는 영향은 9장에 위험으로 적었다.

**검증 기준.** 대조 스크립트가 불일치 0건을 보고하고 위 다섯 항목이 각각 통과로 찍힌다. 불일치가 나면 어느 항목의 어느 부분이 다른지 경로와 함께 출력된다.

## 8. 제작 순서

### 8.1 순서와 각 단계가 여는 것

**지금 무엇을 먼저 만들면 가장 빨리 쓸모가 생기는지가 질문이다.** 답은 명확하다. 작업 단계 4(계측 코드와 이미지)가 4.5 왜곡 검증만 남겨 두고 멈춰 있는데, 그 검증이 요구하는 것은 계측 유무 빌드를 같은 부하로 돌려 비교하는 일이고(`instrumented_build_2026-09-21.md` 7장) 그것을 막고 있는 것이 바로 부하 도구다. **검색 전용 최소 부하기만 나와도 멈춰 있던 작업 하나가 닫힌다.**

**제작 순서는 M0부터 M6까지로 부른다.** 설계서 4.6절의 작업 단계 번호(1부터 5까지와 그 아래 3.1 같은 소번호)와 혼동하지 않기 위해서다. 이 문서 전체가 작업 단계 3에 해당하고, 아래 M0부터 M6까지는 그 안에서 무엇을 먼저 만드는가의 순서다.

| 제작 순서 | 만드는 것 | 이 순서가 여는 것 |
|---|---|---|
| M0 | `driver floor` 와 후보 셋 비교 | **언어 결정.** 뒤의 모든 작업이 여기에 달렸다 |
| M1 | `loader load` 와 `loader verify` 와 `loader master` | `instrumented_build_2026-09-21.md` 6.3절의 수동 curl 적재를 대체한다. 다른 모든 순서의 전제다 |
| M2 | `driver run` (검색만, 고정 동시성, HDR 히스토그램, `run.json`, `requests.tsv`) | **왜곡 검증이 열린다. 작업 단계 4.5가 닫힌다** |
| M3 | 제어기 `runner` (4.7절)와 그것이 도는 사다리 (양방향, 계수기 연동, 6.5절의 묶음 파일) | 설계서 1.1절의 포화점 탐색이 가능해진다 |
| M4 | 저장 혼합과 세션 치우침 | 설계서 5.1절이 동료에게 받는 값을 그대로 넣을 수 있게 된다 |
| M5 | `driver trace` 와 대조 스크립트 | 설계서 4.4절의 충실도 검증이 닫힌다 |
| M6 | `driver recall` (`exact` 대조) | 설계서 4.5.3절의 리콜 측정이 가능해진다. 부하 구간 밖에서만 돈다 |

### 8.2 단계마다의 검증 방법

| 제작 순서 | 어떻게 끝났다고 판정하나 |
|---|---|
| M0 | 세 후보의 바닥 지연 분포와 최대 QPS를 담은 비교표가 나오고, 그 표를 근거로 언어를 확정한 한 문단이 설계서 4.4절에 추가된다 |
| M1 | `loader verify` 가 포인트 수와 세션 수와 payload 인덱스 개수 11개를 보고하고, `loader master` 가 만든 마스터의 `du -sb` 가 작업본과 같으며, `preparation_2026-09-21.md` 5.9절의 1000만 개 예비 적재에서 적재 속도를 실측해 1억 개 소요 시간을 외삽한다 |
| M2 | `instrumented_build_2026-09-21.md` 7장의 왜곡 검증을 실제로 수행해 계측 유무 두 빌드의 지연 분포 비교표를 얻는다. 그 표가 나오면 작업 단계 4.5의 상태를 완료로 바꾼다 |
| M3 | 4.7절의 검증 기준을 통과하고, 6.4절의 올림과 내림 사다리 일치 확인이 통과한다 |
| M4 | `run.json` 에 의도한 비율과 달성 비율이 함께 남고, 동시성이 올라갈수록 저장 쪽 달성 비율이 떨어지는지 `series.csv` 에서 보인다 |
| M5 | 7.3절의 대조가 불일치 0건을 보고한다 |
| M6 | 같은 질의 집합에 대해 평소 검색과 `exact` 검색의 결과가 나오고 리콜이 계산된다 |

### 8.3 M0을 건너뛰지 않는다

언어를 정하지 않고 M2를 만들면 나중에 다시 만들게 된다. M0은 반나절 규모다.

아래는 M0의 바닥 측정이다. 스모크용 소형 컬렉션을 대상으로 동시성을 바꿔 가며 같은 질의를 던진다. 서버 시간이 거의 0인 대상이므로 여기서 나오는 지연이 곧 도구의 바닥이다. 후보 셋을 같은 조건에서 돌려 비교한다.

```bash
if [ -z "${RUNDIR:-}" ]; then
  echo "RUNDIR 이 비어 있다. 수집 문서 9.1절로 돌아간 뒤 이 블록을 다시 실행한다."
else
  for C in 1 64 256 1000; do
    driver floor --concurrency "$C" --duration 60 --out "$RUNDIR/load/floor_c$C"
  done
  echo "네 디렉터리에 각각 run.json 과 hist/search.hgrm 이 생겼는지 확인한다."
fi
```

후보 셋은 파이썬 `qdrant_client` 비동기, 파이썬 `httpx` 직접 조립, Rust `reqwest` 다. **파이썬이 2.2절의 기준을 통과하면 파이썬을 쓴다.**

### 8.4 M2에서 멈추고 한 번 써 본다

왜곡 검증을 실제로 돌려 보면 결과 형식과 환경 지문에 무엇이 빠졌는지가 드러난다. M3 이후를 먼저 다 만들면 그 피드백이 늦게 온다.

**이때 수집 문서 10장의 수집기 비용 검증을 함께 돌린다.** 둘 다 같은 조건을 두 번 돌려 비교하는 작업이라 한 번에 끝난다.

### 8.5 M6은 부하 구간과 분리된 별도 모드다

설계서 4.5.3절이 부하 중에 `exact` 를 섞으면 그 자체가 부하를 왜곡한다고 못 박았다. `driver recall` 은 부하 워커를 띄우지 않고 미리 정한 질의 집합으로 평소 검색과 `exact` 검색을 각각 한 번씩 돌려 비교만 한다.

## 9. 미확인 사항과 위험

### 9.1 환경 문서가 확정해 닫힌 것

**조건마다 적재를 다시 하는가, 마스터 사본에서 복원하는가는 이미 정해졌다.** `cgroup_trap_check_2026-09-21.md` 7.1절과 설계서 4.6.1절은 조건마다 데이터를 다시 적재하는 것으로 적혀 있었으나 마스터 복원으로 고쳐졌고, 그래서 `preparation_2026-09-21.md` 5.7절의 마스터 사본 복원과 더는 어긋나지 않으며 `environment_setup_2026-09-21.md` 5.5절이 이를 불변식 하나로 통일했다. 지켜야 하는 것은 복원 방식이 아니라 **컨테이너가 데이터 페이지를 처음 만지는 주체여야 한다**는 것이다. 마스터 복원은 호스트가 마스터 사본을 작업본으로 복사한 뒤 시스템 캐시를 비우고 컨테이너를 새로 띄워 처음 읽게 하는 절차이며, 두 경로 모두 그 불변식을 게이트 A(캐시 잔류 없음)와 게이트 C(컨테이너 앞으로 디스크 읽기 과금)로 조건마다 증명한다. 같은 절이 기본값을 마스터 복사 쪽으로 정했고 5.3절 스크립트의 `RELOAD=${RELOAD:-copy}` 가 그 기본값이다. 게이트가 한 번이라도 실패한 조건만 `RELOAD=ingest` 로 다시 세운다. **따라서 이 항목은 합의를 기다리는 미결이 아니다.**

**부하 도구가 여기서 지는 몫은 `ingest` 경로 하나다.** `RELOAD=ingest` 는 빈 저장소를 만들어 두고 적재기가 채우게 하는 경로이므로 적재기가 그 자리를 메워야 한다. 기본값이 `copy` 라 해도 적재기는 여전히 필요하다. 마스터 사본을 뜨는 일 자체가 적재를 한 번은 해야 가능하기 때문이며, 그 마스터를 뜨는 일도 `loader master` 로 적재기가 한다(4.2절). 재적재는 마스터가 없을 때의 대안일 뿐이다.

**복원이 385GB를 호스트 페이지 캐시를 거쳐 쓴다는 점도 절차로 닫혔다.** 복사 직후 캐시 비우기를 빠뜨리면 함정이 그대로 재현되는데, 환경 5.3절의 `run_condition.sh` 가 복원과 `drop_caches` 와 게이트 A를 한 스크립트 안의 연속된 단계로 묶어 두어 사람이 둘을 분리할 여지가 없다.

### 9.2 구현 전에 확인해야 할 것

**부하 도구를 파이썬으로 만들어도 되는지 아직 재지 않았다.** 4.6절의 Rust 권고는 GIL과 가비지 수집이 꼬리 지연에 기여한다는 일반 원리에 기댄 것이고 이 서버에서 실측한 것이 아니다. M0 바닥 측정 전에는 확정으로 쓰지 말아야 한다.

**검색의 `with_payload` 는 닫혔다.** 2026-09-21 판이 "코드와 트레이스가 어긋난다"고 적은 것은 msr_multiuser(`89bec05`) 소스의 `qdrant_vector_store.py:373`(`with_payload=return_properties`)과 `event_memory.py:428`(`return_properties=True`)을 speedkick `a8322a7` 에서 채취된 트레이스와 나란히 놓아 생긴 착오였다. 옛 브랜치에서 코드와 트레이스가 어긋났던 문제는 speedkick 에서 인자 자체가 제거되어 해소되었다(부록 5.4절). speedkick 에서는 어댑터가 `with_vector=False, with_payload=False` 를 리터럴로 고정하고(`common/vector_store/qdrant_vector_store.py:361-362`) 인터페이스에 `return_properties` 인자 자체가 없어(`common/vector_store/vector_store.py:63-79`) 에피소드 검색과 시맨틱 검색 모두 `with_payload=false` 로 나간다. 부록 5.4절이 경로별로 확정했고 3.4절의 값은 잠정값이 아니라 확정값이다. 이 값이 측정을 바꾸는 폭이 크다는 점(payload 를 돌려받으면 payload 저장소 읽기가 응답 경로에 들어와 메모리 한도가 낮은 조건에서 디스크 읽기가 늘어난다)은 그대로이므로 7.3절의 다섯째 항목으로 대조에 넣었다. speedkick 에서 `with_payload=true` 인 요청은 검색이 아니라 레지스트리 조회(`retrieve`, ids 1개) 하나뿐이다.

**`_producer_id` 의 실제 카디널리티를 모른다.** 3.5절이 이 필드를 선택도 다이얼로 쓰기로 했는데, MemMachine 실제 데이터에서 이 필드가 어떤 분포를 갖는지 확인하지 못했다. 실제가 소수 값에 몰려 있다면 균등 100개 배정은 실제와 다른 카디널리티 추정을 유발한다. 설계서 5.1절 (가)에서 동료에게 받는 자료로 확인해야 한다.

**방식 B의 필터 필드가 트레이스와 다르다.** 트레이스 S8은 `user_id` 로 거르는데 그 필드는 색인 11개에 들어 있지 않다. 색인된 필드로 거를 때와 색인 없는 필드로 거를 때는 Qdrant가 카디널리티를 추정하는 방식이 다르고, 따라서 전수 비교와 그래프 탐색의 갈림도 달라질 수 있다. 3.5절이 색인된 `_producer_id` 를 고른 것은 payload 인덱스 개수를 11개로 유지하기 위해서이고 그 판단 자체는 유지하되, **실제 운영이 색인 없는 필드로 거르는 비중이 크다면 그 경로를 따로 재야 한다.** 동료에게 받는 필터 조합 자료로 확인한다.

### 9.3 첫 측정 뒤에 정해야 할 숫자

**합격 기준의 구체 숫자를 아직 정하지 못했다.** 바닥 지연 p99가 측정 대상 p50보다 충분히 작아야 한다는 조건의 배수, 사다리 양방향 일치 판정의 허용 오차, 부하기 CPU 포화 임계가 모두 미정이다. 본 측정 대상의 지연 규모를 모르는 상태에서 숫자를 정하면 지어낸 값이 된다. 첫 스모크 측정 뒤에 정한다. 설계서 5.4절과 `preparation_2026-09-21.md` 11.7절이 같은 이유로 판정 기준을 절대 수치로 정하지 않았다.

**`requests.tsv` 의 크기와 쓰기 비용을 산정하지 않았다.** 요청 한 건이 한 줄이므로 높은 QPS에서 이 파일이 매우 커지고, 측정 구간 동안 디스크에 쓰는 일 자체가 부하가 될 수 있다. `$RAW` 가 `$BENCH` 와 다른 장치라 Qdrant 쪽 통계는 오염되지 않지만 부하기 코어의 시간은 쓴다. 완화책은 6.1절에 적은 대로 버퍼에 쌓아 주기적으로 비우고 필요하면 표본을 솎는 것이며, 솎더라도 `series.csv` 와 `hist/` 와 `run.json` 의 에러 총계는 전수로 남는다. **솎을지와 그 비율은 첫 스모크에서 정한다.**

**적재기가 1억 개를 적재하는 데 얼마나 걸릴지 산정하지 않았다.** 파이썬 적재기가 너무 느리면 그 자체가 일정 위험이 된다. `preparation_2026-09-21.md` 5.9절의 1000만 개 예비 적재에서 속도를 재고 외삽해야 한다.

**`exact: true` 리콜 측정의 비용을 산정하지 않았다.** 1억 개 전수 스캔이 질의당 얼마나 걸리는지 모르는 상태이며, 설계서 4.5.3절이 측정점마다 재라고 요구하므로 총 소요 시간이 일정에 크게 들어올 수 있다.

### 9.4 구조적으로 남는 제약

**폐루프 모델은 조정된 누락에 구조적으로 취약하다.** 서버가 느려지면 부하기가 자동으로 요청을 덜 보내므로 지연 분포가 실제보다 낙관적으로 나온다. 기록 방법은 5.1절에 적은 대로 수집 문서 9.3절의 `t_plan` 과 `t_send` 로 이미 정해져 있으나, **개루프 모드를 어느 조건에서 돌릴지와 두 지연을 어떻게 나란히 해석할지는 아직 정하지 않았다.**

**Qdrant와 부하기가 같은 호스트에 있어 통신이 루프백이다.** 실제 운영의 망 조건과 다르며 NIC 인터럽트와 패킷 분할이 없다. 설계서 4.1절이 단일 서버 구성을 확정했으므로 대안이 없고 기록만 할 수 있다.

**원문 트레이스를 뜨기 전에는 부하기가 보낸 본문을 트레이스와 바이트 단위로 대조할 수 없다.** 기존 `qdrant_request_trace.json` 은 검색과 저장의 `body` 를 원본 JSON이 아니라 요약 문자열로 남겼고, 요약에 적히지 않은 필드는 실제와 달라도 대조가 잡아내지 못한다. 이 공백은 부록 9장의 `trace_qdrant_requests_raw.py` 를 speedkick `8d7b832` 에서 한 번 실행해 원문 본문을 남기면 닫힌다(7.2절). 그때까지는 부록에 적힌 직렬화 본문이 기준이며, 그 실행이 M1 착수 조건이다(10장).

**트레이스는 64차원으로 기록되었다.** 768부터 2560차원에서의 요청 본문 크기와 그에 따른 서버 측 JSON 파싱 비용은 외삽이며 실측이 아니다. 이 비용은 Qdrant의 16코어 예산 안에서 발생하므로 무시할 수 없다.

## 10. 다음 단계

**M1 착수 조건은 부록 9장의 트레이스 검증 1회다.** `loader load` 가 만드는 컬렉션과 색인의 본문은 부록 3장을 따르는데, 그 본문이 speedkick `8d7b832` 가 실제로 보내는 것과 같다는 확인은 원문 트레이스로만 할 수 있다. `docs/msr/qdrant_requests/reproduce/` 에서 `reset_stores.sh` 로 저장소를 비우고 `trace_qdrant_requests_raw.py` 를 한 번 돌려, 구간별 요청 수(P0=1, S1=17, S2=17, S3=0, S4=1, S5=1, S6 부터 S9 각 1, S10=0, S11=2, S12=1, S13=4)가 맞고 `request_body` 가 부록 9.3절의 표를 통과하면 M1 을 시작한다. 실행에는 Docker 와 빈 Qdrant 와 빈 PostgreSQL 이 필요하며(부록 9.2절), 결과 파일 `qdrant_request_trace_raw.json` 과 그때 쓴 Qdrant 서버 이미지 태그를 함께 남긴다.

**M2가 끝나면 작업 단계 4.5 왜곡 검증이 닫힌다.** 그때 설계서 4.6절의 표에서 4.5의 상태를 완료로 바꾸고, M0에서 확정한 언어를 설계서 4.4절에 한 문단으로 적는다.

**환경 문서와의 경계는 `run_condition.sh` 가 "조건이 섰다"를 출력하는 자리다.** 그 지점까지는 `environment_setup_2026-09-21.md` 5.3절의 몫이고, 그 뒤의 적재기 호출과 마스터 사본 생성과 사다리와 저장 부하 뒤 마스터 복원은 4.7절의 제어기가 한다. 환경 문서 담당은 그 스크립트의 종료 조건만 지키면 되고, 부하 호출을 스크립트에 끼워 넣지 않는다. 재적재와 마스터 복원의 갈림은 9.1절에 적은 대로 환경 문서 5.5절이 이미 확정했으므로 따로 합의할 것이 없다. 부하 도구가 맞추어야 할 것은 `RELOAD=ingest` 조건에서 적재기가 빈 저장소를 채우고 마스터 사본을 뜨는 경로다.
