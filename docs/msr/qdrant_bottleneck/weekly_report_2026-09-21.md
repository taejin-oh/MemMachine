## 1. 진행 계획

- 작업 1부터 4까지는 대체로 서로 독립이라 병렬로 진행하고, 4.5 왜곡 검증만 작업 1과 3.3 뒤에 옴. 작업 5는 넷이 끝나야 시작함

### 작업 1. Qdrant Docker 환경 준비

- Qdrant를 컨테이너로 띄우되 CPU 16코어와 메모리 한도 128/256/512GB가 **실제로 물리게** 만드는 작업임. 한도가 물리지 않으면 "메모리를 줄여도 디스크를 읽지 않는다"가 되어 실험 전체가 무효가 되므로, 띄우는 일보다 물렸는지 확인하는 절차가 더 중요함
- 1.1 소스 확보, 패치 적용, 이미지 빌드. 계측 이미지와 대조 이미지를 같은 소스와 같은 Dockerfile로 한 번에 둘 다 만들며, 계측 스위치(FEATURES)만 다름
- 1.2 조건에 맞춰 띄우기. 큰 서버는 CPU와 메모리가 몇 개의 묶음(NUMA 노드)으로 나뉘어 있고 자기 묶음의 메모리와 장치에 닿을 때가 빠름. 그래서 **Qdrant 저장소가 놓인 NVMe가 어느 묶음에 붙었는지를 먼저 확인하고 그 묶음의 코어 16개와 메모리를 쓰며,** 부하 도구와 수집기는 다른 묶음의 코어를 씀. 스왑은 컨테이너 단위로 차단하고, 디스크 입출력을 블록 수준에서 추적하는 blktrace를 준비함
- 1.3 함정 확인 **[완료]**. 2장에 상세를 적음
- 1.4 준비 완료 확인. 한도, 코어 고정, 스왑 차단, NUMA 정합을 컨테이너의 cgroup 값에서 읽어 확인함. 요청한 값이 아니라 실제로 물린 값을 봄
- 1.5 조건 전환 스크립트, 잡음 제거, 부하 도구와 수집기의 코어 예약, 수집기

### 작업 2. 데이터셋 받기

- 벡터 1억 건을 실제 임베딩으로 확보하는 작업임. 합성 벡터는 군집 구조가 없어 그래프 탐색 구간의 지연과 리콜이 실제를 예측하지 못하므로 공개 임베딩을 받음
- 2.1 라이선스 확인. Zilliz 배포본은 이용 조건이 명시되어 있지 않음
- 2.2 받기. 스모크용 SIFT(525MB), 주 데이터 `laion_large_100m`(212GB), 차원 스윕용 Pes2o(39.7GB)
- 2.3 검증. 행 수, 차원, 정규화, 체크섬

### 작업 3. Qdrant 부하 도구(에뮬레이터) 제작

- MemMachine 서버를 거치지 않고 Qdrant에 직접 요청을 보내는 도구임. MemMachine을 거치면 임베딩 생성과 세션 관리 비용이 응답 시간에 섞여 들어와 달라진 것이 Qdrant인지 그 앞단인지 가를 수 없고, 필터 통과 비율과 저장 배치 크기 같은 변수를 임의로 바꿀 수도 없음
- 3.1 부하 평가 변수 정리 **[완료. 설계서 4.4절]**. 데이터 형상(포인트 수, 차원, 세션 수, 세션 크기 분포)과 부하 형상(동시 요청 수, 검색 대 저장 비율, 필터 통과 비율 등)으로 나눔
- 3.2 적재기. 데이터 파일을 읽어 Qdrant에 넣음. 넣으면서 세션 키를 붙이는 **세션 배정**(기본 분포 zipf, s=1.0)과 적재 완료 판정, **적재 후 마스터 사본 생성**까지가 적재기 몫임
- 3.3 부하기. 검색과 저장 요청을 보내고 QPS와 지연을 기록함. 동시 요청 수를 1, 2, 4, 8, 16으로 올리는 사다리로 처리량이 더 늘지 않고 지연만 오르는 포화점을 찾음
- 3.4 제어기. 조건 전환 스크립트를 호출하고 적재, 부하, 수집을 순서대로 수행함. **부하 도구의 산출물임**
- 3.5 충실도 검증. 실제 MemMachine의 요청 기록과 요청의 모양을 대조함

### 작업 4. 계측 코드와 이미지

- Qdrant는 요청 하나가 내부의 어느 단계에서 시간을 쓰는지 알려주지 않음. 병목 지점을 특정하려면 이 정보가 필요하므로 소스에 시간을 재는 코드를 직접 넣는데, 이것이 계측임
- 4.1 단계 묶음 정의. 코드의 18개 지점은 그대로 두고, 읽을 때는 검색 4묶음과 저장 4묶음으로 봄. 18개 상세는 묶음에서 이상이 보일 때 파고드는 용도임
- 4.2 계측 방법 **[완료]**, 4.3 코드 삽입 **[완료]**, 4.4 동작 확인 **[개발 빌드로 완료. 서버 빌드 확인은 1.1에서]**
- 4.5 왜곡 검증. 계측을 켠 빌드와 끈 빌드를 같은 부하로 돌려 결과가 달라지지 않음을 확인함. 작업 1과 3.3이 있어야 가능함

### 작업 5. 측정

- 5.1 예비 측정. 1,000만 건으로 세 조건을 한 바퀴 돌려 절차가 실제로 도는지 보고, 문서의 추정값(예열 완료 임계, 수집 주기, 복사 시간, blktrace 비용)을 실측으로 교정함
- 5.2 본 측정. 1억 건, 세 조건, 포화점 탐색. 1단계(박준혁 TL)로부터 병목 조건 인계가 필요함
- 5.3 분석. 병목 조건, 병목 지점, 병목 원인의 순서로 좁힘

## 2. 진행 사항

### 함정 확인 (1.3) — 완료

- **무엇을 했나.** 16GB 파일과 4GB 한도 컨테이너로, 같은 파일을 컨테이너가 먼저 읽는 조건과 호스트가 먼저 읽는 조건을 만들어 컨테이너의 cgroup 계수기를 비교함
- **왜 했나.** 리눅스는 파일 캐시를 먼저 읽은 쪽 앞으로 과금함. 호스트가 데이터를 먼저 읽어 두면 컨테이너는 한도와 무관하게 그 데이터를 공짜로 쓰고, 한도를 낮춰도 디스크를 읽지 않음. 이 상태로 측정하면 **"메모리는 병목이 아니다"라는 정반대 결론에 이름**
- **결과.** 함정이 실재함

| 지표 | 컨테이너가 먼저 읽음 | 호스트가 먼저 읽음 |
|---|---|---|
| 컨테이너 디스크 읽기 | 32GiB | **0** |
| 한도 도달 횟수 | 12,296회 | **0회** |
| 컨테이너 앞 과금량(`memory.current`) | 4GiB (한도) | **0.01GiB** |

- 호스트가 먼저 읽은 조건의 컨테이너는 4GB 한도를 걸었는데도 디스크를 한 번도 읽지 않았고 한도에 한 번도 부딪히지 않음
- **판정 기준을 정정함.** 처음에는 읽기 소요 시간을 1차 근거로 삼았으나 두 조건이 4.2초와 4.4초로 차이가 없었음. 초당 7.6GB는 디스크 속도가 아니라 단일 스레드 메모리 복사 병목이며, 이 서버에서는 시간으로 캐시 적중과 디스크 읽기를 구분할 수 없음. **판정은 계수기로만 함**
- **그래서 바뀐 것.** 조건마다 "컨테이너가 데이터 페이지를 처음 만져야 한다"가 원칙이 됨. 방법은 호스트가 적재 직후 떠 둔 마스터 사본을 작업본으로 복사한 뒤 시스템 캐시를 비우고, 컨테이너를 새로 띄워 처음 읽게 하며, 게이트 A(캐시 잔류 없음)와 게이트 C(컨테이너 앞으로 디스크 읽기 과금)로 증명하는 것임. 재적재는 수 시간이 걸리지만 복사는 약 6분임. 이 절차만큼 측정 1회의 소요 시간이 늘어남

### 데이터셋 (작업 2) — 진행 중

- **무엇을 했나.** 확보 방법 25가지를 비교한 조사 위에서 주 데이터를 골랐고, URL과 바이트 수를 직접 확인한 다운로드 런북을 작성함
- **선정 결과.** 주 데이터는 Zilliz의 `laion_large_100m`(768차원 1억 건, 212GB)이고 이유는 셋임
  - 목표 규모 1억 건을 목표 차원 중 하나인 768차원으로 정확히 제공하면서 다운로드가 212GB에 그치고, 계정 없이 익명으로 받아짐
  - 전수 비교로 만든 정답이 이미 들어 있어 리콜 검증을 정답 생성 없이 바로 돌릴 수 있음
  - 벡터가 이미 정규화되어 있음을 직접 확인했고, 768차원 1억 건은 벡터가 307GB라 RAM 1TB 안에 여유가 남음
- **이전 안에서 바뀐 이유.** 이전 안은 2560차원 Pes2o-VE(843GB)였음. 2560차원 1억 건은 벡터만 1TB라 RAM에 올라가지 않고, 8,845만 건이라 1억에 미달하며, Globus 로그인이 필요한 접근 절차가 미확인이고, 정답이 없음. 차원 스윕은 Zenodo Pes2o(2560차원 829만 건, 39.7GB, CC-BY-4.0)로 규모를 낮춰 따로 봄
- **위험.** Zilliz 배포본은 README와 파일 목록 어디에도 라이선스가 명시되어 있지 않음. 사내 측정에 쓰고 수치만 보고하는 것은 통상 문제가 되지 않지만, 데이터나 파생물의 외부 공개 계획이 있다면 법무 확인이 선행되어야 함
- **다음.** 2.1 라이선스 확인 요청을 먼저 보내고, 2.2 스모크 데이터부터 받은 뒤 본체를 백그라운드로 걸고, 2.3 행 수와 차원과 정규화와 체크섬을 검증함

### 계측 (작업 4) — 코드 완료, 서버 빌드 남음

- **무엇을 했나.** v1.19.1 소스에 계측 지점 18개소를 넣는 패치를 완성하고, 서버를 띄워 저장 9단계와 검색 8단계가 실제로 값을 올리는 것을 확인함. 검색의 마지막 지점(재검색)은 드물게 일어나는 지점이라 0으로 남는 것이 정상임
- **왜 했나.** 검색과 저장의 내부 단계별 시간은 측정 항목 11개 가운데 Qdrant 기본 기능으로 얻을 수 없는 유일한 둘이고, 2단계의 핵심 질문인 "내부 어디서 막히는가"에 직접 답하는 정보임. 특히 **WAL 확정과 전역 쓰기 락 대기는 기존 어떤 지표에도 잡히지 않는 사각지대**인데 이번 계측이 이를 포함함
- **결과.** 계측은 개발 빌드로 확인함. 공식 Dockerfile로 계측 이미지와 대조 이미지를 만드는 서버 빌드는 1.1에서 함
- **읽기 묶음.** 18개 지점은 코드에 그대로 두고 보고할 때는 4묶음씩으로 봄

| 경로 | 묶음 |
|---|---|
| 검색 | 잠금 대기(S0) / 후보 고르기(S1+S2) / 거리 계산(S3+S4+S5+S6) / 결과 합치기(S7, S8은 횟수) |
| 저장 | 대기열(W0) / WAL 기록과 확정(W1+W2) / 락 대기(W3+W4) / 세그먼트 쓰기(W5+W6+W7+W8, 색인 W8은 따로 볼 수 있게) |

- **다음.** 1.1 서버 빌드, 4.5 왜곡 검증. 왜곡 검증은 작업 1의 환경과 3.3의 검색 전용 부하기가 있어야 가능함

### 환경과 부하 도구 절차 정리 (작업 1, 3) — 문서 완료, 실행 전

- **무엇을 했나.** 조건 하나를 세우는 스크립트(`run_condition.sh`)와 통과 조건 세 개(게이트), 측정 항목 11개의 수집 체계, 부하 도구 명세(적재기, 부하기, 제어기의 역할과 명령행 계약, 변수, 세션 치우침, 충실도 검증), 서버 접속 전 준비 절차를 문서로 정리함
- **왜 했나.** 함정이 실재하므로 조건 전환이 "한도를 바꾼다"에서 "폐기, 복원, 캐시 비우기, 재생성, 검증"으로 바뀜. 손으로 하면 순서를 건너뛴 무효 조건이 섞여 들어가고, 무효라는 사실이 결과를 보아서는 드러나지 않음. 그래서 스크립트로 묶고 단계마다 통과 조건을 둠
- **결과.** 게이트 A는 컨테이너 생성 직전에 작업본이 캐시에 남지 않았는지, 게이트 B는 한도와 코어 고정이 실제로 물렸는지, 게이트 C는 적재된 데이터가 컨테이너 앞으로 과금되었는지를 확인함. **제어기의 소유를 확정함.** `run_condition.sh`는 "조건이 섰다"까지 책임지고, 그 뒤의 적재기 호출과 부하기 호출과 스냅샷과 저장 부하 뒤 마스터 복원은 제어기(3.4, 부하 도구의 산출물)가 함
- **한계.** 서버에 접속하지 못한 채 작성했으므로 명령의 합격 기준은 표준 도구의 일반적인 출력에 기댄 추정임. 첫 실행에서 출력이 다르면 기준 문구부터 고쳐야 함
- **다음.** 서버 접속 후 1.2, 1.4, 1.5를 실행하고 3.2와 3.3을 제작함. 3.1 변수 정리는 설계서 4.4절로 완료됨

## 4. 위험과 확인 필요

- **라이선스.** 주 데이터의 이용 조건이 어디에도 명시되어 있지 않음. 측정 결과가 사내 보고로만 쓰이는지 외부 공개 계획이 있는지를 먼저 확정해야 하며, 외부 공개 계획이 있다면 라이선스가 명시된 후보(Zenodo Pes2o 등 CC-BY-4.0과 CC0 계열)로 바꿔야 함. 회신이 늦으면 작업 2 전체가 늦어짐
- **동료 인계 시점.** 5.2 본 측정은 1단계가 넘겨줄 병목 조건이 있어야 시작할 수 있고, 합류 시점이 미정임. 우리가 통제할 수 없는 유일한 blocker이므로 인계 자료의 형식(병목 전, 꺾이는 지점, 병목 후의 세 좌표)과 시점을 먼저 합의해야 함. 동료가 쓴 Qdrant 버전도 미리 확인해야 하며, v1.17이면 저장 대기열 기본값이 달라(1M 대 200) 비교가 성립하지 않음
- **서버 합의.** 캐시 비우기, 주기 작업 정지, 주파수 거버너 고정은 호스트 전역 조작이라 같은 서버를 쓰는 다른 작업에 영향을 줌. 공용 서버라면 소유 부서와 독점 사용 창을 합의해야 하고, 캐시 비우기 합의 없이는 조건 전환 스크립트 자체를 돌릴 수 없음
- **NUMA 노드당 메모리.** 노드당 로컬 메모리가 512GB 미만이면 512GB 조건에만 원격 메모리 접근이 섞여 세 조건이 같은 성격의 세 점이 아니게 됨. 1.2에서 가장 먼저 확인함
- **blktrace 비용.** 오버헤드가 IOPS에 비례해 커지므로 항상 켜지 않음. 5.1에서 비용을 재고 5.2에서 켤 조건을 정하며, 오버헤드가 낮은 eBPF 계열(biolatency, biosnoop)도 함께 검토함. 출력은 반드시 `$RAW`에 써서 `$BENCH` 장치의 읽기량 판정을 오염시키지 않음
