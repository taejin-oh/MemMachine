# 0부. 먼저 알아야 할 것

**기준 브랜치.** 이 부의 값(`m=0`, `payload_m=16`, `sys-partition_key` 테넌트 색인, payload 인덱스 11개, `wait=true`)은 MemMachine speedkick 브랜치 `8d7b832` 소스에서 확인했으며, 이 문서가 처음 인용한 옛 브랜치(msr_multiuser `89bec05`)와 같은 값이다. Qdrant 요청 명세는 부록 `emulator_request_spec_2026-09-22.md` 를 참조한다.

## 0.1 용어

| 말 | 뜻 |
|---|---|
| **포인트** | Qdrant에 저장되는 한 건. 벡터 하나와 거기 붙은 payload로 이루어진다 |
| **payload** | 포인트에 붙는 부가 정보. 필터는 이 값으로 건다 |
| **세그먼트** | Qdrant가 데이터를 쪼개 보관하는 단위. 전체를 하나로 두지 않고 여러 세그먼트로 나눈다 |
| **샤드** | 세그먼트들을 담는 상위 단위. 저장 처리를 담당하는 워커가 샤드마다 하나씩 있다 |
| **payload 인덱스** | payload 값으로 걸러내기 위한 보조 자료 |
| **HNSW 그래프** | 비슷한 벡터를 빨리 찾으려고 점들 사이에 미리 깔아 두는 연결망. 전부 훑는 대신 이 연결을 따라가며 찾는다 |
| **테넌트** | 한 사용자 몫의 데이터 묶음. MemMachine은 세션마다 payload 값을 달리해서 구분한다 |
| **옵티마이저** | 뒤에서 도는 정리 담당. 세그먼트를 합치고 HNSW 그래프를 만든다 |
| **WAL** | 실제 반영 전에 "이런 변경을 하겠다"를 먼저 적어 두는 장부 |
| **리콜** | 찾아야 할 정답 중 실제로 찾은 비율 |

## 0.2 검색 하나가 처리되는 과정

```
1. 요청을 받는다
2. 데이터가 여러 세그먼트에 나뉘어 있다 → 세그먼트마다 동시에 찾는다
3. 세그먼트 안에서: 필터에 맞는 게 몇 개쯤일지 먼저 어림잡는다
4. 어림값을 보고 두 길 중 하나를 고른다
      적을 것 같다 → 그냥 전부 훑는다 (전수 스캔)
      많을 것 같다 → HNSW 그래프를 따라간다
5. 세그먼트별 결과를 모아 정렬한다
6. 응답한다
```

**Qdrant는 4번에서 어느 길을 골랐는지, 그 길로 몇 번 갔고 총 몇 초 썼는지 기록해 둔다.** 길이 9가지라 칸이 9개다. 이 기록을 HTTP로 읽어갈 수 있다.

**그러나 3번이 몇 초, 4번 안에서 필터 확인이 몇 초, 거리 계산이 몇 초인지는 알려주지 않는다.** 단계마다 시간을 재는 장치가 Qdrant 안에 없다. 여러 단계를 쪼개 재는 표준 도구(분산 추적)도 지원하지 않는다.

**그래서 소스에 계측 코드를 넣어 직접 얻기로 했다.** 어느 함수의 어느 줄에 넣을지는 소스에서 이미 특정했고(검색 9개소, 저장 9개소), `stage_isolation_2026-09-18.md` 에 정리했다. 방법은 3.2절에 있다.

## 0.3 저장 하나가 처리되는 과정

```
[클라이언트] 저장 요청
     │
     ▼
① 디스크 여유 확인
② 처리 대기줄에 자리 잡기        ← 줄이 꽉 차면 여기서 기다린다
③ WAL에 적기                      (메모리에 복사만. 디스크에 바로 안 쓴다)
     │
     ├─ wait=false 면 여기서 응답
     │
     ▼
─ ─ 여기부터는 샤드마다 하나뿐인 업데이트 워커가 순서대로 ─ ─
     │
④ wait=true 면 WAL을 디스크에 확정      ← 요청마다 발생하는 디스크 비용
⑤ 어느 세그먼트에 넣을지 고른다
⑥ 벡터 저장 → payload 저장 → payload 인덱스 11개 갱신   (전부 이 시점에)
⑦ HNSW 그래프 갱신                      ✗ 여기서 안 한다
     │
     ├─ wait=true 면 여기서 응답
     ▼
─ ─ 이후는 완전히 뒤에서, 클라이언트와 무관하게 ─ ─
     │
⑧ 옵티마이저가 조건을 보고 정리 작업을 시작한다
     여기서 비로소 HNSW 그래프가 만들어진다
```

**세 가지를 기억하면 된다.**

1. **HNSW 그래프는 저장할 때 만들지 않는다.** 나중에 옵티마이저가 만든다. 그래서 저장 응답은 빠른데 그 비용이 뒤로 미뤄진다
2. **payload 인덱스 11개는 저장할 때 바로 갱신한다.** 인덱스가 많을수록 저장이 그만큼 느려진다
3. **`wait=true`는 요청마다 WAL을 디스크에 확정시킨다.** MemMachine이 이 설정을 쓰고 있다

**위 그림은 개념도이고, 소스에서 실제로 세어 보면 저장은 9단계다.** ②와 ④ 사이에 락 대기가 두 곳 더 있다. 특히 **④ WAL 확정과 그 뒤의 전역 쓰기 락 대기는 현재 Qdrant의 어떤 지표에도 잡히지 않는다.** 느린 요청 기록의 소요 시간조차 이 둘이 끝난 뒤부터 재기 시작한다. 단계 목록과 근거는 `stage_isolation_2026-09-18.md` 4장에 있다.

## 0.4 옵티마이저는 단계별 시간을 알려준다

검색과 저장은 단계별 시간을 안 주지만, **정리 작업만큼은 준다.** 우리 구성(`m=0`)에서는 이런 단계로 나온다.

```
Segment Optimizing
├── copy_data                 세그먼트 데이터를 새 세그먼트로 복사   (디스크)
├── populate_vector_storages  벡터 파일을 미리 읽어 캐시에 올림      (디스크)
├── wait_cpu_permit           CPU 자리 기다리기
└── additional_links          payload 필드별 그래프 링크 생성       (CPU)  ← 우리 구성의 주 비용
```

각 단계에 `duration_sec`이 붙는다. **저장 쪽의 무거운 일이 사실상 여기 다 있으므로, 이 창구가 저장 병목 분석의 핵심이다.**

`populate_vector_storages`가 채우는 캐시는 저장소가 어느 백엔드로 열렸느냐에 달렸다. mmap이면 **OS 페이지 캐시**이고, disk_cache 백엔드면 **Qdrant 자체 캐시**다. 상세는 계측 문서 4.3절에 있다.

## 0.5 우리 구성이 특이한 점

MemMachine은 Qdrant를 이렇게 설정해 두었다.

```
m = 0            전체를 아우르는 HNSW 그래프를 만들지 않는다
payload_m = 16   대신 payload 값마다 작은 그래프를 만든다
sys-partition_key 에 테넌트 표시
```

문서상 의도는 세션마다 작은 그래프를 갖는 것이고, 전체 그래프를 안 만들어 적재가 빠르다.

**그러나 실제 동작은 "세션마다 따로"가 아니다.** 소스 확인 결과 payload 값마다 만든 그래프들이 **하나의 링크 집합으로 병합되고**, 검색은 그 병합된 그래프를 한 번 탐색한다. 진입점도 함께 병합되므로 **어느 진입점에서 출발하느냐에 따라 도달하지 못하는 영역이 생긴다.** Qdrant 유지보수자의 설명이 이를 확인한다.

> "if you disable the global HNSW graph (m=0), it becomes disjoint. It starts searching in one part of the graph and can never reach the other part."

**그리고 작은 세션은 애초에 링크를 받지 못한다.** 링크 블록은 포인트 수가 `full_scan_threshold` 를 넘는 값에만 만들어진다. 768차원 float32 기준 약 3,333개가 경계다. 세션 대부분이 수천 개 규모라면 `payload_m=16` 은 그 세션들에 대해 **아무 일도 하지 않고 있다.**

대가는 5.2와 5.3에서 다룬다.

## 0.6 왜 v1.19인가

v1.17과 비교해 **디스크와 메모리를 다루는 방식이 크게 바뀌었고, 그게 이번 실험의 주제와 정면으로 맞물린다.**

| 항목 | v1.17 | v1.19 |
|---|---|---|
| 메모리 설정 모델 | `on_disk` 계열 플래그 | `pinned / cached / cold` 3단계로 통합 |
| 메모리 상태 조회 창구 | **없음** | `/collections/{c}/memory` 있음 (v1.18+) |
| 저장 대기열 기본 길이 | 1,000,000 | **200** |

**메모리 축이 이번 실험의 주 변수인데, 그 상태를 직접 보여주는 창구가 v1.18부터 생겼다.** 그리고 저장 대기열 기본값이 1M에서 200으로 바뀌어 부하가 밀릴 때 클라이언트가 기다리기 시작하는 시점이 완전히 달라졌다. **v1.17 기준 자료의 수치를 그대로 적용하면 안 된다.**

# 1부. 병목 지점은 어떻게 판단할 것인가

"병목"이 세 가지를 뭉뚱그리고 있다. 쪼개야 판정이 된다.

```
① 병목 조건   언제 막히는가               → 부하를 올려 포화점을 찾는다
② 병목 지점   Qdrant 내부 어디서 막히는가  → 저장·검색·정리 중 어느 처리의 어느 단계인가
③ 병목 원인   왜 막히는가                 → CPU·메모리·디스크 중 무엇이 한계인가
```

**셋은 순서가 있다.** ①로 포화 조건을 특정하고, 그 조건을 재현한 상태에서 ②로 처리 단계를 좁힌 뒤, ③으로 자원을 판정한다. 앞 단계가 없으면 뒤 단계는 근거를 잃는다.

**1단계와 2단계의 경계가 ①과 ② 사이다.** ①은 동료가 전체 경로에서 관측하고, 우리는 그 조건을 넘겨받아 ②와 ③을 규명한다.

## 1.1 ① 병목 조건 — 언제 막히는가

동시 요청 수를 한 칸씩 올리면서 두 가지를 본다.

```
동시 요청 1 → 2 → 4 → 8 → 16 ...

처리량(초당 몇 건)이 더 안 오르는데
지연(한 건에 몇 초)만 오르기 시작하는 지점  =  포화점
```

**판정 규칙 (초안).** 동시 요청을 2배로 올렸는데 처리량이 10% 미만으로 오르고 p99 지연이 1.5배 이상 뛰면 포화로 본다. 숫자는 첫 측정 후 조정한다.

## 1.2 ② 병목 지점 — Qdrant 내부 어디서 막히는가

포화 조건을 재현해 둔 상태에서 세 갈래를 차례로 좁힌다.

| 순서 | 물음 | 판정 근거 |
|---|---|---|
| ㉮ | Qdrant 밖인가 안인가 | 클라이언트가 잰 시간 중 Qdrant 응답 대기가 몇 %인가 |
| ㉯ | 저장인가 검색인가 정리 작업인가 | 저장 대기열이 찼는가, 검색 지연이 올랐는가, 정리 작업이 밀렸는가 |
| ㉰ | **그 안의 어느 단계인가** | 검색 S0~S8 / 저장 W0~W8 중 어디에 시간이 쌓였나 |

**㉰이 2단계의 핵심 질문이다.** 그리고 Qdrant가 이 단계별 시간을 기본 제공하지 않는 유일한 항목이기도 하다. 확보 방법은 3.2절에 있다.

## 1.3 ③ 병목 원인 — 왜 막히는가

㉰에서 특정한 단계가 **어느 자원 때문에** 막히는지 판정한다.

| 자원 | 판정 근거 |
|---|---|
| CPU | 컨테이너 CPU 사용률이 할당 한도에 붙었는가 |
| 메모리 | 캐시에 있어야 할 양 대비 실제 올라온 양의 격차가 벌어졌는가 |
| 디스크 | 메모리에 없어 실제로 읽어온 횟수가 늘었는가. 무엇을 읽었는가 |

## 1.4 병목과 구분해야 할 것 — 정확도 위험

이 구성에는 **느려지는 것과 별개로 틀려지는 실패**가 있다.

```
느려진다   ← 위 ①②③으로 판정하는 병목
틀려진다   ← 이 구성 특유의 실패. 병목 판정 축이 아니다
```

**틀려지는 실패는 지연 그래프에 전혀 나타나지 않는다.** 빠르게 대답하는데 답이 틀린 것이라, 응답 시간만 보면 "문제 없음"으로 보인다.

**그래서 병목 측정 항목에 넣지 않고 별도 검토 항목으로 분리했다.** 부하를 올려 포화점을 찾는 일과 결과가 맞는지 확인하는 일은 목적도 측정 구간도 다르다. 섞으면 둘 다 흐려진다. 상세는 5.2절에 있고, 측정은 4.5.3절대로 부하 구간과 분리해 수행한다.

조사가 찾은 실측이 이를 보여준다(1M 규모, 전용 링크가 없을 때).

| 필터가 통과시키는 비율 | 정확도 | 응답 시간 |
|---|---|---|
| 20% | 62.9% | 1.6ms |
| 10% | 20.6% | 1.7ms |
| **1%** | **0.1%** | 1.6ms |

**시간은 거의 그대로인데 정확도만 무너진다.** 탐색 폭을 넓혀도 복구되지 않는다.

## 1.5 1부의 답

```
병목이다 = 부하를 올려도 처리량이 안 늘고 지연만 는다

그 조건을 재현한 뒤 원인을
  Qdrant 밖/안 → 저장/검색/정리 → 내부 단계 → 자원
  순서로 좁힌다

정확도 저하는 병목 판정과 분리해 별도로 확인한다 (1.4, 5.2절)
```

## 3.1 측정 대상별 수단

| 측정 대상 | 수단 | 비고 |
|---|---|---|
| 처리량·지연 분포 | 부하 생성기가 직접 기록 | 가장 신뢰할 수 있다 |
| 정확도 (리콜) | 같은 질의를 `exact: true`로 한 번 더 실행해 비교 | **정답을 Qdrant가 만들어 준다** |
| 9개 경로별 시간 | `/telemetry?details_level=4` 를 부하 전후로 찍어 **차이를 뺀다** | 누적값이라 반드시 뺄셈 |
| 저장 대기줄 | `/collections/{c}` 의 `update_queue.length` | v1.19 상한 200. 200에 붙으면 포화 |
| 정리 작업 밀린 정도 | `/collections/{c}/optimizations` 의 `queued_segments`, `queued_points` | |
| 정리 작업 단계별 시간 | 같은 창구의 `duration_sec` | Qdrant가 기본 제공하는 유일한 단계별 시간 |
| **검색 내부 단계별 시간** | **소스에 계측 코드 삽입** | 기본 기능으로 확보 불가. 3.2절 |
| **저장 내부 단계별 시간** | **소스에 계측 코드 삽입** | 기본 기능으로 확보 불가. 3.2절 |
| 느린 요청 개별 확인 | `/profiler/slow_requests` | 50ms 넘는 것만. 요청 본문 포함 |
| CPU 사용률 | 컨테이너 통계 | |
| CPU를 어느 함수가 쓰나 | Pyroscope 연결 | 재빌드 불필요 |
| 디스크 읽은 양 | 컨테이너의 `io.stat` | 캐시 적중은 안 잡히고 **진짜 디스크 읽기만** 잡힌다 |
| 디스크 읽기의 블록 수준 추적 | `$BENCH` 장치에 `blktrace`, 또는 eBPF 계열 `biolatency`, `biosnoop` | 항목 11(디스크 읽기)의 보조 수단. 항상 켜지 않는다. 아래 설명 |

각 수단의 상세와 한계는 `qdrant_instrumentation_2026-09-17.md` 에 있다.

**디스크 읽기(측정 항목 11)에는 블록 수준 I/O 추적을 보조 수단으로 둔다.** Qdrant 저장소가 `$BENCH` 전용 장치에 있으므로 그 장치의 I/O 는 곧 Qdrant 의 I/O 다. `blktrace` 를 그 장치에 걸면 `io.stat` 의 합계가 보여 주지 못하는 요청 하나하나의 크기와 시각과 완료까지의 시간을 얻는다. 출력은 반드시 `$RAW` 에 쓴다. `$BENCH` 에 쓰면 추적 자체가 항목 11의 읽기량을 오염한다. 오버헤드가 IOPS 에 비례해 커지므로 항상 켜지 않는다. 5.1 예비 측정에서 비용을 재고, 5.2 본 측정에서 켤 조건을 정한다. eBPF 계열(`biolatency`, `biosnoop`)이 오버헤드가 낮은 대안이므로 함께 준비하되, 어느 쪽을 쓸지도 5.1에서 정한다. 도구 준비는 1.2에서 한다.

## 3.2 단계별 시간이 없을 때 — 소스에 계측 코드를 넣는다

검색과 저장은 단계별 시간을 주지 않는다. **Qdrant 소스에 시간을 재는 코드를 직접 넣어 얻는다.**

**계측 지점은 소스에서 함수 단위로 특정을 마쳤다.** 검색 9개소, 저장 9개소다. 전체 목록과 근거 코드는 `stage_isolation_2026-09-18.md` 에 있고, 여기서는 요지만 적는다.

```
검색  S0 세그먼트 읽기 잠금 대기        S4 거리 계산        S7 세그먼트 결과 병합
      S1 카디널리티 추정                S5 결과 수집·정렬    S8 재검색 발생
      S2 필터 평가                      S6 후처리
      S3 스코어러 준비

저장  W0 대기열 자리 확보    W3 전역 쓰기 락 대기   W6 벡터 저장
      W1 WAL 기록           W4 세그먼트 홀더 락    W7 payload 저장
      W2 WAL 확정           W5 세그먼트 선택       W8 색인 갱신
```

**보고할 때는 18개 지점을 그대로 나열하지 않고 여덟 묶음으로 읽는다.** 코드의 18개 지점은 그대로 두고, 읽을 때 검색 4묶음과 저장 4묶음으로 본다. 18개 상세는 묶음에서 이상이 보일 때 파고드는 용도다. 이 묶음 정의가 4.6절의 4.1이다.

| 경로 | 묶음 | 지점 |
|---|---|---|
| 검색 | 잠금 대기 | S0 |
| 검색 | 후보 고르기 | S1, S2 |
| 검색 | 거리 계산 | S3, S4, S5, S6 |
| 검색 | 결과 합치기 | S7. S8은 시간이 아니라 횟수로 본다 |
| 저장 | 대기열 | W0 |
| 저장 | WAL 기록과 확정 | W1, W2 |
| 저장 | 락 대기 | W3, W4 |
| 저장 | 세그먼트 쓰기 | W5, W6, W7, W8. 색인 갱신 W8은 따로 볼 수 있게 남긴다 |

**이 작업이 드러낸 사각지대가 둘 있다.** `W2 WAL 확정`과 `W3 전역 쓰기 락 대기`는 **현재 Qdrant의 어떤 지표에도 잡히지 않는다.** 느린 요청 기록의 소요 시간조차 이 둘이 끝난 뒤부터 재기 시작한다. 현재 설정이 요청마다 WAL 확정을 기다리므로 저장 지연의 상당 부분이 여기일 수 있으나, 계측을 넣기 전에는 확인할 방법이 없다.

**계측 방식이 두 갈래다.**

| 방식 | 대상 | 방법 |
|---|---|---|
| 전후 시각차 | 요청당 1회 호출되는 구간 | 호출 전후 시각을 재어 차이를 기록한다 |
| **누적 카운터** | 루프 안에서 반복 호출되는 구간 (S4, S5, W8) | 시각차를 누적 변수에 더하고 요청이 끝날 때 총합만 기록한다 |

거리 계산은 한 요청에서 수백에서 수만 번 반복되므로, 호출마다 기록하면 **계측 비용이 측정 대상을 넘어선다.** 그래서 누적 방식이어야 한다.

**검증해야 할 것 둘.**

| 항목 | 방법 |
|---|---|
| 계측 자체의 왜곡 | 계측을 넣은 빌드와 넣지 않은 빌드를 같은 부하로 돌려 전체 시간이 달라지지 않음을 확인한다 |
| 대표성 | 공식 배포 이미지와 같은 빌드 설정을 쓰고 소스만 패치한다 |

계측 이미지와 대조 이미지는 같은 소스와 같은 Dockerfile에서 FEATURES 스위치만 달리해 4.6절의 1.1에서 한 번에 둘 다 만든다. 서버 빌드의 동작 확인도 그 자리에서 한다. 왜곡 검증(4.5)은 환경(1단계)과 부하기(3.3)가 있어야 할 수 있다.

**대상 버전을 v1.19.1로 고정한다.** 패치를 따라가며 유지할 필요가 없어진다.

**한 가지는 계측으로도 얻지 못한다.** 그래프 탐색 경로는 순회 도중 필터 확인과 거리 계산이 뒤섞여 단계 경계가 없다. 이 경로는 전체 시간만 얻는다. 다만 현재 구성은 세션 필터를 항상 붙이고 세션 대부분이 임계 미만이라 **전수 비교가 주 경로이므로**, 실질적 손실은 작다.

# 4부. 환경을 어떻게 구축하는가

## 4.1 호스트 구성

단일 서버(344 vCPU / 1TB RAM / 디스크 16TB)에 전부 올린다.

```
┌─ 리눅스 서버 ────────────────────────────────────┐
│                                                  │
│  ┌ Qdrant 컨테이너 ─────────┐  ┌ 부하 생성기 ──┐ │
│  │ CPU  코어 16개 고정      │  │ CPU  다른 코어 │ │
│  │ 메모리 128 / 256 / 512GB │  │ 메모리 별도 한도│ │
│  │ 스왑  꺼짐               │  │               │ │
│  └──────────────────────────┘  └───────────────┘ │
│              ▲                        │          │
│              └────── 네트워크로만 ────┘          │
└──────────────────────────────────────────────────┘
```

**CPU는 개수 제한이 아니라 코어 고정으로 나눈다.** 개수만 제한하면 스레드가 344개 코어 사이를 옮겨 다니며 캐시 지역성을 잃고, 한도를 주기 앞부분에서 소진해 지연이 톱니처럼 튄다.

**코어는 SSD 위치에서 출발해 고른다.** 순서는 SSD 위치, 코어, 메모리 노드다. 먼저 `$BENCH` 가 놓인 NVMe 가 어느 NUMA 노드에 붙어 있는지 확인한다. `/sys/block/` 아래 그 장치의 `device/numa_node` 값이 그것이다. 그 노드에서 서로 다른 물리 코어 16개를 뽑아 Qdrant 에 고정하고, `--cpuset-mems` 도 그 노드로 준다. 부하 도구와 수집기는 다른 노드의 코어를 쓴다. 이렇게 해야 디스크에서 올라온 페이지가 놓이는 메모리와 그 페이지를 읽는 코어와 그 장치가 한 노드에 모여, 메모리 축 세 조건이 원격 접근 없이 같은 성격의 세 점이 된다. 구체적인 명령은 환경 문서 3.1절에 있으며, 그 절의 순서도 코어부터가 아니라 SSD 위치부터로 맞추었다. 이것이 4.6절의 1.2다.

**부하 생성기는 데이터 파일을 직접 만지면 안 된다.** 네트워크로만 접근한다. 이유는 4.3에 있다.

## 4.2 메모리 축을 어떻게 만드나

벡터 총량을 고정한 채 **컨테이너 메모리 한도만 낮춘다.** 어느 지점에서 디스크를 읽기 시작하는지 본다.

```
데이터 고정  ──┬── 메모리 512GB → 다 올라감, 디스크 안 읽음
               ├── 메모리 256GB → 일부 쫓겨남, 디스크 읽기 시작
               └── 메모리 128GB → 많이 쫓겨남, 지연 꼬리가 무너짐
```

조사로 확인했다. **컨테이너를 128GB로 묶으면 호스트에 872GB가 남아 있어도 그 컨테이너는 128GB만 쓰고, 넘치면 실제로 디스크를 읽는다.**

## 4.3 실험을 무효로 만드는 함정

리눅스는 **"그 파일을 누가 먼저 읽었나"로 메모리 사용량을 매긴다.**

```
데이터를 호스트에서 넣는다
  → 그 몫이 호스트 앞으로 달린다
  → 컨테이너는 한도와 상관없이 그 데이터를 공짜로 쓴다
  → 한도를 낮춰도 디스크를 안 읽는다
  → 실험이 통째로 무효
```

**대책 네 가지.**

1. 조건을 바꿀 때마다 컨테이너를 새로 만든다. 한도만 바꾸지 않는다
2. 새로 만들기 직전에 시스템 캐시를 비운다
3. 부하 생성기는 데이터 파일을 직접 만지지 않는다
4. 스왑을 끈다. 안 끄면 디스크 대신 스왑으로 빠져 측정이 오염된다

**2026-09-21에 측정 대상 서버에서 확인했고, 함정은 실재한다.** 16GB 파일과 4GB 한도로 검증했다. 호스트가 먼저 읽은 조건에서 컨테이너는 디스크를 한 번도 읽지 않았고, 한도에 한 번도 부딪히지 않았으며, 자기 앞으로 과금된 양이 0.01GB에 그쳤다. 같은 조건에서 컨테이너가 먼저 읽었을 때는 32GiB를 읽고 한도에 12,296번 부딪혔다.

따라서 **위 대책 네 가지는 권고가 아니라 지키지 않으면 측정이 무효가 되는 조건이다.** 특히 "한도만 바꿔서 다시 측정"은 금지한다. 검증 절차와 실측값은 `cgroup_trap_check_2026-09-21.md` 에 있다.

검증 과정에서 판정 기준 하나를 바로잡았다. 처음에는 읽기 소요 시간을 1차 근거로 삼았으나, 디스크를 읽은 조건이 32GiB를 초당 7.6GB로 읽었고 이 값은 디스크 속도가 아니라 단일 스레드 `dd`의 메모리 복사가 병목이라는 뜻이다. 캐시에서 읽는 조건도 같은 복사를 해야 하므로 빨라질 여지가 없었고, 캐시 적중과 디스크 읽기의 시간 차이가 나지 않았다. **판정은 cgroup 계수기로만 해야 한다.** 근거는 `cgroup_trap_check_2026-09-21.md` 6.1절에 있다.

## 4.4 에뮬레이터 구조

MemMachine 서버 없이 **Qdrant에 직접 요청을 보내는 도구**를 만든다. 아래 값을 전부 실행 파라미터로 노출해 조건을 임의로 조합할 수 있게 한다.

```
제어 파라미터
  포인트 수        1만 ~ 1억
  벡터 차원        768 / 1024 / 1536 / 2560
  세션 수          1 ~ 10만
  세션당 포인트 수  분포까지 지정
  필터 통과 비율   1% ~ 99%
  필터 조합        파티션 키만 / 파티션 키 AND 사용자 조건
  동시 요청 수     1 ~ 1000
  검색 대 저장 비율
  top_k            임의
  저장 배치 크기   1 ~ 256
  wait             true / false
  payload 인덱스 개수  0 ~ 12 (long_term 은 11개, semantic 은 12개. 부록 3장)
```

**충실도 검증**: 원문 트레이스(`trace_qdrant_requests_raw.py` 로 채취, 부록 9장)와 에뮬레이터가 보내는 요청의 모양을 대조해 같음을 보인다.

**도구는 적재기, 부하기, 제어기의 세 프로그램으로 나눈다.** 위 파라미터 가운데 포인트 수, 벡터 차원, 세션 수, 세션당 포인트 수 분포, payload 인덱스 개수는 데이터 형상이라 적재기가 쓰고, 나머지는 부하 형상이라 부하기가 쓴다. 세션 배정은 적재기가 데이터를 넣으면서 세션 키를 붙이는 방식으로 하며, 세션 수와 크기 분포는 위 변수이고 기본 분포는 zipf(s=1.0)다. 라벨 파일을 미리 만들어 두는 방식은 쓰지 않는다. 적재 완료 판정과 적재 후 마스터 사본 생성도 적재기의 몫이다. 제어기는 조건 전환 스크립트를 호출한 뒤 적재기와 부하기와 수집을 순서대로 돌리는 프로그램이며, 부하 도구의 산출물이다. 4.6절의 3.2, 3.3, 3.4가 각각 이 셋이고, 위 파라미터 목록이 3.1이다. 상세는 `emulator_spec_2026-09-21.md` 3장과 4장에 있다.

## 4.5 데이터 준비

### 4.5.1 합성 벡터란 무엇인가

**합성 벡터**는 실제 문장을 임베딩해서 얻은 것이 아니라, 프로그램으로 숫자를 만들어 낸 벡터다.

**균등 무작위**는 그중 가장 단순한 방법이다. 벡터 하나가 숫자 768개라면 그 768개를 각각 독립적으로 난수로 채운다.

```
실제 임베딩    "고양이가 잠을 잔다"  →  임베딩 모델  →  [0.03, -0.11, 0.27, ...]
합성 (균등)    난수 생성기                              [0.71, -0.44, 0.09, ...]
```

**균등 무작위가 문제가 되는 이유.** 차원이 높으면 이렇게 만든 벡터들끼리 거리가 거의 다 같아진다. 어느 두 점을 뽑아도 비슷한 거리가 나온다. 그러면 "가장 가까운 것 10개"와 "아무거나 10개"의 차이가 사라져서, 리콜을 재도 그 숫자가 실제 상황을 예측하지 못한다.

실제 임베딩은 반대다. 비슷한 뜻의 문장이 가까이 모여 **군집**을 이루고, HNSW 그래프는 바로 그 군집 구조를 이용한다. 군집이 없으면 그래프가 실제와 다르게 만들어진다.

그래서 합성을 쓰더라도 **군집 구조를 넣어야** 한다. 군집 중심을 여럿 두고 그 주위에 흩뿌리는 방식이다.

### 4.5.2 측정 축은 따로 도는 실험이 아니다

한 번의 측정에서 처리량, 지연, 디스크 읽기, 리콜을 **동시에** 잰다. 축을 나눈 것은 "따로 실험한다"는 뜻이 아니라 **데이터가 결과를 얼마나 바꾸는가**가 다르다는 뜻이다.

| 데이터가 결과를 바꾸는 정도 | 측정 대상 | 이유 |
|---|---|---|
| **거의 안 바꾼다** | 메모리 점유 · 디스크 읽은 양 · 저장 처리량 | 벡터 값이 무엇이든 개수와 바이트가 같으면 같다 |
| **조금 바꾼다** | 전수 스캔 구간의 검색 지연 | 거리 계산 횟수가 포인트 개수에만 달렸다 |
| **많이 바꾼다** | 그래프 탐색 구간의 검색 지연 · **리콜** | 벡터가 어떻게 뭉쳐 있느냐에 직접 달렸다 |

그래서 **"메모리 한도를 낮춘 상태에서 처리량과 지연을 본다"** 는 조합은 그 자체가 이번 실험의 핵심이고, 데이터 요구는 그때 어느 경로를 타느냐로 갈린다.

```
그 구간이 전수 스캔이다    →  합성 벡터로 충분하다
그 구간이 그래프 탐색이다  →  군집 구조가 결과를 바꾼다
```

어느 경로였는지는 사후에 확인할 수 있다. `/telemetry`의 9칸 중 어디에 시간이 쌓였는지 보면 된다.

### 4.5.3 리콜은 언제 재는가

**"필요할 때만 쓰는 검증 도구"가 아니다.** 용도가 둘이고 성격이 다르다.

**용도 ① 상시 측정 — 병목 판정의 한쪽 축**

1부의 판정 (나)가 이것이다. 부하를 올릴 때 지연은 그대로인데 리콜이 무너지는 것이 이 구성 특유의 실패라서, **각 측정점마다 같이 재야 한다.**

**용도 ② 합성 데이터 검증 — 실험 초기에 한 번**

합성 벡터가 실제와 같은 리콜 곡선을 주는지 맞춰보는 작업이다. 안 맞으면 합성 파라미터를 고친다.

**비용 문제와 대책.** 정답을 만드는 `exact` 검색은 전수 스캔이라 비싸다. 그래서 모든 요청을 그렇게 재지 않는다.

```
부하 구간      평소 검색만 돌린다. 리콜은 재지 않는다
측정점마다     부하를 멈추고, 미리 정한 질의 집합으로
               평소 검색과 exact 검색을 각각 한 번씩 돌려 비교한다
```

**부하 중에 exact를 섞으면 그 자체가 부하를 왜곡한다.** 측정 구간을 분리하는 것이 핵심이다.

### 4.5.4 확보 방법

**선택지는 따로 정리했고 2026-09-21에 골랐다.** `dataset_options_2026-09-17.md` 에 25가지 방법을 7개 기준으로 비교해 두었다. 주 데이터는 Zilliz의 `laion_large_100m`(212GB, 1억 건, 768차원)이고, 차원 스윕은 Zenodo의 Pes2o(39.7GB, 829만 건, 2560차원)이며, 스모크 테스트는 525MB 소형 데이터로 한다. 절차는 `dataset_download_2026-09-21.md` 에 있고 4.6절의 2단계가 그것이다. 세션 라벨은 데이터셋에서 가져오지 않고 3.2 적재기가 배정한다.

| 측정 축 | 필요한 데이터 |
|---|---|
| 메모리·디스크·저장 처리량 | 합성 벡터, 1억 개까지 |
| 전수 스캔 구간의 지연 | 합성 벡터 |
| 그래프 탐색 구간의 지연 | 합성 벡터. 단 군집 구조 필요 |
| **리콜** | **실제 임베딩, 수백만 개** |

**정답은 데이터셋이 아니라 Qdrant가 만들어 준다.** 같은 질의를 `exact: true`로 돌리면 전부 훑어서 진짜 정답을 준다. 그래서 "정답이 딸려 있는 데이터셋"을 구할 필요가 없고, 선택지가 넓어진다.

### 4.5.5 확정된 전제

| 항목 | 값 | 무엇이 달라지나 |
|---|---|---|
| 서버 GPU | **있다** | 실제 데이터의 통계를 떠서 대량 생성하는 방법을 쓸 수 있다. 목표의 1/100만 받으면 되므로 다운로드가 264GB에서 2~4GB로 줄어든다 |
| 양자화 (벡터 압축) | **실험 축에 넣지 않는다** | 좌표를 섞는 방법들이 후보로 되살아난다 |
| 세션당 포인트 수 분포 | **우리가 정해도 된다** | 실제 라벨이 들어 있는 데이터셋의 이점이 사라져 후보 선택이 단순해진다 |
| 디스크 | **16TB (확장 가능)** | 용량은 제약이 아니다. 전체 규모 스냅샷을 여러 벌 들고 있을 수 있다 |

**규모의 상한 하나.** 2560차원 1억 개는 벡터만 1,024GB라 RAM 1TB에 들어가지 않는다. 이 조합은 "메모리에 전부 올라간 상태"를 기준선으로 삼을 수 없다. 네 차원을 모두 1억 개로 보관하면 약 2.36TB다.

## 4.6 작업 순서

작업은 다섯 단계로 나누고, **모든 문서가 아래 번호와 이름을 쓴다.** 이전 판의 0번부터 7번까지의 번호는 폐기했다. 다른 문서에 "설계서 4.6절 N번"이라고 남아 있는 곳은 모두 아래 번호로 읽는다. 부하 도구 문서 8.1절의 제작 순서 M0부터 M6까지는 단계 번호가 아니라 "제작 순서"이며, 이 표의 3단계 안에서 무엇을 먼저 만드는지를 정한 것이다.

이 절의 단계 번호는 "이 문서의 위치"에 적은 과제 전체의 1단계부터 3단계와는 다른 것이다. 이 절과 4.6.1절에서 과제 단계를 가리킬 때는 "과제 1단계"처럼 적어 구분한다.

상태는 네 가지로 적는다.

| 상태 | 뜻 |
|---|---|
| 완료 | 실물로 확인했다 |
| 작성됨·미실행 | 절차나 스크립트는 있으나 측정 서버에서 돌리지 못했다 |
| 명세만 | 무엇을 만들지는 정했으나 코드가 없다 |
| 미착수 | 절차도 명세도 없다 |

| 단계 | 항목 | 상태 | 막고 있는 것 | 절차가 있는 곳 |
|---|---|---|---|---|

### 4.6.1 2026-09-21 기준 진행 상황

**1.3 함정 확인이 끝났고 함정은 실재하는 것으로 확인되었다.** 그 결과 4.3절의 대책 네 가지가 측정 절차의 필수 조건이 되었다. 다만 이것이 "조건마다 적재를 다시 해야 한다"는 뜻은 아니다. 원칙은 **조건마다 컨테이너가 데이터 페이지를 처음 만져야 한다**는 것이고, 방법은 재적재가 아니라 호스트가 3.2 적재기가 만들어 둔 마스터 사본을 작업본으로 복사한 뒤 시스템 캐시를 비우고, 컨테이너를 새로 띄워 그 작업본을 처음 읽게 하는 것이다. 재적재는 수 시간이 걸리지만 복사는 약 6분이다. 환경 문서 5.5절의 `RELOAD=copy` 기본값이 이 원칙을 따르고, 캐시에 잔류가 없는지는 게이트 A가, 디스크 읽기가 실제로 컨테이너 앞으로 과금되는지는 게이트 C가 조건마다 증명한다. 재적재(`RELOAD=ingest`)는 마스터가 없거나 게이트가 실패했을 때의 대안일 뿐이다. 함정 검증 문서 7.1절의 "조건마다 적재를 다시 해야 한다"는 서술은 이 원칙으로 바로잡는다.

**4단계 계측은 4.5 왜곡 검증만 남았다.** 18개 지점을 삽입한 패치를 깨끗한 v1.19.1 클론에 적용해 지점 수를 확인했고, 개발 빌드로 서버를 띄워 저장 아홉 단계와 검색 여덟 단계가 실제로 값을 올리는 것을 보았다(4.2, 4.3, 4.4). 서버 빌드의 확인은 1.1에서 계측 이미지와 대조 이미지를 함께 만들 때 한다. 왜곡 검증은 환경(1단계)과 부하기(3.3)가 있어야 할 수 있다. 절차는 `instrumented_build_2026-09-21.md` 에 있다.

**2단계 데이터는 확보 방법이 정해졌다.** 주 데이터는 Zilliz의 `laion_large_100m`(212GB, 1억 건, 768차원)이고 인증 없이 받을 수 있으며, 차원 스윕은 Zenodo의 Pes2o(39.7GB, 829만 건, 2560차원)로 분리했다. 절차는 `dataset_download_2026-09-21.md` 에 있다. 다만 Zilliz 배포본의 라이선스가 어디에도 명시되어 있지 않아 2.1 라이선스 확인이 2.2 받기보다 앞선다.

**1단계 환경 준비와 3단계 부하 도구는 절차와 명세가 나와 있고 실행과 구현이 남았다.** 환경 준비는 `environment_setup_2026-09-21.md` 와 `metrics_collection_2026-09-21.md` 에 절차와 스크립트가 있으나 측정 서버에서 한 번도 돌리지 못했다. 부하 도구는 `emulator_spec_2026-09-21.md` 가 적재기와 부하기와 제어기의 역할과 명령행 계약을 정했고 코드는 없다. 세션 배정은 3.2 적재기가 데이터를 넣으면서 세션 키를 붙이는 방식으로 하고, 데이터 문서 3.8절의 라벨 parquet 사전 생성 방식은 쓰지 않는다. 제어기는 3.4로서 부하 도구의 산출물이며, 환경 문서의 `run_condition.sh` 는 "조건이 섰다"까지만 책임진다.

받을 것을 **세 부류로 나눈다.** 성격이 달라서 섞어 놓으면 무엇을 왜 받는지 불분명해진다.

| 세션당 포인트 수 | 세션 하나에 몇 개씩. 분포까지 |
| 벡터 차원 | |
| 동시 요청 수 | |
| **검색 대 저장 비율** | 예: 검색 9 저장 1. **이것도 실험 변수다.** 저장은 샤드당 워커 하나로 직렬화되고 옵티마이저를 깨우므로, 같은 동시 요청 수라도 비율이 다르면 결과가 다르다 |

**총 포인트 수는 받지 않아도 된다.** 세션 수 × 세션당 포인트 수로 계산된다. 검산용으로만 같이 받는다.

**세 좌표로 받는다.** 값 한 벌이 아니라 세 벌이다.

```
병목 전 (여유)  →  꺾이는 지점  →  병목 후 (포화)
```

꺾이는 지점만 받으면 우리 재현이 맞는지 판정할 기준이 없다.

## 5.2 이 구성의 알려진 위험

### 위험 1 — 조건을 겹쳐 걸면 정확도가 무너질 수 있다

Qdrant는 **payload 필드 하나하나에 대해 그래프 링크를 만들지, 필드 조합에 대해 만들지 않는다.** 우리 구성은 세션 필드에 링크가 있다. 여기에 사용자 조건을 더 걸면(방식 B), **그 조합에는 전용 링크가 없다.** 조건이 강하게 걸러낼수록 정확도가 떨어질 수 있다.

**이것은 MemMachine의 결함이 아니라 Qdrant의 구조적 한계다.**

**확인 항목으로 정식 등록한다.**

| 확인할 것 | 방법 |
|---|---|
| 세션 링크만 있을 때의 리콜 | 파티션 키 필터만 걸고 `exact` 대비 리콜 측정 |
| 세션 + 사용자 조건일 때의 리콜 | 두 조건을 AND로 걸고 같은 측정. 통과 비율을 1%~99%로 스윕 |
| 저하가 시작되는 통과 비율 | 위 스윕에서 리콜이 꺾이는 지점 |

이 결과는 **사용자 분리 방식 A/B 결정에 직접 들어간다.** 기존 발표 자료의 A/B 비교표에는 "검색 정확도" 항목이 없어 보강이 필요하다.

### 위험 2 — 같은 구성에서 정확도가 무너진 보고가 열려 있다

**우리 구성과 같은 형태에서 정확도가 무너진 보고(#7147)가 있고, 아직 열려 있으며 원인이 밝혀지지 않았다.**

경과가 좋지 않다.

| 시점 | 내용 |
|---|---|
| 개설 | `m=0, payload_m=32`, 테넌트 표시, 477만 포인트. 자기 벡터로 검색했는데 top-100 안에 34%만 나옴 |
| 1차 우회 | `payload_m` 을 0으로 바꿨다 되돌려 재빌드 → 정밀도 0.9995로 회복 |
| 악화 | 하루 91만 포인트 적재 후 **정밀도 0.2625**. 재빌드 우회가 더는 듣지 않음 |
| 현재 | v1.16.3, v1.17.0에서도 미해결. 유지보수자도 재현하지 못함 |
| 제3자 | `m=0, payload_m=16` 에서 정밀도 0.4를 겪은 별도 보고. 답변 없이 남아 있음 |

**우리가 할 일이 정확히 대량 적재라 재현 가능성이 낮지 않다.** 그리고 제3자 보고의 구성이 우리와 정확히 같다.

**그래서 실험 순서를 바꾼다.** 부하 측정에 앞서 **현재 구성이 이미 이 문제를 겪고 있는지부터 판정한다**(5.3의 실험 1).

### 위험 3 — 큰 세션이 있으면 정리 비용이 커진다

`m=0`이면 그래프 링크를 만들 때 블록 크기 상한이 사라져서, 포인트가 많은 세션은 그 비용을 전부 치른다. 세션별 포인트 수 분포를 실험 변수로 잡아야 한다.

## 5.3 대안 — 그래프를 아예 쓰지 않는 구성

제기된 질문은 이것이었다. 정확도만 놓고 보면 `payload_m`도 0으로 두어 **그래프를 아예 만들지 않고 전수 스캔만 하는 편이 더 정확하지 않은가.**

**조사 결론: 맞다. 조건 셋이 붙는다.**

### 5.3.1 그래프를 끄면 어떻게 되는가

`m=0` 이면서 `payload_m` 도 0이면 검색이 **항상** 전수 스캔으로 간다. 필터가 있든 없든 다른 분기가 끼어들 여지가 없다. 세그먼트 안에서는 필터를 통과한 모든 포인트를 빠짐없이 채점하므로 그 세그먼트에 대한 정확한 답이다. 세그먼트 결과를 합치는 과정도 손실이 없다(코드 분석 기준. 공식 보증 문구는 없다).

**붙는 조건 셋.**

| 조건 | 안 지키면 |
|---|---|
| 양자화(벡터 압축)를 쓰지 않아야 한다 | 전수 스캔이 압축된 벡터로 채점해 정확하지 않다. **우리는 양자화를 실험 축에서 뺐으므로 해당 없다** |
| 세션이 작아야 실용적이다 | 비용이 세션 크기에 정비례한다 |
| strict mode에서 exact 검색을 막아두지 않아야 한다 | 요청 자체가 거부된다 |

### 5.3.2 판단을 바꾸는 발견 — 현재 구성은 이미 절반쯤 이 상태다

**링크 블록은 포인트 수가 `full_scan_threshold` 를 넘는 값에만 만들어진다.**

| 차원 (float32) | 링크를 받는 경계 |
|---|---|
| 768 | 3,333개 |
| 1536 | 1,666개 |

**세션 대부분이 수천 개 규모라면 `payload_m=16` 은 그 세션들에 대해 아무 일도 하지 않고 있다.** 질의 시점에도 임계 미만이라 전수 스캔으로 간다.

즉 그래프를 끄는 변경은 **작은 세션의 동작을 바꾸는 것이 아니라, 큰 세션에만 만들어지던 그래프를 없애는 것**이다. 세션 크기 분포가 이 결정을 가른다.

### 5.3.3 네 구성 비교

| 구성 | 정확도 | 검색 속도 | 적재 속도 | 메모리 |
|---|---|---|---|---|
| **A** `m=16` 전역 그래프 | 단일 필터는 강함(99% 안팎). **조합 필터에서 무너짐** (4%에서 63.7%, 0.012%에서 1.8%) | 1.0~1.2ms | **4.4~5.6배 느림** | 전역 그래프 + 필드별 링크 |
| **B** `m=0, payload_m=16` **현재** | 미해결 보고 다수(위험 2). 전역 검색은 설계상 깨짐 | 큰 세션은 그래프, 작은 세션은 전수 스캔 | 빠름 | 큰 세션의 링크만 |
| **C** `m=0, payload_m=0` 그래프 없음 | **구조적으로 정확** | 필터 통과 포인트 수에 정비례 | **가장 빠름** | **링크 0** |
| **D** C + payload 인덱스 제거 | C와 같음 | **훨씬 느림** | 가장 빠름 | 가장 적음 |

수치는 Qdrant 공개 측정(v1.18.2, 100만 개, 96차원, 노트북급)이라 **절대값이 아니라 비율로 읽어야 한다.**

### 5.3.4 payload 인덱스는 빼면 안 된다

**구성 D는 정확도 이득이 없으면서 속도만 크게 잃는다.** 이유는 처리 순서다.

```
인덱스 있음   필터로 대상을 먼저 좁힌다 → 그 포인트만 채점
인덱스 없음   세그먼트 전체를 훑으며 포인트마다 payload를 읽는다
```

세션 밖 벡터는 거리 계산을 한 번도 하지 않는 것이 멀티테넌트에서 전수 스캔이 성립하는 이유인데, 인덱스를 빼면 그 순서가 깨진다.

**`is_tenant=true` 도 유지해야 한다.** 이 표시가 있으면 정리 작업 때 같은 세션의 포인트를 디스크에 붙여 배치한다. 전수 스캔은 "한 세션의 벡터를 전부 읽는" 동작이라 **이 효과가 오히려 더 중요해진다.** 흩어져 있으면 임의 접근, 모여 있으면 순차 접근이 된다.

### 5.3.5 전수 스캔이 느리다는 통념

관련 이슈(#10311)에서 제보자가 **"작은 세그먼트에도 그래프를 쓰자"고 제안했다가 벤치마크 후 스스로 철회했다.**

> "below roughly 20k live points a linear scan beats graph traversal, and forcing the graph there costs up to 60% of search time."

**약 2만 포인트 미만에서는 전수 스캔이 그래프보다 빨랐다.** 이 이슈는 결과적으로 전수 스캔을 지지하는 근거다.

### 5.3.6 조사가 권고한 것

**정확도가 최우선이면 구성 C다.** 단 payload 인덱스와 `is_tenant=true` 는 유지한다.

큰 세션이 섞여 있으면 대안이 둘이다.

1. `m=16` 으로 전역 그래프를 복구하고, 조합 필터 질의에만 ACORN을 켠다. 측정치로 4% 교집합에서 39.7%에서 100%로, 지연은 1.1ms에서 7.3ms로. 대신 적재가 4~5배 느려진다
2. 구성 C를 기본으로 두고 큰 세션만 달리 처리한다. 다만 Qdrant 설정은 컬렉션 단위라 컬렉션을 분리해야 한다

### 5.3.7 먼저 해야 할 실험

**실험 1이 가장 시급하다.** 부하 측정보다 앞선다.

| # | 실험 | 방법 |
|---|---|---|
| **1** | **현재 구성이 이미 정확도 문제를 겪는지 판정** | 세션별로 포인트 1,000개를 뽑아 각 포인트의 벡터로 그 세션을 검색한다. 자기 자신이 top-100에 들어오는 비율을 센다. 정상이면 100%에 가까워야 한다. `exact: true` 와 비교한다. **세션 크기별로 나눠 집계하면 임계값 경계 효과도 같이 보인다** |
| 2 | 정확도 기준선 만들기 | 질의 200~500개를 `exact` 로 돌려 정답으로 저장. 조합 필터와 단일 필터를 **반드시 분리해 집계** |
| 3 | 전수 스캔 지연 측정 | 세션 크기 분포를 먼저 구하고, 구간별 대표 세션의 지연을 C 구성에서 측정 |
| 4 | 구성별 메모리 실측 | A·B·C 컬렉션을 만들어 링크 파일 크기를 직접 잰다 |

## 5.4 아직 정하지 않은 것

| 항목 | 상태 |
|---|---|
| 벡터 데이터를 어떻게 확보할 것인가 | **확정(2026-09-21).** 주 데이터 `laion_large_100m`, 차원 스윕 Pes2o(4.5.4절). 남은 것은 2.1 라이선스 확인뿐이다 |
| 그래프 없는 구성으로 바꿀 것인가 | **조사 완료(5.3), 결정 대기.** 세션 크기 분포와 실험 1 결과가 정해야 한다 |
| 세션당 포인트 수 분포 | **방식 확정.** 3.2 적재기가 데이터를 넣으면서 세션 키를 붙이고, 분포는 3.1의 변수로 두며 기본값은 zipf(s=1.0)다(부하 도구 문서 3.3절). 실제 서비스의 분포는 과제 1단계 인계 값(5.1절)으로 대체한다 |
| 포화 판정의 구체적 임계값 (1.1절의 10%, 1.5배) | 5.1 예비 측정 후 조정 |
| "준비 완료"의 정의 | **항목 확정.** 1.4에서 한도, 코어 고정, 스왑 차단, NUMA 정합을 컨테이너의 cgroup 값에서 읽어 확인한다. 통과 기준의 수치는 첫 실행에서 정한다 |
| 동료의 1단계 합류 시점 | 미정 |

**측정 설계 자체는 확정되었다.** 측정 항목 11개(2부), 항목별 확보 수단(3.1), 계측 지점 18개소(3.2)가 정해졌으므로 **환경 구축과 도구 제작은 위 미결 항목을 기다리지 않는다.**

**조사로 확인된 공백 하나.** 합성 데이터가 실제와 같은 정확도를 주는지 비교한 자료는 전부 **전역 HNSW 그래프를 하나 두는 구성**을 전제로 한다. 우리 구성은 전역 그래프를 만들지 않고 payload 값마다 만든 링크를 **하나의 집합으로 병합해** 쓴다(0.5절). 그래서 합성 데이터의 군집 구조를 전체 규모에서 맞추는 것으로 충분한지, **세션 단위로도 맞춰야 하는지**를 다룬 자료가 없다. 소규모로 두 조건을 만들어 직접 비교해야 한다.

## 5.5 이 문서가 기대고 있는 조사

| 주제 | 결론 요약 |
|---|---|
| Qdrant 검색 관측 수단 | 단계별 타이머 없음. 경로별 9칸이 최선. 분산 추적 미지원 |
| Qdrant 쓰기 경로와 옵티마이저 | 저장도 단계별 없음. 단 정리 작업은 단계별 시간 제공 |
| 리눅스 메모리 한도와 mmap | 한도는 실제로 물린다. 단 "먼저 읽은 쪽에 과금" 함정이 있다 |
| 벡터 데이터 확보 방법 | 25가지 정리. 개수와 차원은 서로 다른 방법이 담당한다 |
| 그래프 없는 구성의 정확도 | 구조적으로 정확. 단 세션 크기가 비용을 가른다. 현재 구성은 작은 세션에 대해 이미 같게 동작 중 |
| **검색·저장 내부 단계와 계측 지점** | v1.19.1 소스에서 검색 9개소·저장 9개소를 함수 단위로 특정. **WAL 확정과 전역 쓰기 락 대기가 기존 지표의 사각지대** |

세 조사 모두 Qdrant 소스와 리눅스 커널 문서를 근거로 삼았고 버전을 명시했다. 확인하지 못한 항목은 각 조사가 별도로 표시해 두었다.

## 5.6 이전 설계와의 관계

`docs/msr/db_bottleneck/design_progress_2026-09-14.md` 에 PostgreSQL과 Qdrant를 함께 보는 설계가 있고 확정 결정 11개가 들어 있다. 이번 설계는 그중 셋을 바꾼다.

| 항목 | 이전 | 이번 |
|---|---|---|
| 범위 | PG와 Qdrant 함께 | **Qdrant만** |
| 에뮬레이터 방식 | MemMachine 저장소 클래스 재사용 | **Qdrant에 직접 요청** |
| 문서 | 그 문서를 이어 씀 | **이 문서로 새로 씀** |

이전 문서는 근거 자료로 남긴다.
