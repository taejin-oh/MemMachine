# cgroup 메모리 과금 함정 검증 절차

- 작성일: 2026-09-21
- 대상: 리눅스 cgroup v2 + Docker
- 관련: `design_2026-09-17.md` 4.3절(함정)
- 위치: 확정된 단계 구조에서 이 문서는 **1.3 함정 확인**에 해당하며 상태는 완료다(6.2절). 옛 "설계서 4.6절 0단계"라는 번호는 더 쓰지 않는다. 이 결과를 이어받아 조건마다 지키는 절차는 `environment_setup_2026-09-21.md` 5장에 있다

---

## 1. 요약

리눅스는 파일 캐시를 **먼저 읽은 cgroup 앞으로 과금한다.** 컨테이너의 메모리 한도는 그 cgroup이 과금받은 양에만 걸리므로, 호스트가 데이터를 먼저 읽어 캐시에 올려 두면 컨테이너는 한도와 무관하게 그 데이터를 쓰게 된다. 그러면 한도를 낮춰도 디스크를 읽지 않아, 2단계 실험의 전제인 "메모리를 줄이면 디스크 읽기가 늘어난다"를 관측할 수 없다.

이 문서는 그 현상이 **실제 서버에서 일어나는지**를 16GB 파일과 4GB 한도로 확인하는 절차다. 같은 파일을 누가 먼저 읽었는지만 바꿔 두 번 읽고, 컨테이너가 디스크를 읽었는지 비교한다.

| 조건 | 읽는 순서 | 함정이 실재한다면 |
|---|---|---|
| **B (기준선)** | 캐시를 비우고 **컨테이너가 먼저** 읽는다 | 한도에 걸려 디스크를 16GB 읽는다 |
| **A (함정)** | 캐시를 비우고 **호스트가 먼저** 읽는다 | 디스크를 거의 읽지 않는다 |

두 조건의 결과가 **다르면 함정이 실재**하고, 4.3절의 대책 네 가지가 본 실험의 필수 절차가 된다. 같으면 대책 없이 진행해도 된다.

소요 시간은 파일 생성 약 2분, 측정 두 번 약 3분으로 전체 5~10분이다.

## 2. 사전 확인

아래 다섯 줄을 먼저 확인한다. 하나라도 어긋나면 측정이 무효가 되므로 넘어가지 않는다.

```bash
stat -fc %T /sys/fs/cgroup/
cat /sys/fs/cgroup/cgroup.subtree_control
free -h
df -Th /var/tmp
docker info --format 'cgroup={{.CgroupVersion}} driver={{.CgroupDriver}}'
```

각 줄에서 볼 것은 다음과 같다.

첫 줄은 `cgroup2fs` 여야 한다. `tmpfs` 가 나오면 cgroup v1이고, v1은 과금 방식이 달라 이 절차가 그대로 적용되지 않는다.

둘째 줄에 `memory` 가 있어야 한다. `io` 도 있으면 컨테이너별 디스크 읽기량을 직접 읽을 수 있고, 없으면 `io.stat` 이 비어 나온다. 그 경우에도 `memory.current` 와 한도 도달 횟수로 판정한다.

셋째 줄의 여유 메모리가 **20GB 이상**이어야 한다. 조건 A에서 호스트가 16GB를 통째로 캐시에 올려야 하기 때문이다.

넷째 줄에서 파일시스템 종류를 본다. `btrfs` 나 `zfs` 처럼 압축을 쓰는 경우 뒤에서 만들 더미 파일이 실제로는 훨씬 작게 저장되어 디스크 읽기량이 왜곡된다. 이 절차는 난수로 파일을 채워 그 위험을 줄이지만, 압축 파일시스템이면 `ext4` 나 `xfs` 위의 경로로 바꾸는 편이 안전하다.

다섯째 줄은 Docker가 실제로 cgroup v2를 쓰는지 확인한다.

## 3. 더미 파일 만들기

```bash
F=/var/tmp/trap_test.bin
sudo dd if=/dev/urandom of=$F bs=1M count=16384 status=progress
ls -lh $F
du -h $F
```

난수로 채우는 이유는 두 가지다. 파일시스템 압축을 피하고, 0으로 채운 파일이 희소 파일(sparse file)로 저장되어 디스크를 실제로 읽지 않는 상황을 막기 위해서다.

`ls -lh` 가 보여 주는 크기와 `du -h` 가 보여 주는 크기가 **둘 다 16G 근처로 같아야 한다.** `du` 쪽이 훨씬 작으면 희소 파일이므로 읽어도 디스크에 가지 않아 실험이 무효다.

## 4. 조건 B — 컨테이너가 먼저 읽는다

먼저 기준선을 잡는다. 이것이 "메모리 한도가 정상적으로 물릴 때의 모습"이다.

### 4.1 캐시 비우기

```bash
sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'
free -h
```

`free -h` 의 `buff/cache` 값이 크게 줄었는지 확인한다. 줄지 않았다면 직전 단계가 듣지 않은 것이므로 그대로 진행하면 안 된다.

### 4.2 한도 4GB 컨테이너를 먼저 띄운다

```bash
CID=$(docker run -d --memory=4g --memory-swap=4g -v "$F":/data/f:ro alpine sleep 900)
PID=$(docker inspect -f '{{.State.Pid}}' "$CID")
CG=/sys/fs/cgroup$(grep '^0::' /proc/$PID/cgroup | cut -d: -f3)
echo "$CG"
```

`--memory-swap` 을 `--memory` 와 같은 값으로 주면 그 컨테이너만 스왑이 막힌다. 호스트 전체의 스왑을 끄지 않고도 스왑 오염을 피할 수 있어, 공용 서버에서는 이 방식이 안전하다. 본 측정에서도 스왑 차단은 이 컨테이너 단위 방식으로 하고 호스트 전역 `swapoff` 는 쓰지 않는다. 근거는 `environment_setup_2026-09-21.md` 3.4절과 준비 문서 3.5절에 있다.

`sleep 900` 으로 컨테이너를 살려 두는 이유는, 컨테이너가 종료되면 cgroup 디렉터리가 사라져 계수기를 읽을 수 없기 때문이다.

마지막 줄이 `/sys/fs/cgroup/system.slice/docker-....scope` 같은 경로를 출력해야 한다. 아무것도 안 나오면 다음 단계가 전부 실패하므로 여기서 멈추고 확인한다.

### 4.3 읽기 전 계수기를 기록한다

```bash
awk '{printf "memory.current = %.2f GiB\n", $1/1073741824}' "$CG/memory.current"
awk '/^max /{print "한도 도달 횟수 =", $2}' "$CG/memory.events"
awk '{for(i=2;i<=NF;i++) if($i ~ /^rbytes=/){split($i,a,"="); s+=a[2]}} END{printf "디스크 읽기 = %.2f GiB\n", s/1073741824}' "$CG/io.stat"
```

세 값이 모두 0에 가까워야 정상이다.

### 4.4 컨테이너가 파일을 처음 읽는다

```bash
time docker exec "$CID" dd if=/data/f of=/dev/null bs=1M
```

출력되는 소요 시간과 처리량을 적어 둔다. 이 값은 참고값이다. 판정은 6장의 계수기로 한다.

### 4.5 읽기 후 계수기를 다시 읽는다

```bash
awk '{printf "memory.current = %.2f GiB\n", $1/1073741824}' "$CG/memory.current"
awk '/^max /{print "한도 도달 횟수 =", $2}' "$CG/memory.events"
awk '{for(i=2;i<=NF;i++) if($i ~ /^rbytes=/){split($i,a,"="); s+=a[2]}} END{printf "디스크 읽기 = %.2f GiB\n", s/1073741824}' "$CG/io.stat"
grep -E '^(file|workingset_refault_file) ' "$CG/memory.stat"
```

기대하는 모습은 다음과 같다. `memory.current` 가 한도인 4GiB 근처에서 멈춰 있고, 한도 도달 횟수가 0보다 크며, 디스크 읽기가 16GiB 근처로 올라간다. 파일 16GB를 4GB 한도 안에서 읽었으니 읽은 만큼 계속 버려지고 다시 읽은 것이다.

### 4.6 정리

```bash
docker rm -f "$CID"
```

## 5. 조건 A — 호스트가 먼저 읽는다

이번에는 **캐시를 채워 둔 상태에서** 같은 일을 한다. 컨테이너 설정은 조건 B와 완전히 같다.

### 5.1 캐시를 비우고, 호스트가 먼저 읽는다

```bash
sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'
free -h

time dd if=$F of=/dev/null bs=1M
free -h
```

두 번째 `free -h` 에서 `buff/cache` 가 **16GB 이상 늘어야 한다.** 늘지 않았다면 호스트 캐시에 파일이 올라가지 않은 것이고, 그러면 조건 A 자체가 성립하지 않아 뒤의 비교가 무의미해진다.

### 5.2 캐시를 비우지 않고 컨테이너를 띄운다

여기서 `drop_caches` 를 다시 실행하면 조건 A가 무너진다. 바로 컨테이너를 띄운다.

```bash
CID=$(docker run -d --memory=4g --memory-swap=4g -v "$F":/data/f:ro alpine sleep 900)
PID=$(docker inspect -f '{{.State.Pid}}' "$CID")
CG=/sys/fs/cgroup$(grep '^0::' /proc/$PID/cgroup | cut -d: -f3)
echo "$CG"
```

### 5.3 읽고 계수기를 확인한다

```bash
time docker exec "$CID" dd if=/data/f of=/dev/null bs=1M

awk '{printf "memory.current = %.2f GiB\n", $1/1073741824}' "$CG/memory.current"
awk '/^max /{print "한도 도달 횟수 =", $2}' "$CG/memory.events"
awk '{for(i=2;i<=NF;i++) if($i ~ /^rbytes=/){split($i,a,"="); s+=a[2]}} END{printf "디스크 읽기 = %.2f GiB\n", s/1073741824}' "$CG/io.stat"

docker rm -f "$CID"
```

## 6. 판정

네 값을 조건 B와 조건 A에서 나란히 놓고 본다.

| 지표 | B (컨테이너가 먼저) | A (호스트가 먼저) | 함정이 실재할 때 |
|---|---|---|---|
| 읽기 소요 시간 | 참고값 | 참고값 | 판정에 쓰지 않는다. 이유는 6.1절 |
| 컨테이너 디스크 읽기 | 16GiB 근처 | 0에 가까움 | **A가 B의 1/10 이하** |
| `memory.current` | 한도인 4GiB 근처 | 수십 MiB | **A가 한도에 한참 못 미침** |
| 한도 도달 횟수 | 0보다 큼 | 0 | **A가 0** |

**판정은 아래 세 계수기로만 한다. 읽기 소요 시간은 판정에 쓰지 않는다.**

| 계수기 지표 | 함정이 실재할 때 |
|---|---|
| 컨테이너 디스크 읽기 | A가 B의 10분의 1 이하 |
| 한도 도달 횟수 | B는 0보다 크고 A는 0 |
| `memory.current` | A가 B의 4분의 1 이하 |

셋 중 **둘 이상이 일치하면 함정이 실재한다.** 조건 A의 컨테이너가 4GB 한도를 걸었는데도 16GB 데이터를 다 읽으면서 자기 앞으로는 거의 과금되지 않았다는 뜻이다.

판정에 앞서 **조건 B가 실제로 한도 압박을 받았는지** 먼저 본다. B의 한도 도달 횟수와 디스크 읽기가 둘 다 0이면 비교 자체가 성립하지 않으므로, 파일 크기와 한도 설정을 확인하고 다시 한다.

조건 A와 B의 계수기가 비슷하게 나왔다면 이 서버에서는 함정이 나타나지 않는다. 다만 그때는 결론을 내리기 전에 5.1의 `free -h` 확인을 되짚는다. 호스트 캐시가 실제로 차 있지 않았다면 함정이 없는 것이 아니라 조건을 못 만든 것이다.

### 6.1 읽기 소요 시간을 판정에서 뺀 이유

처음에는 읽기 소요 시간을 1차 근거로 삼았다. 캐시에서 읽으면 디스크에서 읽을 때보다 훨씬 빠를 것이라고 보았기 때문이다. **실측 결과 그 가정이 틀렸다.**

측정 대상 서버에서 조건 B는 32GiB를 4.2초에 읽었다. 초당 7.6GB이며, 이는 디스크가 아니라 단일 스레드 `dd`의 메모리 복사가 병목이라는 뜻이다. 캐시에서 읽는 조건 A도 같은 복사를 해야 하므로 빨라질 여지가 없었고, 실제로 4.4초로 **근소하게 더 느렸다.**

단일 스레드 읽기의 메모리 복사가 병목이 되는 장비에서는 시간으로 캐시 적중과 디스크 읽기를 구분할 수 없다. 시간을 판정에 넣으면 이런 장비에서 함정을 놓친다.

### 6.2 측정 대상 서버의 실측 결과

2026-09-21에 실제로 수행했다. **함정이 실재하는 것으로 확인되었다.**

| 지표 | B (컨테이너가 먼저) | A (호스트가 먼저) | 판정 |
|---|---|---|---|
| 컨테이너 디스크 읽기 | 32GiB | **0** | 일치 |
| 한도 도달 횟수 | 12,296 | **0** | 일치 |
| `memory.current` | 4GiB (한도) | **0.01GiB** | 일치 |
| 읽기 소요 시간 | 4.2초 | 4.4초 | 판정에 쓰지 않음 |

계수기 세 지표가 모두 일치한다. 조건 A의 컨테이너는 4GB 한도를 걸었는데도 **디스크를 한 번도 읽지 않았고, 한도에 한 번도 부딪히지 않았으며, 자기 앞으로 과금된 양이 한도의 400분의 1에 그쳤다.**

조건 B가 16GB 파일을 읽는 데 32GiB를 읽었다는 점도 함께 볼 만하다. 4GB 한도 안에서 16GB를 읽느라 이미 읽은 페이지를 버리고 다시 읽기를 반복한 결과이며, 한도가 정상적으로 작동할 때의 모습이다.

## 7. 결과에 따른 조치

**함정이 실재하는 것으로 확인되었으므로**, 설계서 4.3절의 대책 네 가지가 본 실험의 필수 절차가 된다. 권고가 아니라 지키지 않으면 측정이 무효가 되는 조건이다.

| # | 대책 | 지키지 않으면 |
|---|---|---|
| 1 | 조건을 바꿀 때마다 컨테이너를 새로 만든다 | 직전 조건이 올린 캐시가 그대로 남아 새 한도가 물리지 않는다 |
| 2 | 새로 만들기 직전에 시스템 캐시를 비운다 | 호스트 앞으로 과금된 페이지가 남아 컨테이너가 공짜로 쓴다 |
| 3 | 부하 생성기가 데이터 파일을 직접 만지지 않는다 | 부하 생성기가 먼저 읽으면 그쪽으로 과금되어 같은 함정이 생긴다 |
| 4 | 스왑을 차단한다 | 디스크 대신 스왑으로 빠져 디스크 읽기 관측이 오염된다 |

**"한도만 바꿔서 다시 측정"은 금지 사항이다.** 이번 측정이 보여 준 것이 정확히 그 실패 형태다. 조건 A의 컨테이너는 한도를 4GB로 걸었는데도 한도에 한 번도 부딪히지 않았다.

이 결과를 설계서 4.3절에 기록하고, 확정된 단계 구조의 1.3 함정 확인을 완료로 표시했다.

### 7.1 측정 절차에 반영할 것

조건 하나를 측정하는 흐름은 반드시 아래 순서를 지킨다.

```
호스트가 마스터 사본을 작업본으로 복사  →  시스템 캐시 비우기  →  컨테이너 새로 생성
    →  컨테이너가 처음 읽음 (게이트 A: 캐시 잔류 없음, 게이트 C: 컨테이너 앞으로 디스크 읽기 과금)
    →  부하 인가  →  지표 수집  →  컨테이너 폐기
```

적재를 호스트에서 미리 해 두고 컨테이너만 바꿔 끼우는 방식은 쓸 수 없다. 원칙은 **조건마다 컨테이너가 데이터 페이지를 처음 만져야 한다**는 것이다. 방법은 호스트가 마스터 사본을 작업본으로 복사한 뒤 시스템 캐시를 비우고, 컨테이너를 새로 띄워 처음 읽게 하며, 게이트 A(캐시 잔류 없음)와 게이트 C(컨테이너 앞으로 디스크 읽기 과금)로 증명하는 것이다. 복사에는 약 6분이 든다. 다시 적재하는 것은 마스터 사본이 없을 때의 대안일 뿐이고 수 시간이 든다. 마스터 사본은 부하 도구의 적재기(3.2)가 적재를 마친 뒤 만들고, 조건 전환의 상세와 복사 방식의 선택 근거는 `environment_setup_2026-09-21.md` 5.5절에 있다.

## 부록 B. mmap 방식으로 다시 확인하기

Qdrant는 벡터 저장소를 `mmap` 으로 연다. 4장과 5장이 쓰는 `dd` 는 `read()` 호출이라 경로가 다르므로, 같은 결과가 `mmap` 에서도 나오는지 확인해 두면 근거가 분명해진다. 과금 규칙 자체는 두 경로가 동일하지만, `mmap` 쪽은 **주요 페이지 폴트(major fault)** 라는 지표가 추가로 잡힌다는 이점이 있다.

조건 A와 조건 B의 4.4 / 5.3 자리에서 `dd` 대신 아래를 쓴다.

```bash
docker exec -i $CID sh -c 'apk add -q python3 && python3 - /data/f' <<'PY'
import mmap, os, sys, time
path = sys.argv[1]
size = os.path.getsize(path)
t0 = time.time()
total = 0
with open(path, 'rb') as f:
    mm = mmap.mmap(f.fileno(), 0, prot=mmap.PROT_READ)
    for off in range(0, size, 4096):
        total += mm[off]
    mm.close()
dt = time.time() - t0
print(f"{size/2**30:.2f} GiB, {dt:.1f} s, {size/dt/2**20:.0f} MiB/s")
PY
```

읽은 뒤 주요 페이지 폴트를 확인한다.

```bash
grep -E '^(pgmajfault|workingset_refault_file) ' $CG/memory.stat
```

조건 B에서는 `pgmajfault` 가 크게 늘고, 함정이 실재한다면 조건 A에서는 거의 늘지 않는다. `read()` 경로에서는 이 값이 원래 늘지 않으므로, 4장과 5장에서 `pgmajfault` 가 0인 것은 정상이며 함정의 증거가 아니다.
