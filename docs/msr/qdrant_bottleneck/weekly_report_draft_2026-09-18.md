# 주간 보고 — DB 병목 분석

- 작성일: 2026-09-18

---

## 요약

- MemMachine과 DB로 이루어진 환경에서 사용자와 기억이 증가할 때 DB가 어디서 막히는지, 그 원인이 무엇인지 규명하는 과제를 진행 중임
- 전체를 세 단계로 구분하며 1·2단계는 병렬로 수행함. 1단계는 실제 환경 전체에 부하를 인가하여 병목 조건을 확인하고, 2단계는 DB만 분리하여 그 조건에서 원인을 규명함
- 이번 주 **2단계 측정 설계를 완료함.** 병목 조건·지점·원인 확인에 필요한 정보 11개를 도출하고 확보 가능 여부를 소스 수준으로 분석함. **9개는 기본 기능으로 확보 가능하고, 2개는 Qdrant가 제공하지 않아 소스에 계측 코드를 삽입하여 확보할 예정임**
- 아울러 현재 Qdrant 설정에서 검색 정확도가 저하될 수 있는 구조적 위험을 확인하여 별도 검토 항목으로 등록함

---

## 1. 최종 목표

- **MemMachine과 DB 환경에서 사용자와 기억이 증가하고 DB 자원(CPU, DRAM)이 제한될 때, DB 병목 구간을 확인하고 그 원인을 파악하여 최적화함**

- **병목 조건** — 언제 막히는가. 어떤 규모와 자원 조건에서 포화하는지 수치로 특정함
- **병목 지점** — DB 내부 어디서 막히는가. 저장·검색·정리 작업 중 어느 처리인지 특정함
- **병목 원인** — 왜 막히는가. CPU, 메모리, Disk 중 무엇이 한계인지 판정함
- **개선 방안** — 유효한 수단을 선별하고 동일 조건 재측정으로 효과를 검증함

---

## 2. 진행 방향

### 2.1 단계 구분

- **1단계 — E2E 분석.** MemMachine을 포함한 전체 경로에 부하를 인가하여 실제 병목을 관측함
- **2단계 — DB 병목 구간 분석.** DB(우선 Qdrant)를 분리하여 1단계가 확인한 조건을 재현하고 내부 원인을 규명함
- **3단계 — 최적화.** 개선 방안을 도출하고 동일 조건 재측정으로 효과를 정량화함. 2단계 결과 확보 후 착수함

### 2.2 단계 간 인계 정보

| 구분 | 항목 |
|---|---|
| 데이터 특성 | 세션 수 · 세션당 기억 수 분포 · 벡터 차원 |
| 워크로드 패턴 | 검색·저장 혼합 비율 · 요청 도착 분포 · 세션 접근 분포 · 요청당 크기 · 필터 조건 구성 |
| 자원 조건 | DRAM 한도 · CPU 할당 |
| 병목 좌표 | 병목 전 · 꺾이는 지점 · 병목 후의 세 지점 |
| 검증 근거 | Qdrant 유입 요청 기록 · latency 분포 · Qdrant 지표 스냅샷 |

- **병목 좌표는 세 지점을 함께 받음.** 꺾이는 지점 단독으로는 재현의 타당성을 판정할 수 없음

### 2.3 진행 체계

- **1·2단계 병렬 진행.** 2단계는 1단계 결과를 대기하지 않고 분석 환경을 선행 구축하며, 조건 전달 즉시 재현에 착수함. 3단계는 2단계 후속으로 진행함
- **1단계 — 박준혁 TL / MemVerge 공동**
  - MemVerge와 논의하며 공동 평가 환경을 구축하고 평가를 수행함
  - 평가 조건과 측정 항목을 양측이 합의하여 확정함
  - 평가 결과를 2.2의 형식으로 정리하여 2단계에 전달함
- **2단계 — 오태진 TL**
  - 1단계와 병행하여 DB 분석 환경을 설계하고 구축함
  - 2.2의 인계 항목을 사전 정의하여 1단계에 요청함

## 3. 2단계 설계 — Qdrant 병목 분석

### 3.1 필요한 정보

- **확인해야 할 것이 세 가지이고, 각각 필요한 정보가 다름**

```
① 병목 조건    언제 막히는가
② 병목 지점    Qdrant 내부 어디서 막히는가
③ 병목 원인    왜 막히는가
```

- **① 병목 조건 — 2개.** QPS, 요청별 latency
  - 부하를 올려도 **QPS가 더 늘지 않고 latency만 커지는 지점**을 병목 조건으로 판단함
- **② 병목 지점 — 6개**

| 경로 | 항목 |
|---|---|
| 저장 | 저장 요청 대기량 · 저장 내부 단계별 시간 |
| 검색 | 검색 방식별 처리 시간 · 검색 내부 단계별 시간 |
| 정리 작업 | 정리 작업 대기량 · 정리 작업 단계별 시간 |

- **③ 병목 원인 — 3개.** CPU 사용률 · 메모리 적재 상태 · 디스크 읽기 발생
  - ②에서 특정한 지점이 **어느 자원 때문에 막히는지** 판정함

### 3.2 확보 가능 여부

| 확보 경로 | 항목 |
|---|---|
| **Qdrant 기본 기능** (7개) | 요청별 latency · 메모리 적재 상태 · 디스크 읽기 발생 · 저장 요청 대기량 · 정리 작업 대기량 · 검색 방식별 처리 시간 · 정리 작업 단계별 시간 |
| **측정 도구와 컨테이너 통계** (2개) | QPS · CPU 사용률 |
| **확보 불가** (2개) | **검색 내부 단계별 시간 · 저장 내부 단계별 시간** |

- **메모리와 디스크는 총량이 아니라 판정에 필요한 형태로 제공됨**
  - 메모리 — 벡터·payload·색인별로 **캐시에 있어야 할 양과 실제 올라온 양.** 둘의 격차가 메모리에 수용되지 못한 규모임
  - 디스크 — **메모리에 없어 읽어온 횟수**와, 벡터·payload·색인 중 무엇을 읽었는지

- **확보 불가 사유** — 단계별 시간을 재는 장치가 Qdrant 내부에 없으며, 요청이 거친 단계를 사후 재구성하는 분산 추적도 지원하지 않음
- **확보 불가 2개는 모두 ② 병목 지점 확인용임.** 2단계의 핵심 질문에 해당함

### 3.3 확보 불가 항목의 확보 방안

- **Qdrant 소스에 계측 코드를 삽입하여 직접 확보함**
  - **계측 지점을 소스에서 함수 단위로 특정 완료함** — 검색 9개소, 저장 9개소
  - 기존 지표의 사각지대도 함께 확인함. **WAL 확정과 전역 쓰기 락 대기는 현재 어떤 지표에도 잡히지 않음**
  - 대상 버전을 v1.19.1로 고정하여 패치 유지 부담을 제거함
- **검증 항목**
  - **계측 오버헤드** — 반복 횟수가 많은 구간은 호출마다 측정하면 계측 비용이 측정 대상을 초과하므로 묶음 단위로 측정함
  - **대표성과 왜곡** — 공식 배포 이미지와 동일한 빌드 설정으로 소스만 패치하고, 계측 유무 빌드를 같은 부하로 비교하여 결과가 바뀌지 않음을 확인함
- 조건을 임의로 조합해 반복 실행해야 하므로, **Qdrant에 직접 요청을 전송하는 측정 도구를 자체 제작함**

### 3.4 데이터셋 확보 방안

- 측정에 사용할 벡터 데이터의 확보 방법을 조사하여 세 갈래로 정리함

| 방안 | 특징 |
|---|---|
| **임의 생성** | 무제한 생성 가능, 다운로드 불필요. 단 균등 무작위는 벡터 간 거리가 고르게 분포하여 정확도 측정에 부적합하므로 군집 구조 부여가 필요함 |
| **공개 데이터셋 활용** | 실제 임베딩 분포 확보. 1억 건 이상 규모의 후보가 다수 존재하나 수백 GB 다운로드가 필요함 |
| **소량 실제 데이터 증폭** | 실제 데이터의 통계를 추출해 대량 생성. 목표의 1/100만 확보하면 되어 다운로드 부담이 적음. GPU 필요 |

- **정답이 포함된 데이터셋은 불필요함.** Qdrant가 전수 비교 모드를 제공하여 정답을 직접 생성할 수 있으므로 후보 범위가 크게 넓어짐
- 규모 측정용과 정확도 측정용의 요구가 다르므로 **용도별로 다른 방안을 조합할 수 있음**

## 4. 검토 필요 사항 — 현재 설정의 정확도 위험

- **부하 및 성능과 별개로, 현재 Qdrant 설정 자체에 검색 결과가 틀릴 수 있는 구조적 위험을 확인함.** MemMachine은 전역 색인 없이 필드별 색인만 사용하도록 설정하고 있으며, 멀티테넌트 권장 방식이나 분석 결과 세 가지가 확인됨

- **① 색인의 세션별 분리 미보장** — 필드 값마다 만든 연결이 하나로 병합되어, 출발 위치에 따라 도달하지 못하는 영역이 생길 수 있음. Qdrant 유지보수자가 해당 동작을 확인함
- **② 동일 설정의 정확도 저하 결함 보고가 미해결 상태** — 대량 적재 후 정확도가 26%까지 하락한 사례가 원인 미규명 상태로 열려 있으며, 제3자의 동일 설정 보고도 미응답 상태임
- **③ 조건 중첩 검색 시 정확도 붕괴** — Qdrant는 필드 각각에는 연결을 만드나 **필드 조합에는 만들지 않음.** 공개 측정에서 조건 두 개를 중첩하면 정확도가 70.8%, 필터가 더 좁아지면 **1.8%**까지 하락함. **응답 시간은 거의 변하지 않아 지연 지표만으로는 발견되지 않음**

- **검토 필요성** — 다중 사용자 구분 방식으로 사용자 조건을 필터에 추가하는 안이 ③에 정확히 해당함. 성능이 아닌 **정확성 문제**이므로 설계 결정 전 확인이 필요함
- **확인 방법** — 전수 비교 모드의 결과를 정답으로 삼아 대조하며, 부하 측정과 분리된 구간에서 수행함
- **대안** — 색인 없이 전수 비교만 수행하는 구성이 구조적으로 정확하며, 2만 건 미만 규모에서는 오히려 더 빨랐다는 공개 측정 근거를 확보함
