## 1. 사전 준비 (모든 문제 공통, 1회만)

### 1.1 외부 인프라 (사용자 책임)

도구가 인프라를 띄워주지 않습니다 (`docs/USAGE.md` §2.1, `configs/profiles/dbs/_example.yaml` 주석).

| 컴포넌트 | 역할 | 비고 |
|---|---|---|
| **Neo4j 인스턴스** | `episodic_memory.long_term_memory.vector_graph_store` (long-term memory 의 vector + graph store) | profile 의 `vector_graph_store` 항목에 host/port/auth |
| **Postgres** (또는 SQLite) | `episode_store.database` / `session_manager.database` / `semantic_memory.config_database` 의 profile / session / episode 저장소 | profile 의 `profile_storage` 항목 |
| **LLM API** | embedder, reranker, answer generation (retrieval_agent), judge | OpenAI-compatible / Bedrock / Ollama 등 — `evaluation/retrieval_agent/README.md` Quick Start 와 동일 표기 |

### 1.2 profile 파일 작성

```sh
cd /home/user/MemMachine
cp configs/profiles/models/_example.yaml configs/profiles/models/my_model.yaml
cp configs/profiles/dbs/_example.yaml     configs/profiles/dbs/my_db.yaml
# 두 파일에서 <PLACEHOLDER> 를 본인 환경값(host/port/api_key/model id)으로 교체
```

이후 모든 명령에서 `--model-profile my_model --db-profile my_db` 사용.

### 1.3 (LoCoMo, #5 만 해당) 데이터셋 파일

`locomo10.json` 을 직접 다운로드해서 절대경로를 기억해 두세요.

### 1.4 Python 환경

선택지는 두 가지이며 **팀의 표준에 맞춰 하나만** 사용합니다.

```sh
# (A) repo 표준이 uv 인 경우 — 권장
uv sync

# (B) retrieval_agent 벤치마크만 빠르게 준비할 경우
```

### 1.5 smoke test (DB / LLM 없이 도구 자체 동작 검증)

DB / LLM 없이 검증할 수 있는 범위는 **run config 와 working configuration 생성 확인** 까지입니다. `analyze` stage 는 `results/{run}/judge.jsonl` 이 없으면 `FileNotFoundError("judge.jsonl missing: ... — run --stage judge first")` 로 실패하므로 (`scripts/stages/analyze.py:285-303`) DB/LLM 없이는 의미 있는 결과를 만들지 못합니다.

```sh
# 1) run config 생성 (DB / LLM 호출 없음)
python scripts/generate_config.py --problem 4 --run-name p4_smoke \
    --model-profile _example --db-profile _example --k-list 10,20 --length 5

# 2) 산출물 두 개 확인
ls configs/runs/p4_smoke.yaml
ls configs/generated/p4_smoke_configuration.yml
```

> 굳이 `analyze` 단계까지 dry 검증하고 싶으면 `results/p4_smoke/judge.jsonl` 과 `results/p4_smoke/retrieve.jsonl` 을 합성으로 직접 만들어야 합니다 (실 산출 schema 참조 — 아래 §3.3 / §10). 일반적인 가이드 사용에서는 §1~§2 까지의 확인만으로 충분합니다.

### 1.6 실행 전 체크리스트

```sh
# 도구 자체의 CLI 가 정상 동작하는지
python scripts/generate_config.py --help
```

## 3. #4 — k 비단조성 (반드시 가장 먼저 실행)

#6, #12 가 #4 산출물을 재사용하므로 **순서상 #4 → #6, #12 → 나머지** 가 효율적입니다.

### 3.1 run config 생성

```sh
python scripts/generate_config.py \
    --problem 4 --run-name p4_full \
    --model-profile my_model --db-profile my_db
```

생성물:

- `configs/runs/p4_full.yaml` (problem 4 sweep 정의)
- `configs/generated/p4_full_configuration.yml` (working copy — 사용자 원본 절대 비변경, `MemMachine_변경사항_문서_claude_0427.md` C5)

### 3.2 전체 파이프라인 실행

```sh
python scripts/run_pipeline.py --config configs/runs/p4_full.yaml --stage all
```

내부 5단계 (`MemMachine_변경사항_문서_claude_0427.md` C2):

1. `ingest` → `results/p4_full/ingest.jsonl` (마지막 row `status=ok` 면 다음 실행 시 자동 skip)
2. `retrieve` → `results/p4_full/retrieve.jsonl` (질문별 chunks/perf/token/fact_hits)
3. `generate` → `results/p4_full/generate.jsonl`
4. `judge` → `results/p4_full/judge.jsonl` (+ `llm_score`)
5. `analyze` → `results/p4_full/analyze.json`

### 3.3 결과 위치

```sh
ls results/p4_full/
cat results/p4_full/analyze.json | jq \
  '.cells[] | {k: .sweep.search_limit, accuracy, mean_recall, overall_recall, by_category}'
```

각 cell 의 실제 schema (`scripts/stages/analyze.py:164-188`):

`cell / sweep / n / accuracy / accuracy_std / mean_recall / overall_recall / total_fact_hits / total_supporting_facts / mean_llm_time / mean_num_episodes / mean_tokens_per_query / mean_<token_field> / by_category / by_tool`

`by_category` 는 `{카테고리키: {n, accuracy}}` 형태이고, `by_tool` 은 `{툴이름: {n, accuracy, mean_input_token, mean_output_token, mean_llm_time}}` 형태입니다 (`analyze.py:113-138`).

> ⚠️ `accuracy_std` 는 **반복 실행 간 σ 가 아니라** 한 cell 안의 question별 0/1 score 분포 표준편차 (`analyze.py:170` `statistics.pstdev(scores)`). 결합 σ 계산용 입력으로 그대로 쓰면 안 됨.

### 3.4 판정 기준 — 현재 도구로 가능한 것 / 불가능한 것

**현재 (PR #7, `n_runs=1`) 에서 가능한 판정**:

- 방향성 확인: k 를 늘리는 동안 `accuracy` 가 단조 증가인지, 어디선가 꺾이는지 raw 값으로 직접 비교
- effect size 참고: cell 간 `accuracy / mean_recall / mean_tokens_per_query` 차이를 수기 비교

**현재 도구로 불가능 (future work)**:

- 반복 실행 기반 결합 σ×2 자동 판정
- 파일럿 5회 후 N 자동 결정

**향후 repeated-run wrapper 구현 후의 최종 판정 기준** (참고용, `MemMachine_재현평가_설계_0425.md` §2 #4):

- 성공: k 를 늘리는 동안 정확도 상승 둔화·꺾임이 결합 σ 2배 초과 / 부분: σ 1~2배 / 실패: k 무관 또는 비례 단조 증가

→ 현재는 `n_runs=1` 이므로 위 σ×2 기준 대신 raw 값 차이를 수기로 해석하고, 결과는 "방향성 외삽" 으로만 보고합니다 (`MemMachine_재현평가_설계_0425.md` §3.5).

### 3.5 자주 막히는 지점

- chunk = on, prefix = on 이 `fixed` 로 박혀 있음 (`configs/problems/p4.yaml:18-20`). chunk on/off 비교는 **별도 run_name + 별도 ingest** 필요 (`docs/USAGE.md` §3 #4 주의 박스).

## 4. #6 — Multi-session 재분해 (#4 산출물 재사용, 1분)

### 4.1 run config 생성 — `--reuse-run` 으로 #4 결과 가리키기

```sh
python scripts/generate_config.py \
    --problem 6 --run-name p6_from_p4 \
    --model-profile my_model --db-profile my_db \
    --reuse-run p4_full
```

### 4.2 analyze 단계만 실행

```sh
python scripts/run_pipeline.py --config configs/runs/p6_from_p4.yaml \
    --stage analyze --decompose-multisession
```

산출 (`MemMachine_변경사항_문서_claude_0427.md` C6, cell 별):

- `ms_accuracy` — multi-session 질문만의 정확도
- `others_mean_accuracy` — 나머지 카테고리(SSU/SSP/SSA/TR/KU) 평균
- `ms_vs_others_gap` — 두 값의 차이

### 4.3 판정 — 현재 도구로 가능한 것 / 불가능한 것

**현재 가능**:

- 모든 k cell 에서 `ms_accuracy` 와 `others_mean_accuracy` raw 값 비교 (방향성)
- `ms_vs_others_gap` 절대값을 k 별로 나열해 추세 확인

**현재 불가능 (future repeated-run wrapper 후)**:

- 모든 k 에서 `ms_accuracy < others_mean_accuracy` 가 결합 σ 2배 초과 → 성공 / 일부만 → 부분 / MS 가 비슷하거나 더 높음 → 실패 (`MemMachine_재현평가_설계_0425.md` §2 #6)

> MS 카테고리 매칭은 `cat.lower() in {"multi-session", "multi_session", "ms"}` 으로만 됩니다 (`analyze.py:23, 200`). LongMemEval 의 `question_type` 이 이 셋 중 어느 것도 아니면 `ms_accuracy` 가 산출되지 않으니, `by_category` 의 keys 를 먼저 확인하세요.
