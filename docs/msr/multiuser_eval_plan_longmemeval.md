# 멀티유저 평가 계획 — 쉽게 풀어 쓴 버전 (longmemeval_m 기준)

*작성 2026-08-11 · 브랜치 `msr_multiuser`*
*이전 문서(`multiuser_eval_design.md`, `multiuser_eval_milestones.md`)를
longmemeval_m 데이터셋 기준으로 다시 쓴 최신판. 이 문서만 봐도 되게 정리함.*

---

## 1. 한 줄 요약

> **유저 N명이 각자 자기 대화 기록을 MemMachine에 넣고(적재),
> 동시에 자기 기억을 검색할 때, 어디가 언제 무너지는지 찾는다.**

그림으로 그리면:

```
유저 1  ──┐                      ┌── 유저 1: "내 전공이 뭐였지?"
유저 2  ──┤  ① 적재 (ingest)     │   ② 동시 검색 (search)
  ...     ├──→  MemMachine  ←────┤        ...
유저 N  ──┘        │             └── 유저 N: "지난달 여행 어디 갔지?"
                   ▼
        벡터DB (Qdrant/Milvus/SQLite-vec)
        + Postgres + SSD
```

보려는 것 두 가지:
- **① 적재 중 문제** — N명이 동시에 부으면 뭐가 막히나
- **② 검색 중 문제** — N명이 동시에 찾으면 얼마나 느려지나, 남의 기억이 섞이진 않나

## 2. 데이터셋 — longmemeval_m을 이렇게 쓴다

### 왜 locomo가 아니라 longmemeval_m인가

locomo는 대화가 10개뿐이라 유저 10명이 한계다.
longmemeval_m은 **질문 500개짜리** 데이터셋이고, 각 질문마다 그 사람의
긴 대화 기록(haystack)이 통째로 붙어 있다.

### 핵심 아이디어: 유저 1명 = 질문 1개의 대화 기록

질문 하나에 딸린 대화 기록을 "유저 한 명의 과거"로 보면,
**복제 없이 실데이터로 유저 500명**까지 만들 수 있다.

실측 수치 (방금 파일에서 직접 확인):

| | longmemeval_**s** (작은 판) | longmemeval_**m** (큰 판) |
|---|---|---|
| 질문 수 = 만들 수 있는 유저 수 | 500 | 500 |
| 유저 1명당 대화 세션 | ~53개 | **~482개** |
| 유저 1명당 대화 turn (=에피소드) | ~550개 | **~5,057개** |
| 유저 1명당 텍스트 양 | ~0.5MB (~12만 토큰) | **~5MB (~127만 토큰)** |

규모 감각:

| 유저 수 | 총 에피소드 (m 기준) | 벡터 데이터 대략 |
|---|---|---|
| 10 | ~5만 | ~0.3GB |
| 100 | ~50만 | ~3GB |
| 500 | ~250만 | **~15GB** |

→ 유저 100명만 넘어도 메모리 제한을 걸면 **SSD까지 I/O가 실제로 내려가는
규모**가 된다. 블록 I/O 측정 목적에 딱 맞는다.

### 덤으로 얻는 것 (locomo에는 없던 이점)

각 질문에는 **정답과 "정답이 들어있는 세션 번호"가 붙어 있다.** 그래서:

1. **검색 품질을 유저별로 채점 가능** — "정답 세션을 찾아왔나?" (recall)
2. **격리 검증이 공짜** — 유저 A의 검색 결과에 유저 B의 세션이 나오면
   그 자체로 버그. 세션 ID가 다 붙어 있어서 자동 판정된다.

## 3. 적재 단계 — 예상되는 문제 (쉽게)

### 문제 A. 유저마다 "서랍"을 만드는 비용 ⚠ 제일 유력한 벽

MemMachine은 유저(세션)마다 Postgres에 **진짜 테이블 파티션을 하나씩**
만든다. 서랍장에 서랍을 실제로 하나씩 짜 넣는 셈이다.

- 유저 500명 = 파티션 500개. Postgres는 파티션이 수천 개로 늘면
  쿼리 계획 세우는 시간부터 느려지는 것으로 알려져 있다.
- 더 나쁜 건, **서랍을 만드는 작업(DDL)은 한 번에 하나씩만** 된다.
  N명이 동시에 첫 적재를 시작하면 서랍 만들기부터 줄을 선다.
  → 적재 시작 직후 시간이 튀는 스파이크로 보일 것.

벡터DB 쪽은 반대로 걱정이 적다. Qdrant/Milvus는 유저마다 통을 새로
만들지 않고 **하나의 큰 통에 유저 딱지를 붙여서** 넣는 방식이라(벤더
권장 방식 그대로), 유저 수 자체로는 잘 안 터진다.
**즉 "벡터DB가 먼저 터질 것"이라는 직관과 달리, Postgres가 먼저일
가능성이 높다** — 이걸 측정으로 확인하는 게 이 평가의 큰 그림.

### 문제 B. DB로 가는 통로가 기본 15개뿐

Postgres 연결 풀 기본값이 `5 + 10 = 최대 15`. 유저 100명이 동시에
적재하면 DB가 느린 게 아니라 **통로에서 줄 서는 것**이 병목으로 잡힌다.
→ 측정 전에 풀을 미리 키워야 한다. 안 그러면 "Postgres가 병목"이라는
엉뚱한 결론이 나온다.

### 문제 C. 임베딩 API가 DB 차이를 가린다

적재 = 텍스트마다 임베딩 API 호출 + DB 쓰기. API 호출이 수십 ms라
DB 쓰기(수 ms)의 차이가 묻혀 버린다.
→ **임베딩을 미리 전부 계산해서 파일로 저장**해 두고, 적재 때는 저장된
벡터를 읽어 쓰기만 한다. 비용도 한 번만 낸다
(500유저 전체 ≈ 6.4억 토큰 ≈ text-embedding-3-small 기준 $13 안팎, 1회).

### 문제 D. SQLite-vec은 한 번에 한 명만 쓸 수 있다

파일 기반이라 동시 쓰기가 안 된다. N명 적재가 사실상 줄서기가 된다.
이건 **예상된 결과**고, 대신 서버 프로세스 없이 파일 하나라서
**SSD I/O가 가장 깨끗하게 보이는 구성**이라는 가치가 있다.

## 4. 검색 단계 — 예상되는 문제 (쉽게)

### 문제 E. 유저가 늘수록 검색이 느려지나

Qdrant/Milvus는 한 통에 전부 들어 있고 검색할 때 "이 유저 것만" 필터를
건다. 유저 500명 치 데이터가 쌓인 통에서 필터 검색하는 것과 유저 10명
치에서 검색하는 것 — 얼마나 차이 나는지가 측정 포인트.
(Qdrant는 유저별로 미니 인덱스를 따로 만들어 주는 옵션(`is_tenant`)이
코드에 이미 켜져 있어서, 이게 얼마나 방어해 주는지도 같이 보인다.)

### 문제 F. 동시에 검색하면 꼬리 지연이 언제 튀나

평균은 괜찮아도 **p95/p99 (느린 5%, 1%)** 가 어느 동시성부터 급증하는지.
유저 입장에서 체감하는 건 평균이 아니라 이 꼬리다.

### 문제 G. 남의 기억이 섞이나 (격리)

한 통에 딱지로 구분하는 구조라, 필터가 잘못되면 남의 대화가 나올 수 있다.
longmemeval은 세션 ID가 전부 붙어 있어서 **검색 결과마다 자동 판정** 가능.

### 문제 H. 서버의 "접수창구 100개" 문제

MemMachine 서버는 유저(세션)별 작업 공간을 **최대 100개까지만 캐시**하고
넘치면 오래된 것부터 버린다. 동시 활성 유저가 100을 넘으면 작업 공간을
버렸다 다시 만들었다를 반복(thrash)하면서 느려질 것.

⚠ **중요**: 지금 평가 코드는 서버를 안 거치고 라이브러리로 직접 부르기
때문에 이 문제는 **그 경로로는 아예 안 보인다.** 그래서:
- **DB 비교** (문제 A~G) → 라이브러리 모드로 측정 (깨끗함)
- **문제 H** → 서버 모드(REST)로 따로 측정
두 모드를 다 만들되 역할을 나눈다.

## 5. 진행 순서 (마일스톤)

| # | 뭘 만드나 | 왜 | 끝났다는 기준 |
|---|---|---|---|
| **0** ✅ | 평가 코드가 Qdrant/Milvus/SQLite-vec을 쓸 수 있게 수리 | 원래 Neo4j 전용으로 박혀 있었음 (+본문 저장 누락 버그도 발견·수정) | 테스트 45+243개 통과 (완료) |
| **1** | **데이터 준비**: longmemeval_m → 유저별 분할 + **임베딩 사전 계산·저장** | 문제 C 제거. 제일 오래 걸리는 준비 작업이라 최우선 | 유저별 (텍스트+벡터) 파일 세트 완성 |
| **2** | **적재 드라이버**: 유저 N명 동시 적재 + 유저별·단계별 시간 기록 | 문제 A·B·D 측정 도구 | 맥에서 유저 10명 dry-run 통과 |
| **3** | **DB 3종 환경**: Qdrant/Milvus/Postgres docker 구성 + 설정 파일 3벌 | 같은 조건으로 갈아 끼우기 | 맥에서 3종 각각 적재→검색 스모크 통과 |
| **4** | **검색 드라이버**: 동시 검색 + 정답 채점(recall) + 격리 자동 판정 | 문제 E·F·G 측정 도구 | 유저 10명 동시 검색에서 채점·격리 리포트 출력 |
| **5** | **계측**: 요청별 지연 기록(p50/p95/p99), DB별 리소스, SSD 도구(iostat 등) 래퍼 | 병목이 앱인지 DB인지 SSD인지 갈라내기 | 실행하면 리포트가 자동으로 나옴 |
| **6** | **서버 모드 스위치**: 같은 워크로드를 REST로도 쏘게 | 문제 H는 이 경로에서만 보임 | `--transport rest`로 같은 실험 실행 가능 |
| **7** | **등가성 확인**: 유저 1명으로 3종 DB recall 일치 확인 | 이거 안 맞으면 이후 숫자 전부 무의미 | 3종 recall 차이가 오차 내 |
| **8** | **포장**: 타겟 서버에서 `git clone → setup → run` 되게 스크립트+문서 | 코드만 받아 다른 서버에서 실행하는 게 최종 목표 | 맥에서 클린 체크아웃 리허설 통과 |

이후 **본 측정은 타겟 리눅스 서버에서**: 유저 수를 1 → 10 → 50 → 100 →
200 → 500으로 늘리며 적재/검색을 반복하고, 문제 A~H가 실제로 어디서
나타나는지 + SSD 블록 I/O 특성을 기록.

*(맥은 도구를 만드는 자리. 중간에 리눅스 VM이 껴 있어서 I/O 수치가
왜곡되므로 성능 숫자는 타겟 서버에서만 의미 있음.)*

## 7. 이전 문서와 달라진 점

- 데이터셋: locomo(유저 10명 한계, 복제 필요) → **longmemeval_m(실데이터 500유저)**
- 유저 정의: 합성 복제 중심 → **질문 1개 = 유저 1명** 매핑
- 검색 품질 채점과 격리 검증이 데이터셋 특성 덕에 **자동화 가능**해짐
- 마일스톤에 **데이터 준비(임베딩 사전 계산)** 가 최우선 단계로 추가됨
