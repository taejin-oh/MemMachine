# 1. 무엇을 알아보려 했나

## 우리가 원하는 구조

AI 에이전트가 여러 사용자의 기억을 저장하고 꺼내 쓴다고 할 때,
우리가 바람직하다고 본 구조는 이렇습니다.

```
   사용자 A                     사용자 B
   ┌──────────────┐            ┌──────────────┐
   │ A의 기억 저장소 │            │ B의 기억 저장소 │
   │  ├ 세션1      │            │  ├ 세션1      │
   │  ├ 세션2      │            │  ├ 세션2      │
   │  └ 세션3      │            │  └ 세션3      │
   └──────────────┘            └──────────────┘
          ▲                            ▲
          │ A가 질문하면                 │ B가 질문하면
          │ A의 저장소만 뒤진다          │ B의 저장소만 뒤진다
```

말로 풀면 세 가지 요구입니다.

| | 요구사항 | 쉽게 말하면 |
|---|---|---|
| **요구 1** | 사용자별로 저장 공간이 나뉜다 | A가 검색할 때 B의 데이터는 **아예 쳐다보지도 않는다** |
| **요구 2** | 사용자 아래에 세션이 나뉜다 | "A의 3번째 대화에서만 찾아줘"가 된다 |
| **요구 3** | 필요한 범위를 골라서 검색한다 | 전체를 볼지, 특정 세션만 볼지 선택 가능 |

## 알아본 것

이 요구를 만족하는 오픈소스 AI 메모리 솔루션이 있는지,
그리고 **우리가 쓰고 있는 MemMachine은 지금 어디쯤인지**를 조사했습니다.

조사는 **소스 코드를 직접 열어서** 확인했습니다. 홍보 문구가 아니라
실제 구현이 어떤지를 봤습니다.

# 2. 왜 이게 어려운 문제인가

*(벡터 검색이 익숙하신 분은 3장으로 건너뛰셔도 됩니다)*

## AI의 기억 검색 = 도서관에서 비슷한 책 찾기

AI 메모리는 "예전에 나눈 대화 중에서 지금 질문과 **의미가 비슷한** 것"을 찾습니다.
키워드가 같은 게 아니라 의미가 비슷한 걸 찾아야 해서, 모든 문장을 숫자 목록
(벡터)으로 바꿔놓고 그 숫자들이 가까운 것을 찾습니다.

문제는 **기억이 수백만 개면 전부 비교할 수 없다**는 점입니다.
그래서 미리 **"비슷한 것끼리 이어놓은 지도"** 를 만들어 둡니다.
이 지도를 인덱스(index)라고 하고, 대표적인 방식이 HNSW입니다.

```
   지도(인덱스)가 없으면          지도가 있으면
   ┌────────────────┐          ┌────────────────┐
   │ ● ● ● ● ● ● ● │          │   ●─●─●        │
   │ ● ● ● ● ● ● ● │          │   │   │        │
   │ ● ● ● ● ● ● ● │          │   ●─●─●─●      │
   └────────────────┘          └────────────────┘
   전부 하나씩 비교               비슷한 것끼리 이어둔 길을
   (100만 개 = 100만 번)         따라가며 몇십 번만 비교
```

## 여기서 다중 사용자 문제가 생긴다

지도를 **하나만** 만들어서 모든 사용자의 기억을 다 넣으면,
A가 검색할 때 그 길을 따라가다 **B, C, D의 기억을 계속 지나가게** 됩니다.

```
   지도가 하나뿐일 때 A가 검색하면
   ┌──────────────────────────────────┐
   │  A─B─C─A─D─B─A─C─D─A             │  ← 길을 따라가는데
   │  ↑     ↑       ↑                 │     남의 것이 계속 나옴
   │  내것   남의것   내것              │
   └──────────────────────────────────┘
        나중에 "A 것만" 걸러냄
```

이렇게 하면 두 가지가 나빠집니다.

1. **느려진다** — 남의 기억을 지나가느라 헛걸음을 합니다.
2. **놓친다** — 지도를 따라가다 보면 A의 기억이 충분히 안 나올 수 있습니다.
   (사용자가 많을수록 심해집니다)

**그래서 "사용자별로 인덱스를 나눈다"는 요구가 나오는 것입니다.**

# 3. 해결 방식은 4가지뿐 — 이 장이 핵심입니다

이 문제를 푸는 방법은 크게 네 가지입니다.
**이 네 가지를 알면 어떤 솔루션이든 바로 분류할 수 있습니다.**

## 방식 ① 건물을 따로 짓기

사용자마다 **저장소(컬렉션)를 통째로 따로** 만듭니다.

```
   ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
   │ A용   │  │ B용   │  │ C용   │  │ D용   │   … 사용자 수만큼
   │ 저장소 │  │ 저장소 │  │ 저장소 │  │ 저장소 │
   └──────┘  └──────┘  └──────┘  └──────┘
```

- 👍 완벽하게 분리됨
- 👎 **벡터DB 회사들이 하지 말라고 명시적으로 경고합니다.**
  Qdrant 공식 문서: *"테넌트마다 컬렉션을 만들지 마세요. 수백 개를 넘기면
  확장이 안 되고 자원을 낭비합니다."* (클라우드는 1,000개 상한)
  Milvus도 확장성 순위에서 이 방식을 낮게 둡니다.

> **직관적으로 떠올리기 쉬운 방식이지만, 실제로는 쓰면 안 되는 방식입니다.**
> 저장소 하나를 만들 때마다 메모리·파일·관리 비용이 고정으로 붙기 때문입니다.

## 방식 ② 건물은 하나, 사용자별 지도를 따로

저장소는 하나인데, **지도(인덱스)를 사용자마다 따로** 만듭니다.
전체를 잇는 지도는 아예 만들지 않습니다.

```
   ┌────────────────────────────────────────┐
   │            하나의 저장소                 │
   │                                        │
   │   A의 지도      B의 지도     C의 지도    │
   │   ●─●─●        ●─●         ●─●─●─●    │
   │                                        │
   │   ← 전체를 잇는 지도은 없음 →            │
   └────────────────────────────────────────┘
     A가 검색 → A의 지도만 따라감 → 남의 것 안 지나감
```

- 👍 요구 1을 만족하면서도 저장소는 하나라 확장에 강함
- 👍 **Qdrant가 공식 권장하는 방식**
- 이것이 **MemMachine이 이미 쓰고 있는 방식**입니다 (5장에서 설명)

## 방식 ③ 이름표 순으로 꽂아두기

지도(ANN 인덱스)를 **아예 안 만듭니다.** 대신 데이터를 **사용자 이름순으로
정렬**해 두고, 검색할 때 그 사용자 구간만 꺼내서 하나씩 비교합니다.

```
   ┌────────────────────────────────────────┐
   │  사용자 이름순 정렬 (일반 DB 인덱스)      │
   │                                        │
   │   A ████████     ← A가 검색하면 이 구간만 │
   │   B ██████          꺼내서 전부 비교      │
   │   C ███                                │
   └────────────────────────────────────────┘
```

- 👍 남의 데이터를 볼 구조적 여지가 **아예 없음**
- 👍 사용자가 아무리 늘어도 다른 사용자 검색에 영향 없음
- 👎 **한 사용자의 데이터가 많아지면 느려짐** (전부 비교하니까)
- 그래서 이 방식을 쓰는 솔루션은 **원본 대화 전체가 아니라 요약본만** 저장합니다

## 방식 ④ 통합 지도로 찾고 나중에 걸러내기

지도를 하나만 만들고, 검색 후에 **"이건 A 것" 딱지를 보고 걸러냅니다.**

```
   ┌────────────────────────────────────────┐
   │          하나의 통합 지도                │
   │   A─B─C─A─D─B─A─C─D─A                  │
   └────────────────────────────────────────┘
              ↓ 찾은 다음
        "user_id = A" 인 것만 남기기
```

- 👍 구현이 간단하고 저장 효율이 좋음
- 👎 **2장에서 설명한 문제가 그대로 발생** (남의 것 지나감, 사용자 많을수록 나빠짐)
- 👎 필터를 빼먹으면 **남의 기억이 그대로 나옴** (구조가 아니라 규율에 의존)

## 정리

| 방식 | 한 줄 | 남의 데이터 지나가나 | 사용자 수 확장 |
|---|---|---|---|
| ① 건물 분리 | 사용자마다 저장소 | 안 지나감 | ❌ 벤더가 금지 |
| ② 사용자별 지도 | 저장소 1개 + 지도 N개 | 안 지나감 | ✅ 좋음 |
| ③ 이름표 정렬 | 지도 없이 정렬로 범위 축소 | 안 지나감 | ✅ 좋음 (데이터 적을 때) |
| ④ 통합 지도 + 필터 | 지도 1개 + 사후 필터 | **지나감** | ⚠ 나빠짐 |

> ### 여기서 중요한 오해 하나를 풀어야 합니다
>
> "사용자별로 인덱스를 나눠야 한다"고 하면 대부분 **방식 ①**을 떠올립니다.
> 하지만 **①은 실제로는 쓰면 안 되는 방식**입니다.
>
> 우리가 진짜 원하는 것은 "**검색할 때 남의 데이터를 안 보는 것**"이고,
> 그건 **② 또는 ③으로 달성됩니다.**
> 즉 목표는 "①을 하자"가 아니라 "**④를 피하자**"입니다.

# 4. 솔루션별 조사 결과

## 4.1 Mem0 — 사용자/세션 구분은 최고, 저장은 방식 ④

**한 줄**: 사용자·에이전트·세션을 구분하는 개념은 가장 잘 갖췄지만,
실제 저장은 통합 지도 + 사후 필터입니다.

```
   저장할 때: 기억에 딱지를 붙임
     { user_id: "A", agent_id: "bot1", run_id: "세션3" }
                         ↓
   ┌────────────────────────────────────────┐
   │     단일 저장소 (설정값 하나, 고정)       │
   │     A─B─C─A─D─B─A  ← 통합 지도          │
   └────────────────────────────────────────┘
                         ↓
   검색할 때: 찾고 나서 딱지로 걸러냄
```

**좋은 점** — 구분 축이 4개나 됩니다.

| 축 | 뜻 |
|---|---|
| `user_id` | 사용자 (세션이 바뀌어도 유지) |
| `agent_id` | 어느 AI 에이전트인지 |
| `run_id` | **세션/실행 단위** ← 우리 요구 2에 해당 |
| `actor_id` | 이 말을 한 주체 (검색 시 필터용) |

**아쉬운 점** — 저장소는 설정에 적힌 **하나**뿐이고, 사용자가 늘어도 늘지 않습니다.
격리는 전적으로 딱지 필터에 의존합니다.

**주목할 점**: Mem0 소스에는 *"사용자가 임의로 넣은 메타데이터가 요청하지 않은
범위에 기억을 심는 것을 막는다"* 는 방어 코드가 있습니다(실제 버그 #6655 대응).
→ **필터 방식 격리가 구조적으로 깨지기 쉽다는 증거**입니다.

**근거 코드** (`mem0/memory/main.py`)

| 확인 내용 | 함수/심볼 | 줄 |
|---|---|---|
| 저장소 이름이 설정값 하나 — 사용자별로 안 늘어남 | `Memory.__init__` 내 `self.collection_name` | 501 |
| 비동기 버전도 동일 | `AsyncMemory.__init__` | 2180 |
| 4개 축을 메타데이터/필터로 변환 | `_build_filters_and_metadata()` | 314 |
| 그래프용 저장소도 공유 | `_entity_collection_name()` | 422 |
| 범위 침범 방어 코드 | `_strip_identity_keys()` | 143 |

## 4.2 Memobase — 방식 ③, 요구사항에 가장 근접

**한 줄**: 모든 데이터가 사용자를 기준으로 정렬되어 있고,
ANN 지도를 **아예 만들지 않습니다.**

```
   프로젝트
     └── 사용자
          ├── 원본 대화 blob
          ├── 사용자별 처리 버퍼      ← 사용자마다 독립
          ├── 프로필 (구조화된 정보)
          ├── 이벤트 타임라인  (+ 벡터)
          └── 이벤트 요약      (+ 벡터)

   모든 테이블의 인덱스가 (user_id, project_id) 로 시작
   ANN 지도(HNSW/IVFFlat) 개수: 0개
```

**핵심**: 데이터베이스 인덱스가 전부 `user_id`로 시작하기 때문에,
검색하면 **그 사용자의 데이터 구간으로 먼저 좁혀지고**, 그 안에서만 벡터를
비교합니다. 남의 데이터를 볼 구조적 여지가 없습니다.

**대가**: 한 사용자 데이터가 많아지면 선형으로 느려집니다.
그래서 Memobase는 **대화 원문 전체가 아니라 프로필과 이벤트 요약만 벡터화**합니다.
설계가 일관되어 있습니다.

**아쉬운 점**: 사용자 아래 **세션 계층은 약합니다.** blob/이벤트 축이 주이고
세션이 1급 개념이 아닙니다.

**근거 코드** (`src/server/api/memobase_server/models/database.py`)

| 확인 내용 | 심볼 | 줄 |
|---|---|---|
| 사용자가 1급 엔티티 | `class User` | 242 |
| 사용자별 원본 blob | `class GeneralBlob` | 286 |
| **사용자별 독립 처리 버퍼** | `class BufferZone` | 346 |
| 사용자 프로필 | `class UserProfile` | 419 |
| 이벤트 + 벡터 | `class UserEvent` / `Vector(...)` | 459 / 485 |
| 이벤트 요약 + 벡터 | `class UserEventGist` / `Vector(...)` | 515 / 554 |
| **모든 인덱스가 user_id 선행** | `idx_*_user_id_project_id` | 323, 447, 498, 559 |
| **ANN 인덱스 0개** | `hnsw`/`ivfflat` 검색 결과 0건 | — |

## 4.3 Zep / Graphiti — 방식 ④ (그래프 버전)

**한 줄**: 그래프의 모든 노드와 연결선에 `group_id`라는 딱지를 붙이고,
검색할 때 그 값으로 범위를 제한합니다.

- 별도의 그래프 인스턴스를 만드는 게 아니라 **속성 기반 필터링**입니다.
- 사용자/세션 계층에 대한 설명이 **공식 문서에 없습니다.** `group_id` 하나를
  어떻게 쓸지는 전적으로 애플리케이션 몫입니다.
- 강점은 다른 데 있습니다: **사실마다 유효기간이 붙는 시간 지식그래프** —
  "예전엔 A였는데 지금은 B다" 같은 변화 추적이 강합니다.

*(공식 문서 확인. 소스 미대조)*

## 4.4 Letta · 기타

| 솔루션 | 구조 | 사용자 구분 |
|---|---|---|
| **Letta** | 메모리가 **에이전트 단위**로 묶임. 핵심 기억(항상 컨텍스트) / 대화 로그 / 장기 보관(pgvector) 3단 | "에이전트 = 사용자"로 쓰는 모델. 저장은 필터 방식 |

## 5.2 잘 되어 있는 것 — 벡터 검색

MemMachine의 Qdrant 설정은 **3장의 방식 ②를 정확히 구현**하고 있습니다.

```python
# common/vector_store/qdrant_vector_store.py:752-764
hnsw_config = HnswConfigDiff(
    m=0,                    # ← 전체를 잇는 지도를 만들지 않음
    payload_m=16,           # ← 대신 사용자별 지도를 만듦
)
create_payload_index(
    field_name=파티션키,
    field_schema=KeywordIndexParams(is_tenant=True),   # ← 사용자 구분용이라고 알려줌
)
```

`m=0`은 "전역 지도를 만들지 마라", `payload_m=16`은 "대신 사용자별 지도를
만들어라"는 뜻입니다. **Qdrant가 공식 권장하는 방식이고, 조사한 솔루션 중
이렇게 하는 것은 MemMachine뿐입니다.**

> **"MemMachine은 사용자별로 인덱스가 안 나뉜다"는 걱정은 벡터 검색에는
> 해당하지 않습니다. 오히려 가장 앞서 있습니다.**

## 5.3 문제인 것 1 — 사용자라는 개념이 없다

대화 기억의 구분 단위는 `org_id/project_id`를 합친 **문자열 하나**입니다.
그 아래에 사용자라는 계층이 없습니다.

누가 말했는지(`producer_id`)는 기록되지만 **격리 키가 아니라 검색용 딱지**입니다.
즉 검색할 때 직접 필터를 걸어야 하고, 안 걸면 안 걸러집니다.

**그리고 사용자 아래 세션이라는 계층도 없습니다.**
세션이 곧 최상위 구분 단위여서, "A 사용자의 3번 세션"을 표현하려면
메타데이터와 필터로 흉내내야 합니다. (= 요구 2 미충족)

*(참고: 프로필 기억 쪽에는 `UserSet`이라는 사용자 개념이 있습니다.
같은 제품 안에 서로 다른 두 모델이 공존하는 상태입니다.)*

## 5.4 문제인 것 2 — Postgres가 방식 ①을 쓰고 있다

```python
# episodic_memory/event_memory/segment_store/sqlalchemy_segment_store.py:166, 194
{"postgresql_partition_by": "LIST (partition_key)"}
```

**세션이 하나 생길 때마다 Postgres에 실제 테이블 파티션이 하나씩 만들어집니다.**
이것이 3장의 방식 ①이고, **조사한 어느 솔루션도 이렇게 하지 않습니다.**

- 파티션이 수천 개가 되면 쿼리 계획 수립 시간과 관리 부하가 급격히 나빠집니다
- 파티션 생성 작업은 한 번에 하나씩만 되므로, 여러 사용자가 동시에 처음
  저장하면 줄을 서게 됩니다

## 5.5 그 밖에 확인된 것

| 항목 | 내용 | 왜 중요한가 |
|---|---|---|
| 세션 작업공간 캐시 | 기본 **100개**, 10분 미사용 시 정리 | 동시 활성 사용자가 100을 넘으면 만들었다 버렸다 반복 |
| 세션별 잠금 | 종료 시에만 정리됨 | 접촉한 세션 수만큼 계속 쌓임 |
| 서버 프로세스 수 | 기본 **1개** | 프로세스를 늘리면 캐시가 프로세스마다 따로 생겨 적중률 하락 |
| 인증·권한 | **없음** | `org_id`는 자기 신고. 보안 경계가 아님 |

# 7. 결론과 다음 할 일

## 결론 1. MemMachine은 "다 틀린" 게 아니라 고칠 곳이 두 군데다

| | 상태 |
|---|---|
| 벡터 검색 방식 | ✅ **조사 대상 중 최선.** 손댈 필요 없음 |
| 사용자·세션 계층 | ❌ 사용자 개념 자체가 없음 → **만들어야 함** |
| Postgres 저장 방식 | ❌ 유일하게 금지된 방식 사용 → **바꿔야 함** |

## 결론 2. 우리가 원하는 구조는 업계 미해결 영역이다

요구 1과 요구 2를 동시에 만족하는 오픈소스 솔루션이 **존재하지 않습니다.**
이것은 문제가 아니라 **기회**입니다.

- 1단계(개인·정확도)에서는 문제를 찾아 adaptive-k로 해결하고 특허로 이어갔습니다
- 2단계(다중 사용자·성능)에서는 **측정하기도 전에 구조적 문제를 이미 찾았습니다**

## 결론 3. 참고할 설계

| 무엇을 | 어디서 배울까 |
|---|---|
| 사용자 아래 세션 계층 | **Mem0** — user / agent / run / actor 4축 |
| 사용자당 데이터가 적을 때의 저장 전략 | **Memobase** — 원문 대신 요약만 벡터화 + 사용자 선행 정렬 |
| 사용자별 지도 | **현재 MemMachine 그대로** |

## 다음 할 일

1. **측정 계획 수정** — Postgres 세션당 파티션은 이제 "가설"이 아니라
   사실상 확정된 설계 결함입니다. 남은 것은 **몇 명에서 무너지는지 숫자**뿐입니다.
2. **측정 항목 추가** — "Qdrant의 사용자별 지도가 실제로 방어해 주는가"를
   확인합니다. 이게 확인되면 **"벡터층은 그대로 두고 관계형만 고친다"** 는
   개선 방향이 수치로 뒷받침됩니다.
3. **개선 설계 착수** — 사용자 계층 도입 + Postgres 파티션 단위를
   세션에서 사용자로 올리는(혹은 파티션 방식 자체를 바꾸는) 설계.
