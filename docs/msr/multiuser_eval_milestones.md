## 1. 멀티테넌트 환경의 구조 정의 (평가용)

### 1.1 용어

| 용어 | 정의 |
|---|---|
| **테넌트 (tenant)** | 데이터가 서로 격리되어야 하는 단위. 이 평가에서는 **유저 1명 = 테넌트 1개** |
| **격리 모델** | Silo(테넌트별 독립 인스턴스) / Pool(공유 저장소 + 식별자 필터) / Bridge(공유 인스턴스 내 파티션 분리) |
| **테넌트당 고정비** | 테넌트 1개가 존재하는 것만으로 소비되는 자원 — 인덱스, 파티션, 커넥션, 캐시 슬롯, 파일 핸들 |
| **공유비** | 테넌트 수와 무관하게 전체가 나눠 쓰는 자원 — 공용 인덱스, buffer pool, 디스크 대역폭 |

멀티테넌트 평가의 본질 = **"고정비 × N이 공유비를 언제 침식하는가"를 재는 것.**

### 1.2 워크로드의 공식 정의 — 5-튜플

평가에서 "멀티테넌트 환경" 하나는 다음 5개 파라미터로 완전히 정의된다.
이걸 고정해야 실험이 재현 가능해진다.

```
W = (N, D, A, RW, S)

N  : 총 테넌트 수                    — 스윕 축 1
D  : 테넌트당 데이터량 (에피소드 수)  — 스윕 축 2
A  : 동시 활성 비율 (활성 테넌트/N)   — 앱 계층 캐시 검증의 핵심
RW : 워크로드 믹스 (적재:검색 비율)   — 단계 분리 or 혼합
S  : 테넌트 크기 분포 (균등 / skewed) — tiered 시나리오
```

**기본값 제안** (확정 필요 — §4 결정 1):

| 파라미터 | 기본안 | 근거 |
|---|---|---|
| N | 1 / 10 / 50 / **100** / 200 / 500 | 100 = LRU 기본 경계(H3), 500 = Postgres 파티션 압력(H2) |
| D | 소 ~250 / 중 ~2.5K / 대 ~25K 에피소드 | 소 = locomo 대화 1개 수준, 대 = 캐시 우회 시작점 |
| A | 1.0 / 0.5 / 0.1 | 1.0 = 최악 동시성, 0.1 = 현실적 활성률 |
| RW | 적재 100% → 검색 100% (분리) 먼저, 혼합(1:9)은 후순위 | 병목 귀속이 깨끗해짐 |
| S | 균등 먼저, skewed(상위 10%가 데이터 50%)는 2라운드 | Qdrant tiered 가정 검증용 |

### 1.3 계층 스택 — 병목 귀속의 좌표계

측정에서 "어디가 막혔나"를 말할 때 쓰는 공통 좌표:

```
L1  클라이언트/드라이버   동시 요청 생성, e2e 지연 관측점
L2  앱 (MemMachine)       세션 라우팅, 인스턴스 캐시, 락, 임베딩·리랭킹 호출
L3  인덱스                ANN 그래프/파티션 — 테넌트 구분이 실제로 일어나는 곳
L4  저장소                벡터DB 프로세스, Postgres, SQLite 파일
L5  디바이스 (SSD)        블록 I/O — 최종 목적지
```

병목 귀속 = 포화 시점에 L2~L5 중 어느 층의 지표가 먼저 한계에 닿는지 분리.

## 2. MemMachine의 멀티테넌트 구조

### 2.1 테넌트 단위

- 내부 공용 단위는 **`session_key` 문자열 하나** (v2: `org_id/project_id` 합성, v1: group/user/session 조합).
- LTM은 `partition_key_for_session()`으로 세션당 파티션 키 생성.
- **평가 매핑: 유저 1명 = session_key 1개** (`user_000`, `user_001`, …).

### 2.2 ⚠ 두 개의 실행 경로 — 측정 대상이 달라진다

이번 정리에서 가장 중요한 구조적 사실:

| | **라이브러리 모드** (현 평가 하네스) | **서버 모드** (REST v2) |
|---|---|---|
| 진입 | `agent_utils` → `EpisodicMemory` 직접 생성 | `memmachine-server` (uvicorn) → API |
| 세션 인스턴스 관리 | 드라이버가 직접 보유 (무제한) | `EpisodicMemoryManager` — **LRU 100 + 세션별 RW 락** |
| 측정되는 것 | L3~L5 (인덱스·저장소·디바이스) 순수 성능 | L2 포함 전체 (LRU thrash, 락 경합) |
| 측정 안 되는 것 | **L2 앱 병목 (H3 검증 불가)** | — (단 HTTP 오버헤드 추가됨) |

→ **가설 H3(LRU 100 경계)는 라이브러리 모드로는 아예 안 보인다.**
   서버 모드 실행이 별도 마일스톤(M5)으로 필요한 이유.

→ 반대로 DB 3종 비교(H1·H2·H4·H5)는 라이브러리 모드가 더 깨끗하다
   (HTTP·직렬화 노이즈 없음). **두 모드 모두 필요하고, 역할이 다르다.**

### 2.3 계층별 테넌트 매핑 (실측 요약)

| 계층 | 테넌트 N개의 물리 형태 | 격리 모델 | 테넌트당 고정비 |
|---|---|---|---|
| Qdrant | 단일 컬렉션 + `is_tenant` payload 인덱스 (HNSW `m=0, payload_m=16` → 테넌트별 서브그래프) | Pool | 서브그래프 1개 (경량) |
| Milvus | 단일 컬렉션 + partition key 필터 | Pool | 거의 0 |
| SQLite-vec | 단일 파일 + 행 구분, 컬렉션별 ANN 인덱스 | Pool/Bridge | 인덱스 조각 |
| **Postgres SegmentStore** | **세션당 LIST 파티션 1개** | **Bridge ⚠** | **테이블 파티션 1개 (무거움)** |
| episode_store | 공유 테이블 + `session_key` 컬럼 | Pool | 0 |
| 앱 (서버 모드) | 세션당 `EpisodicMemory` 인스턴스 (LRU 100) | — | 캐시 슬롯 + 락 |

테넌트당 고정비 열이 곧 **스케일 벽 후보의 우선순위**다:
Postgres 파티션(H2) > 앱 인스턴스(H3) > SQLite 인덱스 조각 > Qdrant 서브그래프.

### 2.4 추가 확인된 잠재 병목 (조사 문서 이후 발견)

- **Postgres 커넥션 풀**: 샘플 기본값 `pool_size 5 + max_overflow 10` = 최대 15.
  N=100 동시 요청이면 풀 대기가 먼저 터질 수 있음 → **측정 전 튜닝 필수**
  (안 하면 "Postgres 병목"으로 오귀속됨).
- **파티션 생성 DDL 직렬화**: 세션 첫 적재 때 LIST 파티션 CREATE가 카탈로그
  락을 잡음. N개 세션 동시 초기 적재 = DDL N개 경쟁 → 적재 단계 초반 스파이크.
  이것도 H2의 일부로 측정.

## 3. 평가 전 마일스톤

```
M0 ✅ ──> M1 결정 ──┬──> M2 드라이버 ──┬──> M6 등가성 검증 ──> M7 이식 패키지 ──> 본 평가
                     │                  │         ▲
                     └──> M3 DB 환경 ───┘         │
                          M4 계측 ────────────────┘
                          M5 서버 모드 (H3 전용, 병렬 진행 가능)
```

### M0. 하네스 백엔드 무관화 — ✅ 완료

event 백엔드 진입 불가 문제(백엔드 하드코딩 + 본문 미저장) 해결.
45 + 243 테스트 통과. 상세는 `multiuser_eval_design.md` §1.

### M1. 워크로드 파라미터 확정

| | |
|---|---|
| 내용 | §1.2의 5-튜플 값 확정 (기본안 제안돼 있음) |
| 선행 작업 | 없음 — **결정만 필요** (타겟 서버 사양이 나오면 N 상한 조정) |
| 산출물 | 확정 파라미터 표 → 드라이버의 CLI 기본값 |
| 완료 기준 | 5개 파라미터에 값과 근거가 적혀 있음 |

### M2. 멀티테넌트 워크로드 드라이버

| | |
|---|---|
| 내용 | ① locomo 대화를 N개 테넌트로 **합성 복제** (대화 10개 → `user_i = 대화 (i mod 10)` 복제 + 세션 키만 변경) ② `ingest_episodes()` 경유로 locomo ingest 마이그레이션 ③ 동시성 제어(활성 비율 A 반영) ④ 요청별 e2e + 단계별 지연 기록 (JSON lines) |
| 선행 작업 | M0 ✅ · M1의 파라미터 · locomo ingest 마이그레이션 (미완 — §1 "남은 것") |
| 산출물 | `evaluation/multitenant/` 드라이버 (ingest / search / sweep) |
| 완료 기준 | 맥에서 SQLite-vec + 오프라인 임베더로 N=10 dry-run 통과 |
| 주의 | **임베딩 사전 계산·캐시 필수** — API 지연이 DB 차이를 덮음. 복제 테넌트는 원본과 임베딩이 같으므로 캐시 적중 100% 가능 = 합성 확장의 부수 이점 |

### M3. DB 3종 환경 구성

| | |
|---|---|
| 내용 | Qdrant / Milvus(standalone: etcd+MinIO 포함) / Postgres 컨테이너 compose + 3종 `configuration.yml` 세트 (bind-mount 볼륨, 메모리 제한 파라미터화) |
| 선행 작업 | `pymilvus` 설치 (`packages/server[milvus]` — venv에 현재 없음) · Milvus standalone compose 구성 조사 |
| 산출물 | `evaluation/multitenant/deploy/compose.yml` + `configs/{qdrant,milvus,sqlite}.yml` |
| 완료 기준 | 맥에서 3종 각각 스모크(적재→검색) 통과 — I/O 수치는 무의미해도 기능 검증은 유효 |

### M4. 계측 계층

| | |
|---|---|
| 내용 | ① 앱: 단계별 지연 히스토그램 (현 Prometheus 팩토리는 카운터뿐) ② DB: cgroup v2 `io.stat` 수집 스크립트 ③ SSD: `iostat`/`biosnoop`/`nvme smart-log` 래퍼 + drop_caches 프리앰블 ④ 결과 병합 리포트 스크립트 |
| 선행 작업 | M2의 드라이버 골격 (계측 훅을 꽂을 자리) |
| 산출물 | `evaluation/multitenant/telemetry/` — 전부 타겟 서버(리눅스)에서만 동작하는 부분은 명시 분리 |
| 완료 기준 | 드라이버 실행 시 요청별 지연 JSON + (리눅스에서) 계층별 리소스 타임라인이 나옴 |

### M5. 서버 모드 경로 (H3 전용 — 병렬 진행 가능)

| | |
|---|---|
| 내용 | `memmachine-server` 기동 + v2 REST(`/projects`, `/memories`)로 같은 워크로드를 쏘는 드라이버 변형. LRU thrash·락 경합이 보이는 유일한 경로 |
| 선행 작업 | M2 드라이버 (요청 생성부 재사용) · v2 API 스펙 확인 · `instance_cache_size` 설정 노출 여부 확인 (하드코딩이면 소규모 패치) |
| 산출물 | 드라이버의 `--transport {library,rest}` 스위치 |
| 완료 기준 | 동일 워크로드가 두 모드에서 돌고, 서버 모드에서 LRU 히트/미스가 관측됨 |

### M6. 구성 등가성 검증

| | |
|---|---|
| 내용 | N=1, 동일 데이터·동일 임베딩으로 3종 recall 일치 확인. ANN 파라미터 등가 매핑표 작성 (Qdrant HNSW m/ef ↔ Milvus 인덱스 타입/파라미터 ↔ usearch) |
| 선행 작업 | M2 + M3 |
| 산출물 | 등가성 리포트 + 고정 파라미터표 (이후 모든 실험의 부록) |
| 완료 기준 | **3종 recall 차이가 오차 범위 내** — 아니면 파라미터 재조정 후 재검증. 이거 없이 나온 성능 수치는 전부 무효 |

### M7. 이식 패키지 (타겟 서버 반출용)

| | |
|---|---|
| 내용 | git clone → `setup.sh`(uv sync + extras + compose up) → `run_sweep.sh` 한 줄 실행 문서화. 환경 변수(.env)로 프록시 base_url·디바이스 경로 주입 |
| 선행 작업 | M2~M6 전부 |
| 산출물 | `evaluation/multitenant/README.md` + 스크립트. **맥에서 클린 체크아웃으로 리허설 통과** |
| 완료 기준 | 리포 클론만 받은 새 환경에서 문서대로 실행하면 dry-run이 돈다 |

### 본 평가 (타겟 서버, 마일스톤 외)

M7 패키지로 스윕 실행 → H1~H5 판정 → 병목 귀속 리포트.
SSD 블록 I/O 계측은 여기서만 유효.

## 4. 그래서 무엇을 해야 하나

### 결정 필요 (3건 — 내 추천 포함)

| # | 결정 | 추천 |
|---|---|---|
| 1 | §1.2 워크로드 기본값 승인 | 제안값 그대로. 타겟 서버 사양 확인 후 N 상한만 조정 |
| 2 | 실행 경로 | **라이브러리 모드 기본** (DB 비교가 주 목적) + 서버 모드는 H3 검증 전용으로 M5에서 추가 |
| 3 | ingest 마이그레이션 범위 | **locomo만** (멀티테넌트 드라이버가 쓸 것만). beam/wikimultihop/longmemeval은 필요해질 때 |

### 즉시 착수 가능 (결정과 무관한 무후회 작업 순서)

1. **M2-②** locomo ingest를 `ingest_episodes()` 경유로 마이그레이션
2. **M3 선행** `pymilvus` 설치 + Milvus standalone compose 조사
3. **M2-①③④** 합성 확장 드라이버 + 지연 기록 (파라미터는 CLI 인자라 M1 결정을 안 기다려도 됨)
4. **M3** compose + 3종 config 작성, 맥에서 기능 스모크
5. **M4** 계측 계층 (리눅스 전용 부분은 스크립트만 작성, 검증은 타겟에서)
6. **M6 → M7** 등가성 검증 → 이식 리허설

### 현재 위치

```
M0 ✅ ── M1 (결정 대기) ── M2~M5 (착수 가능) ── M6 ── M7 ── 타겟 서버 반출
```
